# Устаревание и перенос

## Обзор

Код — обязательство, а не актив. У каждой строки кода есть постоянная стоимость
поддержки: ошибки, которые нужно исправлять, зависимости, которые нужно
обновлять, исправления безопасности, которые нужно применять, и новые инженеры,
которых нужно вводить в курс. Устаревание — это дисциплина удаления кода, который
больше не оправдывает себя, а перенос — процесс безопасного перевода пользователей
со старого на новое.

Большинство инженерных организаций хорошо умеют создавать. Немногие хорошо умеют
убирать. Этот навык закрывает этот разрыв.

## Когда использовать

- при замене старой системы, API или библиотеки новой;
- при выводе из эксплуатации возможности, которая больше не нужна;
- при объединении повторяющихся реализаций;
- при удалении мёртвого кода, которым никто не владеет, но все пользуются;
- при планировании жизненного цикла новой системы (планирование устаревания
  начинается на этапе проектирования);
- при решении, поддерживать унаследованную систему или вкладываться в перенос.

## Основные принципы

### Код — обязательство

У каждой строки кода есть постоянная стоимость: тесты, документация, исправления
безопасности, обновления зависимостей и умственные усилия всех, кто работает
рядом. Ценность кода — в возможностях, которые он даёт, а не в самом коде. Когда
те же возможности можно дать меньшим объёмом кода, меньшей сложностью или лучшими
абстракциями, старый код должен уйти.

### Закон Хайрума делает удаление трудным

При достаточном числе пользователей на любое наблюдаемое поведение кто-нибудь
начнёт опираться — включая ошибки, особенности по времени и недокументированные
побочные эффекты. Поэтому устаревание требует активного переноса, а не только
объявления. Пользователи не могут «просто переключиться», когда они опираются на
поведение, которое замена не воспроизводит.

### Планирование устаревания начинается на этапе проектирования

Создавая что-то новое, спроси: «как мы это уберём через три года?» Системы с
чистыми интерфейсами, переключателями возможностей и минимальной площадью
поверхности устаревают легче, чем системы, которые выставляют детали реализации
повсюду.

## Решение об устаревании

Прежде чем что-то устаревать, ответь на вопросы:

```
1. Даёт ли эта система по-прежнему уникальную ценность?
   → Если да, поддерживай её. Если нет, продолжай.

2. Сколько пользователей или потребителей от неё зависит?
   → Оцени объём переноса количественно.

3. Есть ли замена?
   → Если нет, сначала сделай замену. Не устаревай без альтернативы.

4. Какова стоимость переноса для каждого потребителя?
   → Если она легко автоматизируется, делай. Если ручная и трудоёмкая,
     взвесь её против стоимости поддержки.

5. Какова постоянная стоимость поддержки, если НЕ устаревать?
   → Риск безопасности, время инженеров, упущенная выгода от сложности.
```

## Обязательное и рекомендательное устаревание

| Вид | Когда использовать | Механизм |
|------|-------------|-----------|
| **Рекомендательное** | Перенос необязателен, старая система стабильна | Предупреждения, документация, напоминания. Пользователи переносятся в своём темпе. |
| **Обязательное** | У старой системы есть проблемы безопасности, она мешает развитию или стоимость поддержки неподъёмна | Жёсткий срок. Старая система будет удалена к дате X. Предоставь инструменты переноса. |

**По умолчанию — рекомендательное.** Обязательное применяй, только когда
стоимость поддержки или риск оправдывают принудительный перенос. Обязательное
устаревание требует инструментов переноса, документации и поддержки: нельзя
просто объявить срок.

## Процесс переноса

### Шаг 1: сделай замену

Не устаревай без работающей альтернативы. Замена должна:

- покрывать все критичные сценарии старой системы;
- иметь документацию и руководство по переносу;
- быть проверенной в рабочей среде (а не «теоретически лучше»).

### Шаг 2: объяви и опиши

```markdown
## Уведомление об устаревании: OldService

**Статус:** устарело с 2025-03-01
**Замена:** NewService (см. руководство по переносу ниже)
**Дата удаления:** рекомендательное — жёсткого срока пока нет
**Причина:** OldService требует ручного масштабирования и не даёт наблюдаемости.
            NewService делает и то и другое автоматически.

### Руководство по переносу
1. Замени `import { client } from 'old-service'` на `import { client } from 'new-service'`
2. Обнови конфигурацию (примеры ниже)
3. Запусти скрипт проверки переноса: `npx migrate-check`
```

### Шаг 3: переносишь постепенно

Переносишь потребителей по одному, а не всех сразу. Для каждого потребителя:

```
1. Найди все точки соприкосновения с устаревающей системой
2. Переведи их на замену
3. Убедись, что поведение совпадает (тесты, интеграционные проверки)
4. Убери ссылки на старую систему
5. Подтверди отсутствие регрессий
```

**Правило ответственности за переделку:** если ты владеешь инфраструктурой, которую
устареваешь, ты отвечаешь за перенос её пользователей — или за обратно совместимые
обновления, не требующие переноса. Не объявляй устаревание и не оставляй
пользователей разбираться самим.

### Шаг 4: удали старую систему

Только после того, как перенеслись все потребители:

```
1. Убедись, что использования нет (метрики, журналы, анализ зависимостей)
2. Удали код
3. Удали связанные тесты, документацию и конфигурацию
4. Убери уведомления об устаревании
5. Отметь это — удаление кода достижение
```

## Образцы переноса

### Образец «удавки»

Запускай старую и новую системы параллельно. Постепенно переводи трафик со
старой на новую. Когда старая система обслуживает 0% трафика, удали её.

```
Этап 1: новая система обслуживает 0%, старая 100%
Этап 2: новая система обслуживает 10% (канареечный выпуск)
Этап 3: новая система обслуживает 50%
Этап 4: новая система обслуживает 100%, старая простаивает
Этап 5: старая система удалена
```

### Образец адаптера

Создай адаптер, который переводит вызовы старого интерфейса в новую
реализацию. Потребители продолжают пользоваться старым интерфейсом, пока ты
переносишь внутреннюю часть.

```typescript
// Адаптер: старый интерфейс, новая реализация
class LegacyTaskService implements OldTaskAPI {
  constructor(private newService: NewTaskService) {}

  // Старая сигнатура метода, делегирует новой реализации
  getTask(id: number): OldTask {
    const task = this.newService.findById(String(id));
    return this.toOldFormat(task);
  }

  // Переводит новую форму обратно в то, что ждут старые потребители
  private toOldFormat(task: Task): OldTask {
    return { id: Number(task.id), title: task.title, done: task.status === 'done' };
  }
}
```

### Перенос через переключатели возможностей

Используй переключатели возможностей, чтобы переводить потребителей со старой
системы на новую по одному:

```typescript
function getTaskService(userId: string): TaskService {
  if (featureFlags.isEnabled('new-task-service', { userId })) {
    return new NewTaskService();
  }
  return new OldTaskService();
}
```

### Миграции схемы базы данных (расширение и сжатие)

Изменение схемы — самый рискованный перенос, потому что данные — единственное, что
нельзя откатить откатом выпуска. Режим отказа — связать изменение схемы с
изменением кода: переименуй столбец в том же выпуске, который начинает
использовать новое имя, и во время раскатки, когда старый и новый код работают
одновременно, один из них запрашивает столбец, которого нет. Лечение —
**никогда не менять столбец на месте**. Переносишь добавочными фазами, чтобы
старый и новый код был верны на каждом шаге.

```
РАСШИРЕНИЕ ─────────→ ПЕРЕНОС ─────────────→ СЖАТИЕ
добавь новый        заполни существующие   когда старый столбец
столбец, допускающий  строки, пиши старый   уже никто не читает,
NULL, рядом со        и новый из приложения    удали его отдельным
старым                                          выпуском позже
```

**Разобранный пример — переименование `name` в `full_name`:**

1. **Расширение.** Добавь `full_name` с допуском NULL. Выпусти. (Старый код его
   игнорирует; ничего не ломается.)
2. **Двойная запись.** Приложение пишет и `name`, и `full_name` при каждой вставке
   и обновлении. Выпусти.
3. **Заполнение.** Скопируй `name → full_name` для существующих строк, партиями,
   чтобы не блокировать таблицу.
4. **Переключение чтения.** Направь приложение на `full_name`, продолжая писать
   оба. Выпусти и дай поработать.
5. **Сжатие.** Перестань писать `name`, затем в *отдельном, более позднем*
   выпуске удали столбец.

Каждый шаг выпускается и откатывается независимо: если шаг 4 ведёт себя неверно,
откати код, и `full_name` всё ещё заполняется. Считай каждую фазу тонким
вертикальным срезом — см. навык `incremental-implementation`.

**Правила:**

- **Сначала добавочное, разрушительное последним и отдельно.** Добавления (новый
  столбец с допуском NULL, новая таблица, новый индекс) безопасны в любом выпуске;
  удаления и переименования получают собственный выпуск *после* того, как код
  перестал ссылаться на старую форму.
- **У каждой миграции есть проверенный путь назад.** Миграция, которую нельзя
  откатить, — это выпуск, который нельзя откатить. Напиши и запусти `down` до
  слияния.
- **Заполняй партиями, вне горячего пути.** Один `UPDATE` по миллионам строк
  блокирует таблицу; дели на части и ограничивай скорость.
- **Строй большие индексы, не блокируя запись** (например, `CREATE INDEX
  CONCURRENTLY` в Postgres).
- **Отвязывай от кода переключателем возможностей**, когда переключение
  рискованно, точно как в образце переноса через переключатели выше.

## Код-зомби

Код-зомби — код, которым никто не владеет, но все пользуются. Его активно не
поддерживают, у него нет ясного владельца, и он накапливает уязвимости
безопасности и проблемы совместимости. Признаки:

- нет коммитов больше полугода, но есть активные потребители;
- нет назначенного сопровождающего или команды;
- падающие тесты, которые никто не исправляет;
- зависимости с известными уязвимостями, которые никто не обновляет;
- документация, ссылающаяся на системы, которых больше нет.

**Ответ:** либо назначь владельца и поддерживай как следует, либо устаревай
с конкретным планом переноса. Код-зомби не может оставаться в подвешенном
состоянии: он либо получает вложения, либо удаляется.

## Частые оправдания

| Оправдание | Действительность |
|---|---|
| «Оно ещё работает, зачем удалять?» | Работающий код, который никто не поддерживает, накапливает долг безопасности и сложность. Стоимость поддержки растёт молча. |
| «Может понадобиться позже» | Если понадобится позже, его можно написать заново. Держать неиспользуемый код «на всякий случай» дороже, чем написать заново. |
| «Перенос слишком дорог» | Сравни стоимость переноса с постоянной стоимостью поддержки за два-три года. Перенос обычно дешевле в долгую. |
| «Устареем после того, как доделаем новую систему» | Планирование устаревания начинается на этапе проектирования. К тому времени, как новая система будет готова, у тебя появятся новые приоритеты. Планируй сейчас. |
| «Пользователи перенесутся сами» | Не перенесутся. Дай инструменты, документацию и стимулы — или переносишь сами (правило ответственности за переделку). |
| «Можем поддерживать обе системы бесконечно» | Две системы, делающие одно и то же, — это двойная стоимость поддержки, тестов, документации и ввода в курс. |
| «Просто переименуем столбец, это одна строка» | Во время раскатки старый и новый код работают вместе — один запросит столбец, которого больше нет. Расширение и сжатие, никогда не переименование на месте. |
| «Добавлю столбец и удалю старый в одной миграции» | Это связывает безопасное добавление с разрушительным удалением. Удаления получают собственный выпуск, после того как код перестал ссылаться на старую форму. |
| «Напишем откат, если понадобится» | Миграция без пути назад — это выпуск, который нельзя откатить. Напиши и запусти `down` до слияния. |

## Тревожные сигналы

- устаревшие системы без доступной замены;
- объявления об устаревании без инструментов переноса и документации;
- «мягкое» устаревание, которое остаётся рекомендательным годами без прогресса;
- код-зомби без владельца, но с активными потребителями;
- новые возможности, добавленные в устаревающую систему (вкладывай в замену);
- устаревание без измерения текущего использования;
- удаление кода без проверки, что активных потребителей нет;
- изменение схемы и зависящий от него код, выпущенные одним выпуском;
- столбец, переименованный или удалённый на месте, а не по схеме «расширение и
  сжатие»;
- миграция, слитая без проверенного пути назад, или заполнение, блокирующее
  таблицу.

## Проверка

После завершения устаревания:

- [ ] замена проверена в рабочей среде и покрывает все критичные сценарии;
- [ ] есть руководство по переносу с конкретными шагами и примерами;
- [ ] все активные потребители перенесены (подтверждено метриками и журналами);
- [ ] старый код, тесты, документация и конфигурация полностью удалены;
- [ ] в проекте не осталось ссылок на устаревшую систему;
- [ ] уведомления об устаревании убраны (они сделал своё дело).

После миграции схемы базы данных:

- [ ] изменение выпускается добавочными фазами (расширение → заполнение →
      сжатие), а не одной правкой на месте;
- [ ] старый и новый код верны относительно схемы на каждом шаге выпуска;
- [ ] у каждой миграции есть проверенный путь назад; заполнения идут партиями с
      ограничением скорости;
- [ ] разрушительные шаги (удаление, переименование) выпускаются отдельно, после
      того как код перестал ссылаться на старую форму.
