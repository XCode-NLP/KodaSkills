# Как писать задания для агента

Задание для агента — это структурированный комментарий в задаче или пул-реквесте
GitHub, публикуемый при переводе в `ready-for-agent`. Это авторитетная
спецификация, по которой будет работать агент без участия человека. Исходное
описание и обсуждение — контекст: контракт — это задание.

Задание говорит, **что агент должен сделать**, и это охватывает обе поверхности:
для задачи — построить изменение с нуля; для пул-реквеста — что осталось сделать
*с уже существующим диффом*: доделать, закрыть пробелы, учесть замечания
проверки. Принципы одни и те же; пример для пул-реквеста ниже показывает
разницу.

## Принципы

### Долговечность важнее точности

Задача может пролежать в `ready-for-agent` дни или недели. За это время проект
изменится. Пиши задание так, чтобы оно оставалось полезным, даже когда файлы
переименованы, перемещены или переработаны.

- **Описывай** интерфейсы, типы и поведенческие контракты.
- **Называй** конкретные типы, сигнатуры функций или формы конфигурации, которые
  агент должен найти или изменить.
- **Не ссылайся** на пути к файлам: они устаревают.
- **Не ссылайся** на номера строк.
- **Не предполагай**, что текущая структура реализации сохранится.

### Поведение, а не процедура

Описывай, **что** система должна делать, а не **как** это реализовать. Агент
изучит проект заново и примет собственные решения о реализации.

- **Хорошо:** «Тип `SkillConfig` должен принимать необязательное поле `schedule`
  типа `CronExpression`».
- **Плохо:** «Открой src/types/skill.ts и добавь поле schedule в строке 42».
- **Хорошо:** «Когда пользователь запускает `/triage` без аргументов, он должен
  видеть сводку задач, требующих внимания».
- **Плохо:** «Добавь оператор switch в основную функцию обработчика».

### Полные критерии приёмки

Агент должен понимать, когда работа закончена. В каждом задании обязаны быть
конкретные проверяемые критерии приёмки. Каждый критерий должен проверяться
независимо.

- **Хорошо:** «Запуск `gh issue list --label needs-triage` возвращает задачи,
  прошедшие начальную классификацию».
- **Плохо:** «Разбор должен работать правильно».

### Явные границы области

Укажи, что вне области работы. Это не даёт агенту переусердствовать и делать
допущения о смежных возможностях.

## Шаблон

```markdown
## Задание для агента

**Категория:** ошибка / улучшение
**Кратко:** одна строка о том, что должно произойти

**Текущее поведение:**
Опиши, что происходит сейчас. Для ошибки это сломанное поведение.
Для улучшения — состояние, на котором строится возможность.

**Желаемое поведение:**
Опиши, что должно происходить после завершения работы агента.
Будь конкретен в крайних случаях и условиях ошибок.

**Ключевые интерфейсы:**
- `TypeName`: что нужно изменить и почему
- тип возврата `functionName()`: что возвращает сейчас и что должен
- форма конфигурации: какие новые параметры нужны

**Критерии приёмки:**
- [ ] Конкретный проверяемый критерий 1
- [ ] Конкретный проверяемый критерий 2
- [ ] Конкретный проверяемый критерий 3

**Вне области работы:**
- То, что НЕ нужно менять или затрагивать в этой задаче
- Смежная возможность, которая может показаться связанной, но отдельна
```

## Примеры

### Хорошее задание для агента (ошибка)

```markdown
## Задание для агента

**Категория:** ошибка
**Кратко:** обрезка описания навыка режет посреди слова и даёт испорченный вывод

**Текущее поведение:**
Когда описание навыка превышает 1024 символа, оно обрезается ровно на
1024 символах без учёта границ слов. Получаются описания, обрывающиеся
посреди слова (например, «Используй, когда пользователь хочет наст…»).

**Желаемое поведение:**
Обрезка должна происходить по последней границе слова перед 1024 символами
и добавлять «…», показывая, что текст обрезан.

**Ключевые интерфейсы:**
- поле `description` типа `SkillMetadata`: тип менять не нужно, но логика
  проверки и обработки, заполняющая его, должна учитывать границы слов
- любая функция, читающая метаданные SKILL.md и извлекающая описание

**Критерии приёмки:**
- [ ] Описания короче 1024 символов не меняются
- [ ] Описания длиннее 1024 символов обрезаются по последней границе слова
      перед 1024 символами
- [ ] Обрезанные описания заканчиваются на «…»
- [ ] Общая длина вместе с «…» не превышает 1024 символа

**Вне области работы:**
- изменение самого ограничения в 1024 символа
- поддержка описаний из нескольких строк
```

### Хорошее задание для агента (улучшение)

```markdown
## Задание для агента

**Категория:** улучшение
**Кратко:** добавить каталог `.out-of-scope/` для учёта отклонённых запросов

**Текущее поведение:**
Когда запрос на возможность отклоняют, задача закрывается с меткой `wontfix`
и комментарием. Постоянной записи о решении и обосновании нет.
Будущие похожие запросы требуют от сопровождающего вспомнить или найти
прежнее обсуждение.

**Желаемое поведение:**
Отклонённые запросы документируются в файлах `.out-of-scope/<понятие>.md`,
которые фиксируют решение, обоснование и ссылки на все задачи, просившие
эту возможность. При разборе новых задач эти файлы проверяются на совпадения.

**Ключевые интерфейсы:**
- формат файлов Markdown в `.out-of-scope/`: в каждом заголовок
  `# Название понятия`, строка `**Решение:**`, строка `**Причина:**`
  и список `**Прежние запросы:**` со ссылками на задачи
- рабочий процесс разбора должен читать все файлы `.out-of-scope/*.md`
  в начале и сопоставлять входящие задачи по сходству понятий

**Критерии приёмки:**
- [ ] Закрытие возможности как wontfix создаёт или обновляет файл в `.out-of-scope/`
- [ ] Файл содержит решение, обоснование и ссылку на закрытую задачу
- [ ] Если подходящий файл в `.out-of-scope/` уже есть, новая задача
      дописывается в его список «Прежние запросы», а не создаёт дубликат
- [ ] При разборе существующие файлы `.out-of-scope/` проверяются и показываются,
      когда новая задача совпадает с прежним отказом

**Вне области работы:**
- автоматическое сопоставление (совпадение подтверждает человек)
- открытие заново ранее отклонённых возможностей
- отчёты об ошибках (в `.out-of-scope/` попадают только отклонённые улучшения)
```

### Хорошее задание для агента (пул-реквест)

Для пул-реквеста «Текущее поведение» описывает состояние диффа, а задание просит
агента доделать или исправить его, а не строить с нуля.

```markdown
## Задание для агента

**Категория:** улучшение
**Кратко:** доделать флаг вывода `--json` для `triage list` из пул-реквеста

**Текущее поведение:**
Пул-реквест добавляет флаг `--json`, сериализующий список задач в JSON.
Основной путь работает, дифф соответствует структуре команд проекта.
Остаются два пробела: ошибки по-прежнему печатаются человеческим текстом
(не JSON), а у нового флага нет тестов.

**Желаемое поведение:**
С `--json` весь вывод (включая ошибки) — корректный JSON в стандартном выводе,
коды возврата команды не меняются. Существующий человекочитаемый вывод
не трогается, когда флаг не указан.

**Ключевые интерфейсы:**
- путь ошибки команды должен выдавать `{ "error": string }` при `--json`
  вместо простого текста ошибки
- используй существующий сериализатор, который пул-реквест уже добавил;
  не вводи второй

**Критерии приёмки:**
- [ ] `triage list --json` выдаёт корректный JSON и при успехе, и при ошибке
- [ ] Коды возврата совпадают с командой без JSON
- [ ] Тест покрывает успешный вывод `--json` и один случай ошибки
- [ ] Вывод по умолчанию (без JSON) не изменился ни на байт

**Вне области работы:**
- добавление `--json` другим командам
- изменение формы JSON успешной нагрузки, которую пул-реквест уже определил
```

### Плохое задание для агента

```markdown
## Задание для агента

**Кратко:** исправить ошибку разбора

**Что сделать:**
Разбор сломан. Посмотри основной файл и исправь.
Проблема в функции около строки 150.

**Файлы для изменения:**
- src/triage/handler.ts (строка 150)
- src/types.ts (строка 42)
```

Это плохо, потому что:

- нет категории;
- описание размытое («разбор сломан»);
- есть ссылки на пути к файлам и номера строк, которые устареют;
- нет критериев приёмки;
- нет границ области;
- нет описания текущего и желаемого поведения.
