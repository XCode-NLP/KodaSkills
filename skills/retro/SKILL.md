Пользователь попросил провести **ретроспективу**. Ты предлагаешь улучшения **окружения** агента, чтобы будущие сессии проходил лучше.

## Шаги

1. Вызови инструмент навыков с навыком `writing-for-agents`, чтобы получить руководство по стилю.

2. Прочитай первоисточники сессии, которую указал пользователь. Возможно, придётся поискать журналы сессий на этой машине. Если сессия не указана, бери текущую.

3. Ищи кандидатов на улучшение в этих категориях.

- **Навигация**: насколько легко агенту было найти нужные файлы? Есть ли скрытые зависимости между файлами? Помог бы **указатель навигации**? _Используйте_, когда поиск части информации занял много времени.
- **Автоматические проверки**: есть ли проверки, которые поймал бы ошибки агента? Линтеры, проверка типов, тесты, проверки файловой системы? Сначала прочитай собственную команду проверки репозитория (скрипты `lint`/`check` в `package.json` или в системе сборки, рабочий процесс CI): находкой будет уже существующая, но не подключённая или молча сломанная проверка, а не её изобретение заново. Репозиторий без **ограничителя** (нет ни хука перед коммитом, ни задания CI, запускающего его линтер, проверку типов или тесты) — сам по себе находка: репозиторий без линтера это постоянная упущенная возможность, а не нейтральное положение по умолчанию. _Используйте_, когда агент ошибся так, что это поймала бы автоматическая проверка, или когда в репозитории нет ограничителей вовсе.
- **Стандарты кода**: нужно ли дать **агенту-ревьюеру** новое правило? Убрать или уточнить существующее? Сначала определи вид нарушения: **механическое** (фиксированный синтаксический шаблон, запрещённый API, форма импорта, правило размещения файлов) требует детерминированной проверки, и точка: пользовательское правило в линтере проекта, новый хук перед коммитом или новое задание CI — что дешевле при языке проекта и имеющихся ограничителях. По умолчанию строй проверку, а не пиши правило. `CODING_STANDARDS.md` оставь для настоящих **суждений** (согласованность между файлами, «соответствие окружающему стилю», всё, что не заменить ограничителем). _Используйте_, когда агент-ревьюер не поймал ошибку.
- **Общий AGENTS.md**: есть ли указания, которые стоит перенести в стандарты кода или автоматические проверки? _Используйте_, когда файл AGENTS.md особенно большой — в репозитории или в глобальной области пользователя.
- **Экономия инструментов**: делал ли агент дорогие вызовы инструментов, которые можно упростить? Есть ли собственные инструменты (CLI, MCP), особенно неэкономные по токенам? _Используйте_, когда агент сделал дорогой вызов инструмента.
- **Пустые указания**: найди в файлах указаний инструкции, которые не меняют поведение агента. _Используйте_, когда файлы указаний большие и громоздкие.
- **Доступ к информации**: найди возможности расширить доступ агента к информации. Дублирование журналов сервера разработки, доступ только для чтения к сторонним сервисам. _Используйте_, когда важная информация была агенту недоступна.

4. Покажи эти кандидаты пользователю в порядке важности.

## Справочные сведения

### Реализация и проверка

Помнишь, что вся работа проходит два этапа: реализацию и проверку. У агента реализации наибольшее **давление на контекст**. Он отвечает за изучение проекта, написание кода и отладку сбоев.

У агента проверки давление на контекст наименьшее: он получает дифф, поэтому изучение проекта ему не нужно. Часто ему не нужно писать код и отлаживать.

Значит, стандарты кода должен навязывать агент проверки, а не агент реализации.

### Файлы

В репозитории тебе доступны несколько файлов:

- `CLAUDE.md` / `AGENTS.md`: эти файлы попадают в контекст любого агента, работающего в репозитории. Используй их крайне скупо, обычно только для **указателей навигации** на другие файлы.
- `CODING_STANDARDS.md`: этот файл читают при проверке, а не при реализации. Добавляй **указатели навигации** на каталоги документации, если файл стандартов разрастается больше 1000 строк.
- Документация: используй документы как справочные файлы, на которые ссылаются другие файлы. Прежде чем писать новое, поищи существующее.
- Навыки: используй навыки для документации (их описание попадает в контекст агента) или для команд, которые вызывает пользователь. Следуй советам навыка `writing-for-agents`.
