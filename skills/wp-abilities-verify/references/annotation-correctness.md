# Корректность аннотаций

Враждебное ядро этого навыка: проверить, что заявляет аннотация, прочитав колбэк.
Возможность с `readonly: true`, которая на самом деле пишет, — катастрофа для безопасности и
удобства, и модульные тесты её не ловят, потому что мок выглядит ровно как настоящий
писатель.

## Почему это важно

Агенты планируют действия на основе аннотаций, которые они читают. Если возможность
помечена `readonly: true`, оркестратор уверенно вызовет её в пробном прогоне, в
исследовательском переборе вариантов или в параллельном запуске нескольких агентов, не
задумываясь, — потому что `readonly` означает «ничего не может сломать».

Поэтому возможность с `readonly: true`, которая на самом деле пишет, — это:

1. **Угроза безопасности** — агенты вызовут её в контекстах, где побочные эффекты
   запрещены.
2. **Катастрофа для удобства** — мысленная модель агента о том, что произошло, молча
   расходится с реальностью.
3. **Необнаружимо на уровне аннотации** — аннотация говорит `readonly: true`, и ничто в
   регистрации не заставляет её быть правдой.

Модульные тесты не поймают этот класс ошибок, потому что мок, который создаёт тест, выглядит
ровно как настоящий писатель. Ловит другое: чтение тела колбэка выполнения и сравнение того,
что он делает, с тем, что говорит аннотация.

## Что обещает каждая аннотация

| Аннотация | Что она обещает (по ядру) |
|---|---|
| `readonly: true` | Никаких долговременных записей в пользовательское или бизнес-состояние. Поведение как у GET, без побочных эффектов. |
| `destructive: false` | Не уничтожит данные необратимо и не потеряет деньги. |
| `idempotent: true` | Повторные вызовы с теми же аргументами не дают дополнительного эффекта на окружение (согласно docblock аннотации `idempotent` в `class-wp-ability.php`). |

`readonly: true` запрещает долговременные записи в пользовательское или бизнес-состояние.
Записи в сквозной кэш (например, `set_transient`) и отметки времени для наблюдаемости
(например, `last_read_at`) допустимы, когда они явно помечены `verify-ignore` — см. раздел
«Подавление законных исключений» ниже. Статическая проверка считает непомеченные записи
FAIL, а помеченные пропускает, записывая причину как обоснование.

Эти аннотации пересекаются, но не избыточны: `readonly` — самая строгая;
`destructive: false` слабее (обновления, которые ничего не уничтожают, допустимы);
`idempotent` ортогональна (POST, который дважды пишет одну и ту же строку, — и «пишет», и
«идемпотентен»).

Контроллер запуска Abilities REST превращает аннотации в маршрутизацию по HTTP-методу
(`readonly: true` → GET, `destructive && idempotent` → DELETE, иначе POST — см.
`WP_REST_Abilities_V1_Run_Controller::validate_request_method()`). Это отображение и есть
несущая семантика; проверка убеждается, что поведение каждого колбэка согласуется с тем, как
его будет трактовать маршрутизация.

## Как проверять

Для каждой возможности найди тело `execute_callback` (см. `static-enumeration.md`, шаг 4),
затем:

1. **Прочитай колбэк целиком.** Построй модель того, что он реально делает. Не полагайся
   только на сопоставление шаблонов.
2. **Сравни с заявлением.** Колбэк с `readonly: true`, который где-либо пишет — в базу через
   `$wpdb`, в опции, записи, пользователей, термы, комментарии, в файловую систему,
   планирует cron или делегирует не-GET HTTP и REST запросы, — даёт FAIL по readonly.
   Колбэк с `destructive: false`, который удаляет, возвращает деньги, аннулирует, отменяет
   или отправляет в корзину, даёт FAIL по destructive. Колбэк с `idempotent: true`, чей
   эффект на окружение *накапливается* с каждым вызовом (счётчики, журналы только на
   добавление, планирование cron на каждый вызов), даёт FAIL по idempotent.
3. **Запиши обоснование.** Укажи файл и строку offending-шаблона, чтобы ревьюер сразу к нему
   перешёл.

Используй grep или ripgrep, чтобы найти *кандидатов*. Частые записи, которые стоит искать:

```text
$wpdb->update / insert / delete / replace
update_option / add_option / delete_option
wp_insert_post / wp_update_post / wp_delete_post
update_post_meta / update_user_meta / update_term_meta
->save / ->delete / ->set_status / ->add_*
wp_remote_post / wp_remote_delete
file_put_contents / wp_upload_bits / unlink / rename
wp_schedule_event / wp_schedule_single_event
```

Считай этот список отправным набором, а не контрольным списком. Словари плагинов
различаются — глаголы предметной области (`->markAsPaid`, `->commit`, `->refund`) и шаблоны
фреймворков (`->persist` у Doctrine, `->dispatch` у очередей) в него не попадут. Найдя
кандидатов через grep, прочитай колбэк, чтобы подтвердить, действительно ли каждое
совпадение является записью и противоречит ли оно аннотации в контексте.

## Известные слепые зоны

Статическое чтение и grep не достают до каждой записи. PASS в статическом режиме означает
«нет нарушений очевидной формы», а не «подтверждено отсутствие записи».

| Слепая зона | Почему статический режим её пропускает | Что делать |
|---|---|---|
| Записи через сервисы — `$repo->persist()`, `$service->commit()`, собственные глаголы. | Любой конечный список глаголов устаревает; словарь предметной области различается. | Изучай колбэки, обращающиеся к собственным сервисам и репозиториям. |
| `do_action()`, слушатели которого пишут. | Неоднозначность происхождения: возможность выглядит чистой, а состояние меняет слушатель. | Проверь слушателей этого действия. Если кто-то пишет, понизь оценку или раздели возможность. |
| Неявные хуки ядра, вызываемые API WordPress — `wp_insert_post()` запускает `save_post`, `update_option()` запускает `updated_option`, `wp_create_user()` запускает `user_register` и т.д. | Вызов API WP И ЕСТЬ запись; хуки срабатывают автоматически как побочный эффект. Агент, ищущий `do_action()`, этого не увидит. | Считай любой вызов пишущего API WP записью независимо от того, вызывает ли колбэк ещё и `do_action()`. |
| Action Scheduler и отложенные записи — `as_schedule_single_action()`, `WC()->queue()->schedule_single()`, собственные диспетчеры задач. | Колбэк возвращается чисто, без немедленно видимой мутации базы; долговременная запись попадает в таблицы AS позже. Grep по `$wpdb->insert` этого не поймает. | Считай отправку в планировщик записью. Обещание «нет дополнительного эффекта на окружение» у `idempotent: true` нарушается накоплением задач в очереди, даже если немедленное возвращаемое значение постоянно. |
| HTTP-методы, собираемые в переменной, у вспомогательных функций делегирования. | Статический режим не прослеживает значения времени выполнения. | Считай подозрительными вызовы функций, чей метод по умолчанию не `GET`. |
| Тавтологичные проверки прав — `current_user_can('read')` на «приватной» возможности. | Право выглядит допустимым, но подписчики его имеют. | Сверься с круговой проверкой прав: подписчик должен получать отказ. |

Для важных плагинов перед слиянием запускай режим выполнения (см. `runtime-harness.md`): он
ловит часть слепых зон через сравнение двойного вызова и осмотр живого состояния.

## Подавление законных исключений

Когда шаблон, похожий на запись, семантически является чтением (например, заполнение
сквозного кэша через `set_transient`, обновление отметки `last_read_at` для отслеживания,
диагностическое журналирование), подави срабатывание встроенным комментарием в offending-строке:

```php
// verify-ignore: readonly -- writes to read-through cache; semantically a read.
set_transient( $cache_key, $data, HOUR_IN_SECONDS );
```

Формат: `// verify-ignore: <annotation> -- <reason>`. Допустимые имена аннотаций:
`readonly`, `destructive`, `idempotent`, `all`. Чем уже, тем лучше; `all` — в последнюю
очередь.

## Дополнение в режиме выполнения

Для возможностей с `idempotent: true` режим выполнения добавляет эвристику: вызвать дважды с
тем же вводом и сравнить. См. `runtime-harness.md`, проверка 6. Разные возвраты — *сигнал*
к изучению, а не приговор: по определению ядра вопрос в том, изменилось ли *окружение*, а не
в том, совпадает ли *возвращаемое значение*. Ответ, включающий отметку времени, nonce или
случайный ID на каждый вызов, нормален; ответ, отражающий счётчик, который вырос между
вызовами, — нет.

## Формат отчёта

Каждое замечание получает одну строку в таблице «Корректность аннотаций» прогона:

```markdown
| Ability | Claim | Result | Evidence |
|---|---|---|---|
| myplugin/get-things | readonly=true | OK | callback reads only |
| myplugin/get-things-with-counts | readonly=true | FAIL | `src/Abilities/Things.php:142`: `$wpdb->update( $table, ... )` |
| myplugin/submit-thing | destructive=false | OK | no destructive patterns |
| myplugin/submit-thing | idempotent=false | OK | check only applies when idempotent=true; false annotation acknowledged |
```

Столбец обоснования ОБЯЗАН указывать файл и строку, чтобы ревьюер сразу перешёл к проблеме.
