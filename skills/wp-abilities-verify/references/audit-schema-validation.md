# Проверка схемы аудита

Как `wp-abilities-verify` проверяет документ аудита, созданный `wp-abilities-audit`.
Каноническая схема (таблицы полей, типы, инварианты, известные ограничения) лежит в
`../../wp-abilities-audit/references/audit-schema.md` — здесь описан только порядок проверки:
как извлечь YAML, какие проверки в каком порядке выполнять и как сообщать результаты.

Если вопрос о типе поля или его форме здесь не раскрыт, ищи ответ в канонической схеме. НЕ
дублируй таблицы полей в этом файле: каноническая схема — единственный источник истины.

## Почему валидатор живёт в навыке проверки

Проверка быстро падает на испорченном аудите, чтобы остальная процедура могла считать ввод
корректным. Аудит создаёт, проверка валидирует созданное. Валидатор рядом с проверкой держит
шаг «проверить аудит» в той же процедуре, что и «проверить зарегистрированные возможности», и
позволяет одному прогону дать один сводный отчёт.

## Шаг 1 — извлеки YAML

Документ аудита — markdown-файл с единственным блоком в ограждении ` ```yaml `, содержащим
структурированные поля:

```bash
# Ищем ограждение ```yaml и захватываем до закрывающего ```.
awk '/^```yaml$/{f=1;next} /^```$/{f=0} f' <audit-doc.md> > /tmp/audit.yaml
```

Если в аудите несколько блоков YAML (так быть не должно, но защитно), возьми первый, у
которого `proposed_abilities` является ключом верхнего уровня.

Разбирай любой библиотекой YAML: `js-yaml` из Node, `yaml` из Python или `yq` из командной
строки. Ни одно каноническое поле не требует нестандартных возможностей YAML (без якорей и
алиасов), поэтому обычного `yaml.load` достаточно.

## Шаг 2 — проверь по канонической схеме

Примени правила формы полей из `../../wp-abilities-audit/references/audit-schema.md`. В
частности:

1. Каждое обязательное поле верхнего уровня присутствует и непусто (см. раздел «Поля верхнего
   уровня» в канонической схеме).
2. `capability_gate` соответствует одной из законных форм (одна строка, объект `{read, write}`
   или — с WARN согласно разделу «Известные ограничения» канонической схемы — устаревшая
   строка с разделителем-косой чертой).
3. Каждая запись в `proposed_abilities` содержит все обязательные поля возможности с верными
   типами (см. раздел «`proposed_abilities`» в канонической схеме).
4. В блоке `annotations` каждой возможности все три логических значения (`readonly`,
   `destructive`, `idempotent`) — настоящие логические значения; строки `"true"` и `"false"`
   дают FAIL (это признак ошибки с кавычками).
5. `backing` каждой возможности — либо объект с каноническими полями, либо `null`; `null` даёт
   WARN, а не FAIL (это намеренный вывод о пробеле).

Отсутствует обязательное поле → FAIL. Неверный тип → FAIL. Устаревшая строка с косой чертой в
`capability_gate` → WARN.

## Шаг 3 — инварианты всего аудита

Выполняй их после того, как проверка отдельных полей прошла.

### Ровно 0 или 1 возможность с `reference_ability: true`

Посчитай возможности, у которых `reference_ability` равно `true`. Больше 1 → FAIL (схема
допускает не более одной эталонной возможности; несколько неоднозначны для исполнителя,
выбирающего отправную точку).

```js
const refCount = audit.proposed_abilities.filter(a => a.reference_ability === true).length;
if (refCount > 1) fail("multiple abilities claim reference_ability: true");
```

### Каждая возможность с `backing: null` присутствует в `surfaced_gaps`

Согласно разделу «Известные ограничения» канонической схемы: `null` в backing — намеренный
вывод о пробеле, и он ОБЯЗАН быть парным записи в `surfaced_gaps`.

```js
const gapNames = new Set((audit.surfaced_gaps || []).map(g => g.name));
for (const ability of audit.proposed_abilities) {
  if (ability.backing === null && !gapNames.has(ability.name)) {
    fail(`ability ${ability.name} has backing: null but is missing from surfaced_gaps`);
  }
}
```

### `excluded_from_mvp` и `surfaced_gaps` могут быть пустыми

Оба поля необязательны; пустые массивы допустимы. Полное отсутствие → WARN (схема ожидает их,
даже пустыми).

## Шаг 4 — выведи раздел отчёта

Каждая проверка попадает в раздел «Проверка документа аудита» итогового отчёта прогона:

```markdown
## Audit doc validation

| Check | Result | Detail |
|---|---|---|
| Top-level required fields | OK | All 7 required fields present |
| `capability_gate` shape | OK | string (single-cap) |
| Per-ability fields | WARN | 1 ability has `backing: null` (intentional) |
| `reference_ability` uniqueness | OK | 1 ability marked |
| `surfaced_gaps` consistency | OK | all `backing: null` entries present |
```

Один FAIL в этом разделе делает FAIL весь прогон: проверка не может осмысленно продолжаться без
достоверного аудита. Записи WARN не блокируют остальную процедуру.

Процедура ручная, но детерминированная: выполни шаги выше по порядку, выведи раздел отчёта и
падай сразу при любом отсутствующем обязательном поле. Будущий вклад может добавить
детерминированную утилиту командной строки, которая извлекает блок YAML и применяет правила
целиком; пока её нет, контрактом являются шаги выше.

## Когда эскалировать

Если валидатор отклоняет аудит, который на самом деле корректен, значит каноническая схема в
`../../wp-abilities-audit/references/audit-schema.md` изменилась. Обнови процедуру в этом файле
под неё (скорее всего, добавив новый инвариант или ослабив правило поля). Не ослабляй проверку
в отрыве от схемы: каноническая схема — контракт, этот файл — его исполнитель.
