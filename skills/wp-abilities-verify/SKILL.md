# Проверка возможностей WordPress

Проверяй регистрации Abilities API в плагине WordPress. В центре внимания —
**враждебная проверка корректности аннотаций**: возможность с `readonly: true`, которая на
самом деле пишет (через `$wpdb->update`, `update_option`, делегирование не-GET-запросом и
т.п.), — катастрофа для безопасности и удобства, потому что агенты планируют действия на
основе аннотаций, которые они читают. Этот навык ловит такую ложь, читая тело колбэка и
сравнивая то, что он делает, с тем, что заявляет аннотация.

Навык также проверяет документы аудита, созданные `wp-abilities-audit`, проверяет барьеры
прав и чистоту схем и, по желанию, выполняет каждую возможность в живом окружении.

## Когда использовать

- После того как возможности зарегистрированы в плагине, но до того как PR попал в основную
  ветку.
- Как проверку здоровья уже выпущенного плагина (ловить регрессии, когда рефакторинг
  превратил возможность только для чтения в пишущую).
- Чтобы проверить документ аудита перед передачей его исполнителю.

## Два режима

- **Статический режим** — работает по исходникам плагина. Без окружения. Перечисляет
  возможности по исходному коду, выполняет враждебную проверку корректности, запускает
  линты схем и прав и проверяет документы аудита.
- **Режим выполнения** — нужно запущенное окружение. Делает всё, что статический, ПЛЮС:
  `wp_get_abilities()` для авторитетного перечисления, выполняет каждую возможность с
  подобранным вводом, подтверждает круговую проверку прав на реальных пользователях и
  применяет эвристику двойного вызова к возможностям с `idempotent: true`, чтобы отметить
  кандидатов на ревью (совпадение возвращаемых значений — сигнал, а не приговор: ядро
  определяет идемпотентность как «отсутствие дополнительного эффекта на окружение»).

Оба режима дают одинаковый формат структурированного отчёта.

Статический режим с результатом PASS означает «нет нарушений очевидной формы», а не
«подтверждено отсутствие записи». Для важных плагинов перед слиянием запускай режим
выполнения: он ловит проблемы порядка инициализации, круговой проверки прав и
идемпотентности, которые статический режим не видит. Слепые зоны статического режима
описаны в `references/annotation-correctness.md`.

## Что нужно на входе

1. **Путь к исходникам плагина** — рабочее дерево для проверки.
2. **Режим** — `static` или `runtime`. Если не указан, по умолчанию статический.
3. **(Только для режима выполнения) Команда запуска окружения** — прочитай `AGENTS.md`
   плагина. Частые варианты: `npm run wp-env start`, `npx wp-env start` или запуск через
   Composer. Семейства плагинов со своими инструментами разработки документируют свою
   команду. НЕ считай, что `npm run wp-env` работает.
4. **(Необязательно) Путь к документу аудита** — включает сверку аудита с
   зарегистрированными возможностями и проверку самого аудита.
5. **Путь для отчёта** — явный путь, обычно хранилище пользователя.

## Требования

- На плагине уже запускался `wp-project-triage`.
- В исходниках плагина есть хотя бы одна зарегистрированная возможность. Ноль совпадений по
  `wp_register_ability(` → верни понятный отчёт «возможности не зарегистрированы», а не
  пустой PASS.

## Порядок работы

### 1. (Если передан аудит) Проверь документ аудита

Прочитай `references/audit-schema-validation.md`. Проверь аудит по канонической схеме,
которой владеет `wp-abilities-audit`. Покажи отсутствующие обязательные поля, несколько
`reference_ability: true` и записи `backing: null` без парной записи в `surfaced_gaps`.
Сам по себе `backing: null` — это WARN (намеренный вывод о пробеле), а не FAIL.

### 2. Перечисли возможности статически

Прочитай `references/static-enumeration.md`. Найди каждый вызов `wp_register_ability(`,
извлеки имя, блок аннотаций и расположение колбэка выполнения. Используй инструмент,
работающий с несколькими строками (`rg --multiline --pcre2`): каноническое форматирование
разбивает вызов на строки. Запиши для каждой возможности файл исходника, строку, аннотации
и диапазон байтов колбэка.

### 3. (Только для режима выполнения) Перечисли через REST и wp-cli

Прочитай `references/runtime-harness.md`. Подними окружение командой из `AGENTS.md`, затем
перечисли возможности через `wp_get_abilities()` по wp-cli и сверь со статической описью.
Есть только в исходниках → FAIL (регистрация не срабатывает). Есть только во время
выполнения → WARN (динамический путь регистрации).

### 4. Корректность аннотаций (враждебное ядро)

Прочитай `references/annotation-correctness.md`. Прочитай тело каждого колбэка и проверь,
что оно соответствует заявленной аннотации:

- `readonly: true` → колбэк не должен писать в базу, таблицу опций, данные записей,
  пользователей, термов и комментариев, файловую систему, cron, а также через делегирование
  не-GET HTTP и REST запросов.
- `destructive: false` → колбэк не должен удалять, возвращать деньги, аннулировать,
  отменять или отправлять в корзину.
- `idempotent: true` → повторные вызовы с тем же вводом не дают дополнительного эффекта на
  окружение (согласно docblock аннотации `idempotent` в `class-wp-ability.php`). Статический
  режим ловит записи счётчиков и планирование cron на каждый вызов; режим выполнения
  добавляет эвристику двойного вызова для видимых изменений состояния.

Справочник перечисляет частые шаблоны записи как отправный набор, а не как контрольный
список: словари плагинов различаются, и агент расширяет набор глаголами, специфичными для
проверяемого плагина.

Ложные срабатывания подавляются встроенным комментарием
`// verify-ignore: <annotation> -- <reason>`.

### 5. Круговая проверка прав

Прочитай `references/permission-roundtrip.md`. Статически: отнеси каждый
`permission_callback` к одной из шести форм (предпочтительна форма A
`current_user_can(...)`; FAIL для плохой формы B с шаблонами `WP_REST_Request` или формы E с
литералом `true`). Во время выполнения: анонимный пользователь и подписчик получают отказ,
администратор — разрешение (если возможность намеренно не публичная). Если передан аудит,
сверь зарегистрированное право с объявленным в аудите барьером.

### 6. Линты схем

Прочитай `references/schema-lints.md`. Шесть небольших принципов, применяемых к
`input_schema` каждой возможности: схемы-объекты объявляют `additionalProperties`;
обязательные поля имеют описания; перечисления непусты; нет `$ref`; значения по умолчанию
статически постоянны (включая `(object) array()`); у эталонных возможностей нет
обязательного ввода.

Сверься с `../wp-abilities-api/references/input-schema-gotchas.md` по четырём ловушкам
времени выполнения (значения по умолчанию не подставляются на пути свойств, расхождение
ключей пагинации, `empty()` на строковых идентификаторах, разная строгость прямого и
косвенного вызова).

### 7. Словарь кодов ошибок

Сверься с `../wp-abilities-api/references/error-code-vocabulary.md`. Изучи возвраты
`WP_Error` в каждом колбэке; коды вне словаря → WARN.

## Проверка

Прогон создаёт структурированный отчёт в markdown по указанному пользователем пути:

```
---
Last updated: <YYYY-MM-DD HH:MM>
---

# <Plugin> Abilities Verification — <Static|Runtime> Mode

## Status: <PASS|WARN|FAIL>

## Audit doc validation (if provided)

## Static inventory

## Annotation correctness
| Ability | Claim | Result | Evidence |
|---|---|---|---|

## Permission gates

## Schema lints

## Error-code vocabulary
```

Каждая возможность получает OK, WARN или FAIL. Один FAIL → итоговый FAIL; WARN без FAIL →
WARN; иначе PASS.

## Сбои и отладка

- **Окружение недоступно (режим выполнения)** — запуск окружения не удался или Docker не
  работает. Перезапусти `wp-project-triage`, затем исправь окружение. Не откатывайся молча к
  статическому режиму: отметь это в отчёте.
- **В исходниках нет возможностей** — верни понятный отчёт «проверять нечего».
- **Несовпадение схемы аудита** — укажи на `references/audit-schema-validation.md`; не
  исправляй аудит автоматически.
- **Ложное срабатывание на «readonly, но пишет»** — см. механизм `// verify-ignore` в
  `references/annotation-correctness.md`. Объясни, почему каждое подавление законно.
- **Во время выполнения перечислено меньше, чем статически** — хук регистрации не
  срабатывает. Проверь момент вызова хука инициализации, состояние активации и порядок
  автозагрузки.

## Когда эскалировать

- Повторяющийся законный шаблон, который ломает враждебную проверку в нескольких плагинах →
  предложи добавить его в указания по подавлению в `annotation-correctness.md`. Не расширяй
  список шаблонов-кандидатов наугад.
- Валидатор схемы аудита отклоняет законный аудит → каноническая схема в
  `../wp-abilities-audit/references/audit-schema.md` изменилась. Обнови
  `references/audit-schema-validation.md` под неё.

## Вне рамок

Измерение бюджета токенов — отдельная ось проверки: набор возможностей с чистыми
аннотациями, чистыми схемами и успешным прогоном во время выполнения всё равно может быть
непригодным к выпуску, если его форма в `tools/list` съедает контекстный бюджет агента. Эта
ось отслеживается отдельно. Не включай ручные и внешние измерения в вердикт PASS или FAIL
этого навыка.
