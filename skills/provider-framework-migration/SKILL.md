# Перенос с Plugin SDKv2 на Plugin Framework

Plugin Framework обязателен для новых ресурсов и источников данных;
SDKv2 только поддерживается. Перенос выполняется **по одному ресурсу и постепенно**:
мультиплексированный провайдер обслуживает реализации SDKv2 и Framework бок о бок,
поэтому переписывать всё сразу не нужно. Навык покрывает настройку мультиплексирования,
порядок переноса одного ресурса и поведенческие ловушки, которые превращают
механический перевод в незаметное ломающее изменение.

**Справочник** (загружай по необходимости):
- `references/schema-mapping.md` — полная таблица перевода SDKv2 → Framework
  с парами кода.

Официальное руководство: [Framework migration](https://developer.hashicorp.com/terraform/plugin/framework/migrating).

## Реши, стоит ли вообще переносить

У переноса есть реальный риск и мало заметной пользователю выгоды, поэтому сначала разберись:

- **Не переноси сложные или активно используемые ресурсы** без насущной
  необходимости (возможность, доступная только в Framework, или баг, который SDKv2
  не может исправить). Два SDK различаются поведением — прежде всего
  в отношении null и нулевых значений, — и эти различия проявляются как ломающие
  изменения для существующих пользователей. Такова действующая политика в крупных провайдерах
  вроде terraform-provider-aws.
- **Простые ресурсы переносятся безопасно**: плоские схемы, без `DiffSuppressFunc`,
  без `CustomizeDiff`, без `StateFunc`, без сложных вложенных блоков.
- Новые возможности никогда не требуют переноса старого кода — включи мультиплексирование
  и напиши новый ресурс на Framework рядом со старыми.

Чтобы понять, в каком режиме провайдер, посмотри `go.mod`: наличие `terraform-plugin-mux`
значит, что он уже обслуживает оба; только `terraform-plugin-sdk/v2` значит
SDKv2 (мультиплексирование — твой первый шаг); только
`terraform-plugin-framework` значит, что перенос завершён.

## Шаг 1: мультиплексируй провайдер

Объедини оба сервера плагинов в `main.go`. Обслуживание протокола версии 6
требует обновить сервер SDKv2 через `tf5to6server` (протокол 6 требует
Terraform CLI >= 1.0; если нужно поддерживать 0.12+, мультиплексируй на протоколе 5
через `tf6to5server` и `tf5muxserver` — но тогда провайдер на Framework
не сможет использовать возможности только протокола 6, например вложенные атрибуты):

```go
package main

import (
    "context"
    "flag"
    "log"

    "github.com/hashicorp/terraform-plugin-framework/providerserver"
    "github.com/hashicorp/terraform-plugin-go/tfprotov6"
    "github.com/hashicorp/terraform-plugin-go/tfprotov6/tf6server"
    "github.com/hashicorp/terraform-plugin-mux/tf5to6server"
    "github.com/hashicorp/terraform-plugin-mux/tf6muxserver"

    "example.org/terraform-provider-examplecloud/internal/provider"
    sdkprovider "example.org/terraform-provider-examplecloud/internal/sdkprovider"
)

func main() {
    var debug bool
    flag.BoolVar(&debug, "debug", false, "run with support for debuggers")
    flag.Parse()

    ctx := context.Background()

    upgradedSDKServer, err := tf5to6server.UpgradeServer(
        ctx,
        sdkprovider.Provider().GRPCProvider,
    )
    if err != nil {
        log.Fatal(err)
    }

    providers := []func() tfprotov6.ProviderServer{
        providerserver.NewProtocol6(provider.New(version)()),
        func() tfprotov6.ProviderServer { return upgradedSDKServer },
    }

    muxServer, err := tf6muxserver.NewMuxServer(ctx, providers...)
    if err != nil {
        log.Fatal(err)
    }

    var serveOpts []tf6server.ServeOpt
    if debug {
        serveOpts = append(serveOpts, tf6server.WithManagedDebug())
    }

    err = tf6server.Serve("registry.terraform.io/example/examplecloud",
        muxServer.ProviderServer, serveOpts...)
    if err != nil {
        log.Fatal(err)
    }
}
```

Требования мультиплексирования, которые кусаются на практике:

- **Схемы провайдера должны полностью совпадать** в обоих плагинах — одни и те же
  атрибуты уровня провайдера, те же типы, те же описания. Держи один источник
  истины для конфигурации провайдера и зеркаль его.
- **Каждый ресурс и источник данных может существовать только в одном** из двух
  плагинов. Финальный шаг переноса — удаление регистрации в SDKv2.
- Если публикуешь в Registry с протоколом 6, задай
  `"metadata": {"protocol_versions": ["6.0"]}` в
  `terraform-registry-manifest.json`.

## Шаг 2: зафиксируй исходное состояние до любых правок

Перенесённый ресурс должен быть неотличим для пользователей. Докажи это
тестами, которые существуют *до* переноса:

1. Убедись, что у ресурса есть проходящее приёмочное покрытие: `_basic` с шагом
   импорта (`ImportStateVerify: true`), `_disappears` и тесты обновления по каждому
   атрибуту. Если покрытия нет, напиши его сначала для реализации SDKv2 —
   эти тесты и есть критерий приёмки переноса, и после него они должны проходить
   **без изменений**.
2. Запиши поведение, которое тесты не ловят: значения по умолчанию у атрибутов, что
   происходит при опущенных необязательных атрибутах (null против `""`, `0`, `false` — это вот-вот
   станет важным) и любую нормализацию в `DiffSuppressFunc` и `StateFunc`.

## Шаг 3: перенеси ресурс

Переведи схему и CRUD по таблице сопоставления из
`references/schema-mapping.md`. Правила, предотвращающие ломающие изменения:

- **Блоки остаются блоками.** Записанный в конфигурациях пользователей синтаксис
  `block { ... }`, который в SDKv2 был `Elem: &schema.Resource{...}`, должен стать **блоком**
  Framework (`schema.ListNestedBlock` или `schema.SetNestedBlock`) — превращение его во вложенный
  *атрибут* меняет синтаксис HCL, который пишут пользователи, а это ломающее
  изменение. Вложенные атрибуты — только для новых схем.
- **Null — не ноль.** SDKv2 `d.Get("name")` возвращал `""` для незаданного значения;
  модель Framework даёт тебе `types.String`, который различает null,
  unknown и `""`. Везде, где старый код проверял `== ""` или полагался на
  `GetOk`, реши явно, что значит null, и убедись, что отправляешь
  API то же, что отправлял SDKv2 (обычно: опустить поле, когда null).
- **Сохрани атрибут `id`.** Новые ресурсы Framework могут опускать избыточный
  `id`, но *перенесённый* ресурс должен сохранить точную схему —
  удаление или переименование атрибутов ломает существующее состояние и конфигурации.
- **Состояние должно проходить круговой путь.** Framework читает состояние, записанное SDKv2.
  Если каждый атрибут сохраняет имя и тип, обновление состояния не нужно. Если
  старая схема хранила значение, которое пакет новых типов нормализует
  иначе, нужен `StateUpgrader` — считай это сигналом, что ресурс, возможно,
  относится к категории «не переносить».

## Шаг 4: перенеси регистрацию

Зарегистрируй ресурс в `Resources()` провайдера Framework и удали
его из `ResourcesMap` провайдера SDKv2 в том же коммите — мультиплексирование
падает на дубликатах.

## Шаг 5: проверь

1. Ранее существовавшие приёмочные тесты проходят **без изменений** —
   особенно `ImportStateVerify`, который сравнивает импортированное состояние с
   сохранённым и ловит большинство регрессий null против нуля.
2. Добавь шаг проверки совместимости состояния: примени конфигурацию последней
   выпущенной версией провайдера (SDKv2), затем построй план перенесённой сборкой — план
   должен быть пустым. В `terraform-plugin-testing` это двухшаговый тест
   с `ExternalProviders` для старой версии, затем
   `ProtoV6ProviderFactories` с `ConfigPlanChecks`, утверждающим пустой
   план. Навык `provider-test-patterns` (если доступен) описывает этот
   приём.
3. `terraform plan` на настоящем файле состояния до переноса не показывает диффа.

## Чек-лист

- [ ] Ресурс достаточно прост для переноса (без сложной настройки диффа) или есть насущная необходимость
- [ ] Мультиплексирование обслуживает оба плагина; схемы уровня провайдера идентичны в обоих
- [ ] Приёмочные тесты существовали до переноса и проходят без изменений после
- [ ] Блоки остались блоками; имена и типы атрибутов не изменились; `id` сохранён
- [ ] Семантика null и опущенных значений сохранена (API получает то, что отправлял SDKv2)
- [ ] Регистрация в SDKv2 удалена в том же изменении
- [ ] Пустой план проверен на состоянии, записанном предыдущим выпуском
- [ ] Добавлена запись в журнал изменений, если репозиторий ведёт заметки о выпуске

## Связанные навыки

Используй навык `provider-resources` (если доступен) для приёмов CRUD, поиска и ожидания
в перенесённом коде, а `provider-test-patterns` — для приёмов тестирования
регрессий и обновления версий.
