Этот навык берёт контекст текущего диалога и понимание проекта и создаёт спецификацию. НЕ опрашивай пользователя: обобщи то, что уже знаешь.

Трекер задач и словарь меток для разбора должны был быть переданы тебе заранее. Если это не так, попроси пользователя выполнить `/setup-matt-pocock-skills`.

## Порядок работы

1. Изучи репозиторий и пойми текущее состояние проекта, если ещё не сделал этого. По всей спецификации используй словарь предметного глоссария проекта и учитывай записи об архитектурных решениях (ADR) в той области, которую затрагиваешь.

2. Наметь границы, на которых ты будешь проверять возможность. Существующие границы предпочтительнее новых. Используй самую высокую из возможных. Если нужны новые границы, предлагай их на максимально высоком уровне. Чем меньше границ в проекте, тем лучше — идеально одна.

Сверь с пользователем, что эти границы совпадают с его ожиданиями.

3. Напиши спецификацию по шаблону ниже и опубликуй её в трекере задач проекта. Поставь метку разбора `ready-for-agent` — дополнительный разбор не нужен.

## Постановка проблемы

Проблема, с которой сталкивается пользователь, с точки зрения пользователя.

## Решение

Решение проблемы с точки зрения пользователя.

## Пользовательские истории

ДЛИННЫЙ нумерованный список пользовательских историй. Каждая история оформляется так:

1. Как <роль>, я хочу <возможность>, чтобы <польза>

<user-story-example>
1. Как клиент мобильного банка, я хочу видеть остаток на своих счетах, чтобы принимать более взвешенные решения о тратах
</user-story-example>

Список должен быть очень подробным и покрывать все стороны возможности.

## Решения по реализации

Список принятых решений по реализации. Сюда может входить:

- модули, которые будут созданы или изменены
- интерфейсы этих модулей, которые будут изменены
- технические уточнения от разработчика
- архитектурные решения
- изменения схемы данных
- контракты API
- конкретные взаимодействия

НЕ включай конкретные пути к файлам и фрагменты кода: они быстро устаревают.

Исключение: если прототип дал фрагмент, который точнее прозы фиксирует решение (машина состояний, редуктор, схема, форма типа), вставь его в соответствующее решение и коротко укажи, что он из прототипа. Оставь только части, важные для решения, а не рабочий пример целиком.

## Решения по тестированию

Список принятых решений по тестированию. Включи:

- описание того, что делает тест хорошим (проверяем только внешнее поведение, а не детали реализации)
- какие модули будут покрыты тестами
- примеры похожих тестов в проекте

## Вне области работы

Описание того, что в эту спецификацию не входит.
