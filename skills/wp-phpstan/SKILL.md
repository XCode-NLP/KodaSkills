# PHPStan в проектах WordPress

## Когда использовать

Используй этот навык при работе с PHPStan в проекте на WordPress, например:

- при настройке или обновлении `phpstan.neon` и `phpstan.neon.dist`;
- при создании или обновлении `phpstan-baseline.neon`;
- при исправлении ошибок PHPStan через дружественные к WordPress PHPDoc-аннотации
  (запросы REST, хуки, результаты запросов);
- при безопасной работе с классами сторонних плагинов и тем (заглушки, автозагрузка,
  точечные исключения).

## Что нужно на входе

- вывод `wp-project-triage` (запусти его первым, если ещё не запускал);
- разрешено ли добавлять или обновлять зависимости Composer для разработки
  (заглушки);
- разрешено ли менять базовый набор ошибок в этой задаче.

## Порядок работы

### 0. Найди точки входа PHPStan

1. Изучи настройку PHPStan (конфигурация, базовый набор, скрипты):

   ```bash
   node skills/wp-phpstan/scripts/phpstan_inspect.mjs
   ```

Предпочитай существующий скрипт `composer` из репозитория (например,
`composer run phpstan`), если он есть.

### 1. Убедись, что загружены заглушки ядра WordPress

`szepeviktor/phpstan-wordpress` или `php-stubs/wordpress-stubs` фактически
обязательны для большинства репозиториев плагинов и тем WordPress. Без них жди
множества ошибок о неизвестных функциях ядра.

- Подтверди, что пакет установлен (смотри `composer.dependencies` в отчёте
  проверки).
- Убедись, что конфигурация PHPStan ссылается на заглушки (см.
  `references/third-party-classes.md`).

### 2. Сделай разумный `phpstan.neon` для проекта WordPress

- Держи `paths` сосредоточенным на своём коде (каталоги плагина или темы).
- Исключай сгенерированный и вендорный код (`vendor/`, `node_modules/`, артефакты
  сборки, тесты, если они не анализируются намеренно).
- Держи записи `ignoreErrors` узкими и снабжёнными пояснениями.

Смотри:

- `references/configuration.md`

### 3. Исправляй ошибки типизацией под WordPress (предпочтительно)

Предпочитай исправление типов игнорированию ошибок. Частые места в WordPress,
которым нужна помощь:

- эндпоинты REST: типизируй параметры запроса через `WP_REST_Request<...>`;
- обратные вызовы хуков: добавь точные типы `@param` для аргументов;
- результаты запросов к базе и перебираемые значения: используй формы массивов и
  объектов для результатов запросов;
- Action Scheduler: типизируй формы массива `$args` для обратных вызовов заданий.

Смотри:

- `references/wordpress-annotations.md`

### 4. Работай с классами сторонних плагинов и тем (только когда нужно)

Когда код взаимодействует с плагинами и темами, которых нет в окружении анализа:

- сначала убедись, что зависимость действительно есть (установлена или требуется);
- предпочитай заглушки под конкретный плагин, уже используемые в репозитории
  (частые примеры: `php-stubs/woocommerce-stubs`, `php-stubs/acf-pro-stubs`);
- если PHPStan всё равно не находит классы, добавь точечные шаблоны
  `ignoreErrors` для конкретного префикса поставщика.

Смотри:

- `references/third-party-classes.md`

### 5. Работа с базовым набором ошибок (инструмент перехода, а не свалка)

- Сгенерируй базовый набор один раз для старого кода, затем постепенно сокращай
  его.
- Не вноси во базовый набор только что появившиеся ошибки.

Смотри:

- `references/configuration.md`

## Проверка

- Запусти PHPStan найденной командой (`composer run ...` или
  `vendor/bin/phpstan analyse`).
- Убедись, что файл базового набора (если используется) подключён и не вырос
  неожиданно.
- Запусти заново после изменения `ignoreErrors` и убедись, что шаблоны не скрывают
  посторонние проблемы.

## Режимы отказа и отладка

- «Class not found»:
  - проверь автозагрузку и заглушки либо добавь узкий шаблон исключения.
- Огромное число ошибок после включения PHPStan:
  - сократи `paths`, добавь `excludePaths`, начни с более низкого уровня и повышай
    его постепенно.
- Несогласованные типы вокруг хуков и параметров REST:
  - добавь явный PHPDoc (см. справочные материалы), а не проверки во время
    выполнения.

## Когда эскалировать

- Если тип зависит от API стороннего плагина, который нельзя подтвердить, спроси
  версию зависимости или исходный код, прежде чем придумывать типы.
- Если исправление требует новых зависимостей Composer (заглушек или расширений),
  сначала согласуй это с пользователем.
