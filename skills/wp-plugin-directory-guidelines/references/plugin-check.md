# Проверка через Plugin Check

Используй Plugin Check (PCP) как слой проверки при ревью кода плагина и проверке внесённых
изменений. Он дополняет контрольный список каталога, функциональные тесты и человеческое ревью;
он не подтверждает одобрение и не удостоверяет корректность.

## 1. Определи плагин и окружение

- Изучи точку входа плагина, объявленные версии WordPress и PHP, инструкции проекта и доступные
  команды линтера, сборки и тестов, прежде чем проверять или менять код.
- Определи фактический слаг или путь исходников плагина и локальную установку WordPress,
  содержащую проверяемый код. Переиспользуй средство запуска команд проекта (например, его
  существующую обёртку контейнера) и его конфигурацию.
- Используй локальный сайт разработки или тестов, а не рабочий. Проверки времени выполнения
  Plugin Check выполняют код плагина.
- Убедись, что доступны WP-CLI и WordPress, затем изучи `wp help plugin check`, чтобы
  подтвердить поддерживаемые параметры. Команду предоставляет Plugin Check, сама по себе она в
  WP-CLI не встроена.

Из корня локального WordPress эти команды проверяют требования:

```sh
wp --info
wp core is-installed
wp plugin is-installed plugin-check
wp plugin is-active plugin-check
wp help plugin check
```

Если настройка локального окружения входит в разрешённый объём задачи, установи и активируй PCP,
когда его нет:

```sh
wp plugin install plugin-check --activate
```

Если он установлен, но неактивен, используй `wp plugin activate plugin-check`. Сохраняй
существующую установку, а не переустанавливай её. При запуске вне корня WordPress добавляй
`--path=/actual/wordpress/root` или используй настроенное в проекте средство запуска для каждой
команды сайта.

Если инструментов нет, продолжай проверку исходников и давай конкретные команды, адаптированные
к известному окружению. Помечай автоматическую проверку как **не выполнена** с указанием
отсутствующего требования. Недоступная проверка не является пройденной.

Даже когда настройка исключена, приводи полную последовательность дальнейших шагов как
инструкцию: получить WP-CLI и локальный тестовый сайт WordPress, сделать там целевые исходники
доступными, при необходимости установить и активировать PCP, изучить справку команды, затем
запустить проверки. Не начинай с `wp plugin check`, когда его требования не выполнены. Для
будущего сайта с готовым WP-CLI и отсутствующим PCP:

```sh
wp --path=/actual/wordpress/root core is-installed
wp --path=/actual/wordpress/root plugin install plugin-check --activate
wp --path=/actual/wordpress/root help plugin check
wp --path=/actual/wordpress/root plugin check /actual/path/to/plugin
```

Заменяй заполнители известными путями и целевым плагином; неизвестные пути отмечай явно. Для
существующей установки PCP используй шаги проверки и активации выше вместо переустановки. Включай
загрузчик времени выполнения ниже, когда требуется покрытие времени выполнения.

## 2. Запусти тесты и проверки

Запусти соответствующие существующие линтеры и тесты, а также необходимые сборки ресурсов. Затем
запусти Plugin Check против фактически изменённого плагина. Замени `<plugin-slug>` перед
выполнением:

```sh
wp plugin check <plugin-slug>
```

В статье `wp plugin check meu-plugin` использует `meu-plugin` как пример слага, а не как
фиксированную цель. Директорию исходников тоже можно проверить через
`wp plugin check /actual/path/to/plugin` в работающем окружении WordPress.

Для структурированных находок используй `wp plugin check <plugin-slug> --format=json`, когда это
поддерживается. Держи ошибки и предупреждения видимыми; не добавляй исключения и флаги
игнорирования только чтобы проверка прошла. Записывай команду, цель, область, вывод и сбои
выполнения.

WP-CLI по умолчанию запускает **статические проверки**. Проверки времени выполнения дополнительно
требуют, чтобы целевой плагин был установлен и активен на локальном тестовом сайте. Сначала
проверь его активацию:

```sh
wp plugin is-active <plugin-slug>
```

Если он неактивен, активируй его, когда настройка локального окружения разрешена:
`wp plugin activate <plugin-slug>`. Иначе сообщи, что проверки времени выполнения **не
выполнены**, и пометь результат как только статический. Загрузка одного лишь `cli.php` из PCP не
гарантирует покрытие времени выполнения.

Чтобы включить проверки времени выполнения на подходящем локальном сайте, загрузи настоящий
`cli.php` из PCP до загрузки WordPress:

```sh
wp plugin check <plugin-slug> --require=/actual/path/to/plugin-check/cli.php
```

Определяй установленную директорию Plugin Check, а не предполагай стандартную директорию
содержимого. Если загрузчик отсутствует или инициализация времени выполнения не удалась, сообщи
об этом ограничении: результат только статической проверки нельзя описывать как проверку времени
выполнения.

## 3. Разбери находки до исправлений

Для каждой находки, требующей действий, сообщай:

- правило или код, важность и файл со строкой, когда они даны;
- почему правило существует и что исходный код реально делает;
- применимо ли оно, включая доказательства возможного ложного срабатывания;
- минимально подходящее исправление и его влияние на поведение плагина.

Отличай автоматические находки о лучших практиках от нарушений политики каталога; ссылайся на
соответствующее правило, только когда оно применимо. Не удаляй предупреждения механически и не
доверяй предложенному исправлению без проверки контекста.

Для запросов только на проверку верни анализ и предложенные исправления, не меняя плагин. Когда
исправления уже разрешены, применяй подходящие правки в этих рамках, не требуя отдельного
согласования по каждой находке. Выноси на ревью неуверенные изменения и изменения вне рамок.

### Необязательный контекст ИИ-ревью

Если в установленной версии Plugin Check есть директория `prompts/`, читай подходящие подсказки
как дополнительные критерии ревью вместе с исходниками плагина и контекстом задачи. Их наличие
различается; они не заменяют ручной контрольный список и фактические результаты проверок.

`wp plugin check <plugin-slug> --ai` необязателен. Используй его, только когда справка
установленной команды подтверждает поддержку, а настройка поставщика и его использование уже
разрешены. Иначе толкуй обычный вывод в текущей сессии агента. Считай ИИ-предположения о ложных
срабатываниях гипотезами, требующими подтверждения исходником, а не автоматическим основанием
отбрасывать находки.

## 4. Проверь, перетестируй и отчитайся

После исправлений изучи дифф, перезапусти затронутые тесты и повтори Plugin Check с той же целью и
тем же покрытием, чтобы результаты были сопоставимы. Проверь затронутое поведение локально,
включая права и обработку данных, когда это уместно. Остановись, когда релевантные находки
устранены или у оставшихся есть явное объяснение либо блокер; избегай повторных прогонов без
изменений и новой диагностической цели.

В отчёте укажи цель, фактические команды, статическое и runtime-покрытие, результаты тестов,
исправления, оставшиеся находки с правилом или кодом и файлом со строкой, когда доступно, а также
невыполненные проверки. Отделяй чистый результат Plugin Check от результатов функциональных
тестов и ручных выводов о политике. Оставь достаточно доказательств для человеческого ревью.

  ограничения.
- [Guga Alves: ревью плагинов с Agent Skills и Plugin Check](https://gugaalves.net/wordpress/revisar-desenvolvimento-agent-skills-plugin-check/):
