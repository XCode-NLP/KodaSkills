### Правило 1: совместимая с GPL лицензия

**Проверка:** есть ли в основном файле плагина заголовок `License:` с совместимым с GPL
значением? Все ли встроенные сторонние библиотеки под совместимыми лицензиями?

**Признаки нарушения:**

- нет заголовка `License:` или `License URI:` в основном файле плагина;
- лицензия — `Proprietary`, `All Rights Reserved`, `CC-BY-NC`, `CC-BY-ND`, `SSPL`, `BSL`,
  `Commons Clause`, `EPL`, `EUPL` или `MPL-1.0`;
- встроенная библиотека под лицензией, которой нет в таблице совместимых с GPL лицензий (см.
  ниже);
- PHP-файлы закодированы ionCube, Zend Guard или подобным — исходник нельзя использовать →
  нарушение.

**Вердикт:** отметить как **FAIL** с указанием конкретного файла и найденного значения лицензии.

**Исправление:** используй `GPL-2.0-or-later` (рекомендуется). Добавь полный текст лицензии или
`License URI:` на `https://www.gnu.org/licenses/gpl-2.0.html`. Замени несовместимые библиотеки.

### Правило 2: ответственность разработчика

**Проверка:** намеренно ли разработчик вернул ранее удалённый код, обошёл прежнее решение по
правилам или включил файлы, которые не вправе распространять?

**Признаки нарушения:**

- история коммитов показывает восстановление файла после того, как его удалила команда ревью;
- встроенные ресурсы без документированной лицензии (считай их нелицензированными, пока не
  доказано обратное);
- условия стороннего API запрещают распространение встроенного SDK.

**Вердикт:** отметить как **FAIL**. Задокументируй конкретный файл или коммит.

**Исправление:** удали offending-файл или получи и задокументируй надлежащее лицензирование.

### Правило 3: стабильная версия в SVN

**Check:** является ли версия в SVN на WordPress.org каноническим релизом? Не распространяется ли
плагин также по внешнему каналу с более новой версией?

**Признаки нарушения:**

- `readme.txt` заявляет версию, которой нет в trunk или tags SVN;
- страница внешней загрузки (собственный сайт разработчика) предлагает сборку новее, чем на
  WP.org;
- плагин обновляет себя с сервера вне WP.org (это ещё и проблема правила 8).

**Вердикт:** отметить как **FAIL**, если активно поддерживаемая внешняя версия опережает каталог.

**Исправление:** держи SVN в актуальном состоянии. Внешние каналы могут зеркалировать, но не
должны опережать версию каталога.

### Правило 4: читаемый человеком код

**Проверка:** весь ли PHP, JS и CSS в форме, которую разработчик может прочитать и понять?
Доступны ли исходники сборки?

**Признаки нарушения:**

- PHP обфусцирован пакером, цепочками `eval` и base64 или именами переменных вида `$a1b2c3`
  повсюду;
- минифицированный JS присутствует **без** карты исходников и без ссылки на репозиторий или
  исходный файл в readme;
- артефакты сборки (`.min.js`) закоммичены без соответствующего неминифицированного исходника в
  пакете или в публичном репозитории, указанном в `readme.txt`.

**Вердикт:** **FAIL** для обфусцированного PHP (всегда). **FAIL** для JS только в минифицированном
виде, если доступ к исходнику не документирован.

**Исправление:** убери обфускацию. Добавь в `readme.txt` раздел `Development` или `Build` со
ссылкой на репозиторий исходников (GitHub, GitLab и т.п.).

### Правило 5: без пробных версий

**Основное правило:** каждая функция, поставляемая в каталоге, должна работать от начала до конца
без ключа лицензии, оплаты или аккаунта.

**Проверка каждого ограничения функции в коде:**

1. Ограничивает ли проверка `has_paid_access()`, `is_licensed()` или `check_license()`
   **локальную** обработку (а не вызов внешнего сервиса)?
2. Есть ли ограничение по времени (`time() > $installed_at + 30 * DAY_IN_SECONDS`) для локального
   поведения?
3. Есть ли квота использования (`if ( $count >= 100 )`), искусственно заниженная и существующая
   только чтобы давить на апгрейд?
4. Видит ли бесплатный пользователь заблокированный интерфейс, который мешает завершить основной
   процесс?

**Признаки нарушения (отмечать как FAIL):**

- `return`, `wp_die()` или блокирующий экран, показываемые, когда `has_paid_access()` ложно для
  локальной функции;
- тернарные ограничения: `$limit = $licensed ? 10000 : 100` без фильтра, позволяющего поднять
  бесплатный предел;
- функции истекают через X дней, даже когда внешний сервис не задействован;
- экран админки целиком заменён предложением обновиться.

**Допустимые шаблоны (не отмечать):**

- уведомление о допродаже рядом с работающей бесплатной функцией (не блокирует);
- премиум-функция вынесена в **отдельный** плагин-дополнение, не размещённый на WP.org;
- функция внешнего SaaS ограничена, потому что **сам сервис** требует оплаты (например, квота
  API ИИ);
- закрываемая таблица сравнения или кнопка обновления в настройках плагина.

**Шаблоны кода:**

```php
// НАРУШЕНИЕ — локальная функция заблокирована проверкой оплаты
if ( ! $this->has_paid_access() ) {
    echo 'Upgrade required';
    return; // ← блокирует выполнение
}

// НАРУШЕНИЕ — искусственное ограничение без точки расширения
$limit = $this->has_paid_access() ? 10000 : 100;
```

```php
// СООТВЕТСТВУЕТ — бесплатный путь работает; премиум его дополняет
$this->render_basic_export();
if ( $this->has_premium_addon() ) {
    do_action( 'myplugin_premium_export_options' );
}

// СООТВЕТСТВУЕТ — ограничение согласовано и расширяется фильтром
$limit = apply_filters( 'myplugin_event_limit', 10000 );
```

**Контрольный список перед подачей:**

- [ ] все бесплатные функции работают без ключа лицензии;
- [ ] нет ограничений по времени и квот использования для локального поведения;
- [ ] нет блокирующего или заблокированного интерфейса, мешающего бесплатным сценариям;
- [ ] предложения о допродаже информативны, не блокируют и закрываются;
- [ ] код только для премиум-версии живёт в отдельном дополнении или внешнем сервисе.

### Правило 6: интеграции с SaaS допустимы — на условиях

**Проверка:** даёт ли внешний сервис реальную функциональность? Описан ли он в readme?

**Признаки нарушения:**

- единственная цель внешнего сервиса — проверка ключа лицензии, а вся обработка локальна;
- код перенесли на сервер специально, чтобы замаскировать то, что на самом деле является
  локальным ограничением функции;
- плагин — витрина или страница оформления заказа внешнего продукта без реальной
  функциональности плагина.

**Вердикт:** **FAIL** для сервисов, которые только проверяют лицензию. Не отмечай настоящие
интеграции с SaaS.

**Исправление:** опиши в `readme.txt`, что делает внешний сервис. Вынеси проверку лицензии из
критического пути плагина, если функциональность локальна.

### Правило 7: без сбора внешних данных без согласия

**Проверка:** отправляет ли плагин какие-либо данные на внешний сервер без явного согласия
пользователя?

**Признаки нарушения:**

- HTTP-запрос на удалённый URL при активации плагина, загрузке страницы админки или в задаче cron
  без согласия пользователя;
- адрес электронной почты пользователя, URL сайта или данные об использовании отправляются без
  видимого флажка согласия или шага регистрации;
- сторонние скрипты аналитики или отслеживания рекламы загружаются в админке или на лицевой части
  без согласия;
- ресурсы (изображения, шрифты, скрипты) загружаются с внешней CDN, которая не является основным
  сервисом плагина.

**Исключение:** плагины, которые являются интерфейсом к названному стороннему сервису (например,
Akismet, Mailchimp, CDN), — согласие подразумевается, когда пользователь настраивает подключение к
сервису.

**Шаблоны кода (нарушение и соответствие):**

```php
// НАРУШЕНИЕ — отправляет данные при активации без согласия
register_activation_hook( __FILE__, function() {
    wp_remote_post(
        'https://api.example.com/collect',
        array(
            'body' => array(
                'site' => home_url(),
                'admin_email' => get_option( 'admin_email' ),
            ),
        )
    );
} );

// СООТВЕТСТВУЕТ — явный барьер согласия
if ( isset( $_POST['myplugin_opt_in'] ) && '1' === $_POST['myplugin_opt_in'] ) {
    update_option( 'myplugin_tracking_opt_in', 1 );
}

if ( get_option( 'myplugin_tracking_opt_in' ) ) {
    wp_remote_post( 'https://api.example.com/collect', $payload );
}
```

**Вопросы ревью:**

1. Делается ли какой-либо исходящий запрос при активации, первом запуске или в cron до того, как
   согласие сохранено?
2. Явен ли интерфейс согласия, однозначен ли он и выключен ли по умолчанию?
3. Сохраняется ли согласие и проверяется ли оно перед каждым путём отправки телеметрии?
4. Описаны ли собираемые поля в разделе приватности `readme.txt`?

**Вердикт:** **FAIL** для любого исходящего вызова без согласия. Укажи найденный URL или домен.

**Исправление:** оберни все исходящие вызовы в барьер согласия. Добавь в `readme.txt` раздел
`Privacy Policy` с описанием того, какие данные собираются и зачем.

**Контрольный список перед подачей:**

- [ ] ни один вызов телеметрии или аналитики не происходит до явного согласия;
- [ ] элемент управления согласием виден и по умолчанию выключен;
- [ ] согласие сохраняется и проверяется в каждом исходящем пути;
- [ ] политика приватности в readme объясняет данные, получателя и цель.

### Правило 8: без удалённо загружаемого исполняемого кода

**Проверка:** весь ли JS и CSS, который выполняется на сайте пользователя, включён в пакет
плагина?

**Признаки нарушения:**

- `wp_enqueue_script()` загружает JS со сторонней CDN (а не собственный ресурс);
- плагин получает и выполняет код с внешнего URL во время работы (`file_get_contents` и `eval`,
  динамический `<script src>`);
- плагин устанавливает или обновляет себя с сервера вне WP.org;
- страница админки целиком отрисовывается внутри `<iframe>`, указывающего на внешний URL.

**Допустимые исключения:**

- веб-шрифты, загружаемые с Google Fonts или аналогичных CDN шрифтов;
- собственный SaaS-сервис плагина, загружающий свои скрипты виджета или встраивания (с согласием
  пользователя согласно правилу 7).

**Шаблоны кода (нарушение и соответствие):**

```php
// НАРУШЕНИЕ — исполняемый JS загружается со сторонней CDN
wp_enqueue_script(
    'myplugin-admin',
    'https://cdn.example.com/myplugin/admin.js',
    array(),
    '1.0.0',
    true
);

// СООТВЕТСТВУЕТ — исполняемый JS включён в пакет плагина
wp_enqueue_script(
    'myplugin-admin',
    plugins_url( 'assets/js/admin.js', __FILE__ ),
    array(),
    MYPLUGIN_VERSION,
    true
);
```

**Вопросы ревью:**

1. Указывают ли какие-либо подключения скриптов и стилей на сторонние домены для исполняемых
   ресурсов?
2. Есть ли какой-либо путь загрузки и выполнения кода во время работы (`eval`, динамический
   `<script>`, удалённые включения)?
3. Обходит ли логика обновления и установки каналы распространения WP.org?
4. Ограничены ли внешние ресурсы разрешёнными исключениями (шрифты, встраивание настоящего
   сервиса)?

**Вердикт:** **FAIL** для каждого внешне загружаемого исполняемого ресурса. Отметь URL и
файл со строкой, где он подключён.

**Исправление:** включи JS и CSS локально. Используй SVN WP.org для обновлений. Замени страницы
админки в `<iframe>` на нормальный интерфейс админки WP, работающий через REST или admin-ajax.

**Контрольный список перед подачей:**

- [ ] весь исполняемый JS и CSS упакован локально в плагин;
- [ ] нет загрузки и выполнения удалённого кода во время работы;
- [ ] нет механизма внешнего самообновления и самоустановки;
- [ ] любые внешние ресурсы документированы и попадают под разрешённые исключения.

### Правило 9: без незаконного, нечестного и оскорбительного поведения

**Проверка:** есть ли в плагине обманчивое, манипулятивное или вредоносное поведение?

**Признаки нарушения:**

- скрытое переполнение ключевыми словами в выводе страницы для манипуляции поисковыми позициями;
- код, который публикует обзоры, оценки или ответы в поддержке от имени пользователя;
- плагин представлен как оригинальная работа, но является форком или копией другого плагина без
  указания авторства;
- плагин заявляет, что делает сайт «соответствующим GDPR» или «соответствующим ADA», без правовых
  оснований;
- код, использующий ресурсы посетителей сайта для майнинга криптовалют, ботнетов и подобного.

**Вердикт:** **FAIL**. Это категория высокой важности; тщательно документируй доказательства.

### Правило 10: без навязанных внешних ссылок

**Проверка:** выводит ли плагин ссылки «Powered by», упоминания в подвале или обратные ссылки,
видимые посетителям сайта?

**Признаки нарушения:**

- ссылка-упоминание выводится по умолчанию без настройки для её отключения;
- плагин требует, чтобы ссылка-упоминание оставалась активной для полной функциональности;
- ссылка встроена в необязательный вывод шаблона;
- текст или ссылка «Powered by» в шаблонах (шаблон сканера: `(?<!x-)powered[ -_]by`);
- обратная ссылка требуется для разблокировки обновления или функции (пересекается с правилами 5
  и 10).

**Исключение:** сервис может брендировать собственный отрисованный вывод (например, форма оплаты с
логотипом платёжного провайдера).

**Шаблоны кода (нарушение и соответствие):**

```php
// НАРУШЕНИЕ — навязанная ссылка-упоминание в публичном выводе
add_action( 'wp_footer', function() {
    echo '<p class="myplugin-credit"><a href="https://vendor.example">Powered by Vendor</a></p>';
} );

// НАРУШЕНИЕ — обратная ссылка требуется для активации функции
if ( ! get_option( 'myplugin_keep_backlink' ) ) {
    wp_die( 'Please keep our credit link active to use this feature.' );
}

// СООТВЕТСТВУЕТ — необязательно, явное согласие, по умолчанию выключено
if ( get_option( 'myplugin_show_credit_link', false ) ) {
    echo '<p class="myplugin-credit"><a href="https://vendor.example">Powered by Vendor</a></p>';
}
```

**Вопросы ревью:**

1. Вставляется ли какая-либо ссылка «Powered by» или упоминание в вывод лицевой части по
   умолчанию?
2. Могут ли пользователи отключить ссылку, не ломая функциональность?
3. Есть ли логика, связывающая доступ к функции с сохранением обратной ссылки?
4. Явно ли согласие на показ упоминаний (не подразумеваемо) и сохраняется ли оно?

**Вердикт:** **FAIL**, если ссылка включена по умолчанию без возможности отказа. **FAIL**, если её
удаление ломает функциональность.

**Исправление:** сделай настройку по умолчанию `false` (скрыто). Дай понятный флажок в настройках
для её включения.

**Контрольный список перед подачей:**

- [ ] ни одно упоминание или обратная ссылка не показывается по умолчанию на публичных страницах;
- [ ] ссылка-упоминание строго по желанию и под контролем пользователя;
- [ ] отключение ссылок-упоминаний не отключает функциональность плагина;
- [ ] ни один путь обновления не требует активной обратной ссылки.

### Правило 11: без захвата панели управления

**Проверка:** ограничены ли уведомления админки, предложения обновления и напоминания и не
навязчивы ли они?

**Признаки нарушения:**

- уведомление админки на весь сайт, которое нельзя закрыть (нет кнопки закрытия, появляется при
  каждой загрузке страницы);
- предложение обновления или допродажи показывается на каждой странице админки, а не только на
  собственном экране настроек плагина;
- плагин переопределяет главную страницу панели управления WordPress или вставляет наложения на
  всю страницу;
- рекламные баннеры или пиксели отслеживания размещены в админке WordPress;
- страница настроек админки отрисовывается как внешний `<iframe>` вместо нативного интерфейса
  админки WP.

**Шаблоны кода (нарушение и соответствие):**

```php
// НАРУШЕНИЕ — внешний iframe на странице админки
add_action( 'admin_menu', function() {
    add_menu_page( 'My Plugin', 'My Plugin', 'manage_options', 'myplugin', function() {
        echo '<iframe src="https://app.vendor.example/dashboard" style="width:100%;height:80vh;border:0"></iframe>';
    } );
} );

// СООТВЕТСТВУЕТ — нативная оболочка страницы админки с получением данных с сервера или API
add_action( 'admin_menu', function() {
    add_menu_page( 'My Plugin', 'My Plugin', 'manage_options', 'myplugin', function() {
        echo '<div class="wrap"><h1>My Plugin</h1><div id="myplugin-admin-app"></div></div>';
    } );
} );

add_action( 'admin_enqueue_scripts', function( $hook ) {
    if ( 'toplevel_page_myplugin' !== $hook ) {
        return;
    }
    wp_enqueue_script(
        'myplugin-admin',
        plugins_url( 'assets/js/admin.js', __FILE__ ),
        array( 'wp-api-fetch' ),
        MYPLUGIN_VERSION,
        true
    );
} );
```

**Вопросы ревью:**

1. Отрисовывает ли какой-либо экран админки интерфейс плагина внутри внешнего iframe?
2. Использует ли плагин нативные страницы админки WP и проверки прав вместо этого?
3. Ограничены ли допродажи и уведомления страницами плагина и можно ли их закрыть?
4. Остаются ли настройки и основные процессы полностью работоспособными после удаления интерфейса
   допродаж?

**Вердикт:** **FAIL** для постоянных незакрываемых уведомлений или уведомлений, появляющихся вне
собственных страниц плагина.

**Исправление:** используй `is_plugin_page()` или эквивалентную проверку, чтобы ограничить
уведомления. Добавь обработчик закрытия через `update_user_meta` или шаблон закрываемого
уведомления WP. Никогда не показывай предложения обновления на посторонних страницах админки.

**Контрольный список перед подачей:**

- [ ] для страниц админки и настроек не используются внешние iframe;
- [ ] интерфейс админки отрисовывается как нативные страницы админки WP;
- [ ] уведомления закрываемы и ограничены экранами плагина;
- [ ] удаление уведомлений и допродаж не ломает функциональность плагина.

### Правило 12: без спама в readme

**Проверка:** свободен ли `readme.txt` от переполнения ключевыми словами, чрезмерных партнёрских
ссылок и меток конкурентов?

**Признаки нарушения:**

- больше 5 меток в поле `Tags:`;
- партнёрские ссылки есть, но не раскрыты, или используются редиректы и маскирующие URL;
- метки называют плагины конкурентов или нерелевантные популярные термины исключительно ради
  поисковой оптимизации;
- `readme.txt` читается как список ключевых слов, а не как полезная документация.

**Вердикт:** **WARNING** для незначительного переполнения; **FAIL** для нераскрытых партнёрских
ссылок или более 5 меток.

**Исправление:** сократи метки до 5 или менее релевантных терминов. Раскрывай все партнёрские
ссылки пометкой «(affiliate link)». Указывай партнёрские URL напрямую, без маскировки.

### Правило 13: используй библиотеки из состава WordPress

**Проверка:** включает ли плагин собственные копии библиотек, которые WordPress уже поставляет?

**Признаки нарушения:**

- плагин содержит собственные `jquery.js`, `jquery.min.js` или загружает jQuery с CDN;
- плагин включает `PHPMailer`, `SimplePie`, `PHPass`, `Backbone`, `Underscore`, `React`,
  `wp-polyfill` или другие библиотеки из состава WP;
- `wp_enqueue_script()` регистрирует библиотеку, уже доступную как дескриптор WordPress (см.
  [скрипты по умолчанию](https://developer.wordpress.org/reference/functions/wp_enqueue_script/));
- индикаторы сканера: `files_library_core` и совпадения имён файлов известных библиотек ядра (см.
  `known-libraries.php` в сканере).

**Шаблоны кода (нарушение и соответствие):**

```php
// НАРУШЕНИЕ — загрузка собственной или встроенной копии jQuery
wp_enqueue_script(
    'myplugin-jquery',
    plugins_url( 'assets/vendor/jquery-3.7.1.min.js', __FILE__ ),
    array(),
    '3.7.1',
    true
);

// СООТВЕТСТВУЕТ — используется дескриптор jQuery из состава WordPress
wp_enqueue_script( 'jquery' );
```

```php
// НАРУШЕНИЕ — прямая вставка PHP-библиотек ядра WP
require_once __DIR__ . '/vendor/PHPMailer.php';
require_once __DIR__ . '/vendor/SimplePie.php';

// СООТВЕТСТВУЕТ — используются API WordPress, опирающиеся на библиотеки ядра
wp_mail( $to, $subject, $message, $headers );
$feed = fetch_feed( $feed_url );
```

```php
// НАРУШЕНИЕ — регистрация локальной копии пакета, поставляемого ядром
wp_register_script(
    'myplugin-underscore',
    plugins_url( 'assets/vendor/underscore.min.js', __FILE__ ),
    array(),
    '1.13.6',
    true
);

// СООТВЕТСТВУЕТ — используется дескриптор ядра
wp_enqueue_script( 'underscore' );
```

**Вопросы ревью:**

1. Поставляет ли плагин имена файлов, совпадающие с шаблонами библиотек ядра (`jquery`,
   `underscore`, `backbone`, `codemirror`, `moment`, `PHPMailer`, `SimplePie`)?
2. Регистрируются ли эквиваленты библиотек ядра из путей плагина вместо дескрипторов WP?
3. Реализованы ли функции SMTP и лент через API WordPress (`wp_mail`, `fetch_feed`), а не через
   встроенные библиотеки ядра?
4. Можно ли удалить встроенные дубликаты, не ломая функциональность?

**Вердикт:** **FAIL** для каждой дублирующей встроенной библиотеки.

**Исправление:** замени встроенные копии на `wp_enqueue_script( 'jquery' )` (или подходящий
дескриптор WP). Удали локальную копию из пакета плагина.

**Контрольный список перед подачей:**

- [ ] нет встроенных копий библиотек, которые уже поставляет ядро WordPress;
- [ ] зависимости скриптов ядра загружаются через дескрипторы WP;
- [ ] функции почты и лент используют API WordPress, а не встроенные библиотеки ядра;
- [ ] оставшиеся сторонние библиотеки не дублируют ядро и имеют документацию и совместимую
  лицензию.

### Правило 14: SVN — репозиторий релизов

**Проверка:** коммиты в SVN имеют релизное качество и делаются нечасто?

**Признаки нарушения:**

- несколько коммитов в день с сообщениями вроде «fix typo», «testing», «debug»;
- отладочный код закоммичен в trunk (например, `var_dump()`, `error_log()`,
  `console.log( 'test' )`);
- номер версии не увеличивается между коммитами, меняющими функциональный код.

**Замечание:** это правило в основном рекомендательное; нарушения не блокируют подачу, но плохо
характеризуют разработчика.

**Исправление:** используй ветку разработки (GitHub или GitLab) и коммить в SVN только релизы.
Каждый коммит в SVN должен соответствовать повышению версии.

### Правило 15: увеличивай номер версии

**Проверка:** увеличивается ли номер версии в `readme.txt` и в заголовке плагина при каждом
релизе?

**Признаки нарушения:**

- `Stable tag:` в `readme.txt` не совпадает с полем `Version:` в основном файле плагина;
- используется `Stable tag: trunk` (не рекомендуется; указывай явный номер версии);
- номер версии одинаков для двух разных функциональных релизов в тегах SVN.

**Шаблоны (нарушение и соответствие):**

```text
// НАРУШЕНИЕ — расхождение readme и заголовка плагина
readme.txt:
Stable tag: 1.4.0

my-plugin.php header:
Version: 1.3.9
```

```text
// СООТВЕТСТВУЕТ — значения согласованы и повышены вместе
readme.txt:
Stable tag: 1.4.1

my-plugin.php header:
Version: 1.4.1
```

```text
// НАРУШЕНИЕ — функциональные изменения выпущены без повышения версии
SVN tag: tags/1.4.1
Current release code: changed features, still Version: 1.4.1

// СООТВЕТСТВУЕТ — каждый функциональный релиз получает новый тег версии
SVN tags: tags/1.4.1 -> tags/1.4.2
```

**Вопросы ревью:**

1. Совпадает ли `Stable tag` из `readme.txt` точно с `Version` основного плагина?
2. Уникальна ли версия нового тега SVN для этого релиза?
3. Были ли функциональные изменения или изменения кода без повышения версии?
4. Согласованы ли все видимые пользователю отметки журнала изменений и релиза с повышенной
   версией?

**Вердикт:** **FAIL**, если `Stable tag` и `Version` в заголовке плагина не совпадают.

**Исправление:** повышай оба значения вместе при каждом релизе. Ставь тег релиза в SVN в
`tags/X.Y.Z`.

**Контрольный список перед подачей:**

- [ ] `Stable tag` совпадает с `Version` в заголовке плагина;
- [ ] версия повышена для этого релиза;
- [ ] тег SVN использует новую версию (`tags/X.Y.Z`);
- [ ] журнал изменений и заметки о релизе отражают ту же версию.

### Правило 16: плагин должен быть завершён при подаче

**Проверка:** работает ли плагин и завершён ли он на момент подачи?

**Признаки нарушения:**

- плагин — скелет с функциями-заглушками или страницами админки «скоро будет»;
- слаг запрошен, чтобы зарезервировать имя для будущего или незавершённого продукта;
- основная функциональность плагина требует отдельного плагина, который ещё не опубликован.

**Вердикт:** **FAIL**. Незавершённый плагин не может быть одобрен.

**Исправление:** подавай плагин, только когда он функционально полон и работает для конечных
пользователей.

### Правило 17: уважай товарные знаки и авторские права

**Проверка:** начинается ли имя или слаг плагина с товарного знака или названия проекта, которым
разработчик не владеет?

**Признаки нарушения:**

- слаг начинается с `woocommerce-`, `elementor-`, `jetpack-`, `yoast-` или любого термина из
  списка товарных знаков для слагов (см. раздел правил именования ниже);
- имя плагина начинается с термина под товарным знаком (например, «WooCommerce Pricing Rates»
  начинается с WooCommerce);
- имя использует словослияние с товарным знаком (например, «PricingPress» использует `-Press` от
  WordPress).

**Правильный шаблон:** товарный знак может стоять только **после** связки: `for`, `with`, `using`,
`and`.

- ✅ `Pricing Rates for WooCommerce`
- ❌ `WooCommerce Pricing Rates`

**Вердикт:** **FAIL** с указанием конкретного товарного знака и правильной структуры имени.

**Исправление:** перенеси товарный знак после связки. Переименуй слаг соответственно (максимум 50
символов, нижний регистр, только дефисы).

**Замечание:** это правило информационное — проверка кода и readme не требуется. Оно
устанавливает, что WordPress.org может в любое время обновлять правила, удалять плагины, отзывать
доступ или изменять плагины ради общественной безопасности. Сообщай об этом разработчикам, когда
