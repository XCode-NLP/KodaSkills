# Стандарты Symfony

Навык намеренно короткий: определи проект, примени пять правил, проверь себя перед сдачей.

## Шаг 0 — прочитай проект, прежде чем писать в него

Никогда не предполагай версии и соглашения. Один раз за сессию:

```bash
php -v | head -1
php -r '$l=json_decode(file_get_contents("composer.lock"),true);
foreach(array_merge($l["packages"],$l["packages-dev"]??[]) as $p)
  if(preg_match("#^(symfony/(framework-bundle|serializer|form|security-bundle|object-mapper|messenger|scheduler|lock|rate-limiter|asset-mapper|ux-live-component)|doctrine/orm|doctrine/doctrine-fixtures-bundle|phpunit/phpunit|twig/twig)$#",$p["name"]))
    echo str_pad($p["name"],40)." ".$p["version"]."\n";'
ls src/ config/packages/
```

Что это даёт:

- **Версии Symfony и PHP** — какие атрибуты существуют. Правило не исчезает, меняются только средства.
- **Какие опциональные компоненты установлены** — на что можно опираться без вопросов. Отсутствующее нужно *предложить*, а не ставить молча.
- **Текущая раскладка `src/`** — какие соглашения соблюдать. Если проект уже группирует код по доменам или держит DTO в другом месте, следуй ему. Границы между слоями не обсуждаются, имена папок — обсуждаются.

**`vendor/` важнее любого текста в этом навыке.** Прочитать исходник атрибута — секунда, и никаких ошибок; память и статьи в блогах ошибаются часто.

## Пять правил

Они действуют всегда, при любой задаче.

**1. Сначала напиши тест и посмотри, как он падает.** Тест, который никогда не был красным, может быть зелёным по неверной причине: перевёрнутое утверждение, слишком снисходительный мок, вообще не выполнялся. Где «сначала красный» невозможно — сломай код и убедись, что тест это заметил.

**2. Контроллер переводит, а не решает.** HTTP на входе, вызов сервиса, ответ на выходе. Никаких бизнес-правил, никакого сохранения в базу.

**3. Никаких DQL, QueryBuilder или SQL вне репозитория.** Запросы называются по намерению вызывающего, а не по механизму. Сервис, который строит запрос, нельзя протестировать без базы.

**4. DTO на обеих границах.** Входные DTO несут валидацию, выходные — контракт. Сущность никогда не попадает в шаблон или в JSON-ответ.

**5. Каждое бизнес-правило живёт в сервисе.** Сущности хранят данные и маппинг, правил в них нет. Это прямое следствие сущностей в формате maker, и оно намеренное.

Если изменение кажется слишком мелким для теста — правило 1 всё равно действует. Если правило кажется неверным для конкретного случая — скажи об этом и объясни почему, а не сгибай его молча.

## Два уровня: ядро и то, что проект должен заслужить

Пять правил выше — это всё **ядро**. Они убирают решения и не добавляют артефактов: проект, который соблюдает только их, уже следует стандарту. Всё остальное — **по требованию**: каждый такой элемент добавляет файл, инструмент или ритуал на каждую функцию, и включается реальной потребностью, никогда заранее.

| Уровень | Что в нём | Чем включается |
|---|---|---|
| **Ядро** | Пять правил; контракт слоёв; входные и выходные DTO; `dama/doctrine-test-bundle`; PHPStan и php-cs-fixer; локальный цикл разработки | Ничем — действует в любом проекте на Symfony |
| **По требованию** | Тесты на число запросов; deptrac; Messenger, Scheduler и приоритезированные очереди; кэши приложения и HTTP; correlation id, проверки здоровья, приёмники алертов; подписанные ссылки и объектное хранилище; Live Components и Mercure | Измеренная медлительность, второй воркер, реальная очередь, реальная цель деплоя, реальная загрузка файлов, реальный второй разработчик |

Проверка любого правила, которое собираешься применить или добавить: **оно убирает решение или добавляет артефакт?** Первое бесплатно, и таких может быть сто. Второе оплачивается каждой функцией и требует триггера из правой колонки, чтобы это было оправдано.

## Чего правила не требуют

Пять правил читаются строго на границах и снисходительно к церемониям. Ничто из перечисленного не сгибает правило — это то же правило, применённое с рассуждением:

- **GET, у которого только параметры маршрута, не нуждается во входном DTO.** `#[MapQueryString]` — для строки запроса, которую надо валидировать, а не для `show(int $id)`.
- **Проекция `SELECT NEW`, уже совпадающая с контрактом, *и есть* выходной DTO.** Слой чтения существует для случая, когда форма запроса и форма API различаются; когда они совпадают, класс один, в `src/Dto/Output/`.
- **Один выходной DTO на форму, а не на эндпоинт.** Строка списка и карточка детали используют один класс, если поля одинаковые.
- **Бизнес-исключение существует только для отказа, в который вызывающий реально может попасть.** Неверный ввод — это 422 из ограничений DTO, а не класс исключения.
- **Класс без правил не получает собственного юнит-теста.** DTO без нормализации, контроллер, команда, геттер: функциональный тест или smoke-тест, доказывающий связность, — это вся нужная им проверка. Правило 1 про поведение, а не про файлы.
- **Сервис чтения может держать все чтения одного ресурса.** `ShelfReader::shelf()` и `ShelfReader::book()` в одном классе — это и есть намерение; класс на каждый запрос — нет.

## Перед сдачей работы

- [ ] Тесты написаны первыми, были красными, теперь проходят — и ты их запускал.
- [ ] Результат `vendor/bin/phpunit` передан как есть, включая падения.
- [ ] Нет бизнес-правил в контроллере, нет запросов вне репозитория, ни одна сущность не пересекает границу.
- [ ] Всё, что пришлось решить за пользователя, сказано прямо, а не спрятано.
- [ ] Всё, что сделать не удалось, названо, а не тихо выброшено.

Последние два пункта важны не меньше кода. Изменение, которое работает, но скрывает решение, — это изменение, которое кому-то придётся потом разгадывать.
