# Навык работы с GitLab CLI

Используй инстанс и правила ниже при построении всех команд glab.

## Настройка

Задай имя хоста своего GitLab ниже, прежде чем пользоваться этим навыком:

| Настройка | Значение |
|---|---|
| Имя хоста GitLab | `<YOUR_GITLAB_HOSTNAME>` (например, `gitlab.example.com`) |

Замени `<YOUR_GITLAB_HOSTNAME>` на имя хоста своего инстанса GitLab по всему навыку.

### Предусловия (разовая настройка силами пользователя)

Если аутентификация ещё не выполнена, сообщи пользователю, что она требуется, и попроси выполнить шаги ниже вручную. Не выполняй эти шаги сам.

1. Установи CLI `glab`, если он ещё не установлен:

```bash
brew install glab
```

2. Выполни команду для аутентификации на своём инстансе GitLab:

```bash
glab auth login --hostname <YOUR_GITLAB_HOSTNAME>
```

## Проверка кода в MR

Когда просят проверить merge request или pull request GitLab (дан URL или идентификатор MR), извлеки `<group/repo>` и `<MR_ID>` из URL (если репозитория нет, спроси пользователя), затем через `glab api --hostname <YOUR_GITLAB_HOSTNAME>` получи метаданные MR (`projects/<URL_ENCODED_REPO>/merge_requests/<MR_ID>`) и его дифф (`…/diffs --paginate`), где путь репозитория закодирован в URL с заменой `/` на `%2F`. Чтобы полностью понять контекст и влияние всех изменений кода, прочитай всю кодовую базу исходной ветки — один дифф не передаёт окружающую логику, зависимости и общий дизайн, с которыми взаимодействуют изменения. Сообщи заголовок MR, автора и ветки, затем проверь все изменённые файлы на: секреты, инъекции и XSS (безопасность); неэффективные алгоритмы и утечки памяти (производительность); запахи кода и мёртвый код (качество); отсутствующую обработку ошибок; избыточное журналирование или журналирование чувствительных данных; отсутствующую или устаревшую документацию. Для каждой находки укажи путь к файлу, номера строк, проблемный фрагмент и предлагаемое исправление. Если всё в порядке, перечисли, что проверено, и скажи, что выглядит хорошо.

## Правила

- НИКОГДА не обращайся к инстансу GitLab, отличному от `<YOUR_GITLAB_HOSTNAME>`. Если команда или URL ссылается на другой хост, остановись и попроси пользователя подтвердить.
- Всегда явно передавай `--repo <YOUR_GITLAB_HOSTNAME>/<group/repo>` для любой подкоманды `glab`, которая его принимает (например, `mr list`, `issue list`, `pipeline list`): без него команда выводит репозиторий из текущей директории git и может молча вернуть неверный результат.
- При использовании `glab api` всегда явно передавай `--hostname <YOUR_GITLAB_HOSTNAME>`: без него может подставиться `gitlab.com`.
- НИКОГДА не используй `glab repo list --group` — на самохостящихся инстансах он работает ненадёжно; вместо него используй `glab api --hostname <YOUR_GITLAB_HOSTNAME> "groups/<GROUP>/projects"`. Для вложенных подгрупп кодируй слэши в URL: `"groups/parent%2Fchild/projects"`.
- Все вызовы `glab api`, возвращающие списки, постраничны (по умолчанию 20 на страницу). Всегда передавай `--paginate`, чтобы получить все страницы: `glab api --hostname <YOUR_GITLAB_HOSTNAME> --paginate "<endpoint>"`.
- Для `glab mr list` предпочитай явные флаги состояния вместо `--state`: `--closed` (`-c`) для закрытых, `--merged` (`-M`) для слитых, `--all` (`-A`) для всех состояний. Без флага состояния по умолчанию возвращаются открытые MR.
