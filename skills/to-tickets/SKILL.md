# Задачи из плана

Разбей план, спецификацию или диалог на набор **задач**: вертикальных срезов-«трассирующих пуль», каждая из которых указывает задачи, её **блокирующие**.

Трекер задач и словарь меток для разбора должны был быть переданы тебе заранее. Если это не так, попроси пользователя выполнить `/setup-matt-pocock-skills`.

## Порядок работы

### 1. Собери контекст

Работай с тем, что уже есть в контексте диалога. Если пользователь передал ссылку (путь к спецификации, номер задачи или URL) как аргумент, получи её и прочитай полностью вместе с комментариями.

### 2. Изучи проект (необязательно)

Если ты ещё не изучали проект, сделай это, чтобы понять текущее состояние кода. В названиях и описаниях задач используй словарь предметного глоссария проекта и учитывай записи об архитектурных решениях в затрагиваемой области.

Ищи возможности подготовительно отрефакторить код, чтобы реализация стала проще. «Сначала сделай изменение лёгким, потом сделай лёгкое изменение».

### 3. Наметь вертикальные срезы

Разбей работу на задачи-«трассирующие пули».

<vertical-slice-rules>

- каждый срез прорезает узкий, но ПОЛНЫЙ путь через все слои (схема данных, API, интерфейс, тесты): вертикально, а НЕ горизонтально по одному слою
- завершённый срез можно показать или проверить отдельно
- каждый срез по размеру помещается в одно чистое окно контекста
- любой подготовительный рефакторинг делается первым

</vertical-slice-rules>

У каждой задачи есть **блокирующие связи**: другие задачи, которые должны завершиться до её начала. Задача без блокирующих может начинаться сразу.

**Широкий рефакторинг — исключение из вертикальных срезов.** **Широкий рефакторинг** — это одно механическое изменение (переименование столбца, смена типа общего символа), **радиус поражения** которого расходится по всему проекту: одна правка ломает тысячи мест вызова, и ни один вертикальный срез не сможет остаться зелёным. Не втискивай его в «трассирующую пулю»; выстрой его как **расширение и сжатие**. Сначала расширение: добавь новую форму рядом со старой, чтобы ничего не сломалось. Затем перенеси места вызова партиями, размер которых определяется радиусом поражения (по пакетам, по каталогам); каждая партия — отдельная задача, заблокированная задачей расширения, и CI остаётся зелёным от партии к партии, потому что старая форма ещё существует. Наконец сжатие: удали старую форму, когда не останется вызывающих, отдельной задачей, заблокированной всеми партиями переноса. Если даже партии не могут оставаться зелёными по отдельности, сохрани последовательность, но дай им общую ветку интеграции, которая блокирует итоговую задачу интеграции и проверки; зелёный результат обещан только там.

### 4. Сверьсь с пользователем

Покажи предложенное разбиение нумерованным списком. Для каждой задачи укажи:

- **Название**: короткое описательное имя
- **Блокируется**: какие другие задачи (если есть) должны завершиться раньше
- **Что даёт**: сквозное поведение, которое эта задача делает работающим

Спроси пользователя:

- подходит ли дробность? (слишком крупно или слишком мелко)
- верны ли блокирующие связи: зависит ли каждая задача только от тех, что действительно её сдерживают?
- не нужно ли какие-то задачи объединить или разделить дальше?

Повторяй, пока пользователь не одобрит разбиение.

### 5. Опубликуй задачи в настроенном трекере

Опубликуй одобренные задачи. **Как** именно — зависит от трекера, настроенного через `/setup-matt-pocock-skills`; сами задачи одинаковы, меняется только форма блокирующих связей:

- **Локальные файлы** → пиши по одному файлу на задачу в `.scratch/<название-возможности>/issues/<NN>-<краткое-имя>.md`, нумеруя с `01` в порядке зависимостей (сначала блокирующие). В поле «Блокируется» каждого файла перечисляй номера и названия, от которых задача зависит. Используй шаблон файла задачи ниже: одна задача — один файл, никогда не один общий файл.
- **Настоящий трекер задач (GitHub, Linear и подобные)** → публикуй по одной задаче на каждую позицию в порядке зависимостей (сначала блокирующие), чтобы блокирующие связи ссылались на реальные идентификаторы. Используй родную связь блокировки, если платформа её поддерживает; иначе укажи в «Блокируется» блокирующие задачи. Если источником была существующая задача, сделай каждую новую задачу её подзадачей (операция из документации трекера). Ставь метку разбора `ready-for-agent`, если не сказано иное: задачи по построению готовы к передаче агенту.

Работай по **фронту**: бери любую задачу, все блокирующие которой выполнены. Для чисто линейной цепочки это сверху вниз.

НЕ закрывай и не изменяй родительскую задачу.

Исключение: если прототип дал фрагмент, который точнее прозы фиксирует решение (машина состояний, редуктор, схема, форма типа), вставь его и коротко укажи, что он из прототипа. Оставь только части, важные для решения, а не рабочий пример целиком.
