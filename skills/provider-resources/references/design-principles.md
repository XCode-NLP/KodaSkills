# Принципы проектирования ресурсов и источников данных

Сжатое изложение [принципов проектирования провайдеров](https://developer.hashicorp.com/terraform/plugin/best-practices/hashicorp-provider-design-principles)
HashiCorp и соглашений крупных рабочих провайдеров (прежде всего
terraform-provider-aws). Применяй это *до* написания кода — большинство
болезненных ошибок провайдеров являются ошибками моделирования.

## Провайдер оборачивает одну поверхность API

Провайдер абстрагирует API или SDK одной платформы в жизненный цикл Terraform. Держи
вне провайдера:

- сырые HTTP- или протокольные клиенты, привинченные к провайдеру на SDK;
- функциональность, требующую дополнительных бинарников или агентов на хосте, где
  запускается Terraform;
- источники данных, единственная задача которых — экспортировать собственные
  учётные данные провайдера в другую конфигурацию (риск утечки учётных данных).

## Ресурсы: наименьший полезный строительный блок

**Эвристика: если API даёт для сущности create, read, (update) и delete, эта
сущность — ресурс.** Предпочитай много небольших ресурсов одному большому —
практики гораздо проще комбинируют небольшие блоки, чем борются с
мегаресурсом с переплетённым поведением атрибутов.

**Один ресурс — один API.** Ресурс должен вызывать API одного сервиса.
Кросс-сервисные ресурсы выглядят удобно, но:

- заставляют пользователей выдавать права на сервисы, о которых они могут не знать;
- разбрасывают аудиторские следы по разным сервисам;
- ломают настройку эндпоинтов и разделов по сервисам;
- молча ломают пользователей одного сервиса, когда меняется другой.

Если два сервиса должны работать вместе, смоделируй каждую сторону как свой ресурс
и дай конфигурации их соединить.

## Моделирование связей и жизненного цикла

| Концепт API | Как моделировать |
|---|---|
| Прикреплённый документ политики или правила | Отдельный ресурс, ссылающийся на родителя, а не атрибут-блоб у родителя |
| Привязка «один ко многим» (например, участник группы) | Отдельный ресурс «привязки» или «членства» |
| Состояние запущено/остановлено/включено/выключено | Атрибут *внутри* ресурса — отдельный ресурс «состояния питания» конфликтует с жизненным циклом родителя |
| Долгая задача, работа или операция, которые открывает API | Отдельный ресурс, представляющий задачу; Create запускает её, Read опрашивает |
| Приглашения, рукопожатия, согласования | Ресурс на принимающей стороне: Create = принять, Read = статус, Delete = отклонить или выйти |
| Версионируемый артефакт (версия функции, версия шаблона) | Обычно отдельный ресурс `<thing>_version`, чтобы версии можно было закреплять и менять независимо |

Когда у одного объекта API есть два защитимых способа моделирования (один ресурс с
вложенными атрибутами против родителя и дочерних ресурсов), предпочитай тот, чья
семантика *обновления* совпадает с API: если дочерние элементы можно добавлять и удалять
на сервере независимо, отдельные ресурсы избавят от классической проблемы диффа
«замена всего списка» — но никогда не поставляй оба подхода для
одной коллекции без предупреждений о конфликте в обоих.

## Источники данных

Источники данных — представления только для чтения. Они не должны создавать, изменять или удалять
что-либо, никогда: источник данных с побочными эффектами ломает обещание
`terraform plan` быть безопасным для запуска.

**Единичные источники данных** (`examplecloud_widget`) получают ровно один объект:

- ноль совпадений → ошибка («ни один Widget не совпал; измени фильтры»);
- больше одного совпадения → ошибка («совпало несколько Widget; добавляй фильтры, пока
  не совпадёт ровно один»).

Возврат произвольного элемента вместо ошибки скрывает реальные проблемы окружения
и даёт недетерминированные планы.

**Множественные источники данных** (`examplecloud_widgets`) получают коллекцию:

- возвращают ноль или больше как атрибут списка или множества;
- ноль совпадений — *валидный, пустой* результат, а не ошибка;
- называй их существительным во множественном числе; держи фильтры согласованными с
  единичной формой.

**Поставляй оба для большинства ресурсов.** Пользователям нужна единичная форма для точечных
запросов («дай мне этот widget по имени») и множественная для перечисления
(«дай мне все widget, подходящие под эти фильтры») — разным конфигурациям
нужны разные формы одних данных, и добавление недостающей позже — частая
просьба о возможности. Пропускай одну, только если API действительно не может
её поддержать.

## Именование

- Тип ресурса: `<provider>_<service?>_<noun>`, всё в нижнем регистре snake_case,
  существительное выводится из собственных имён CRUD-операций API (`CreateWidget` →
  `_widget`), чтобы пользователи могли сопоставлять документацию и API.
- Go: фабричные функции `NewWidgetResource`, правильные аббревиатуры в
  MixedCaps (`VPCEndpoint`, а не `VpcEndpoint`).
- Имена атрибутов: переводы имён полей API в snake_case; не
  изобретай новый словарь, который документация API не объяснит.

## Когда *не* добавлять ресурс

- «Ресурс» на самом деле RPC без постоянного объекта за ним — лучше подойдёт
  **действие** провайдера (см. навык `provider-actions`, если доступен).
- Объект в API только для чтения → источник данных.
- Объект — единичная настройка уровня аккаунта, которую нельзя создать или
  уничтожить → ресурс с Create = принять или настроить и Delete = сбросить к
  значениям по умолчанию, с документацией об этом; либо опусти его.
