# Современные правила Docker и BuildKit

Используй этот навык при создании, правке, проверке и модернизации любых файлов сборки и запуска: `Dockerfile`, `.dockerignore`, `docker-bake.hcl` и `compose.yaml`. Держись выраженной позиции и применяй эти значения по умолчанию проактивно, если только в репозитории уже нет явных конфликтующих соглашений или пользователь прямо не попросил другого компромисса.

Эти правила предполагают, что сборщик — **BuildKit** (значение по умолчанию в современном Docker Engine и в `docker buildx`). Именно это допущение позволяет использовать все современные возможности фронтенда ниже без оглядки на устаревшие сборщики.

## Стиль работы

1. Осмотри репозиторий до того, как писать. Определи язык и рантайм, менеджер пакетов, файлы блокировки, директорию результата сборки и существующие файлы Docker, чтобы результат соответствовал реальности, а не общему шаблону.
2. Предпочитай минимальное правильное изменение, но не сохраняй устаревшие приёмы (`version:` в compose, секреты, впечённые в слои, `apt-get` без кэш-монтирований), если ты и так правишь этот файл.
3. Никогда не выдумывай теги базовых образов, имена пакетов, порты или команды сборки как факты. Если репозиторий не раскрывает значение, используй явно помеченный заполнитель и скажи об этом. Теги образов особенно «плывут» — когда не уверен, что тег существует, попроси пользователя сверить его с каталогом реестра, а не утверждай.
4. Выполни чек-лист сдачи ниже, чтобы пользователь мог поддерживать каждое изменение.

## Структура Dockerfile

Dockerfile проще поддерживать, когда то, что меняют чаще всего — версии и конфигурация — лежит сверху в предсказуемых местах, а логика сборки читается сверху вниз. Соблюдай такой порядок:

```dockerfile
# syntax=docker/dockerfile:1          # 1. директива фронтенда — ОБЯЗАТЕЛЬНО первой строкой
ARG NODE_VERSION=22                   # 2. глобальные ARG версий — одно место для подъёма баз
ARG ALPINE_VERSION=3.22

FROM node:${NODE_VERSION}-alpine${ALPINE_VERSION} AS deps   # 3. все стадии FROM, у каждой имя через AS
FROM deps AS build
FROM cgr.dev/chainguard/node:latest AS runtime
# ... далее тела стадий, в порядке сборки ...
```

### 1. Директива фронтенда — первой строкой

Начинай каждый Dockerfile с:

```dockerfile
# syntax=docker/dockerfile:1
```

Это подтягивает при сборке последний стабильный фронтенд Dockerfile **линии 1.x** с Docker Hub, что отвязывает возможности Dockerfile от версии движка — даже старый Docker Engine тогда понимает новейший синтаксис. Закрепление на `:1` (не `:1.0` и не полную версию) намеренное: линия v1 гарантирует отсутствие ломающих изменений, поэтому новые возможности и исправления приходят бесплатно. Жёстко закрепляй минорную версию (например, `:1.7`), только когда пользователю нужна побайтовая воспроизводимость самого фронтенда.

Директива должна быть **первой строкой** — до комментариев, до `ARG`. Если она не первая, BuildKit её игнорирует и молча откатывается на встроенный фронтенд.

### 2. Централизуй версии в глобальных ARG

Объявляй версии базовых образов как `ARG` в глобальной области (до первого `FROM`), чтобы все версии жили одним блоком сверху:

```dockerfile
ARG NODE_VERSION=22
ARG ALPINE_VERSION=3.22
```

Глобальный `ARG` виден в строках `FROM`. Чтобы использовать его ещё и _внутри_ стадии (например, в `RUN`), переобъяви голый `ARG NODE_VERSION` (без значения по умолчанию) внутри этой стадии — глобальные аргументы не переходят в тела стадий автоматически. Выигрыш: подъём версии — правка одной строки сверху, а любое значение можно переопределить при сборке через `--build-arg NODE_VERSION=20`, не трогая файл.

### 3. Все стадии FROM сверху, у каждой имя через AS

Перечисли `FROM` каждой стадии сборки ближе к началу файла с явным `AS <имя>`, до длинных тел стадий. Собранные вместе строки `FROM` делают граф образа читаемым с одного взгляда и держат все ссылки на базовые образы по соседству, что сочетается с ARG версий выше. Именованные стадии также дают стабильные цели для `COPY --from=<имя>` и позволяют собрать одну стадию через `--target <имя>`.

### 4. ENV ближе к началу своей стадии

Собирай объявления `ENV` стадии вместе ближе к её началу, а не разбрасывай между `RUN`. Переменные окружения — первая конфигурация, к которой тянутся люди; группировка делает их находимыми и сохраняет предсказуемый сброс кэша (изменение `ENV` инвалидирует всё ниже).

### 5. Используй возможности фронтенда BuildKit

Поскольку BuildKit предполагается, предпочитай их устаревшим аналогам — они быстрее, безопаснее или и то и другое:

```dockerfile
# Кэш-монтирования: сохраняют кэши менеджера пакетов между сборками (не раздувают слои)
RUN --mount=type=cache,target=/root/.npm npm ci

# Монтирования секретов: секреты доступны во время RUN, но никогда не пишутся в слой
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci

# Связывающие монтирования: читают контекст или другую стадию во время RUN без COPY
RUN --mount=type=bind,source=package.json,target=package.json npm ci

# COPY --link: слой не зависит от цепочки родителей → лучше переиспользование кэша
COPY --link ./dist /app/dist

# Heredoc: многострочный RUN без обратных слэшей в конце
RUN <<EOF
set -eux
apt-get update
apt-get install -y --no-install-recommends curl
rm -rf /var/lib/apt/lists/*
EOF

# ADD --checksum: проверка целостности удалённого артефакта
ADD --checksum=sha256:24454f8...d68d https://example.com/app.tar.gz /opt/
```

## Базовые образы: усиленные по умолчанию

По умолчанию бери минимальные усиленные базовые образы. В них гораздо меньше пакетов, а значит меньше поверхность атаки, меньше CVE для патчей и меньше сами образы. К полноценной базе общего назначения (Debian, Ubuntu, официальный `alpine`) прибегай, только когда приложению действительно нужен лишний инструментарий в рантайме и усиленный вариант не подходит, — и объясняй почему.

Два бесплатных рекомендуемых источника:

- **Chainguard Images** — `cgr.dev/chainguard/<name>`. Публичный каталог тянется **без аутентификации**, что делает его вариантом с наименьшим трением. У большинства образов два варианта:
  - `:latest-dev` — включает оболочку и менеджер пакетов `apk`. Используй в **стадиях сборки**, где нужно что-то устанавливать.
  - `:latest` (и `static`) — **distroless**: без оболочки и менеджера пакетов. Используй в **финальной стадии рантайма**.
- **Docker Hardened Images (DHI)** — `dhi.io/<name>`. Бесплатно, но для загрузки нужен однократный `docker login dhi.io` с аккаунтом Docker. Теги выглядят как `dhi.io/python:3.13` или `dhi.io/python:3.12-alpine3.22`, а варианты `-dev` добавляют оболочку и менеджер пакетов для стадий сборки. Предпочитай DHI, когда пользователь уже в экосистеме Docker или хочет подписанные метаданные цепочки поставок SBOM/VEX от Docker.

Многоэтапный приём, который делает усиленные образы практичными: делай грязную работу (компиляторы, установку пакетов) в стадии сборки `-dev`, затем копируй через `COPY --from` только собранные артефакты в distroless-финал, где нет ни оболочки, ни менеджера пакетов, которые можно эксплуатировать.

```dockerfile
# syntax=docker/dockerfile:1
ARG GO_VERSION=1.24

FROM cgr.dev/chainguard/go:latest-dev AS build
FROM cgr.dev/chainguard/static:latest AS runtime

FROM build AS compile
WORKDIR /src
COPY . .
RUN --mount=type=cache,target=/root/.cache/go-build \
    --mount=type=cache,target=/go/pkg/mod \
    CGO_ENABLED=0 go build -o /app ./cmd

FROM runtime
COPY --from=compile /app /app
ENTRYPOINT ["/app"]
```

У distroless-финалов нет оболочки, поэтому `ENTRYPOINT` и `CMD` должны быть в exec-форме (`["/app"]`, а не `/app`), а `RUN`, `apt` и `apk` там не работают — в этом и смысл. Поскольку точные теги различаются от образа к образу и меняются со временем, считай теги выше формой, а не догмой; когда это важно, попроси пользователя сверить их с каталогом.

## Закрепляй каждый внешний образ по дайджесту

Закрепляй каждую ссылку на внешний образ — и строки `FROM`, и `COPY --from=<образ>`, которые тянут образ из реестра, — на **теге _и_ дайджесте**. Тег вроде `node:24` или `:latest` изменяем: реестр может в любой момент перенаправить его на новое содержимое, поэтому две сборки «одного» Dockerfile могут дать разные образы. Дайджест `@sha256:...` — неизменяемая адресация по содержимому, поэтому он делает сборку воспроизводимой и закрывает дыру в цепочке поставок (ты получаешь ровно те байты, которые проверил, а не то, что запушили после). Оставляй человекочитаемый тег рядом с дайджестом, чтобы читатель видел, _что_ это за образ:

```dockerfile
FROM node:24.11.1@sha256:9a2ed90cd91b1f3412affe080b62e69b057ba8661d9844e143a6bbd76a23260f
```

Чтобы получить дайджест, предпочитай `regctl`, если он установлен: он опрашивает реестр, не вытягивая образ целиком:

```bash
regctl manifest head node:24.11.1     # печатает дайджест текущего тега
```

Если `regctl` недоступен, используй `docker buildx imagetools inspect <image>:<tag>` (тоже без полной загрузки) либо вытяни образ и прочитай `docker inspect --format '{{index .RepoDigests 0}}' <image>:<tag>`. Не выдумывай дайджест: если не можешь получить настоящий, оставь явно помеченный заполнитель `@sha256:<PIN-ME>` и скажи пользователю точную команду, чтобы его подставить.

Это сочетается с централизованными ARG версий: держи тег в ARG для читаемости, а дайджест — в соседнем ARG, чтобы вся ссылка по-прежнему жила в одном месте сверху:

```dockerfile
ARG NODE_VERSION=24.11.1
ARG NODE_DIGEST=sha256:9a2ed90cd91b1f3412affe080b62e69b057ba8661d9844e143a6bbd76a23260f
FROM node:${NODE_VERSION}@${NODE_DIGEST} AS build
```

Два уточнения, чтобы это не вышло боком:

- Правило относится только к **URI внешних образов**. `COPY --from=build`, ссылающийся на _именованную внутреннюю стадию_, дайджеста не требует: он разрешается внутри сборки, а не тянется из реестра.
- Закрепление по дайджесту замораживает образ, в этом и смысл, но это также значит, что ты перестаёшь получать вышестоящие патчи безопасности, пока закрепление не обновят. Скажи пользователю, чтобы автоматизация (поддержка Docker в Dependabot или Renovate) поднимала эти дайджесты по расписанию — так же, как обновляют любую зависимость, — а не правил хэши вручную и тем более не возвращался к голым тегам, чтобы «оставаться свежим».

## Всегда создавай .dockerignore

У каждого контекста сборки должен быть `.dockerignore`. Он уменьшает то, что отправляется сборщику (быстрее сборка, лучше кэш), и — что важнее — это реальный механизм безопасности: весь контекст отправляется демону, поэтому исключение `.git`, `.env` и ключей не даёт секретам и истории утечь в образы.

Строй его, начиная с `.gitignore` репозитория (если он есть, скопируй его записи, чтобы уже игнорируемый мусор вроде `node_modules`, результатов сборки и `dist` тоже исключался), затем добавь записи, специфичные для Docker, которых в `.gitignore` не будет:

```gitignore
# --- скопировано из .gitignore ---
# (вставь сюда содержимое .gitignore проекта)

# --- добавления для Docker ---
.git
.gitignore
.dockerignore
Dockerfile*
compose*.yaml
docker-compose*.yml
docker-bake.hcl

# secrets & local env
.env
.env.*
*.pem
secrets/

# CI / docs / editor / OS cruft
.github/
README.md
.vscode/
.idea/
.DS_Store
```

`.git` — главное добавление: он часто огромен и несёт полную историю (включая когда-либо закоммиченные секреты), а внутри образа почти никогда не нужен.

## Всегда добавляй файл Bake

Добавляй `docker-bake.hcl`, чтобы сборки описывались воспроизводимой конфигурацией под контролем версий, а не длинными «плывущими» командными строками `docker build`. Bake (`docker buildx bake`) читает его, чтобы собрать одну или много целей с согласованными тегами, платформами и аргументами, и именно его должен вызывать CI, чтобы локальные сборки и сборки в CI оставались одинаковыми.

```hcl
variable "TAG" {
  default = "latest"
}

group "default" {
  targets = ["app"]
}

target "app" {
  context    = "."
  dockerfile = "Dockerfile"
  tags       = ["myapp:${TAG}"]
  # platforms = ["linux/amd64", "linux/arm64"]   # раскомментируй для мультиархитектуры
}
```

Собирай через `docker buildx bake` (группа `default`) или `docker buildx bake app`. Переопределяй переменные в рантайме (`TAG=v2 docker buildx bake`) или для конкретной цели (`--set app.platforms=linux/arm64`). Используй `inherits`, чтобы делить настройки базовой цели, и `matrix`, чтобы размножить одну цель в варианты. Учти: `docker buildx bake` без `-f` находит `compose.yaml` _раньше_, чем `docker-bake.hcl`, и превращает блоки `build:` сервисов в цели, поэтому если в репозитории есть оба файла, укажи CI нужный файл через `-f docker-bake.hcl`.

## Compose для локальной разработки

Для первой настройки без файла Compose заверши запрошенные файлы сборки и предложи добавить `compose.yaml` в финальном ответе. Оставляй создание Compose на утверждение, чтобы пользователь управлял объёмом работ по локальной разработке. Когда пользователь недоступен, включи предложение для его следующего ответа. Если файл Compose уже есть, модернизируй его на месте.

Соглашения:

- **Называй файл `compose.yaml`** (каноническое имя по спецификации Compose), а не `docker-compose.yml`.
- **Никакого ключа `version:` верхнего уровня.** В Compose V2 он устарел и теперь выдаёт предупреждение — удаляй его из любого файла, который правишь.
- **Предпочитай синхронизацию файлов связывающим монтированиям для исходного кода.** Классическое связывающее монтирование (`./src:/app/src`) привязывает пути контейнера к раскладке хоста и может быть медленным или с проблемами прав. Современный механизм `develop.watch` вместо этого _синхронизирует_ изменённые файлы в контейнер: это быстрее, кроссплатформенно и позволяет выбрать, что делать при изменении каждого пути.

```yaml
services:
  web:
    build: .
    ports:
      - "3000:3000"
    develop:
      watch:
        # sync: отправляет живые изменения исходников в работающий контейнер (горячая перезагрузка)
        - action: sync
          path: ./src
          target: /app/src
          ignore:
            - node_modules/
        # rebuild: манифестам зависимостей и компилируемым языкам нужен свежий образ
        - action: rebuild
          path: package.json
        # sync+restart: конфигурация, которую процесс читает только при старте
        - action: sync+restart
          path: ./config.yml
          target: /app/config.yml
```

Запускай через `docker compose watch`. Выбирай действие по тому, что требует изменение: `sync` для исходников с горячей перезагрузкой, `rebuild` для файлов блокировки и компилируемого кода, `sync+restart` для конфигурации, читаемой только при старте.

## Когда заканчиваешь

Выполни эти проверки в финальном ответе пользователю, чтобы он мог поддерживать файлы, не открывая другой документ:

- Дай каждому применённому значению по умолчанию или модернизации свою строку `изменение — причина`. Покрой фронтенд, базовый образ, закрепление по дайджесту, кэш-монтирования, пользователя рантайма, `.dockerignore`, Bake и каждое изменение Compose, когда они использованы. Причины объясняют выгоду; один список настроек неполон.
- Включи точные команды сборки и запуска, результаты проверок и неразрешённые заполнители, чтобы пользователь мог воспроизвести работу.
- Для первой настройки включи описанное выше предложение про Compose, чтобы пользователь мог утвердить следующий шаг.
