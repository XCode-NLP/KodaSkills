# Производительность WordPress (только бэкенд)

## Когда использовать

Используй этот навык, когда:

- сайт, страница или эндпоинт WordPress работает медленно (TTFB лицевой части, админка, REST,
  WP-Cron);
- нужен план профилирования и рекомендации по инструментам (WP-CLI profile и doctor, Query
  Monitor, Xdebug и XHProf, APM);
- ты оптимизируешь запросы к базе, автозагружаемые опции, объектное кэширование, задачи cron или
  удалённые вызовы HTTP.

Навык исходит из того, что агент не может использовать интерфейс браузера. Предпочитай WP-CLI,
журналы и HTTP-запросы.

## Что нужно на входе

- Окружение и безопасность: разработка, стенд или рабочее окружение; ограничения (без записи,
  без установки плагинов).
- Как обращаться к установке:
  - корень WP `--path=<path>`;
  - (мультисайт и выбор сайта) `--url=<url>`.
- Симптом и область проблемы:
  - какой URL, маршрут REST или экран админки;
  - когда это происходит (всегда или периодически; у вошедшего пользователя или у анонимного).

## Порядок работы

### 0) Ограничения: сначала измерь, избегай рискованных операций

1. Подтверди, можно ли выполнять операции записи (установка плагинов, изменение конфигурации,
   сброс кэша).
2. Выбери воспроизводимую цель (URL или маршрут REST) и сними базовый уровень:
   - TTFB и время через `curl`, если возможно;
   - профилирование WP-CLI, если доступно.

Читай:
- `references/measurement.md`

### 1) Получи детерминированный отчёт о производительности бэкенда

Запусти:

- `node skills/wp-performance/scripts/perf_inspect.mjs --path=<path> [--url=<url>]`

Скрипт определяет:

- доступность WP-CLI и версию ядра;
- доступны ли `wp doctor` и `wp profile`;
- размер автозагружаемых опций (если возможно);
- наличие drop-in объектного кэша.

### 2) Быстрые улучшения: сначала диагностика, потом глубокое профилирование

Если есть доступ к WP-CLI, предпочитай:

- `wp doctor check --all` (добавь `--spotlight`, чтобы показать только предупреждения и ошибки);
- либо перечисли проверки для прогона, сфокусированного на производительности:
  `wp doctor check autoload-options-size constant-savequeries-falsy constant-wp-debug-falsy`.

`wp doctor check` без имён проверок и без `--all` завершается ошибкой, а не запускает что-либо.

Этот прогон ловит частые промахи в рабочем окружении (раздувание автозагрузки, `SAVEQUERIES` и
`WP_DEBUG`, число плагинов, обновления).

Читай:
- `references/wp-cli-doctor.md`

### 3) Глубокое профилирование (браузер не нужен)

Предпочтительный порядок:

1. `wp profile stage` — увидеть, куда уходит время (инициализация, основной запрос, шаблон).
2. `wp profile hook` (при необходимости с `--url=`) — найти медленные хуки и колбэки.
3. `wp profile eval` — для отдельных путей кода.

Читай:
- `references/wp-cli-profile.md`

### 4) Query Monitor (использование без интерфейса)

Query Monitor обычно работает через интерфейс, но его можно применять без него — через заголовки
ответов REST API и ответы с `_envelope`:

- пройди аутентификацию (nonce или пароль приложения);
- запрашивай ответы REST и смотри заголовки (`x-qm-*`) и/или свойство `qm` при использовании
  `?_envelope`.

Читай:
- `references/query-monitor-headless.md`

### 5) Исправляй по категории (выбери доминирующее узкое место)

По выводу профилирования выбери *одну* основную категорию узкого места:

- **Запросы к базе** → сократи число запросов, исправь шаблоны N+1, улучши индексы, избегай
  дорогих запросов к метаданным.
  - `references/database.md`
- **Автозагружаемые опции** → найди самые крупные автозагружаемые опции и перестань
  автозагружать большие блоки данных.
  - `references/autoload-options.md`
- **Промахи объектного кэша** → введи кэширование или исправь использование ключей и групп кэша;
  добавь постоянный объектный кэш там, где это уместно.
  - `references/object-cache.md`
- **Удалённые вызовы HTTP** → добавь таймауты, кэширование, пакетную обработку; не обращайся к
  удалённым API при каждом запросе.
  - `references/http-api.md`
- **Cron** → сократи пики задач, срок которых наступил, устрани дубликаты событий, вынеси тяжёлые
  задачи из путей обработки запросов.
  - `references/cron.md`

### 6) Проверь (повтори то же измерение)

- Повтори тот же `wp profile`, `wp doctor` или запрос REST.
- Подтверди разницу в производительности и то, что поведение не изменилось.
- Если исправление рискованное, по возможности выпускай его за флагом функции или поэтапно.

## Улучшения производительности в WordPress 6.9

Учитывай эти изменения 6.9 при профилировании.

**CSS по требованию для классических тем:**

- классические темы теперь получают загрузку CSS по требованию (раньше это было только у блочных
  тем);
- объём CSS сокращается на 30–65%: стили загружаются только для блоков, которые реально
  используются на странице;
- если профилируешь классическую тему, это уже должно помогать.

**Блочные темы без блокирующих отрисовку ресурсов:**

- блочные темы, которые не объявляют собственных таблиц стилей (например, Twenty Twenty-Three и
  Twenty Twenty-Four), теперь могут загружаться без CSS, блокирующего отрисовку;
- стили приходят из глобальных стилей (`theme.json`) и отдельных стилей блоков, всё встроено;
- это заметно улучшает LCP (Largest Contentful Paint).

**Порог встроенного CSS повышен:**

- порог, при котором небольшие таблицы стилей встраиваются, увеличен, что сокращает число
  блокирующих отрисовку ресурсов.

Ссылка: https://make.wordpress.org/core/2025/11/18/wordpress-6-9-frontend-performance-field-guide/

## Проверка

- Зафиксированы числа до и после (то же окружение, тот же URL или маршрут).
- `wp doctor check --all` чист или улучшился, когда применимо.
- В журналах нет новых ошибок и предупреждений PHP.
- Сброс кэша не требуется для корректности (сброс кэша — крайняя мера).

## Сбои и отладка

- «Ничего не изменилось» после правок кода:
  - измерялся другой URL или сайт (несовпадение `--url`), кэши скрыли результат или устарел кэш
    опкода.
- Данные профилирования шумные:
  - устрани фоновые задачи, тестируй на прогретом кэше, делай несколько замеров.
- `SAVEQUERIES` и Query Monitor дают накладные расходы:
  - не запускай их в рабочем окружении без явного разрешения.

## Когда эскалировать

- Если это рабочее окружение и нет явного разрешения, не:
  - устанавливай плагины, включай `SAVEQUERIES`, запускай нагрузочные тесты и сбрасывай кэши под
    трафиком.
- Если нужно профилирование на уровне системы (APM, расширения-профайлеры PHP), согласуй это с
  эксплуатацией или хостингом.
