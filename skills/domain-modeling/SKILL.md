# Предметное моделирование

Активно строй и уточняй предметную модель проекта по ходу проектирования. Это *деятельная* дисциплина: оспаривай термины, придумывай сценарии с крайними случаями, записывай глоссарий и решения в тот момент, когда они сложились. (Просто *читать* `GLOSSARY.md` ради словаря — это не этот навык: такую привычку может позволить себе любой навык. Этот навык нужен, когда ты меняешь модель, а не только пользуесь ею.)

## Структура файлов

В большинстве репозиториев один контекст:

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

Если в корне есть `GLOSSARY-MAP.md`, в репозитории несколько контекстов. Карта показывает, где живёт каждый из них:

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← решения для всей системы
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← решения конкретного контекста
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

Создавай файлы по мере необходимости: только когда есть что записать. Если `GLOSSARY.md` нет, создай его, когда определён первый термин. Если нет `docs/adr/`, создай каталог, когда понадобится первая запись.

## В ходе работы

### Сверяйся с глоссарием

Когда пользователь использует термин, противоречащий языку в `GLOSSARY.md`, сразу говоришь об этом. «В твоём глоссарии „отмена“ означает X, а ты, похоже, имеешь в виду Y. Что именно?»

### Уточняй размытые формулировки

Когда пользователь использует нечёткие или перегруженные термины, предложи точный канонический термин. «Ты говоришь „аккаунт“: имеешь в виду клиента или пользователя? Это разные вещи.»

### Обсуждай конкретные сценарии

Когда обсуждаются связи в предметной области, проверяй их на конкретных сценариях. Придумывай сценарии, которые задевают крайние случаи и заставляют пользователя точно определить границы между понятиями.

### Сверяйся с кодом

Когда пользователь объясняет, как что-то работает, проверь, согласен ли код. Нашёл противоречие — покажи его: «Твой код отменяет заказы целиком, а ты только что сказал, что возможна частичная отмена. Что верно?»

### Обновляй GLOSSARY.md сразу

Когда термин определён, обновляй `GLOSSARY.md` тут же. Не копи правки: фиксируй по мере появления. Используй формат из [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md).

`GLOSSARY.md` должен быть полностью свободен от деталей реализации. Не считай `GLOSSARY.md` спецификацией, черновиком или местом для решений по реализации. Это глоссарий и ничего больше.

### Предлагай записи об архитектурных решениях умеренно

Предлагай создать запись, только когда верны все три условия:

1. **Трудно отменить**: позже передумать будет дорого
2. **Неочевидно без контекста**: будущий читатель спросит «почему сделал именно так?»
3. **Результат настоящего компромисса**: был реальные варианты, и ты выбрал один по конкретным причинам

Если хотя бы одно условие не выполнено, запись не нужна. Используй формат из [ADR-FORMAT.md](./ADR-FORMAT.md).
