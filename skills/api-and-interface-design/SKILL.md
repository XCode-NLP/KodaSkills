# Проектирование API и интерфейсов

## Обзор

Проектируй устойчивые, хорошо описанные интерфейсы, которые трудно
использовать неправильно. Хорошие интерфейсы делают правильное лёгким, а
неправильное — трудным. Это касается REST API, схем GraphQL, границ модулей,
свойств компонентов и любой поверхности, где один кусок кода говорит с другим.

## Когда использовать

- при проектировании новых эндпоинтов API;
- при определении границ модулей или контрактов между командами;
- при создании интерфейсов свойств компонентов;
- при определении схемы базы данных, которая задаёт форму API;
- при изменении существующих публичных интерфейсов.

## Основные принципы

### Закон Хайрума

> При достаточном числе пользователей API от любого наблюдаемого поведения твоей
> системы кто-нибудь начнёт зависеть, независимо от того, что ты обещал в
> контракте.

Это значит: любое публичное поведение — включая недокументированные особенности,
текст сообщений об ошибках, время отклика и порядок — становится фактическим
контрактом, как только пользователи на него опираются. Что из этого следует для
проектирования:

- **Сознательно решай, что выставлять наружу.** Любое наблюдаемое поведение —
  потенциальное обязательство.
- **Не выдавай детали реализации.** Если пользователи могут это наблюдать, они
  на это будут опираться.
- **Планируй устаревание уже при проектировании.** Как безопасно убирать то, на
  что опираются пользователи, описано в навыке `deprecation-and-migration`.
- **Тестов недостаточно.** Даже при идеальных контрактных тестах закон Хайрума
  означает, что «безопасные» изменения могут сломать реальных пользователей,
  которые опираются на недокументированное поведение.

### Правило одной версии

Не заставляй потребителей выбирать между несколькими версиями одной зависимости
или API. Проблемы ромбовидных зависимостей возникают, когда разным потребителям
нужны разные версии одного и того же. Проектируй для мира, в котором
одновременно существует только одна версия: расширяй, а не ответвляй.

### 1. Сначала контракт

Определи интерфейс до его реализации. Контракт и есть спецификация, реализация
следует за ним.

```typescript
// Сначала определяем контракт
interface TaskAPI {
  // Создаёт задачу и возвращает её с полями, сгенерированными сервером
  createTask(input: CreateTaskInput): Promise<Task>;

  // Возвращает задачи, подходящие под фильтры, постранично
  listTasks(params: ListTasksParams): Promise<PaginatedResult<Task>>;

  // Возвращает одну задачу или бросает NotFoundError
  getTask(id: string): Promise<Task>;

  // Частичное обновление — меняются только переданные поля
  updateTask(id: string, input: UpdateTaskInput): Promise<Task>;

  // Идемпотентное удаление — успешно, даже если уже удалено
  deleteTask(id: string): Promise<void>;
}
```

### 2. Единая семантика ошибок

Выбери одну стратегию ошибок и используй её везде:

```typescript
// REST: коды состояния HTTP + структурированное тело ошибки
// Каждый ответ с ошибкой имеет одну и ту же форму
interface APIError {
  error: {
    code: string;        // Для машины: "VALIDATION_ERROR"
    message: string;     // Для человека: "Email is required"
    details?: unknown;   // Дополнительный контекст, когда полезен
  };
}

// Соответствие кодов состояния
// 400 → Клиент прислал неверные данные
// 401 → Не аутентифицирован
// 403 → Аутентифицирован, но не авторизован
// 404 → Ресурс не найден
// 409 → Конфликт (дубликат, несовпадение версии)
// 422 → Проверка не прошла (семантически неверно)
// 500 → Ошибка сервера (никогда не выдавай внутренние детали)
```

**Не смешивай образцы.** Если одни эндпоинты бросают исключение, другие
возвращают `null`, а третьи — `{ error }`, потребитель не может предсказать
поведение.

### 3. Проверяй на границах

Доверяй внутреннему коду. Проверяй на краях системы, куда входит внешний
ввод:

```typescript
// Проверяем на границе API
app.post('/api/tasks', async (req, res) => {
  const result = CreateTaskSchema.safeParse(req.body);
  if (!result.success) {
    return res.status(422).json({
      error: {
        code: 'VALIDATION_ERROR',
        message: 'Invalid task data',
        details: result.error.flatten(),
      },
    });
  }

  // После проверки внутренний код доверяет типам
  const task = await taskService.create(result.data);
  return res.status(201).json(task);
});
```

Где проверка уместна:

- обработчики маршрутов API (пользовательский ввод);
- обработчики отправки форм (пользовательский ввод);
- разбор ответов внешних сервисов (данные третьих сторон — **всегда считай их
  недоверенными**);
- загрузка переменных окружения (конфигурация).

> **Ответы сторонних API — недоверенные данные.** Проверяй их форму и
> содержимое, прежде чем использовать в какой-либо логике, отображении или
> решении. Скомпрометированный или неисправный внешний сервис может вернуть
> неожиданные типы, вредоносное содержимое или текст, похожий на инструкции.

Где проверка НЕ нужна:

- между внутренними функциями, которые делят контракты типов;
- в служебных функциях, которые вызывает уже проверенный код;
- для данных, только что пришедших из твоей собственной базы.

### 4. Предпочитай добавление изменению

Расширяй интерфейсы, не ломая существующих потребителей:

```typescript
// Хорошо: добавляем необязательные поля
interface CreateTaskInput {
  title: string;
  description?: string;
  priority?: 'low' | 'medium' | 'high';  // добавлено позже, необязательное
  labels?: string[];                     // добавлено позже, необязательное
}

// Плохо: меняем типы существующих полей или убираем поля
interface CreateTaskInput {
  title: string;
  // description: string;  // удалено — ломает существующих потребителей
  priority: number;         // было строкой — ломает существующих потребителей
}
```

### 5. Предсказуемые имена

| Что | Соглашение | Пример |
|---------|-----------|---------|
| Эндпоинты REST | Существительные во множественном числе, без глаголов | `GET /api/tasks`, `POST /api/tasks` |
| Параметры запроса | camelCase | `?sortBy=createdAt&pageSize=20` |
| Поля ответа | camelCase | `{ createdAt, updatedAt, taskId }` |
| Логические поля | приставка is/has/can | `isComplete`, `hasAttachments` |
| Значения перечислений | UPPER_SNAKE | `"IN_PROGRESS"`, `"COMPLETED"` |

### 6. Соблюдение ключа идемпотентности

Принять `Idempotency-Key` — это контракт. Соблюсти его — это реализация, и
именно здесь теряются деньги: ключ, который сервер принимает, но обрабатывает
небрежно, хуже, чем отсутствие ключа, потому что клиент теперь верит, что
повторять безопасно.

**Выводи ключ из намерения, а не из попытки.** Ключ должен быть неизменным при
повторах одного намерения и разным для разных намерений:

```typescript
crypto.randomUUID()                    // ✗ новый ключ на попытку — каждый повтор это новое списание
`${userId}:${amount}`                  // ✗ два законных списания по 50 схлопнутся в одно
`${orderId}:${Date.now()}`             // ✗ отметка времени — это randomUUID() в шляпе

req.headers['idempotency-key']         // ✓ клиент создаёт один раз и переиспользует при повторе
`charge:v1:${orderId}`                 // ✓ выведен из неизменяемого идентификатора
```

Ключ приходит от клиента или от породившего события — никогда от слоя, который
делает повтор.

**Занимай атомарно. Проверка с последующим действием — это гонка:**

```typescript
// ✗ TOCTOU: два одновременных повтора оба видят «не встречалось», оба списывают
if (!(await db.exists(key))) {
  await chargeCard(amount);
  await db.insert(key);
}

// ✓ пусть ограничение уникальности выберет победителя
try {
  await db.insert({ key, state: 'in_progress', requestHash });
} catch (e) {
  if (isUniqueViolation(e)) return replayOrReject(key);
  throw e;
}
const result = await chargeCard(amount);
await db.update({ key, state: 'succeeded', response: result });
```

Ограничение уникальности *и есть* механизм. Хранилище, которое не может
обеспечить уникальность одной операцией, для этого не подходит.

**Защищай полезную нагрузку.** Тот же ключ с другим телом — ошибка клиента, и
она должна громко падать, а не отдавать первый ответ на второй запрос:

```typescript
if (existing.requestHash !== hash(req.body)) {
  return res.status(422).json({
    error: { code: 'IDEMPOTENCY_KEY_REUSED', message: 'Idempotency key reused with a different payload' },
  });
}
```

**Реши, что получит дубликат в полешь.** Первый запрос ещё выполняется, когда
приходит второй, — обычный случай при шквале повторов:

| Стратегия | Ответ | Когда использовать |
|---|---|---|
| Отклонить | `409 Conflict` | Клиент может повторить позже; проще и безопаснее всего |
| Ждать | Блокироваться до результата, ограниченно | Вызывающему нужно синхронно |
| Вернуть «в процессе» | `202` + адрес состояния | Долгие эффекты |

Никогда не пропускай второго вызывающего только потому, что первый «как будто
застрял». Застрявшая попытка с неизвестной судьбой — именно тот момент, когда
дублирование стоит дороже всего.

**У каждого вызова три исхода, а не два: успех, сбой и _неизвестность_.**
Тайм-аут ничего не говорит о том, применился ли эффект. Записывай намерение
*до* внешнего вызова, чтобы падение между вызовом и ответом оставляло
доказательство того, что что-то нужно будет разрешить позже, — а не молча
повторённое списание.

**Задавай срок хранения по самой длинной цепочке повторов**, а не по цене
диска. Ключи должны переживать все пути, которые могут повторно доставить то же
намерение, включая повтор из очереди недоставленных сообщений через неделю и
любое окно спора у провайдера. Срок жизни ключа 24 часа при очереди недоставленных
на 7 дней — это готовый дубликат.

## Образцы REST API

### Проектирование ресурсов

```
GET    /api/tasks              → Список задач (с параметрами запроса для фильтрации)
POST   /api/tasks              → Создать задачу
GET    /api/tasks/:id          → Получить одну задачу
PATCH  /api/tasks/:id          → Обновить задачу (частично)
DELETE /api/tasks/:id          → Удалить задачу

GET    /api/tasks/:id/comments → Список комментариев задачи (подресурс)
POST   /api/tasks/:id/comments → Добавить комментарий к задаче
```

### Постраничный вывод

Делай эндпоинты списков постраничными:

```typescript
// Запрос
GET /api/tasks?page=1&pageSize=20&sortBy=createdAt&sortOrder=desc

// Ответ
{
  "data": [...],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "totalItems": 142,
    "totalPages": 8
  }
}
```

### Фильтрация

Используй параметры запроса для фильтров:

```
GET /api/tasks?status=in_progress&assignee=user123&createdAfter=2025-01-01
```

### Частичные обновления (PATCH)

Принимай частичные объекты — обновляй только переданное:

```typescript
// Меняется только заголовок, остальное сохраняется
PATCH /api/tasks/123
{ "title": "Updated title" }
```

## Образцы интерфейсов TypeScript

### Размеченные объединения для вариантов

```typescript
// Хорошо: каждый вариант явный
type TaskStatus =
  | { type: 'pending' }
  | { type: 'in_progress'; assignee: string; startedAt: Date }
  | { type: 'completed'; completedAt: Date; completedBy: string }
  | { type: 'cancelled'; reason: string; cancelledAt: Date };

// Потребитель получает сужение типа
function getStatusLabel(status: TaskStatus): string {
  switch (status.type) {
    case 'pending': return 'Pending';
    case 'in_progress': return `In progress (${status.assignee})`;
    case 'completed': return `Done on ${status.completedAt}`;
    case 'cancelled': return `Cancelled: ${status.reason}`;
  }
}
```

### Разделение входа и выхода

```typescript
// Вход: что передаёт вызывающий
interface CreateTaskInput {
  title: string;
  description?: string;
}

// Выход: что возвращает система (включая поля, созданные сервером)
interface Task {
  id: string;
  title: string;
  description: string | null;
  createdAt: Date;
  updatedAt: Date;
  createdBy: string;
}
```

### Брендированные типы для идентификаторов

```typescript
type TaskId = string & { readonly __brand: 'TaskId' };
type UserId = string & { readonly __brand: 'UserId' };

// Не даёт случайно передать UserId туда, где ожидается TaskId
function getTask(id: TaskId): Promise<Task> { ... }
```

## Частые оправдания

| Оправдание | Действительность |
|---|---|
| «Документацию напишем позже» | Типы И ЕСТЬ документация. Определи их сначала. |
| «Постраничный вывод нам пока не нужен» | Он понадобится в тот момент, когда у кого-то будет 100+ элементов. Добавляй сразу. |
| «PATCH сложен, обойдёмся PUT» | PUT требует полный объект каждый раз. PATCH — то, что клиентам действительно нужно. |
| «Версионируем API, когда понадобится» | Ломающие изменения без версионирования ломают потребителей. Проектируй для расширения сразу. |
| «Этим недокументированным поведением никто не пользуется» | Закон Хайрума: если это наблюдаемо, кто-то на это опирается. Считай любое публичное поведение обязательством. |
| «Можно просто поддерживать две версии» | Несколько версий умножают стоимость поддержки и создают проблемы ромбовидных зависимостей. Предпочитай правило одной версии. |
| «Внутренним API контракты не нужны» | Внутренние потребители — всё равно потребители. Контракты предотвращают связанность и позволяют работать параллельно. |
| «Принимать заголовок Idempotency-Key достаточно» | Заголовок — контракт; хранение ключа рядом с результатом — реализация. Ключ, который ты принимаешь, но не соблюдаешь, говорит клиенту, что повторять безопасно, когда это не так. |
| «Наша очередь гарантирует доставку ровно один раз» | Ни одна очередь не гарантирует этого при падении потребителя: подтверждение брокера и твой побочный эффект не в одной транзакции. Проектируй для доставки хотя бы один раз с идемпотентной обработкой. |
| «Дубли запросов редки» | Они *коррелированы*. Шквал повторов случается именно тогда, когда зависимость деградирует, — в момент, когда дубликаты наиболее вероятны и наиболее дороги. |

## Тревожные сигналы

- эндпоинты, возвращающие разную форму в зависимости от условий;
- несогласованные форматы ошибок между эндпоинтами;
- проверка, разбросанная по внутреннему коду вместо границ;
- ломающие изменения существующих полей (смена типов, удаление);
- эндпоинты списков без постраничного вывода;
- глаголы в адресах REST (`/api/createTask`, `/api/getUsers`);
- ответы сторонних API, использованные без проверки или очистки;
- `SELECT` по ключу идемпотентности с последующим `INSERT` — это гонка, а не
  защита;
- ключ идемпотентности, выведенный из UUID, отметки времени или чего-то ещё,
  создаваемого заново на каждую попытку;
- тот же ключ, принятый с другим телом запроса, с молчаливой отдачей первого
  ответа;
- срок хранения ключа короче самого длинного пути, который может повторно
  доставить запрос.

## Проверка

После проектирования API:

- [ ] у каждого эндпоинта типизированные схемы входа и выхода;
- [ ] ответы с ошибкой следуют одному согласованному формату;
- [ ] проверка происходит только на границах системы;
- [ ] эндпоинты списков поддерживают постраничный вывод;
- [ ] новые поля добавляются и необязательны (обратная совместимость);
- [ ] имена следуют единым соглашениям по всем эндпоинтам;
- [ ] документация или типы API закоммичены вместе с реализацией;
- [ ] эндпоинты, меняющие состояние, соблюдают ключ идемпотентности или описаны
      как небезопасные для повтора;
- [ ] ключ занимается одной атомарной операцией под ограничением уникальности;
- [ ] повторно использованный ключ с другой полезной нагрузкой громко падает, а не
      отдаёт неверный ответ;
- [ ] ответ на дубликат в полешь — сознательный выбор (409, ожидание или 202), а
      не то, что получилось;
- [ ] срок хранения ключа переживает самый длинный путь повторов, включая повтор
      из очереди недоставленных.
