# WordPress Playground

Это тонкая обёртка маршрутизации. Используй её, чтобы выбрать правильный процесс
Playground, а затем загружай только нужный справочник или навык.

## Порядок работы

1. Определи намерение пользователя: написание и проверка Blueprint, локальный запуск
   через CLI, работа только в браузере с сайтом и ссылками для публикации,
   Xdebug или зависший запуск CLI, смешанный запрос по Playground.
2. Перейди к нужному источнику ниже; загружай больше одного, только если в запросе
   несколько разных частей.
3. Для смешанных запросов передай работу с JSON Blueprint навыку `blueprint`, а затем
   вернись сюда за указаниями по среде выполнения, CLI, отладке и публикации.

- **JSON Blueprint, схема, шаги, ресурсы, наборы или проверка Blueprint**: используй
  навык `blueprint` напрямую. Не дублируй здесь подробности схемы Blueprint.
- **Локальный запуск через CLI**: читай `references/cli.md` — про сервер
  `@wp-playground/cli`, `run-blueprint`, `build-snapshot`, примонтированные пути,
  переключение версий и локальную проверку.
- **Xdebug или зависшие запуски CLI**: читай `references/debugging.md` — про Xdebug,
  журналы среды выполнения, флаги воркеров и зависшие запуски.
- **Работа с сайтом Playground только в браузере**: читай `references/website.md` —
  про Query API и настройку URL Blueprint, ссылки для публикации и ограничения
  браузера. Он направляет операции с существующим сайтом к отдельным справочникам по
  WebMCP, Playground MCP и Sites API; загружай только выбранный способ. Если
  пользователь не просит конкретный способ подключения, предпочитай доступные
  инструменты WebMCP для поддерживаемых операций в браузере.

## Что нужно на входе

- Предполагаемый процесс: написание Blueprint, локальный запуск CLI, сайт и ссылка для
  публикации, снимок или отладка.
- Путь к проекту или набору, если локальный код нужно примонтировать или упаковать.
- Желаемые версии WordPress и PHP, если важна совместимость.
- Предпочтение по порту, если нужен локальный сервер.
- Нужна ли публикация только через браузер или доступ к локальной файловой системе.

## Ограничения

- Экземпляры Playground одноразовые и работают на SQLite: никогда не направляй их на
  рабочие данные.
- Держи указания по JSON Blueprint в навыке `blueprint`, чтобы схема и примеры имели
  единственный источник истины.
- Для локальной работы через CLI перед запуском команд проверь Node.js 20.18+ и
  наличие `npm`/`npx`.
- Playground в браузере не читает пути локальной файловой системы: используй публичные
  URL, размещённые ZIP-наборы или JSON Blueprint прямо в ссылке.

## Проверка

- Содержимое Blueprint проверяй по опубликованной схеме и следуй проверке из навыка
  `blueprint`.
- При локальных запусках через CLI проверь примонтированный плагин или тему либо
  побочные эффекты Blueprint в экземпляре Playground.
- Для ссылок для публикации открой сгенерированный URL и убедись, что открывается
  ожидаемая страница и загружаются установленные ресурсы.

## Сбои

- **Работа с Blueprint попала сюда**: остановись и используй навык `blueprint` для
  ключей схемы, шагов, ресурсов, наборов, проверки и ревью Blueprint.
- **В браузерном сценарии нужна локальная файловая система**: используй
  `references/cli.md`; `playground.wordpress.net` не читает пути локальной файловой
  системы.
- **Нужна переносимая ссылка из локального запуска CLI**: используй
  `references/website.md`; URL локального сервера не годится как ссылка для публикации.
- **Отладка воспринимается как ссылка второго уровня**: читай
  `references/debugging.md` напрямую — про Xdebug, журналы, флаги воркеров и зависшие
  запуски CLI.

## Когда эскалировать

- Если задаче нужны расширения PHP, прямой доступ к базе, сохранность данных или
  инфраструктура, близкая к рабочей, и Playground этого дать не может, используй полный
  стек WordPress: wp-env, Docker или окружение, предоставленное проектом.
