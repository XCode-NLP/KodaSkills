# Завершение ветки разработки

## Обзор

**Главный принцип:** проверить тесты → определить окружение → показать варианты →
выполнить выбор → убрать за собой.

**Объяви в начале:** «Использую навык finishing-a-development-branch, чтобы
завершить эту работу.»

## Шаг 1: проверь тесты

Запусти полный набор тестов проекта (`npm test` / `cargo test` / `pytest` /
`go test ./...`).

**Если тесты падают**, сообщи о сбоях и остановись — меню идёт после зелёного
набора:

```
Тесты падают (<N> сбоев). Нужно исправить до завершения:

[Показать сбои]
```

**Если тесты проходят:** переходи к шагу 2.

## Шаг 2: определи окружение

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# Запомни сейчас, пока ты ещё внутри рабочей области: шаг 5 меняет каталог,
# а уборке (шаг 6) это значение нужно
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

Это определяет, какое меню показать и как работает уборка:

| Состояние | Меню | Уборка |
|-------|------|---------|
| `GIT_DIR == GIT_COMMON` (обычный репозиторий) | Стандартные 3 варианта | Убирать нечего |
| `GIT_DIR != GIT_COMMON`, именованная ветка | Стандартные 3 варианта | По происхождению (см. шаг 6) |
| `GIT_DIR != GIT_COMMON`, отделённый HEAD | Сокращённые 2 варианта (без слияния) | Управляется извне — оставить на месте |

## Шаг 3: определи базовую ветку

Базовая ветка — та, от которой ответвилась эта работа: обычно она названа в
плане, в разговоре или в upstream ветки. Если она неизвестна, спроси: «Эта
ветка ответвилась от `<твоя лучшая догадка>` — верно?» Подтверди до слияния:
слияние не в ту базу дорого отменять.

## Шаг 4: покажи варианты

**Обычный репозиторий и worktree с именованной веткой — покажи ровно эти 3
варианта:**

```
Реализация завершена. Что хочешь сделать?

1. Слить локально обратно в <base-branch>
2. Отправить и создать пул-реквест
3. Оставить ветку как есть (займусь позже)

Какой вариант?
```

**Отделённый HEAD — покажи ровно эти 2 варианта:**

```
Реализация завершена. Ты на отделённом HEAD (рабочая область под внешним управлением).

1. Отправить как новую ветку и создать пул-реквест
2. Оставить как есть (займусь позже)

Какой вариант?
```

Показывай меню ровно как написано — кратко, и каждый вариант из списка выше.
Отбрасывание работы происходит только в ответ на явную просьбу собеседника (см.
«Если собеседник просит отбросить работу» ниже). Дождись его ответа: решение о
встраивании принимает он.

## Шаг 5: выполни выбор

### Вариант 1: слить локально

```bash
# Корень основного репозитория, чтобы безопасно сменить каталог
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# Сначала слияние — убедись в успехе, прежде чем что-то удалять
git checkout <base-branch>
git pull
git merge <feature-branch>

# Проверь тесты на слитом результате
<test command>
```

Если тесты на слитом результате падают: остановись, оставь worktree и ветку
на месте и разбирайся — ничего не отправлено, поэтому слияние локальное и
отменяемое.

Когда слитый результат зелёный: убери worktree (шаг 6), затем удали ветку:

```bash
git branch -d <feature-branch>
```

### Вариант 2: отправить и создать пул-реквест

```bash
git push -u origin <feature-branch>
# Из отделённого HEAD назови новую ветку на сервере:
# git push origin HEAD:refs/heads/<new-branch>
```

Затем создай пул-реквест против `<base-branch>` средствами твоей системы
хостинга — её командной строкой, если она есть, или адресом создания, который
большинство систем печатают при отправке, — следуя шаблону и соглашениям
пул-реквестов проекта, если они есть, и сообщи адрес собеседнику.

Worktree оставь: собеседник дорабатывает там по замечаниям к пул-реквесту.

### Вариант 3: оставить как есть

Сообщи: «Оставляю ветку `<name>`. Worktree сохранён в `<path>`.»

### Если собеседник просит отбросить работу

Этот путь существует только как ответ на явную просьбу выбросить работу.
Сначала подтверди:

```
Это безвозвратно удалит:
- ветку <name>
- все коммиты: <commit-list>
- worktree в <path>

Введи 'discard' для подтверждения.
```

Дождись именно этого подтверждения. Когда оно придёт:

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

Затем убери worktree (шаг 6) и удали ветку принудительно:

```bash
git branch -D <feature-branch>
```

## Шаг 6: убери рабочую область

**Выполняется для варианта 1 и подтверждённого отбрасывания.** Варианты 2 и 3
всегда сохраняют worktree. Оба вызывающих уже перешли в корень основного
репозитория — удаление worktree должно выполняться снаружи worktree — и
используют значения `GIT_DIR`, `GIT_COMMON` и `WORKTREE_PATH`, запомненные на
шаге 2, до смены каталога.

**Если `GIT_DIR == GIT_COMMON`:** обычный репозиторий, worktree убирать не нужно.
Готово.

**Если `WORKTREE_PATH` внутри `.worktrees/` или `worktrees/`:** этот worktree
создал Superpowers — уборка наша:

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune  # Самовосстановление: чистит устаревшие регистрации
```

**Если удаление отклонено** (`contains modified or untracked files`): в worktree
есть файлы, которых нет больше нигде — незакоммиченные планы, заметки или
черновая работа. Никогда не применяй `--force` по своей инициативе. Покажи
собеседнику, чем рискуешь, и спроси:

```bash
git -C "$WORKTREE_PATH" status --porcelain -uall
```

```
Удаление worktree отклонено — эти файлы никогда не коммитились:

<file list>

1. Закоммитить их в <branch> перед уборкой
2. Перенести их в <main repo root>
3. Удалить их (безвозвратно)

Что выбираешь?
```

Выполни выбор, затем удали worktree.

**Иначе:** этой рабочей областью владеет среда — оставь её на месте. Если
платформа даёт инструмент выхода из рабочей области, используй его.

## Краткая справка

| Вариант | Слияние | Отправка | Worktree | Удаление ветки |
|--------|-------|------|---------------|----------------|
| 1. Слить локально | да | - | - | да |
| 2. Создать пул-реквест | - | да | да | - |
| 3. Оставить как есть | - | - | да | - |
| Отбросить (только по явной просьбе) | - | - | - | да (принудительно) |

## Частые оправдания

| Оправдание | Действительность |
|--------|---------|
| «Тесты проходил раньше в этой сессии» | Запусти набор на том дереве, которое собираесь встраивать. Зелёный прогон доказывает только то дерево, на котором шёл. |
| «Он явно хочет слияния» | Встраивание решает собеседник. Покажи меню и ждёшь. |
| «Похоже, он закончил с этой возможностью — предложу отбросить» | Меню полное в написанном виде. Отбрасывание происходит только когда собеседник прямо об этом просит. |
| «„Да, убери это“ считается подтверждением» | Удаление разрешает только набранное слово `discard`. |
| «Пул-реквест создан, worktree теперь мусор» | Замечания к пул-реквесту правятся в этом worktree. Он остаётся, пока работа не вольётся. |
| «Этот другой worktree выглядит заброшенным — уберу и его» | Убирай только worktree внутри `.worktrees/` или `worktrees/`. Всё остальное принадлежит среде. |
| «Удаление отклонено — `--force` просто докончит уборку» | Отказ означает, что файлы есть только в этом worktree. `--force` уничтожит их безвозвратно. Покажи собеседнику и спроси. |
| «Сбой на слитом результате, наверное, нестабильный тест» | Падающий слитый результат останавливает всё. Ветка и worktree остаются на месте, пока ты разбираесь. |
| «Базовая ветка очевидно `main`» | Подтверди точку ответвления или спроси. Слияние не в ту базу дорого отменять. |
| «Отправку отклонил — принудительная отправка это исправит» | Отклонённая отправка означает, что сервер ушёл вперёд. Разбирайся; принудительная отправка только по явной просьбе собеседника. |
