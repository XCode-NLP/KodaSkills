# Разработка GUI на Lazarus и Object Pascal

## Зачем нужен этот навык

Разработка GUI в Lazarus обычно идёт в IDE: ты перетаскиваешь `TButton` на форму мышью, и IDE
сама пишет текстовое представление формы (`.lfm`) и соответствующий класс Pascal (`.pas`),
синхронно и автоматически. В терминале или контексте агента нет ни мыши, ни визуального
дизайнера — каждый элемент приходится добавлять, **правя файлы `.lfm` и `.pas` вместе вручную**,
поддерживая их согласованность так же, как это делала бы IDE. Для этого навык и нужен: знать
точный текстовый формат, который произвела бы IDE, и держать два файла в ногу.

## Анатомия проекта Lazarus

| Файл | Роль |
|---|---|
| `project.lpr` | Главная программа (исходник Pascal). Инициализирует приложение и создаёт главную форму (или формы). Правится редко — только чтобы добавить новые формы и модули. |
| `project.lpi` | Настройки проекта в XML (целевые ОС и процессор, список модулей, пути поиска). Сама вики Lazarus отмечает, что этот файл «лучше всего создавать и править в IDE Lazarus», — считай его данными, которые расширяют, копируя существующие записи, а не чем-то, что перепроектируют. |
| `unitname.pas` | Обычно один на форму. Объявляет класс формы (`TForm1 = class(TForm)`), её поля-элементы и реализации обработчиков событий. |
| `unitname.lfm` | Текстовая форма того, что произвёл бы визуальный дизайнер: дерево блоков `object ... end`, описывающих каждый элемент формы и значения его свойств. Подключается в модуль через `{$R *.lfm}`. |

Форма на самом деле — **одна логическая единица, разделённая на два файла**: `.pas` для поведения,
`.lfm` для раскладки и свойств. И они всегда должны совпадать:

- Каждому блоку `object Name: TSomeControl ... end` в `.lfm` нужно соответствующее поле
  `Name: TSomeControl;` в объявлении класса в `.pas`.
- Каждому `OnClick = SomeHandler` (или `OnChange`, `OnCreate` и т. п.) в `.lfm` нужна
  соответствующая `procedure SomeHandler(Sender: TObject);`, объявленная в классе и реализованная
  в разделе `implementation`.
- Имена выглядят регистрозависимыми, но Pascal регистронезависим; всё равно повторяй регистр,
  уже использованный в файле, ради читаемости.

Прочитай оба файла, прежде чем править любой из них, — не восстанавливай текущее состояние формы
по памяти или только по одному из двух файлов.

## Создание нового GUI-проекта с нуля

CLI-эквивалента мастеру «New Project» из IDE нет, поэтому начинай с шаблона в
`assets/template/` (минимальное приложение с одной формой и одной кнопкой, которое уже собирается
без ошибок), а не с написания `.lpi` с нуля:

1. Скопируй `assets/template/` в папку целевого проекта.
2. Переименуй согласованно — смена имени проекта затрагивает несколько мест, и пропуск одного
   ломает сборку:
   - `project1.lpr` → `<projectname>.lpr`, и внутри него строку `program <ProjectName>;`;
   - `project1.lpi` → `<projectname>.lpi`, и внутри него каждую ссылку
     `<Filename Value="project1...">`;
   - оставь `unit1.pas` и `unit1.lfm` как есть для первой формы либо тоже переименуй (имя файла
     модуля должно совпадать со строкой `unit UnitName;` внутри него, а секция `uses` в `.lpr`
     и вызов `Application.CreateForm(TForm1, Form1)` должны ссылаться на правильные имена
     типа и переменной).
3. Сразу после переименования собери проект один раз (см. «Сборка» ниже), чтобы поймать
   несоответствия раньше, до добавления настоящего интерфейса.
4. Дальше добавляй элементы и формы по порядку работы ниже.

## Расширение существующего проекта

**Добавление элемента на форму** — две правки, всегда вместе:
1. В `.lfm` добавь блок `object ControlName: TControlClass ... end` внутрь родителя (формы либо
   панели, группы). Задай ему `Left`, `Top`, `Width`, `Height` (и `Height` для большинства
   элементов, даже если дизайнер обычно его задаёт), чтобы он разумно располагался относительно
   соседей, плюс важные свойства (`Caption`, `Text`, `Items.Strings` и т. п.).
2. В объявлении класса в `.pas` добавь `ControlName: TControlClass;` полем, в том же
   относительном порядке, в каком он идёт в `.lfm` (IDE держит их синхронно; для компиляции порядок
   не важен, но совпадение избавляет от путаных диффов).
3. Добавь модуль элемента в секцию `uses` файла `.pas`, если он вводит модуль, которого там ещё нет
   (какой элемент в каком модуле живёт — см. таблицу ниже).

**Подключение обработчика события:**
1. В блоке объекта в `.lfm` добавь `OnClick = ButtonNameClick` (или имя нужного события).
2. В объявлении класса в `.pas` добавь `procedure ButtonNameClick(Sender: TObject);`.
3. В разделе `implementation` напиши тело обработчика, например
   `procedure TForm1.ButtonNameClick(Sender: TObject); begin ... end;`.

**Добавление целой новой формы:**
1. Создай пару `.pas` и `.lfm`, тесно повторяя существующую форму проекта (скопируй её и урежь,
   а не пиши с пустого шаблона) — так соглашения вроде `{$mode objfpc}{$H+}` и секция `uses`
   останутся такими же, как в остальном проекте.
2. Добавь новый модуль в секцию `uses` главного `.lpr`.
3. Если форма должна создаваться автоматически при запуске, добавь
   `Application.CreateForm(TFormName, FormName);` в `.lpr` перед `Application.Run;`. Если она
   создаётся по требованию (например, диалог, открываемый кнопкой), этого не делай — просто
   создавай её через `TFormName.Create(...)` и `.ShowModal` там, где нужно, и не создавай
   автоматически.
4. Добавь для неё блок `<Unit>` в `.lpi`, копируя структуру записи `<Unit>` существующей формы
   (те же теги: `Filename`, `IsPartOfProject`, `ComponentName`, `HasResources`,
   `ResourceBaseClass`, `UnitName`) и обновляя значения.

## Частые элементы LCL

Самые используемые элементы и модуль, откуда они берутся:

| Элемент | Модуль | Типичное назначение |
|---|---|---|
| `TForm` | `Forms` | Окно или диалог |
| `TButton` | `StdCtrls` | Кнопка |
| `TLabel` | `StdCtrls` | Статический текст |
| `TEdit` | `StdCtrls` | Однострочный ввод |
| `TMemo` | `StdCtrls` | Многострочный текст |
| `TCheckBox` | `StdCtrls` | Логический переключатель |
| `TRadioButton` | `StdCtrls` | Выбор одного из вариантов |
| `TComboBox` | `StdCtrls` | Выпадающий список |
| `TListBox` | `StdCtrls` | Выбор из списка |
| `TPanel` | `ExtCtrls` | Контейнер для группировки |
| `TTimer` | `ExtCtrls` | Периодический вызов |
| `TOpenDialog` / `TSaveDialog` | `Dialogs` | Выбор файлов |
| `TStatusBar` | `ComCtrls` | Строка состояния |
| `TPageControl` / `TTabSheet` | `ComCtrls` | Страницы с вкладками |

Более полный справочник — в `references/lcl-components.md` (больше элементов, их частые свойства
и события, пара готовых фрагментов `.lfm` и `.pas`); читай его, когда работаешь с элементом не из
таблицы выше или не уверен, какие свойства ему обычно нужны.

## Сборка

Проверь окружение, прежде чем выбирать стратегию сборки: пользователь собирает под **Windows**, но
как к этому прийти, зависит от того, где запущен агент:

```bash
grep -qi microsoft /proc/version 2>/dev/null && echo "WSL" || echo "not-WSL"
```

- **Не WSL** (нативная оболочка Windows либо Linux или macOS с установленным Lazarus и
  кросс-компилятором под Windows) и `lazbuild` есть в PATH: собирай напрямую и всегда явно
  нацеливайся на Windows независимо от ОС хоста:
  ```bash
  lazbuild --build-all --os=win64 --cpu=x86_64 <project>.lpi
  ```
  (`--os` и `--cpu` переопределяют то, что записано в `.lpi`, поэтому цель в самом файле проекта
  не обязана быть идеально настроенной.) Читай вывод на ошибки — `lazbuild` печатает обычные
  ошибки компилятора FPC (`file.pas(line,col) Error: ...`), которые указывают прямо на сломанную
  строку.
- **WSL**: не пытайся собирать вообще. Сделай все правки файлов, объясни, что изменено, и скажи
  пользователю собрать самому через IDE Lazarus или терминал Windows. Не пробуй `lazbuild.exe`
  через `/mnt/c/...`, `wine` или кросс-компилятор Linux как обходной путь, если пользователь явно
  не попросил что-то из этого.

Если `lazbuild` вообще не найден (и это не WSL), скажи об этом прямо, а не угадывай путь
установки — спроси пользователя либо сначала проверь обычные места (`/usr/bin/lazbuild`,
`/usr/lib/lazarus/*/lazbuild`) через `which` или `find`.

## Частые ловушки

- **Отсутствие `{$mode objfpc}{$H+}`** в начале модуля даёт непонятные ошибки — модули Lazarus
  пишутся в режиме Object Pascal с длинными строками, а не со стандартными умолчаниями Pascal
  или Delphi.
- **`{$R *.lfm}`** должен быть в разделе `implementation` каждого модуля формы — именно он
  связывает значения свойств формы с скомпилированным бинарником. Легко потерять при копировании
  модуля.
- **Имя файла модуля должно совпадать с именем в `unit X;`** (без учёта регистра) — переименование
  одного без другого ломает сборку путаной ошибкой «can't find unit».
- **Строковые литералы используют удвоенную одинарную кавычку** для встроенной кавычки, например
  `Caption = 'Mustermann''s Shop'` — одиночная `'` ломает разбор `.lfm`.
- **Свойства-множества** (например, `Anchors`) используют синтаксис скобок:
  `Anchors = [akTop, akLeft, akRight]`.
- **Забыть добавить типы элементов нового модуля в секцию `uses`** файла `.pas` — например,
  добавление `TStatusBar` без `ComCtrls` в `uses` не скомпилируется.
- **Забыть запись `<Unit>` в `.lpi`** для новой формы — форма соберётся сама по себе нормально, но
  IDE (а иногда и `lazbuild`, в зависимости от настроек) не узнает, что она часть проекта.
- **Отсутствие файла `.res` в проекте, созданном с нуля.** IDE молча создаёт `project.res` (пустой
  файл ресурсов, подключаемый через `{$R *.res}` в `.lpr`) при первом сохранении нового проекта —
  чего никогда не происходит, когда проект собирают вручную вне IDE. Без него `lazbuild` и `fpc`
  падают с `Can't open resource file "...res"`. В поставляемом шаблоне уже есть рабочий пустой
  `project1.res`; если создаёшь проект не из шаблона, сгенерируй его так же:
  `touch empty.rc && fpcres -of res empty.rc -o project1.res` (`fpcres` требует хотя бы один
  входной файл, даже пустой).
