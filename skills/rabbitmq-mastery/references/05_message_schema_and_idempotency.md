# Контракт сообщения и идемпотентность потребителя

## 1. Стандартный контракт тела сообщения

У любого бизнес-сообщения есть стандартная внешняя обёртка с метаданными:

```json
{
  "trace_id": "01HZZ58YV6K0M2PQ3XYZ123456",
  "msg_id": "msg_order_created_100298",
  "event_type": "order.created",
  "timestamp": 1726646400,
  "payload": {
    "order_id": 100298,
    "user_id": 4567,
    "amount": 299.00
  }
}
```

---

## 2. Двухуровневая идемпотентность на потребителе

Повторная отправка по сети неизбежна, поэтому потребитель обязан быть абсолютно идемпотентным:

1. **Быстрое удаление дублей в Redis**:
   - перед обработкой выполни `SET "idemp:msg:" + msg_id 1 NX EX 86400`;
   - если запись не удалась, сообщение уже обрабатывается или обработано — сразу верни `basicAck` и отбрось дубль.
2. **Уникальное ограничение в базе**:
   - в локальной транзакции вставь запись в таблицу `consumed_messages (msg_id UNIQUE)`;
   - уникальный индекс базы обеспечивает идемпотентность на уровне транзакции.
