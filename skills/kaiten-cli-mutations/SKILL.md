# Записи в kaiten-cli

Этот навык — для карточек, чек-листов, связей, комментариев, участников, документов и других удалённых изменений.

## Язык общения

Перед каждой командой, включая поиск инструментов и чтение JSON, передавай `--locale ru` для разговора на русском или `--locale en` для английского и других языков. Меняй его, когда пользователь меняет язык. Явный флаг перекрывает `KAITEN_CLI_LOCALE`; без того и другого CLI использует английский. Добавляй флаг в примеры ниже. Имена команд, ключи JSON и данные пользователей не меняй.

## Обязательная последовательность

1. Найди точную команду один раз через `search-tools`, `describe` и `examples`.
2. Выбери профиль явно и проверь авторизацию без записи:

   ```bash
   kaiten --json --profile <name> --read-only profile probe
   ```

3. Выполняй исследовательские чтения с `--read-only`. Используй пакетные пути или снимки вместо циклов по сущностям.
4. Покажи точные цели, порядок, исключения и предпросмотр тела до запроса авторизации.
5. После авторизации сохрани частный возобновляемый манифест вне репозитория.
6. Выполняй небольшими ограниченными пакетами и фиксируй каждый результат до продолжения.
7. Перечитывай только те поля, которые должны были измениться.

## Возобновляемый манифест

Используй JSONL, одна операция на строку:

```json
{"operation_id":"stable-hash","canonical_name":"cards.update","target_key":"CARD-1","input":{"card_id":"CARD-1","title":"New title"},"status":"pending","attempts":0}
```

- Выводи `operation_id` из канонической команды, устойчивого ключа цели и нормализованного входа, чтобы одна и та же запланированная запись сохраняла один идентификатор.
- Храни файл с правами `0600` во временном или рабочем каталоге по выбору пользователя; никогда не коммить его.
- Не храни в нём токены, настройки профиля, сырые заголовки API и посторонние данные сущностей.
- Обновляй статус только после фиксации результата команды. Используй `pending`, `applied`, `verified` или `failed`.
- При возобновлении пропускай `verified`, перечитывай `applied` и повторяй `failed` только после классификации ошибки.

## Правила безопасности

- Обычный профиль может писать. Метаданные профиля `sandbox` не являются защитой.
- Никогда не убирай `--read-only`, пока предпросмотр не авторизован.
- Используй специфичный для команды пробный запуск, когда `describe` о нём сообщает; не выдумывай универсальный `--dry-run`.
- Не повторяй 401, 403, 404, 405 и 422 как временные сбои.
- Повторяй только ограниченные 429, 5xx, таймауты и сбои транспорта.
- После неоднозначного таймаута перечитай состояние до повтора создания или обновления.
- Предпочитай существующие пакетные команды. Не создавай внешний цикл по сущностям, когда есть массовая альтернатива.
- Не отмечай пункт чек-листа выполненным и не добавляй комментарии или смену статуса, если эти эффекты явно не авторизованы.

## Запись содержимого документов

Используй `documents update --content-mode yjs` как явно выбранный временный запасной вариант совместимости для установок без исправленного серверного API. Он сохраняет родословную Yjs и является кандидатом на удаление в будущем, но не устаревшим. Не выводи состояние выката из влитых серверных PR; следуй критериям вывода из эксплуатации в `docs/DOCUMENT_YJS_VERIFICATION.md`. Требуется уже установленный Node.js 20+; CLI сам его не ставит и не запускает npm. Передавай либо `data`, либо `text`, а метаданные обновляй отдельной командой. `--socket-url` используй только для известного отдельного источника Socket.IO.

Замена через API может продублировать весь документ, когда синхронизируется открытый редактор. Она блокируется, если явно не передан `--allow-unsafe-content-replace`. Не выбирай этот флаг автоматически, когда Yjs не сработал. После потерянного подтверждения обновление может быть уже сохранено: сообщи о неопределённости и разберись до следующей записи. Конфликт проверки Yjs может означать одновременные правки, а не повод их перезаписать. `--read-only` блокирует оба транспорта.

## Запись данных дополнений

Состояние дополнения не входит в сущность карточки. Привязки GitHub и состояние других дополнений по карточке живут в отдельной строке, доступной через `card-addon-data` и `github-addon`, и никогда не появляются в `cards get`. Считай их отдельным семейством изменений:

- Предпочитай `github-addon <pulls|branches|commits|issues> attach|detach` вместо сырого `card-addon-data set`. Типизированные команды читают текущий список, убирают дубли по собственной идентичности дополнения и перезаписывают только затрагиваемый ключ.
- Сырой `card-addon-data set` сливает по ключам верхнего уровня, поэтому частичное значение для ключа заменяет весь ключ. Отправка одной привязки перезапишет остальные. Сначала прочитай текущее значение и отправь полный список замены.
- Делай предпросмотр собственным `--dry-run` команды. Он выполняет чтение и сообщает результат без записи, но всё равно считается изменением, поэтому не работает под `--read-only`. Исследуй через `github-addon ... list` (обычное чтение), затем убери `--read-only` для пробного запуска и только потом авторизуй.
- `detach` отказывает селектору, который совпадает более чем с одной привязкой. Сузь его через `--owner` и `--repo`, а не через `--all`.
- В манифесте устойчивый ключ цели — это идентификатор карточки плюс ключ дополнения плюс идентичность привязки (идентификатор PR или issue, `owner/repo/branch`, хеш коммита), а не один идентификатор карточки.
- Общая строка не несёт версии или ETag, поэтому цикл чтения и записи гоняется с интерфейсом дополнения и параллельным запуском CLI, и запись проигравшего теряется. Держи чтение и запись в одной команде, не распараллеливай записи в одну карточку и перечитывай перед повтором.
- UUID дополнения выводится из пути монтирования только на локальном Kaiten; облачный тенант хранит случайный UUID. Команды заново определяют его по карточке, если выведенный UUID ничего не нашёл, но это стоит лишнего чтения на карточку, а каждая запись сбрасывает область кэша. Поэтому для повторяющихся записей прочитай UUID один раз из `space-addons list` и передавай `--addon-uid` явно.
- `github-addon ... list`, который не может подтвердить, какое дополнение прочитал, падает вместо возврата пустого списка. Считай такую ошибку требованием сначала определить UUID, а не признаком того, что к карточке ничего не привязано.
- Запись не выполняется, когда на одном пути монтирования доски карточки сидят несколько дополнений: команда не может их различить и не станет писать данные GitHub в строку чужого дополнения. Реши через `space-addons list` и явный `--addon-uid`.
- Запись не выполняется, когда сохранённый ключ не является простым списком объектов, потому что перезапись потеряет то, что CLI не умеет описать. Прочитай ключ через `card-addon-data get`, реши, каким должен быть правильный список, и почини его через `card-addon-data set` до повтора.

## Обратное чтение

Обратное чтение должно быть ограничено полями и целями:

```bash
kaiten --json --profile <name> cards batch-get \
  --card-ids '[101,102]' \
  --fields id,title,state \
  --compact
```

Для записи в дополнение перечитывай хранилище дополнения: чтение карточки ничего не покажет, потому что изменение не попадает в поля карточки.

```bash
kaiten --json --profile <name> github-addon pulls list \
  --card-id 101 \
  --fields number,htmlUrl,state
```

Сравни возвращённые поля с манифестом, отметь совпавшие операции как `verified` и сообщи количество запрошенных, применённых, проверенных и провалившихся.

## Граница продукта

В этой версии нет универсального исполнителя изменений. Используй манифест как контракт восстановления на стороне агента и предпочитай существующие пакетные команды. Предлагай новую пакетную команду только когда последующий аудит найдёт одно и то же семейство изменений минимум в трёх сеансах или минимум в 20 вызовах.
