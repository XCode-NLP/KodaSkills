# Основы Redis

Базовые рекомендации по моделированию данных в Redis. Охватывает выбор типа данных и соглашения об именах ключей — два решения, которые напрямую определяют память, производительность и сопровождаемость.

## Когда применять

- Кэширование объектов, сессий или состояния конкретного пользователя.
- Счётчики, таблицы лидеров, списки последних элементов, наборы уникальных участников.
- Проверка и переработка имён ключей Redis.
- Выбор между Redis Hash и JSON-документом для сущности.

## 1. Выбирай подходящую структуру данных

Бери тип, соответствующий *шаблону доступа*, а не просто форме данных.

| Сценарий | Рекомендуемый тип | Почему |
|---|---|---|
| Простые значения, счётчики | String | Атомарные `INCR` и `DECR`, `SET` и `GET` |
| Объект с независимо обновляемыми полями | Hash | Чтение и запись по полям, без перезаписи объекта целиком |
| Очередь, последние N элементов | List | O(1) на добавление и извлечение с концов |
| Уникальные элементы, проверка участия | Set | O(1) для `SADD`, `SISMEMBER`, `SCARD` |
| Рейтинги, диапазоны по счёту | Sorted Set | Порядок по счёту; `ZADD`, `ZRANGE`, `ZRANK` |
| Вложенные и иерархические данные | JSON | Обновление по пути, вложенные массивы, индексация RQE |
| Журнал событий, разветвлённая доставка | Stream | Постоянное хранение, группы консьюмеров |
| Поиск по сходству векторов | Vector Set | Нативное хранение векторов с HNSW |

**Частый антипаттерн:** заталкивание плоского объекта в сериализованную строку. Обновление одного поля означает чтение, разбор, изменение и полную перезапись. Используй Hash.

Полное обоснование и примеры на Python и Java — в [references/choose-data-structure.md](references/choose-data-structure.md).

## 2. Используй единые имена ключей

Применяй сегменты через двоеточие со стабильной иерархией:

```
{сущность}:{id}:{атрибут}
user:1001:profile
user:1001:settings
order:2024:items
session:abc123
article:987:likes
game:space-invaders:leaderboard
```

Практические правила:

- **Нижний регистр, разделитель — двоеточие.** Без пробелов, без смешанного регистра (`User_1001_Profile` — плохо).
- **Ключи короткие, но читаемые** — они живут в памяти и появляются в каждой команде.
- **Не используй полные URL и длинные строки как ключи.** Извлекай короткий идентификатор или бери хеш от URL.
- **Префикс для мультитенантности** (`tenant:42:user:7:cart`), чтобы сканирование и ACL точно нацеливались на арендатора.
- **Будь последовательным.** Выбери одно соглашение на сервис и применяй его ко всем ключам.

Примеры приведения к порядку и пограничные случаи — в [references/key-naming.md](references/key-naming.md).
