# Разборы цепочек учётных данных

Два рабочих дизайна на противоположных концах шкалы сложности. Читай их,
чтобы откалибровать, насколько большая цепочка реально нужна твоему провайдеру,
и затем реализуй по общему образцу из `credential-chain.md`.

## Разбор 1: провайдер AWS (`aws-sdk-go-base`)

Провайдер Terraform для AWS, провайдер AWSCC и бэкенд S3 находят учётные данные
через одну общую библиотеку
[`hashicorp/aws-sdk-go-base`](https://github.com/hashicorp/aws-sdk-go-base)
(MPL-2.0). Её точка входа `GetAwsConfig(ctx, *Config)` — самая проверенная
боем цепочка учётных данных в экосистеме Terraform.

### Порядок поиска

1. **Статические учётные данные прерывают поиск.** Если конфигурация провайдера несёт
   access key, secret key или token, библиотека сразу создаёт статический провайдер
   учётных данных и пропускает остальную цепочку. Явная конфигурация
   всегда побеждает, а частичные статические учётные данные падают громко, а не
   уходят дальше — осознанный выбор для секретов.
2. **Цепочка по умолчанию из SDK**, с профилем, закреплённым первым, когда
   конфигурация провайдера его задаёт. Затем AWS SDK ищет по порядку:
   переменные окружения → общие файлы учётных данных и конфигурации (включая SSO,
   web-identity и директивы assume-role для исходного профиля, объявленные *внутри*
   этих файлов) → учётные данные контейнера → метаданные инстанса EC2 (IMDS).
3. **Явное переопределение web identity.** Блок `assume_role_with_web_identity`
   заменяет то, что дала цепочка по умолчанию, провайдером web identity STS
   (с проверкой: обязательный ARN роли, ровно один источник токена).
4. **Обёртка assume-role.** `assume_role` — это *список*; каждая запись оборачивает
   ранее найденные учётные данные в провайдер assume-role STS, что позволяет
   *выстраивать* роли в цепочку (учётные данные → роль A → роль B). Каждый переход несёт своё
   имя сессии, внешний ID, политику, метки и длительность, обёрнутые в
   кэш учётных данных.

### Приёмы, которые стоит копировать независимо от масштаба

- **Немедленная проверка.** `Retrieve()` найденного провайдера вызывается
  во время настройки и — если не задан `skip_credentials_validation` —
  вызов `sts:GetCallerIdentity` доказывает, что учётные данные действительно работают.
  Сбои проявляются на этапе плана с ошибками в терминах конфигурации, а не
  в середине применения с ошибками в терминах API.
- **`NoValidCredentialSourcesError`.** Диагностика отсутствующих учётных данных
  встраивает URL документации, переданный вызывающим (`CallerDocumentationURL`), и
  нижележащую ошибку. Каждый нижестоящий продукт (провайдер, бэкенд) направляет
  пользователей к *своей* документации по аутентификации через один и тот же тип ошибки.
- **Предупреждения о конфликтах.** Если одновременно есть `profile` и статические
  учётные данные из переменных окружения, выдаётся предупреждение о «конфликте
  конфигурации» с объяснением, какой источник получил приоритет, — и если поиск
  затем падает, ошибка помечается этим контекстом.
- **Внедрение эндпоинтов для самой цепочки.** Свои эндпоинты STS, SSO и IAM
  передаются в собственные вызовы цепочки, чтобы изолированные и
  правительственные развёртывания вообще могли аутентифицироваться. Если у твоей платформы
  есть региональные или приватные эндпоинты аутентификации, цепочка обязана их учитывать.
- **Миграция устаревших переменных окружения.** Устаревшие переменные (например,
  `AWS_METADATA_URL`) всё ещё читаются, с предупреждением, называющим замену.
  Переименование переменной без предупреждения о миграции молча ломает пользователей.

### Чем обходится цепочка такого масштаба

`Config` несёт десятки полей (прокси, наборы CA, режимы повторов, переключатели IMDS,
белые и чёрные списки идентификаторов аккаунтов), а спецификация поведения живёт в
очень большом наборе тестов, проверяющем каждую ветку приоритета. Не начинай
отсюда — расти к этому.

## Разбор 2: цепочка, написанная вручную в небольшом провайдере

Недавно сделанному провайдеру для API в стиле прибора (IBM Power HMC) требовалось
ровно три источника — блок провайдера, переменные окружения и файл учётных данных YAML
с именованными профилями, — и цепочка была реализована вручную в
самодостаточном пакете `internal/credentials`, той же формы, что в
`credential-chain.md`. Его решения, в обобщённом виде:

- **Интерфейс `Provider` с одним методом и сигнальная ошибка.** `Retrieve(ctx)`
  возвращает учётные данные или `ErrNoCredentials`, что значит «идти дальше». Агрегированная
  `ChainError` записывает каждый испробованный источник и реализует
  `Is(ErrNoCredentials)`, чтобы `Configure` провайдера мог выбрать между
  «вот как передать учётные данные» и «твой файл сломан» одним
  `errors.Is`.
- **Секреты набором; настройки подключения по полям.** Имя пользователя и
  пароль ищутся вместе через цепочку, а `host` и `insecure`
  независимо следуют порядку конфигурация > окружение > профиль файла > значение по умолчанию. Поэтому профиль
  может содержать только настройки подключения, пока учётные данные берутся из
  окружения.
- **Сокрытие на уровне типа.** `String()` и `GoString()` структуры учётных данных
  печатают `***REDACTED***` вместо секрета, делая значение безопасным для журналов
  по построению.
- **Семантика файла, настроенная под людей.** Отсутствующий файл или профиль, взятые
  лишь *по умолчанию*, дают молчаливый переход дальше; отсутствующий файл по
  *явно заданному* пути, *явно запрошенный* профиль, которого нет,
  или испорченный файл — жёсткие ошибки, каждая из них является ошибкой
  пользователя, которую стоит сообщить точно.
- **Предупреждения о почти правильном.** Файлы учётных данных, доступные на чтение группе
  и всем, дают предупреждение про `chmod 0600`; отключение проверки TLS даёт
  предупреждение, называющее риск.
- **Герметичные модульные тесты.** Внедряемая функция `getenv` и файлы учётных данных
  во временной директории позволяют тестам приоритета (`StaticWins`, `EnvBeatsFile`,
  `FallsThroughToFile`), тестам агрегированной ошибки и тестам сокрытия работать
  без обращения к настоящему окружению.

## Как выбрать цепочку

| Твоя ситуация | Какую цепочку строить |
|---|---|
| Один токен API, без файлов | Статика + окружение. Два провайдера, но цепочка всё равно нужна ради агрегации ошибок |
| Люди-операторы, несколько аккаунтов | Добавь файл учётных данных с профилями (разбор 2) |
| Работа внутри управляемой платформы | Добавь в конец источник удостоверения платформы (метаданные или OIDC) |
| В API есть делегирование и роли | Добавь поверх цепочки *обёртку* assume-role (разбор 1) |

Каким бы ни был размер: держи порядок в одном конструкторе, агрегируй каждый
пропущенный источник в сообщение о сбое и проверяй сразу в
`Configure`.
