# Разработка плагинов WordPress

## Когда использовать

Используй этот навык при работе над плагином, например:

- при создании или переработке структуры плагина (загрузчик, включаемые файлы,
  пространства имён и классы);
- при добавлении хуков, действий и фильтров;
- при работе с активацией, деактивацией, удалением и миграциями;
- при добавлении страниц настроек, опций и административного интерфейса
  (Settings API);
- при исправлении безопасности (nonce, права, очистка и экранирование,
  безопасность SQL);
- при сборке релиза (артефакты сборки, readme, ресурсы).

## Что нужно на входе

- корень репозитория и целевые плагины (путь к главному файлу плагина, если
  известен);
- где работает плагин: один сайт или сеть сайтов; соглашения WP.com, если они
  применимы;
- целевые версии WordPress и PHP (от них зависят доступные API и поддержка
  заполнителей в `$wpdb->prepare()`).

## Порядок работы

### 0. Разберись и найди точки входа плагина

1. Запусти разбор:

   ```bash
   node skills/wp-project-triage/scripts/detect_wp_project.mjs
   ```

2. Определи заголовки плагинов (детерминированный поиск):

   ```bash
   node skills/wp-plugin-development/scripts/detect_plugins.mjs
   ```

Если это репозиторий всего сайта, выбери конкретный плагин в
`wp-content/plugins/` или `mu-plugins/`, прежде чем менять код.

### 1. Держись предсказуемой архитектуры

Правила:

- держи один загрузчик (главный файл плагина с заголовком);
- избегай тяжёлых побочных эффектов при загрузке файла, подключайся на хуках;
- предпочитай отдельный загрузчик или класс для регистрации хуков;
- держи код только для административной части за `is_admin()` (или
  административными хуками), чтобы не нагружать лицевую часть.

Смотри:

- `references/structure.md`

### 2. Хуки и жизненный цикл (активация, деактивация, удаление)

Хуки активации хрупкие, соблюдай ограничения:

- регистрируй хуки активации и деактивации на верхнем уровне, а не внутри других
  хуков;
- сбрасывай правила перезаписи, только когда это нужно и только после регистрации
  типов записей и правил;
- удаление должно быть явным и безопасным (`uninstall.php` или
  `register_uninstall_hook`).

Смотри:

- `references/lifecycle.md`

### 3. Настройки и административный интерфейс (Settings API)

Для опций предпочитай Settings API:

- `register_setting()`, `add_settings_section()`, `add_settings_field()`;
- очистка через `sanitize_callback`.

Смотри:

- `references/settings-api.md`

### 4. Основы безопасности (всегда)

Перед выпуском:

- проверяй и очищай ввод рано, экранируй вывод поздно;
- используй nonce против CSRF **и** проверку прав для авторизации;
- не доверяй напрямую `$_POST` и `$_GET`; применяй `wp_unslash()` и конкретные
  ключи;
- для SQL используй `$wpdb->prepare()`; не собирай SQL склейкой строк.

Смотри:

- `references/security.md`

### 5. Хранение данных, cron и миграции (если нужно)

- для небольшой конфигурации предпочитай опции; свои таблицы — только при
  необходимости;
- для задач cron обеспечь идемпотентность и путь ручного запуска (WP-CLI или
  административная часть);
- при изменении схемы пиши процедуры обновления и храни версию схемы.

Смотри:

- `references/data-and-cron.md`

## Проверка

- плагин активируется без фатальных ошибок и замечаний;
- настройки сохраняются и читаются верно (права и nonce проверяются);
- удаление убирает нужные данные (и ничего кроме них);
- запусти линтер и тесты репозитория (PHPUnit, PHPCS, если они есть) и шаги сборки
  JavaScript, если плагин поставляет ресурсы.

## Режимы отказа и отладка

- хук активации не срабатывает:
  - хук зарегистрирован неверно (не в области главного файла), неверный путь к
    главному файлу или плагин активирован для всей сети;
- настройки не сохраняются:
  - настройки не зарегистрированы, неверная группа опций, нет прав, сбой nonce;
- регрессии безопасности:
  - nonce есть, но нет проверки прав; либо очищенный ввод не экранируется при
    выводе.

Смотри:

- `references/debugging.md`

## Когда эскалировать

За каноническими подробностями обращайся к справочнику по плагинам и правилам
безопасности, прежде чем придумывать собственные образцы.
