# Жизненный цикл процесса n8n

## Шесть этапов

1. **ПЛАНИРОВАНИЕ.** Собери требования, задай уточняющие вопросы, поищи уже существующие процессы и подпроцессы, которые делают то же самое.
2. **СБОРКА.** Напиши код через SDK, соблюдая правила читаемости из раздела ниже. `validate_node_config` используй как вспомогательный канал для итераций, отладки и правок одного узла: он даёт чистые ошибки по параметрам без шума всего графа. Это не замена `validate_workflow` на этапе проверки.
3. **ПРОВЕРКА.** `validate_workflow` плюс `get_workflow_details` для связей. Затем пользователь проверяет учётные данные по каждому узлу и создаёт то, что ты создать не можешь (недостающие данные, папки и так далее).
4. **ТЕСТИРОВАНИЕ.** `test_workflow` с `prepare_workflow_pin_data`; повторяй, пока вывод не совпадёт с замыслом.
5. **ПУБЛИКАЦИЯ.** `publish_workflow` — только после того, как этапы 3 и 4 прошли чисто.
6. **ПЕРЕДАЧА.** Передача в эксплуатацию: как запускать, что возвращает, за чем следить, что нужно знать, чтобы пользоваться хорошо.

Пропуск этапа даёт процессы, которые выглядят готовыми, но ломаются в продакшене или решают не ту задачу. Три самых частых пропуска:

- **Сборка без плана.** «Пользователь попросил X, начну кодить», не уточнив, что такое X, нет ли уже такой логики в подпроцессе и в какую папку это положить. Задать один уточняющий вопрос дешевле, чем переделывать.
- **Тест до настройки на стороне пользователя.** Запуск `test_workflow` до того, как пользователь проверил учётные данные по узлам, попадает не в тот сервис или получает 401. Настройка на стороне пользователя — часть этапа проверки.
- **Публикация без теста.** Успешная проверка означает, что SDK-код корректен по форме, и НЕ означает, что процесс работает правильно.

## Непреложные правила

1. **Проверяй И верифицируй до публикации.** Запусти `validate_workflow` на коде SDK, затем после каждого создания или обновления вызывай `get_workflow_details` и проверяй объект `connections`. Одна проверка пропускает молча потерянные связи. `validate_node_config` — отдельный инструмент итераций по узлу, а не замена этому шагу.
2. **Сообщай пользователю об известных ограничениях.** Если папки, доступ по MCP или иное ограничение блокирует запрос — скажи прямо и предложи путь. Не сваливай процессы молча в неправильное место и не отчитывайся об успехе запроса, который выполнен не полностью.
3. **Спрашивай перед тестом, если ниже по потоку есть побочные эффекты.** `test_workflow` автоматически закрепляет триггеры, узлы с учётными данными и узлы HTTP-запросов. Всё остальное (Code, Edit Fields, If, Wait, Execute Command, файловые операции, вызовы подпроцессов, таблицы данных) выполняется по-настоящему. Спроси пользователя, если что-то из этого даст видимые ему побочные эффекты.

## Сильные умолчания

- **Тестируй до публикации** через `test_workflow` и `prepare_workflow_pin_data`. Для внутренних одноразовых скриптов, за запуском которых ты наблюдаешь, можно мягче.
- **Всегда указывай `description`** при `create_workflow_from_code`: одно-два предложения о том, *что* и *зачем*. Подробности — в разделе о читаемости.

## Проверки недостаточно

`validate_workflow` проверяет схему и форму: отсутствующие параметры, ошибки типов, ссылки на несуществующие узлы. Он **не** ловит:

- ловушку связи `.to()` внутри `.add()` (молча потерянные связи);
- разветвления, схлопнутые в одну связь;
- ошибку на единицу в индексе объединения;
- выходы ошибок, подключённые без `onError: 'continueErrorOutput'`;
- параметры синтаксически верные, но семантически неверные (не тот идентификатор листа, не то имя столбца).

Настоящий критерий готовности:

1. `validate_workflow` проходит.
2. `get_workflow_details` возвращает объект `connections`, соответствующий замыслу.
3. `test_workflow` даёт правильный вывод на показательных закреплённых данных.

Только после этого вызывай `publish_workflow`.

## Модель выполнения

Процессы n8n выполняются **последовательно: слева направо, сверху вниз**. Ветви, которые на холсте выглядят параллельными (разветвление от одного источника к нескольким приёмникам), выполняются одна за другой в порядке Y-позиции целевых узлов. Автоматической параллельности нет.

Практические следствия:

- Разветвление на три медленных HTTP-вызова выполняется последовательно; общая задержка равна сумме, а не максимуму.
- «Параллельные» ветви делят состояние процесса в порядке выполнения: следующие потребители видят то, что оставила последняя ветвь.
- Для настоящей параллельности запускай подпроцессы с `mode: 'each'` и `waitForSubWorkflow: false`.

Это поведение платформы, а не особенность SDK. Не проектируй разветвления, исходя из предполагаемой параллельности.

## Соглашения об именовании

Плохие имена накапливают проблемы: процесс, который через полгода трудно найти, будет продублирован.

- **Процессы:** начинай с глагола и ограничивай область. `Отправить недельный отчёт клиентам`, а не `Отправщик отчёта`.
- **Узлы:** описывай, что узел *делает* в этом процессе, а не его тип. `Получить активных клиентов`, а не `Postgres1`.
- **Подпроцессы:** простое описательное имя (`Разобрать дату RFC2822`); категорию неси в тегах (`subworkflow`, тег домена, `tool`), а не в префиксе имени. Поиск по тегам работает через `search_workflows({ tags })`.
- **Теги:** механизм обнаружения на стороне агента. Списки (`list_workflow_tags`), фильтрация (`search_workflows({ tags })`) и прикрепление (`update_workflow` с `addTags` и `removeTags`, неизвестные имена создаются автоматически). Нижний регистр, 2–4 тега на процесс.

## Читаемость: описания, группы узлов, заметки, соглашения

Четыре рычага несут нагрузку читаемости; группировка нужна начиная с 7 блоков, остальные три — примерно с 5 узлов.

- **`description` процесса: зачем он существует, включая контекст из разговора.** Два предложения: что делает и зачем нужен. Главное — зафиксируй контекст, который был в беседе и иначе не сохранится в файле: ограничение, определившее решение, почему выбран этот подход, зачем пользователь об этом попросил. Иначе это умрёт вместе с чатом.
- **Группы узлов — единственный способ группировать узлы.** Именованные рамки, по одной на логический шаг (`Проверить ввод`, `Обогатить заказ`, `Уведомить`). Это только организация: участники выполняются на месте, изоляция и переиспользование — задача подпроцесса. Что знать сразу:
  - **Когда:** больше **7 блоков** при всех развёрнутых группах, обычно 3–5 групп. Блок — это триггер, каждая группа и каждый негруппированный узел; подузлы и заметки не считаются.
  - **Группа должна быть связным участком без триггера, с не более чем одним участником, смотрящим наружу в каждую сторону**; подузлы агента все внутри или все снаружи. Участники — это **имена** узлов, не идентификаторы.
  - **Неверная операция с группой пропускается, а не валит всё**, и посторонняя правка может молча удалить существующую группу, поэтому сохранение с виду чистое может потерять группу. Исключение — описание длиннее 145 символов: оно отклоняет весь вызов `update_workflow`. Читай поля групп при каждом создании и обновлении и исправляй до отчёта о готовности.
- **Заметки (sticky) аннотируют, а не группируют.** Группировка — дело групп узлов. Заметки несут то, что не выразить именем группы: выноску, TODO, предупреждение.
  - **При создании всегда привязывай к узлам.** `sticky(content, [nodes], { color })` выводит рамку из узлов, которые оборачивает, уже после раскладки. Координаты — угадывание холста, которого ещё нет; опустить и то и другое хуже: запасной вариант центрирует заметку под всем графом и обходит только другие заметки, но не узлы. Если не можешь назвать узлы, о которых заметка, ей не место на холсте.
  - **Три роли, и набор привязки следует из роли.** **Зона этапа** привязывается к узлам одного этапа; **выноска** — к единственному узлу, о котором предупреждает; серая **полоса заголовка** привязывается ко всему потоку и редка: только для холста, который сознательно оставлен без групп.
  - **Масштаб:** меньше ~5 узлов — ни одной. От 5 до 7 блоков — одна зона на этап. Больше 7 — группы узлов разделяют и документируют холст своими описаниями, а к узлу внутри группы ничего не привязывай: там позиции в свёрнутом виде, и заметка нарисуется поверх развёрнутой группы.
  - **Зонам нужно больше места, чем даёт выведенная рамка.** Указывай `height: 272` для зоны в один ряд, `464` для ветвления (плюс 32 для Message an Agent v2 и выше). Ширину не указывай никогда. Затем, **когда холст окончателен**, расширь все зоны одним пакетным `update_workflow`: `x = min(node.x) - 56`, `width = span + 112`. Значения считаются по узлам, поэтому повтор безопасен, но это финальный шаг, а не правка на каждой итерации.
  - **В `update_workflow` нет операции для заметок.** Заметка там — это `addNode` с `n8n-nodes-base.stickyNote` и полями `content`, `width`, `height`, `color` в `parameters`; опущенная `position` означает `[0, 0]`.
  - **Содержание и цвет:** `### Заголовок` с сутью плюс одна короткая строка. Узлы перекрывает только верхние 64 px, поэтому высоту под текст не добавляй: длинный текст идёт в `notes` узла или в `description` процесса. `color` от 1 до 7 означает, что там происходит: зелёный — создание или участие человека, красный — разрушительное или необратимое, синий — маршрутизация и преобразование, серый — документация. Предпочтение пользователя и соседние процессы важнее этого.
- **`notes` узла — для неочевидной конфигурации.** Объясняй, *почему* существует обходной путь или что делает узел Code. Очевидные узлы не аннотируй.

Ещё два замечания:

- **Сначала подстраивайся под соглашения проекта, потом вводи свои.** Просмотри пару соседних процессов через `search_workflows` и `get_workflow_details` и повтори палитру заметок, имена и стиль описаний.
- **Раскладка выполняется при создании и никогда при обновлении.** `create_workflow_from_code` раскладывает каждый узел без явной `position`, поэтому не задавай их и дай ему сделать работу. Задать часть и не задать остальные — худший случай: твои позиции соблюдаются, остальные раскладываются вокруг них, и узлы налезают друг на друга. `update_workflow` раскладку не выполняет вовсе, поэтому добавленное останется ровно там, где указано.

## Работа с папками

На зарегистрированном экземпляре MCP создаёт и упорядочивает папки: `create_folder`, `update_folder` (переименование и перемещение), `move_workflows_to_folder` и `folderId` в `create_workflow_from_code` для размещения при создании. `search_folders` переводит имена в идентификаторы.

Если нужной пользователю папки нет — создай её, а не строй в корне и не отчитывайся об успехе. Если инструментов для папок нет, экземпляр не зарегистрирован: папки заблокированы и в интерфейсе, поэтому попроси пользователя зарегистрироваться (бесплатно, в настройках), а не создавай папку вручную. Инструмента удаления папки нет, а проекты доступны только для чтения.

## Доступ к процессу по MCP

У каждого процесса есть флаг `availableInMCP`. Значение по умолчанию зависит от того, кто его создал:

- **Процессы, созданные через MCP** (`create_workflow_from_code`), по умолчанию **доступны по MCP**. Переключать ничего не нужно: их можно найти через `search_workflows` и сразу с ними работать.
- **Процессы, созданные в интерфейсе n8n**, могут быть по умолчанию недоступны. Пока пользователь не включит флаг, процесс для тебя невидим.

Главный случай, когда это мешает: **пользователь собрал процесс вручную в интерфейсе и хочет, чтобы ты его посмотрел или поправил, а ты его не видишь.** Прежде чем решать, что процесса нет или что ты ищешь не в том проекте, попроси пользователя подтвердить, что доступ по MCP включён.

Подпроцессы, вызываемые по MCP: вызывающий может использовать их как подпроцессы на уровне кода без флага. Чтобы вызывать их как **инструменты**, флаг обязателен (и по умолчанию включён для подпроцессов, созданных через MCP).

## Настройка на стороне пользователя (часть этапа 3)

Есть вещи, которые должен сделать пользователь, и до тестирования, иначе тест сработает не с теми данными, попадёт в отсутствующую папку или получит 401. Перечисли их коротким списком на этапе проверки, до тестов:

- **Проверить учётные данные по каждому узлу.** `newCredential('Label')` — косметика. n8n автоматически подставляет последние изменённые данные нужного типа, что молча выбирает не те, когда у пользователя их несколько (продакшен и стейджинг Gmail, два ключа API). Скажи: «открой каждый узел с учётными данными и подтверди, что выбраны правильные».
- **Создать недостающие учётные данные.** Если пользователь вставил секрет в чат или процессу нужен ещё не существующий аккаунт, назови *тип* данных и попроси создать их в интерфейсе.
- **Зарегистрироваться для работы с папками** (только если инструментов нет). Инструменты папок требуют зарегистрированного экземпляра. Если их нет, пользователь регистрируется (бесплатно, в настройках) до того, как ты сможешь создавать папки или размещать в них процессы.
- **Флаг доступа по MCP для процессов, созданных в интерфейсе.** Процессы, созданные через MCP, доступны по MCP по умолчанию. Флаг важен, только когда тест зависит от вызова процесса, созданного в интерфейсе.

Не переходи к тестированию, пока это не подтверждено.

## Передача в эксплуатацию (этап 6)

После `publish_workflow` и чистого теста процесс технически работает, но пользователю нужен контекст, чтобы им реально пользоваться. Относись к этому как к передаче работы заказчику: коротко, структурно и про то, как он будет это эксплуатировать.

Что включить:

- **Как запускается.** URL вебхука (действует после публикации), расписание и часовой пояс, кнопка ручного запуска, вызывающий подпроцесс — что применимо. Для вебхуков отдай URL.
- **Что возвращает и куда идут данные.** Одно предложение: «пишет новые строки в таблицу `customers`», «отвечает JSON вызывающему», «отправляет в канал дежурных в Slack».
- **Как вызвать по-настоящему, с примером.** «Отправь `curl -X POST <url> -d '{...}'` на вебхук», «запусти вручную из интерфейса», «дождись 09:00 UTC для первого запуска по расписанию».
- **За чем следить.** Режимы отказа, которые проявятся как алерты и ошибки, ограничения частоты на внешних сервисах и куда смотреть первым делом при поломке (вкладка выполнений, процесс обработки ошибок, журнал аудита).
- **Статус доступа по MCP.** Если процесс создан через MCP, он уже доступен по MCP; сообщи, что доступ можно отозвать в настройках. Если он собран в интерфейсе, флаг нужно включить, чтобы его мог вызвать другой агент.
- **Что осталось на стороне пользователя.** Ротация секрета, если токен вставляли в чат; доработки, до которых ты не дотянулся; известные TODO, оставленные в заметках.

Держи коротко: полдюжины пунктов, а не стена текста. Пользователь не должен спрашивать «и что теперь?».

## Антипаттерны

| Антипаттерн | Что идёт не так | Как исправить |
|---|---|---|
| Вызов `publish_workflow` без проверки | Сломанные процессы попадают в продакшен | Проверь, верифицируй связи, затем тестируй |
| Создание процессов в корне, потому что нужной папки нет | Процессы теряются, пользователю приходится перетаскивать их вручную | Сообщи об ограничении *до* сборки |
| Общие имена узлов (`HTTP Request1`, `Set2`) | Через месяц процессы нечитаемы | Переименуй по действию |
| Нет `description` при `create_workflow_from_code` | Процесс невидим в поиске, у сопровождающих нет контекста | Всегда добавляй одно-два предложения |
| Просьба включить флаг MCP для процесса, созданного через MCP | Тратит время пользователя: такие процессы доступны по умолчанию | Упоминай флаг только для процессов из интерфейса или когда доступ нужно отозвать |
| Запуск `test_workflow` без вопросов, когда ниже по потоку есть побочные эффекты | Настоящая запись в таблицу данных, реальные эффекты подпроцесса, реальный вывод Execute Command | Спроси сначала |
