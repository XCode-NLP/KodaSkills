# Метрики в kaiten-cli

Этот навык — для времени выполнения, времени цикла, пропускной способности, объёма незавершённой работы, соблюдения сроков, снимков для аудита и похожей аналитики канбана.

## Язык общения

Перед каждой командой, включая поиск инструментов и чтение JSON, передавай `--locale ru` для разговора на русском или `--locale en` для английского и других языков. Меняй его, когда пользователь меняет язык. Явный флаг перекрывает `KAITEN_CLI_LOCALE`; без того и другого CLI использует английский. Добавляй флаг в примеры ниже. Имена команд, ключи JSON и данные пользователей не меняй.

## Выбор источника

- Предпочитай `cards list-all`, когда метрику можно посчитать по полям карточки.
- Предпочитай `snapshot build` плюс `query metrics`, когда одно и то же пространство метрик будет запрашиваться многократно.
- По умолчанию смотри карточки локально через `query cards --view summary`; переходи к `detail` или `evidence` только для суженного набора кандидатов.
- Предпочитай `space-topology get`, чтобы определить структуру доски, колонок и дорожек до сбора данных.
- Предпочитай `space-activity-all get` вместо ручных циклов по смещениям вокруг `space-activity get`.
- `card-location-history batch-get` бери только когда метрике действительно нужна история перемещений каждой карточки.
- `time-logs batch-list` бери только когда метрика действительно зависит от журналов работ по карточкам.
- Инструменты графиков бери, когда Kaiten уже считает метрику на своей стороне.

## Порядок работы по умолчанию

### 1. Осмотри поверхность команд

```bash
kaiten search-tools "lead time cards"
kaiten describe space-topology.get
kaiten describe cards.list-all
kaiten describe card-location-history.batch-get
```

### 2. Если сценарий повторяется, сначала сделай снимок

Для повторяющейся генерации отчётов и аналитики без интерфейса:

```bash
kaiten --json snapshot build \
  --name team-q1 \
  --space-id 10 \
  --preset analytics \
  --window-start 2026-01-01T00:00:00Z \
  --window-end 2026-03-31T23:59:59Z

kaiten --json query metrics --snapshot team-q1 --metric throughput --group-by board_id
```

`query metrics` работает только локально после построения снимка.
Его семантика намеренно общая на этом этапе; профили потока под конкретного заказчика стоит настраивать поверх, а не угадывать автоматически.
Снимки `analytics` теперь включают локальные журналы работ, так что повторяющиеся вопросы про учёт времени должны идти через снимок и запросы.

### 3. Начинай с массовых карточек, когда снимок слишком дорог или не нужен

Для большинства метрик начни с:

```bash
kaiten --json cards list-all \
  --board-id 10 \
  --selection all \
  --fields id,title,created,first_moved_to_in_progress_at,last_moved_to_done_at,state,condition,due_date,time_spent_sum,time_blocked_sum \
  --compact
```

Используй `active_only` для чтения под объём незавершённой работы и `archived_only` для чтения под завершение.
`cards.list-all` падает, а не молча обрезает данные, когда полная страница достигает `max_pages`; поднимай лимит только после проверки ожидаемого объёма.

### 4. Переходи к деталям, только если полей карточки мало

Если метрика зависит от детальной истории перемещений:

```bash
kaiten --json card-location-history batch-get \
  --card-ids '[101,102,103]' \
  --workers 2 \
  --fields changed,column_id,subcolumn_id
```

Если метрика зависит от связей или комментариев по многим карточкам:

```bash
kaiten --json card-children batch-list --card-ids '[101,102,103]' --workers 2 --compact --fields id,title
kaiten --json comments batch-list --card-ids '[101,102,103]' --workers 2 --compact --fields id,text
```

Если метрика зависит от журналов работ или нужно обогатить детали для суженного набора кандидатов:

```bash
kaiten --json time-logs batch-list --card-ids '[101,102,103]' --workers 2 --fields id,time_spent,for_date
kaiten --json cards batch-get --card-ids '[101,102,103]' --workers 2 --fields id,title,description
```

Пакетные команды для связей, комментариев и журналов работ листают каждую карточку до конца. Достижение границы `max_pages` по отдельной карточке сообщается как ошибка, а не как частичный набор данных.

## Чего избегать

- Не считай метрики вызовом `card-location-history get` на каждую карточку.
- Не считай метрики по подтверждениям в цикле по `card-children list` или `comments list`.
- Не тяни полные тела карточек, если достаточно полей времени.
- Не строй цикл в оболочке из повторных `kaiten cards get`, когда `cards list-all` уже даёт весь набор.
- Не игнорируй метаданные `describe`; проверяй `execution_mode`, `bulk_alternative` и `cache_policy`.

## Кэш в аналитических сценариях

- Повторы в пределах одного процесса уже покрыты кэшем запроса.
- `--cache-mode auto` по умолчанию сохраняет кэшируемые безопасные чтения между процессами CLI и даёт тяжёлой и пакетной аналитике более долгий срок жизни.
- Плотные циклы по сущностям одного семейства тоже получают продление срока после достаточного числа свежих записей, поэтому обёрткам обычно стоит оставлять `auto`.
- Не выставляй в обёртках крошечные сроки для исторических или многоверсионных прогонов метрик; оставь `auto` или построй снимок.
- Перед финальным отчётом используй `refresh`, если важна свежесть данных.
- Применяй `refresh` к одной границе свежести; никогда не ставь его внутрь цикла по сущностям или пагинации.
- `off` бери только для отладки кэша, приватных чтений или частого опроса.
- `readwrite` бери только с явным `--cache-ttl-seconds`, когда контракт отчёта требует фиксированного срока.

Примеры:

```bash
kaiten --json boards list --compact --fields id,title
kaiten --json columns list --board-id 10 --compact --fields id,title
kaiten --json card-location-history batch-get --card-ids '[101,102,103]' --workers 2 --fields changed,column_id
```

## Когда брать графики

Предпочитай эндпоинты графиков, когда нужна готовая аналитика, а не её сборка на клиенте:

- кумулятивная диаграмма потока
- контрольная карта
- график времени выполнения
- график времени цикла
- графики пропускной способности

Отправку графика и опрос `compute-jobs get` используй только ради самого результата графика. Не жди, что `compute-jobs get` получит выгоду от постоянного кэша.

Если сервер возвращает `404` или ответы о недоступности на инструменты графиков, сразу переходи на `cards.list-all`, `space-activity-all.get` и `card-location-history.batch-get`, а не перебирай другие варианты графиков.

## Режимы кэша

Держи все четыре режима и выбирай осознанно:

- `--cache-mode auto`: рекомендуемое значение по умолчанию для обычной и аналитической работы; флаг можно не указывать.
- `--cache-mode refresh`: один раз перед результатом, где важна свежесть; никогда внутри цикла по сущностям; для готового снимка используй `snapshot refresh`.
- `--cache-mode off`: только для диагностики кэша, требований приватности или частого опроса.
- `--cache-mode readwrite`: только для намеренно фиксированного срока и всегда вместе с `--cache-ttl-seconds`.

## Трассировка долгих аналитических прогонов

Каждый ответ `--json` содержит `stats` верхнего уровня: длительность команды, `http_request_count`, `api_wait_ms`, счётчики кэша и агрегаты по семействам методов и путей. Смотри эти поля, прежде чем расширять запрос метрик.

Когда отчёт запускается обёрткой на оболочке или Python, включи трассировку на дорогих шагах CLI:

```bash
kaiten --json --trace-file ./kaiten-trace.jsonl card-location-history batch-get --card-ids '[101,102,103]'
```

Трассировка сохраняет статистику между командами и показывает реальное число HTTP-запросов, даже когда внешний лог агента видит только команду обёртки.

Трассировка обязательна для обёрток из трёх и более команд CLI, прогонов длиннее десяти HTTP-запросов и неизбежных циклов. Смотри её локально, не отправляя данные обратно в Kaiten:

```bash
kaiten --json trace summarize --file ./kaiten-trace.jsonl
```

## Быстрое правило выбора

- Объём незавершённой работы, пропускная способность, время выполнения и цикла по меткам времени: `cards list-all`
- Повторяющиеся итерации отчёта или дашборда по одному окну: `snapshot build` → `query metrics`
- Нужны журналы работ по многим карточкам: `time-logs batch-list`
- Нужны детали после локального сужения: `cards batch-get`
- Начальная структура пространства: `space-topology get`
- Выгрузка окна активности: `space-activity-all get`
- Подтверждения по связям и комментариям: `card-children batch-list` и `comments batch-list`
- Восстановление перемещений по колонкам: `card-location-history batch-get`
- Готовая аналитика: инструменты графиков и `compute-jobs get`
