# Как писать хорошие тесты

**Загружай этот материал, когда:** пишешь или меняешь тесты, добавляешь подделки
либо добавляешь методы очистки и помощники для тестов.

## Обзор

Тест существует, чтобы поймать конкретную поломку. Здесь всем управляют два
принципа:

```
1. Каждый тест называет поломку, которую ловит
2. Каждый тест работает с настоящим кодом
```

Строгий TDD даёт и то и другое естественно: тест, написанный первым и увиденный
падающим на настоящем коде, уже доказал, что умеет падать, и заслуживает подделку,
только когда настоящая зависимость оказывается медленной или внешней.

## Принцип 1: назови поломку

Прежде чем писать тело теста, ответь: **какое изменение в рабочем коде должно
уронить этот тест — и это изменение ошибка или решение?** Тест заслуживает места,
когда ловит неверную ветвь, пропущенный побочный эффект, неверный аргумент,
граничный случай или нарушенный контракт.

**Выводи ожидания независимо.** Используй литералы и вручную проверенные
данные; табличные тесты с литеральными значениями `want` — предпочтительная форма.
Ожидание, вычисленное проверяемым кодом или его помощниками, проходит при любом
поведении этого кода:

```typescript
// ❌ Зеркальная проверка: обе стороны вычисляет один и тот же построитель — всегда истина
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ Литерал, выведенный вручную
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**Никаких детекторов изменений.** Если тест может упасть только из-за намеренных
решений — значения константы, точной формулировки сообщения, приватной структуры —
он срабатывает при переделке и спит, когда есть ошибка. Проверяй поведение,
которое зависит от решения: не `expect(MAX_RETRIES).toBe(5)`, а «неудачный вызов
повторяется 5 раз, а шестая попытка не происходит».

**Поведение, а не текст.** Утверждение, что скрипт, навык или конфигурация содержит
точную строку, доказывает лишь то, что исходник есть исходник. Запускай скрипты на
контролируемых входах и проверяй вывод, побочные эффекты или коды возврата.
Документы, которые инструктируют агентов, проверяются поведением потребляющего
агента (`superpowers:writing-skills`); проза для людей теста не заслуживает вовсе.

**Твой код, а не библиотека.** Проверяй контракт, который твой код даёт на своих
границах: маршрут, который ты регистрируешь, запрос, который ты порождаешь,
полезную нагрузку, которую ты формируешь. Механика вышестоящего кода — тесты его
сопровождающих (классика: проверять, что твой маршрутизатор вызывает
зарегистрированный обработчик, — это тест библиотеки, а не твой). Когда поведение
вышестоящего кода тебя действительно удивило, напиши один узкий
характеризующий тест, называющий допущение. Та же граница действует внутри твоего
кода: конструкторы, геттеры, константы и тривиальное перенаправление заслуживают
тестов, только когда проверяют, нормализуют, задают значения по умолчанию,
выводят, навязывают или дают побочные эффекты, — иначе проверяй первый видимый
потребителю результат, который от них зависит.

### Проверка перед написанием

```
ПЕРЕД написанием тела теста:
  Назови изменение в рабочем коде, которое уронит этот тест.

  Не можешь назвать          → переделай вокруг наблюдаемого поведения
  «Изменился текст исходника» → запусти артефакт и проверь его эффекты
  Только намеренные решения   → это детектор изменений; проверяй поведение,
                                которое зависит от решения

  Убедись, что ожидаемое значение выведено без проверяемого кода.
  ЕСЛИ оно переиспользует логику или помощники кода:
    Замени его литералом или вручную проверенными данными
```

## Принцип 2: работай с настоящим кодом

**Подделка не заслуживает проверок.** Проверка подделки проходит, когда подделка
присутствует, и падает, когда её нет: она ничего не говорит о компоненте.
Проверяй поведение настоящего компонента; если проверяешь именно подделку,
убери её или удали проверку.

```typescript
// ✅ Настоящее поведение
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ Существование подделки
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**Замечание твоего собеседника:** «Мы что, проверяем поведение подделки?»

**Подделывай на правильном уровне.** Изучи каждый побочный эффект настоящего
метода, прежде чем его заменять; подделывай медленную или внешнюю операцию и
оставляй настоящим то, от чего зависит тест. Если сомневаесь, сначала запусти
тест на настоящей реализации и посмотри, что действительно должно произойти.

```typescript
// ❌ Подделка проглатывает запись конфигурации, которую читает поиск дубликатов
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// ✅ Подделываем только медленный запуск сервера; запись конфигурации остаётся настоящей
vi.mock('MCPServerManager');
```

**Делай подмены конкретными.** Когда аргументы, число вызовов или порядок входят в
контракт, проверяй их — подмена, принимающая что угодно, ничего не подтверждает.
Дай каждой ветви (успех, ошибка, испорченные данные) собственные данные или
шпиона, чтобы неверная ветвь не могла удовлетворить ожидание.

**Отражай настоящие данные полностью.** Подделывай полную структуру, как она
существует в реальности, — все описанные поля, а не только те, что читает твой тест.
Частичные подделки молча ломаются, когда код ниже по потоку читает пропущенное
поле: тест проходит, а интеграция ломается.

**Рабочие классы несут только рабочие методы.** Очистка, нужная только тестам,
живёт в тестовых утилитах, никогда как `destroy()` в рабочем классе. Спроси:
вызывается ли этот метод только из тестов? Владеет ли этот класс жизненным циклом
этого ресурса? Неверные ответы → тестовая утилита.

**Предпочитай настоящие компоненты сложным подделкам.** Когда подготовка подделки
перерастает логику теста, подделки не имеют методов настоящих компонентов или тесты
ломаются при изменении подделки, переходи на интеграционный тест с настоящими
компонентами. **Вопрос твоего собеседника:** «Нам здесь действительно нужна
подделка?»

### Проверка перед добавлением подделки

```
ПЕРЕД добавлением подделки или тестового помощника:
  Перечисли побочные эффекты настоящего метода; оставь настоящими те,
  от которых зависит тест, — подделывай медленный или внешний уровень ниже них.

  Ответы подделок отражают полную настоящую структуру.

  Метод, который вызывают только тесты, живёт в тестовых утилитах, а не в рабочем коде.

  Собираесь проверять саму подделку?
    Убери её или удали проверку.
```

## Тесты идут вместе с реализацией

Цикл TDD — падающий тест, минимальная реализация, рефакторинг — и есть смысл слова
«готово». Отдавай тесты, которые нужны поведению, и только их: тривиальный код и
проза для людей не заслуживают ничего, а тест, написанный ради процесса, стоит
поддержки вечно.

## Проверка мутациями

Перед завершением мысленно измени рабочий код; хотя бы один тест должен упасть на
каждую реалистичную мутацию:

- неверная константа или аргумент;
- неверный обработчик ветви;
- пропущенное изменение состояния или побочный эффект;
- пустой или заданный по умолчанию возврат;
- отсутствие проверки на ноль, пустое значение, `nil`, отсутствие прав или
  испорченный ввод.

Мутация, которую ничто не ловит, помечает поведение как незащищённое — или тест как
тавтологичный.

## Краткая справка

| Когда ты... | Делай |
|-------------|-----|
| Пишешь любой тест | Назови поломку, которую он ловит, — ошибку, а не решение |
| Формируешь ожидаемое значение | Выведи его вручную; никогда проверяемым кодом |
| Проверяешь скрипт или документ | Запусти его или проверь нагрузкой его потребителя; никогда не ищи текст |
| Тянесь к тесту зависимости | Проверяй свой контракт на границе, а не их описанную механику |
| Хочешь проверить подделанный элемент | Проверь настоящий компонент или убери подделку |
| Собираесь подделать метод | Изучи его побочные эффекты; подделывай медленный или внешний уровень |
| Строи ответ подделки | Отрази настоящую структуру полностью |
| Нужна очистка только для тестов | Положи её в тестовые утилиты |
| Видишь, как подготовка подделки разрастается | Переходи на интеграционный тест с настоящими компонентами |
| Заканчиваешь файл тестов | Проведи проверку мутациями |

## Тревожные признаки

- подготовка и проверка используют один объект, гарантируя равенство;
- тест может упасть только через панику, падение или отсутствующий селектор;
- тест падает на каждом намеренном изменении и никогда на случайной поломке;
- ожидаемые значения спрятаны за циклами, построителями или помощниками;
- тест ищет текст исходника или утверждает, что удалённый символ остался удалённым;
- тест имел бы смысл, даже если бы осталась только библиотека;
- тест существует ради покрытия и не проверяет ни побочный эффект, ни результат;
- проверка смотрит на идентификатор `*-mock` или падает, если убрать подделку;
- метод вызывается только из файлов тестов;
- подготовка подделки занимает больше половины теста или ты не можешь объяснить,
  зачем подделка нужна;
- подделываешь «на всякий случай».
