## Моделирование угроз (начни здесь)

Прежде чем браться за средства защиты, потрать пять минут на мышление атакующего:

- [ ] границы доверия размечены (запросы, загрузки, вебхуки, сторонние API, вывод LLM и локальные
  значения, записанные процессами, которые ты не контролируешь);
- [ ] активы названы (учётные данные, персональные данные, платёжные данные, действия
  администратора, движение денег);
- [ ] по каждой границе прогнан STRIDE (подмена, подделка, отказ от авторства, раскрытие
  информации, отказ в обслуживании, повышение прав);
- [ ] сценарии злоупотребления выписаны рядом со сценариями использования («как бы я этим
  злоупотребил?»).

## Проверки перед коммитом

- [ ] в коде нет секретов
  (`git diff --cached -i -G'password|secret|api_key|token' --name-only` — выводит только имена
  файлов, чей подготовленный дифф совпал, и никогда само значение; любой вывод означает, что эти
  файлы надо проверить перед коммитом);
- [ ] `.gitignore` покрывает: `.env`, `.env.local`, `*.pem`, `*.key`;
- [ ] `.env.example` использует значения-заглушки (не настоящие секреты).

## Аутентификация

- [ ] пароли хешируются bcrypt (не менее 12 раундов), scrypt или argon2;
- [ ] cookie сеанса: `httpOnly`, `secure`, `sameSite: 'lax'`;
- [ ] срок жизни сеанса настроен (разумный `max-age`);
- [ ] на эндпоинте входа есть ограничение частоты (не более 10 попыток за 15 минут);
- [ ] токены сброса пароля: ограничены по времени (не более часа), одноразовые;
- [ ] блокировка аккаунта после повторных неудач (необязательно, с уведомлением);
- [ ] MFA поддерживается для чувствительных операций (необязательно, но рекомендуется).

## Авторизация

- [ ] каждый защищённый эндпоинт проверяет аутентификацию;
- [ ] каждый доступ к ресурсу проверяет владельца или роль (предотвращает IDOR);
- [ ] эндпоинты администратора требуют проверки роли администратора;
- [ ] ключи API ограничены минимально необходимыми правами;
- [ ] токены JWT проверяются (подпись, срок действия, издатель).

## Проверка ввода

- [ ] весь пользовательский ввод проверяется на границах системы (маршруты API, обработчики
  форм);
- [ ] проверка использует белые списки (а не чёрные);
- [ ] длины строк ограничены (минимум и максимум);
- [ ] числовые диапазоны проверены;
- [ ] форматы email, URL и дат проверяются подходящими библиотеками;
- [ ] загрузки файлов: тип ограничен, размер ограничен, содержимое проверено;
- [ ] SQL-запросы параметризованы (без склейки строк);
- [ ] вывод HTML кодируется (используй автоэкранирование фреймворка);
- [ ] URL проверяются перед перенаправлением (предотвращает открытый редирект);
- [ ] серверные запросы по URL идут по белому списку; частные и зарезервированные IP заблокированы
  (предотвращает SSRF);
- [ ] разрушительные операции с путями (удаление, перемещение, перезапись): символические ссылки
  разрешены, корень из белого списка, минимальная глубина, подтверждение владения прочитано до
  вызова.

### Разрушительные операции с путями

Удержание цели, названной данными. Сначала разреши, потом решай — и считай результат кандидатом,
а не авторизацией:

```typescript
import { realpath, readFile } from 'node:fs/promises';
import { resolve, relative, isAbsolute, join, sep } from 'node:path';

const ALLOWED_ROOTS = ['/var/lib/myapp/sessions']; // an allowlist, not a pattern
const MIN_DEPTH = 1;                               // so a root is never the target

async function resolveDeletable(candidate: string, expectedOwner: string) {
  const target = await realpath(resolve(candidate)); // symlinks resolved BEFORE the check
  const inRoot = ALLOWED_ROOTS.some((root) => {
    const rel = relative(root, target);
    // `rel === '..'` / `'../'` only — a plain `startsWith('..')` would also
    // reject a legitimate child named `..cache`.
    if (rel === '' || rel === '..' || rel.startsWith(`..${sep}`) || isAbsolute(rel)) return false;
    return rel.split(sep).length >= MIN_DEPTH;
  });
  if (!inRoot) throw new Error(`refusing: outside allowed roots (${target})`);

  const owner = await readFile(join(target, '.owner'), 'utf8').catch(() => null);
  if (owner?.trim() !== expectedOwner) throw new Error(`refusing: unproven owner (${target})`);
  return target;
}
```

Чего этот код не делает — и это нужно говорить там, откуда копируют фрагмент:

- **Маркер — самоаттестация.** Всё, что может писать внутри корня, может записать `.owner`.
  `expectedOwner` должен приходить из аутентифицированного состояния, а маркеру нужна защита
  целостности (ограничительные права владельца или MAC), прежде чем он станет авторизацией, а не
  проверкой согласованности с неверно выведенной целью.
- **Возврат пути оставляет гонку между проверкой и использованием.** Там, где недоверенный процесс
  может подменить предка между проверкой и вызовом, работай с дескриптором в режиме без перехода по
  ссылкам, с семантикой «внутри корня», либо гарантируй неизменность иерархии на это время.

## Заголовки безопасности

```
Content-Security-Policy: default-src 'self'; script-src 'self'
Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
X-XSS-Protection: 0  (disabled, rely on CSP)
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

## Настройка CORS

```typescript
// Restrictive (recommended)
cors({
  origin: ['https://yourdomain.com', 'https://app.yourdomain.com'],
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE'],
  allowedHeaders: ['Content-Type', 'Authorization'],
})

// NEVER use in production:
cors({ origin: '*' })  // Allows any origin
```

## Защита данных

- [ ] чувствительные поля исключены из ответов API (`passwordHash`, `resetToken` и т.п.);
- [ ] чувствительные данные не логируются (пароли, токены, полные номера карт);
- [ ] персональные данные шифруются при хранении (если этого требует регулирование);
- [ ] HTTPS для всей внешней связи;
- [ ] резервные копии базы шифруются;
- [ ] персональные данные классифицированы, собираются под заявленную цель и минимизированы;
- [ ] у персональных данных есть предел хранения и работающий путь удаления (включая резервные
  копии, кэши, индексы);
- [ ] запросы на экспорт и удаление данных субъекта поддерживаются там, где это требуется;
  передача третьим сторонам имеет согласие и договор об обработке данных.

## Безопасность зависимостей

Сначала найди **границу установки**. Если пакет попадает под объявление `workspaces` родителя,
используй корень этой рабочей области; иначе — ближайший корень проекта, которому принадлежат и
манифест, и граф зависимостей. На этой границе сверь `packageManager` (если есть), файл блокировки
и команды CI. Остановись, если они расходятся или там есть конкурирующие файлы блокировки разных
менеджеров. Вложенный проект независим, только когда он вне рабочей области родителя; независимые
подпроекты могут законно использовать разные менеджеры.

| Признак менеджера и версии | Замороженная установка в CI | Аудит известных уязвимостей |
|---|---|---|
| npm (`package-lock.json` или `npm-shrinkwrap.json`) | `npm ci` | `npm audit` |
| pnpm | `pnpm install --frozen-lockfile` | `pnpm audit` |
| Yarn 2+ | `yarn install --immutable` | `yarn npm audit -A -R` |
| Yarn 1 | `yarn install --frozen-lockfile` | `yarn audit` |

Для менеджера или версии, которых нет в таблице, смотри его официальную документацию; не подставляй
команды другого менеджера и значения по умолчанию из более новых версий.

### Барьер для скриптов установки

Никогда не выясняй, какие скрипты жизненного цикла есть у зависимостей, запуская обычную установку
на клиенте, чьи значения по умолчанию не проверены.

1. Начни с отключёнными скриптами зависимостей либо с документированной политикой «по умолчанию
   запрещено» и отказом в закрытом состоянии.
2. Изучи точный исходник скрипта и версию пакета до одобрения.
3. Запиши самую узкую родную политику разрешения и запрета на границе установки и закоммить её.
4. Выполни чистую замороженную установку с этой политикой и проверь, что нужные пакеты всё ещё
   собираются.

**Снимок на момент времени:** значения по умолчанию и имена команд пакетных менеджеров меняются
быстро. Сверь эту матрицу с текущей официальной документацией закреплённого клиента, прежде чем на
неё полагаться.

| Версия менеджера | Родная политика |
|---|---|
| npm без проверенных точечных разрешений | Начни с `npm ci --ignore-scripts` либо закрепи `ignore-scripts=true`, если блокировка нужна для всего проекта. Держи скрипты отключёнными или осознанно обнови версию, прежде чем разрешить какой-либо проверенный скрипт зависимости. |
| npm 11.18.x (проверено на 11.18.0) | Непроверенные скрипты зависимостей по умолчанию выполняются с предупреждением. Включи `strict-allow-scripts=true` до обычной установки, затем используй `npm install-scripts ls` (он не учитывает рабочую область) с границы установки; держи разрешения привязанными к версии, а запреты — по имени. |
| npm 12.x (проверено на 12.0.1) | Непроверенные скрипты зависимостей по умолчанию пропускаются; `strict-allow-scripts=true` делает их наличие причиной отказа установки до выполнения. Используй тот же процесс проверки и одобрения через `npm install-scripts`. |
| pnpm 11+ | Используй `pnpm approve-builds` и коммить решения `allowBuilds`; `strictDepBuilds` по умолчанию `true`, поэтому непроверенные сборки падают. |
| pnpm 10.26–10.x | Настрой `allowBuilds` явно или используй `pnpm approve-builds` с устаревшими списками `onlyBuiltDependencies` и `ignoredBuiltDependencies`. Поставь `strictDepBuilds: true`; в v10 по умолчанию `false`. |
| pnpm 10.1–10.25 | `pnpm approve-builds` записывает устаревшие списки; включи `strictDepBuilds`, где поддерживается (10.3+). |
| Старый или неизвестный pnpm | Начни с `pnpm install --frozen-lockfile --ignore-scripts`. Держи скрипты отключёнными, если закреплённая версия не документирует исполнимую политику. |
| Yarn 4.14+ | Пост-установочные скрипты зависимостей отключены по умолчанию. Выдавай только необходимые исключения через `dependenciesMeta.<package>.built: true` верхнего уровня. |
| Yarn 2–4.13 | Поставь `enableScripts: false` в `.yarnrc.yml`, затем выдавай только необходимые исключения через `dependenciesMeta.<package>.built: true` верхнего уровня; не включай скрипты глобально. |
| Yarn 1 | Начни с `yarn install --ignore-scripts`; держи скрипты отключёнными, если каждое нужное исключение не проверено по документированному процессу закреплённого клиента. |

Авторитетные источники: [npm install-scripts](https://docs.npmjs.com/cli/v11/commands/npm-install-scripts/),
[политика установки](https://docs.npmjs.com/cli/v11/commands/npm-install/) и
[релизы CLI](https://github.com/npm/cli/releases);
[pnpm approve-builds](https://pnpm.io/cli/approve-builds) и
[настройки сборки](https://pnpm.io/settings#allowbuilds);
[безопасность Yarn](https://yarnpkg.com/features/security) и
[манифест](https://yarnpkg.com/configuration/manifest#dependenciesMeta).

**Гигиена цепочки поставок** (аудит известных уязвимостей не ловит новые вредоносные пакеты):

- [ ] на корень проекта или рабочей области закоммичен ровно один авторитетный файл блокировки, и
  CI никогда его не переписывает;
- [ ] находки критической и высокой важности разобраны на достижимость; у отложенных есть причина
  и дата пересмотра;
- [ ] принудительное исправление по аудиту (`npm audit fix --force` или аналог) никогда не
  выполняется автоматически; диффы исправлений и журналы изменений проверяются;
- [ ] подписи и происхождение пакетов из реестра проверяются там, где менеджер это поддерживает;
- [ ] скрипты жизненного цикла зависимостей блокируются до первого выполнения и одобряются только
  через родную политику закреплённого менеджера;
- [ ] новые зависимости проверяются на владельца, поддержку, возраст релиза, происхождение,
  транзитивный граф и тайпсквоттинг.

## Безопасность ИИ и LLM

Для любой функции, которая вызывает LLM (чат-боты, суммаризаторы, агенты, RAG):

- [ ] вывод модели считается недоверенным — никогда не в `eval`, SQL, оболочку, `innerHTML` или
  пути к файлам;
- [ ] внедрение в подсказку считается возможным; права проверяются в коде, а не в системной
  подсказке;
- [ ] секреты, данные других арендаторов и полные системные подсказки не попадают в контекстное
  окно;
- [ ] права инструментов и агентов ограничены; разрушительные и необратимые действия требуют
  подтверждения;
- [ ] заданы лимиты на токены, частоту и рекурсию (циклы), ограничивающие расход.

## Обработка ошибок

```typescript
// Production: generic error, no internals
res.status(500).json({
  error: { code: 'INTERNAL_ERROR', message: 'Something went wrong' }
});

// NEVER in production:
res.status(500).json({
  error: err.message,
  stack: err.stack,         // Exposes internals
  query: err.sql,           // Exposes database details
});
```

## Краткая справка по OWASP Top 10

Нумерация следует [OWASP Top 10:2025](https://owasp.org/Top10/2025/). Указывай категорию с годом
(`A06:2025`), поскольку издание 2021 года использовало другие номера для нескольких тех же
категорий.

| № | Уязвимость | Предотвращение |
|---|---|---|
| A01 | Нарушение контроля доступа (теперь включает SSRF) | Проверки аутентификации на каждом эндпоинте, проверка владельца; проверка и белый список URL серверных запросов, ограничение исходящих запросов |
| A02 | Небезопасная конфигурация | Заголовки безопасности, минимальные права, безопасные значения по умолчанию |
| A03 | Сбои цепочки поставок ПО | Аудит зависимостей экосистемы (`npm audit`, `pip-audit` и т.п.), обновление зависимостей, минимум зависимостей, проверка новых пакетов и скриптов установки |
| A04 | Криптографические сбои | HTTPS, стойкое хеширование, отсутствие секретов в коде |
| A05 | Внедрение | Параметризованные запросы, проверка ввода |
| A06 | Небезопасный дизайн | Моделирование угроз, разработка от спецификации |
| A07 | Сбои аутентификации | Стойкие пароли, ограничение частоты, управление сеансами |
| A08 | Сбои целостности ПО и данных | Проверка обновлений, подписанные артефакты, отсутствие десериализации недоверенных данных |
| A09 | Сбои журналирования и оповещения о безопасности | Логируй события безопасности, оповещай о них, не логируй секреты |
| A10 | Неверная обработка исключительных ситуаций | Отказ в закрытом состоянии, обработка каждого пути ошибки, общие тела ошибок |

## Краткая справка по OWASP Top 10 для LLM

Для приложений с функциями LLM. См.
[OWASP GenAI Security Project](https://genai.owasp.org/llm-top-10/).

| ID | Риск | Предотвращение |
|---|---|---|
| LLM01 | Внедрение в подсказку | Не считай системную подсказку границей; проверяй права в коде |
| LLM02 | Раскрытие чувствительной информации | Держи секреты и персональные данные вне подсказок; фильтруй вывод |
| LLM03 | Цепочка поставок | Проверяй модели, наборы данных и плагины как любую зависимость |
| LLM04 | Отравление данных и модели | Используй доверенные источники моделей, проверяй целостность; проверяй данные дообучения и RAG |
| LLM05 | Неверная обработка вывода | Считай вывод модели недоверенным; проверяй, параметризуй, кодируй |
| LLM06 | Чрезмерная автономность | Ограничивай права инструментов; подтверждай разрушительные действия |
| LLM07 | Утечка системной подсказки | Исходи из того, что системная подсказка может утечь; не кладите в неё секретов |
| LLM08 | Слабости векторных представлений | Разделяй эмбеддинги RAG по арендаторам; проверяй документы до индексации |
| LLM09 | Дезинформация | Обосновывай ответы ссылками; проверяй критичные утверждения; оставляй человека в цикле |
| LLM10 | Неограниченный расход | Ограничивай токены, частоту запросов и глубину циклов и рекурсии |
