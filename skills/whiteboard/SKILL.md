# Whiteboard

Превращай объяснение в диаграмму, которую пользователь может увидеть, сохранить и вставить куда угодно. Исходник диаграммы пишешь ты; `scripts/render.mjs` рендерит его через локально установленный CLI пользователя и точно говорит, что не так, если исходник не разбирается.

## Порядок работы

1. **Выбери тип диаграммы и язык.** По умолчанию — Mermaid. Для больших архитектурных
   диаграмм с вложенными контейнерами используй D2, PlantUML — только когда пользователь
   просит или проект уже его использует. Синтаксис каждого типа — в
   [references/syntax.md](references/syntax.md).
2. **Читай до того, как рисовать.** Когда диаграмма описывает код, сначала прочитай код. Рисуй то,
   что есть, с настоящими именами, а не общую картинку. Для запросов по всему проекту (архитектура,
   поток управления, модель данных) следуй [references/modes.md](references/modes.md).
3. **Напиши исходник и отрендери его.** Передай его через stdin с коротким заголовком (не более 80
   символов). Заголовок даёт имена файлам, поэтому используй его же, когда перерисовываешь ту же
   диаграмму:

   ```bash
   node <skill-dir>/scripts/render.mjs --title "Checkout sequence" <<'EOF'
   sequenceDiagram
     Browser->>API: POST /checkout
     API->>Payments: charge(card)
     Payments-->>API: ok
     API-->>Browser: 201 Created
   EOF
   ```

   `<skill-dir>` — папка, в которой лежит этот файл. Добавь `--language d2` или `--language plantuml`
   для этих языков. В Windows или когда heredoc неудобен, запиши исходник во
   временный файл и передай `--file <path>`.
4. **Исправляй и перезапускай при сбое.** Код выхода 1 значит, что рендерер отклонил исходник;
   сообщение называет строку. Исправь эту строку и запусти ту же команду снова. Не отдавай
   пользователю диаграмму, которая не отрендерилась. Частые исправления перечислены в конце
   [references/syntax.md](references/syntax.md).
5. **Отчитайся кратко.** Скажи, что показывает диаграмма, и дай пути файлов, которые напечатал
   скрипт (например, `diagrams/checkout-sequence.svg`). Если пользователь хочет вставить её в
   README, issue или вики, дай исходник в блоке ```mermaid: GitHub, GitLab и
   Notion его рендерят.

## Справка по скрипту

| Опция | Назначение |
|---|---|
| `--title <text>` | Обязательна. Даёт имена файлам: `diagrams/<slug>.svg` и исходнику рядом. |
| `--language <name>` | `mermaid` (по умолчанию), `d2` или `plantuml`. |
| `--file <path>` | Читать исходник из файла вместо stdin. |
| `--out <dir>` | Папка вывода; по умолчанию `diagrams` в текущей папке. |
| `--png` | Дополнительно записать PNG (слайды, чаты, терминалы с картинками). |
| `--theme <name>` | `default`, `neutral`, `dark` или `forest`. |
| `--config <file>` | JSON-конфигурация Mermaid для цветов и шрифтов команды. |
| `--check` | Только проверить; ничего не записывать. |
| `--open` | Открыть SVG в просмотрщике пользователя по умолчанию. Используй, когда пользователь хочет увидеть диаграмму сейчас. |
| `--share` | Загрузить исходник в **секретный** gist GitHub и напечатать ссылку. Запускай только после того, как пользователь попросил поделиться и согласился на загрузку. |
| `--json` | Машиночитаемый результат. |
| `--doctor` | Проверяет Node, каждый рендерер и GitHub CLI и говорит, что установить. |

Коды выхода: `0` отрендерено, `1` исходник отклонён (исправь и запусти снова), `2` неверные
аргументы, `3` рендерер не установлен.

Диаграммы никогда не читают локальные файлы, переменные окружения или URL в изображение:

- **Mermaid** рендерится в изолированной странице браузера, которая не может ничего загрузить из
  сети или с диска. Любой синтаксис Mermaid работает, но удалённые и локальные изображения и
  CSS-ресурсы остаются пустыми; если изображение нужно, встрой его как `data:` URL.
- **PlantUML**: директивы, кроме простых (`!define`, `!if`, `!procedure`, `!$var`,
  `!theme <name>`, `!include <stdlib>` и т. п.), встроенные функции вроде `%getenv` и `<img:…>`
  отклоняются. Встраивай содержимое вместо них.
- **D2**: импорты через `@` отклоняются. Диаграммы с иконками, блоками строк, HTML или URL
  рендерятся только в SVG, где они остаются ссылками.

Только если пользователь явно хочет include или внешние изображения, перезапусти с
`WHITEBOARD_ALLOW_INCLUDES=1`.

Перерисовка с тем же заголовком сохраняет прежние файлы в `diagrams/.versions/<slug>/<n>/`,
поэтому итерации над диаграммой никогда не теряют предыдущую версию.

## Когда рендерер отсутствует

Код выхода 3 печатает команду установки. Скажи пользователю, что запустить, и не устанавливай
глобальные пакеты сам, если он не попросил:

- Mermaid: `npm i -g @mermaid-js/mermaid-cli`
- D2: `brew install d2` или см. https://d2lang.com/tour/install
- PlantUML: `brew install plantuml` или `apt install plantuml` (нужна Java)

Если рендерер установлен, но не найден (часто в настольных приложениях, которые стартуют без PATH
из login-оболочки), задай `WHITEBOARD_MMDC`, `WHITEBOARD_D2` или `WHITEBOARD_PLANTUML` полным
путём к нему. Рендеринг Mermaid использует браузер и пакет Mermaid из mermaid-cli; если скрипт
находит `mmdc`, но не его пакет, задай `WHITEBOARD_MERMAID_CLI_DIR` папкой
`@mermaid-js/mermaid-cli`. Когда установить ничего нельзя, дай исходник Mermaid в блоке кода, чтобы
он всё равно отрисовался на GitHub, и скажи, что рендерером он не проверялся.

## Хорошие диаграммы

- Одна идея на диаграмму. Всё, что больше примерно 15 узлов или 20 сообщений, разделяй на обзор
  и детальные диаграммы.
- Подписывай каждое ребро тем, что по нему течёт или происходит (`HTTP`, `publishes OrderPlaced`, `1..*`).
- Используй имена из кода: имена классов, модулей и сервисов, настоящие эндпоинты, настоящие таблицы.
- Выбирай тип под вопрос: кто кого вызывает во времени → последовательность;
  из каких частей состоит система → архитектура или блок-схема; как выглядят данные → ER или классы;
  как что-то меняется во времени → состояния.
- Держи текст внутри узлов коротким; подробности — в подписях рёбер или заметках.
