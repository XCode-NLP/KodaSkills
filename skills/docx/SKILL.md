# Создание, правка и разбор DOCX

`.docx` — это ZIP-архив с XML-файлами. Выбирай подход по задаче:

| Задача                                    | Подход                                                                                       |
|-------------------------------------------|----------------------------------------------------------------------------------------------|
| **Создать** новый документ                | Напиши скрипт на `docx` (npm) — см. подводные камни ниже                                     |
| **Отредактировать** существующий документ | распаковать → править `word/document.xml` → `zip` (docx-js не умеет открывать готовые файлы) |
| **Прочитать** содержимое                  | `pandoc -t markdown file.docx`                                                               |

> Пути к скриптам ниже указаны относительно директории этого навыка.

## Создание через docx-js — подводные камни

`docx` уже установлен — не запускай `npm install` заранее; пиши скрипт и сразу подключай через `require('docx')`. Ставь пакет, только если этот `require` падает. API модель знает; ниже — места, где легко ошибиться:

- **Размер страницы по умолчанию — A4.** Для US Letter задай `page: { size: { width: 12240, height: 15840 } }` (DXA; 1440 = 1″).
- **Альбомная ориентация:** передавай размеры книжной страницы и `orientation: PageOrientation.LANDSCAPE` — docx-js сам поменяет ширину и высоту местами.
- **Таблицы требуют двойной ширины:** задай `columnWidths` у таблицы И `width` у каждой ячейки, оба в `WidthType.DXA` (PERCENTAGE ломается в Google Docs). Сумма ширин столбцов должна равняться ширине таблицы.
- **Заливка таблицы:** используй `ShadingType.CLEAR`, никогда `SOLID` (отрисуется чёрным).
- **Списки:** никогда не вставляй `•` в текст; используй конфигурацию `numbering` с `LevelFormat.BULLET`.
- **`ImageRun` требует `type:`** (`"png"`, `"jpg"`, …).
- **`PageBreak` должен быть внутри `Paragraph`.**
- **Никогда не используй `\n`** — делай отдельные элементы `Paragraph`.
- **Заголовки:** оформи каждый используемый уровень (`title`, `heading1`, `heading2`…) в `styles.default`: `heading1: { run: { font: "Arial", size: 32, bold: true }, paragraph: { spacing: { before: 240, after: 120 }, keepNext: true } }`. Каждому уровню нужен собственный шрифт (даже при шрифте по умолчанию у документа), `before` и `after` (даже если 0) и `keepNext`: встроенные стили не задают ничего из этого.
- **Оглавление:** заголовки должны использовать встроенные `HeadingLevel.*`; пользовательским стилям заголовков нужен `outlineLevel`, иначе они не попадут в оглавление.
- **Не используй таблицу как горизонтальную линию** — ставь нижнюю границу абзаца.
- **Точки-заполнители и выравнивание вправо в той же строке:** используй `PositionalTab` (`alignment: PositionalTabAlignment.RIGHT`, `leader: PositionalTabLeader.DOT`) внутри `TextRun`, а не литеральные точки или пробелы.

## Проверка результата

После записи `.docx` отрисуй его и посмотри глазами:

```bash
zip -d output.docx '*/' >/dev/null || true   # удаляет записи папок из ZIP: Word отказывался открывать такой файл через облачный сервис совместного редактирования
python scripts/office/soffice.py --headless --convert-to pdf output.docx
pdftoppm -jpeg -r 100 output.pdf page
ls page-*.jpg   # затем прочитай изображения
```

`pdftoppm` дополняет номера страниц нулями до ширины общего числа страниц (`page-01.jpg`…`page-12.jpg`).

## Правка существующих документов

Старые `.doc` сначала нужно конвертировать: `python scripts/office/soffice.py --headless --convert-to docx file.doc`.

```bash
python3 -c "import sys,zipfile; zipfile.ZipFile(sys.argv[1]).extractall('unpacked')" doc.docx   # не unzip: он восстанавливает символические ссылки, а docx от третьих лиц недоверенный
python scripts/merge_runs.py unpacked/   # объединяет фрагментированные прогоны, чтобы текст находился поиском
# правь unpacked/word/document.xml на месте — НЕ переформатируй и не делай pretty-print
(cd unpacked && rm -f ../out.docx && zip -XrDy ../out.docx .)
python scripts/office/validate.py out.docx --original doc.docx   # проверки по XSD; --auto-repair исправляет частые проблемы
# отслеживаемые изменения? добавь --author "<имя, под которым вносились правки>", чтобы проверить, что все правки отслежены
```

Word разбивает текст на множество прогонов `<w:r>` (идентификаторы ревизий, маркеры проверки орфографии), поэтому фраза, видимая в документе, часто не существует в XML как непрерывная строка. `merge_runs.py` объединяет соседние одинаково оформленные прогоны в `word/document.xml`, не меняя содержимое и внешний вид; он также принимает `.docx` напрямую (`python scripts/merge_runs.py doc.docx -o merged.docx`).

**Отслеживаемые изменения:** при правке с рецензированием проверяй через `--author "<имя, под которым вносились правки>"` (нужен `--original`) — скрипт сообщит о любом изменённом тексте без обёртки `<w:ins>`/`<w:del>`, а такое легко сделать случайно и незаметно в режиме принятых правок. Оборачивай прогоны в `<w:ins>`/`<w:del>` с атрибутами `w:id`, `w:author`, `w:date`. Внутри `<w:del>` текстовый элемент — `<w:delText>`, а не `<w:t>`. Удалённый знак абзаца (`<w:pPr><w:rPr><w:del w:id=".." w:author=".." w:date=".."/></w:rPr></w:pPr>`) означает «объединить этот абзац со следующим», поэтому полное удаление абзаца — это он плюс `<w:del>` вокруг каждого прогона. Элемент `<w:del/>` должен идти перед остальными дочерними элементами rPr; их порядок задан схемой.

Чтобы получить чистую копию со всеми принятыми изменениями: `python scripts/accept_changes.py in.docx out.docx`.

Принятие удалённого знака абзаца должно присоединять этот абзац к следующему, поэтому абзац, у которого удалены *все* прогоны, исчезает. Word делает так; `accept_changes.py` и `pandoc --track-changes=accept` — не всегда. Оба ошибаются одинаково: убирают удалённый текст, но оставляют опустевший абзац, который читается как лишний пустой маркер, если абзац был автоматически нумерованным:

- `pandoc --track-changes=accept` никогда не объединяет абзацы.
- `accept_changes.py` (через LibreOffice) объединяет их правильно, кроме случая, когда за удалённым абзацем идёт пустой абзац-разделитель.

Пустой маркер в любом из режимов — артефакт этого режима, а не дефект документа. Проверяй удаление абзацев по XML.

## Комментарии

Комментарии требуют шести связанных файлов. Используй помощник — режим директории, когда будешь ещё править `document.xml` (экономит цикл распаковки и упаковки), иначе режим прямого `.docx`:

```bash
# Для уже распакованной директории (предпочтительно, если ещё расставляешь маркеры)
python scripts/comment.py unpacked/ "Лимит по расходам слишком низкий"
python scripts/comment.py unpacked/ "Согласовано" --parent 0

# Сразу для .docx
python scripts/comment.py contract.docx "Этот лимит слишком низкий" -o annotated.docx
```

Скрипт создаёт `comments.xml`, `commentsExtended.xml`, `commentsIds.xml`, `commentsExtensible.xml`, связи и переопределения типов содержимого. Идентификаторы комментариев назначаются автоматически. Затем он печатает фрагмент `<w:commentRangeStart>`/`<w:commentRangeEnd>`/`<w:commentReference>`, который нужно добавить в `word/document.xml`, чтобы комментарий привязался к конкретному тексту — пока маркеры не расставлены, комментарий существует, но не виден.
