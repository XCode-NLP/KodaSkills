# mindbox-email-ops — операции Mindbox для писем

Исполнитель всех интеграционных действий, знающий проект. Генератор JSX — это `mindbox-email`; этот навык не придумывает содержимое письма и **не меняет JSX молча**. Ошибки предпросмотра, редактора и сохранения возвращаются дословно — генератору, когда они про JSX (это текст редактора, с номерами строк), иначе пользователю; не переформулируй их, не классифицируй и не исправляй молча.

## Общение с пользователем

JSX, внутренние идентификаторы и rowVersion — внутренние детали исполнения. В обычном разговоре с пользователем говори «письмо», «вёрстка письма», «содержимое», «предпросмотр» и «сохранение», а не JSX, `internalId` кампании, `variantInternalId`, `formatInternalId`, `rowVersion` или `visualTemplateRowVersion`. Не показывай сырой JSX и GUID, если пользователь явно не просил код, экспорт, разметку или технические детали.

Работающая автоматическая кампания хранит письмо в двух версиях, и пользователь видит обе: «активную», которая уходит клиентам, и «черновик», который он применит в редакторе. Называй их именно так. У неработающей кампании версия одна: не называй её «черновиком» и вообще не упоминай версию — пользователь видит одно письмо. Инструменты называют черновик «версией в подготовке» — это их язык для агента, не для пользователя. «Работает» — это то, что `campaign_get` пишет в строке редактируемости («This campaign is working, and …»), а не догадка по `kind`: автоматическая кампания в состоянии `in development` или `ready to send` ещё никуда не ушла и не работает.

## Отзыв о навыке через MCP feedback

MCP `feedback` текущего сервера Mindbox/email — необязательный канал, чтобы передать разработчикам подтверждённый отзыв о работе навыка. Используй одну из двух точек входа:

1. **Инициатива агента.** Если ты убедился, что видишь критическую проблему, которую текущим навыком не решить, — расхождение инструкций или справочников с фактическим поведением бэкенда, повторяющиеся ошибки одного типа, заблокированный безопасный сценарий, — предложи пользователю отправить отзыв разработчикам. Не отправляй без явного согласия.
2. **Инициатива пользователя.** Если пользователь спрашивает, как передать сообщение или отзыв разработчикам, ответь: «Это возможно. Какое сообщение вы хотите отправить?» Затем оформи его слова по формату ниже.

Протокол отправки обязателен в обоих случаях:

1. Сначала составь точный текст сообщения. Первая строка — маркер `[skill-feedback:v1]`, затем поля `skill=<email|email-ops>` (навык, к инструкциям которого относится проблема), `skillVersion=<metadata.version из SKILL.md этого навыка>`, `source=user-report|agent-observation`, `problem` и `context`. `problem` — суть: что мешает, что пошло не так. Для `user-report` пиши в `problem` точные слова пользователя, а `context` добавляй сам. Для `agent-observation` оба поля пишешь ты. `context` — коротко: входные данные и запросы, как сложилась текущая ситуация, дословные тексты ошибок бэкенда, факты воспроизведения (дата прогона, одноразовая кампания). Добавляй `area=<layout|save|preview|gallery|personalization|other>` только если область очевидна.
2. **Всегда сначала показывай пользователю весь текст к отправке** и спрашивай явное разрешение, например: «Отправить этот отзыв разработчикам?»
3. Вызывай `feedback` именно на текущем сервере Mindbox/email, через который выполняются операции этого навыка, и только после однозначного подтверждения. Если пользователь просит изменить текст, покажи исправленный вариант снова и получи подтверждение заново.
4. Не отправляй отзыв скрытно, не предполагай согласие и не прикрепляй его молча к другой операции. Не включай содержимое писем, персональные данные, секреты, подписанные ссылки и токены.

## Быстрый старт: выбери маршрут

| Задача | Маршрут |
|---|---|
| Новое письмо в JSX | поиск цели (§1–§2), если нужно сохранение → изображения → Генератор → предпросмотр → подтверждение и сохранение (§4–§5) |
| Правка существующего письма по ID | `campaign_get` → §1–§7 |
| Правка JSX, который дал пользователь | Генератор вносит только запрошенные изменения → предпросмотр → подтверждение и сохранение, если есть целевая кампания |
| Сохранённые шаблоны: письмо «по шаблону X», «покажи мои шаблоны», изменить, переименовать, создать («сохрани это письмо как шаблон»), копировать | `references/saved-template.md` |
| Сохранённый блок редактора | `visual_template_saved_block_list` → пользователь выбирает в панели → `visual_template_saved_block_get` с `internalId` из его сообщения → Генератор размещает; строку, которую get отклоняет, — попроси другой блок, без похожего |
| Изменить содержимое внутри `<QuokkaBlock>` прочитанного письма или блока библиотеки | `visual_template_quokka_block_describe` по `templateId` блока → Генератор → §4–§5 |
| Изменить содержимое внутри `<SyncBlock>` | не через MCP: скажи, что это «Сквозной блок» (по-английски «Universal block»), он правится только в редакторе |
| «заголовок», hero, содержимое в теле письма | визуальный маршрут, не тема |
| «оформление», «дизайн», «общие стили», «стиль всех кнопок/заголовков» | общие стили письма: `visual_template_theme_get` и `<Theme>` в JSX (§3), не тема |
| Смена типа шаблона: «пересобери в визуальном редакторе», «переведи в HTML» | «Смена типа шаблона» |
| «тема письма», отправитель, прехедер | `campaign_get` → `campaign_edit_content` |
| Название, UTM, расписание | `campaign_get` → `campaign_edit` |
| Блок или строка только для сегмента либо скрытые от него | `segments_list` с `entityType: User`, только сегменты сегментаций `Active`, пользователь выбирает по имени → показать или скрыть → Генератор пишет `targeting` → строка в подтверждении сохранения |
| Задать получателей: сегмент или фильтр | `references/recipients.md` |
| Новая кампания с нуля | «Новая кампания с нуля» |
| Тестовая отправка письма | «Тестовая отправка» |
| Изображение: в галерее / с машины пользователя / по HTTPS-ссылке | «Изображения» |
| PNG, десктоп/мобильный, проверка HTML | «Проверки, предпросмотр и QA» |

Если данных не хватает:

- нет internalId рассылки для чтения или правки по ID — остановись и спроси;
- нет точной цели сохранения (`variantInternalId` + `formatInternalId` версии, в которую пишешь) или нет подтверждения сохранения — остановись и спроси;
- не придумывай `internalId` кампании, `variantInternalId`, `formatInternalId`, URL, ресурс галереи или `fileName`.

Живая отправка, активация и удаление, применение черновика, создание формата и получателей из разового файла в MCP недоступны. Агент не делает их за пользователя — ни в редакторе, ни через автоматизацию браузера: назови действие, скажи, что оно выполняется в интерфейсе кампании, и остановись.

## Изображения

Ops ничего не выбирает молча; сначала идёт поиск цели (быстрый старт, «Новое письмо в JSX»). Генератор всегда получает пару `{url, fileName}` из вывода инструмента или строки панели.

### Поиск уже загруженного изображения

1. `gallery_images_list` по имени из запроса пользователя.
2. Кандидатов нет — скажи это. Чаще промах означает другое написание, а не отсутствие файла: если пользователь ждал, что изображение там есть, спроси про имя, а не загружай вторую копию. Иначе предложи HTTPS-ссылку или панель загрузки.
3. Когда изображение предложено, говори, системная это иконка платформы или ресурс проекта.
4. Один кандидат — верни `{url, fileName}`, `fileName` как напечатано в той же строке.
5. Несколько кандидатов — не выбирай. Показывай `fileName`; размер и дату — только если они есть, URL — только если варианты без него не различить. У одной соцсети часто несколько вариантов иконки — спроси. Сети нет — попроси ссылку или файл; никаких похожих.

### Визуальный выбор изображения из галереи

В клиенте, поддерживающем MCP Apps, каждый вызов `gallery_images_list` открывает ещё и панель выбора с поиском и миниатюрами; пользователь отмечает изображения и нажимает «send to chat», а сообщение несёт по строке `file name — URL` на каждое изображение. Текстовый ответ одинаков с панелью и без неё.

- При нескольких похожих кандидатах или когда пользователь хочет увидеть изображения, предложи выбрать в панели. Одного вызова достаточно: панель листает и ищет сама.
- Бери `url` из строки, а имя файла — как `fileName`. Для изображения, хранящегося в WebP, это ссылка на его PNG-копию — так и должно быть.
- Пришло несколько изображений, а письму нужно одно, либо непонятно, какая строка куда идёт — спроси.
- Пользователь не видит панели — его клиент её не поддерживает: скажи это и продолжай с текстовым списком.

### Загрузка изображений

`gallery_image_upload` — как им пользоваться, написано в его описании и ответах. Навык добавляет:

- **Когда загружать.** Триггер — намерение поместить изображение в письмо, а не наличие вложения. Скриншот бага, образец макета, «вот как это выглядит сейчас, исправь» — просто посмотри на изображение и ничего не загружай. Если непонятно, чего хотят, спроси.
- **Что куда идёт — решает пользователь.** Имя файла — это метка для разговора, а не описание содержимого: не угадывай по имени или порядку, спрашивай.
- **Ссылка от пользователя** не на https: `http://` — попроси https или файл; строка `data:`/`blob:`/`file:`/`cid:` — не ссылка: попроси сохранить картинку файлом и использовать панель.

### Ошибки галереи

Если инструмент галереи вернул ошибку, передай её смысл пользователю и останови зависящую от изображения часть. Не придумывай причину, не спрашивай локальные учётные данные, не подставляй похожее изображение. Без URL от инструмента письмо можно собрать только без этого изображения, по согласованию.

## Проверки, предпросмотр и QA

- **Каждая генерация или правка JSX заканчивается одним `visual_template_preview`** итогового JSX за ход — пользователь должен увидеть, что собрано. Сначала открой оба снимка сам (с макетом — сравни их с ним, `mindbox-email/SKILL.md`, шаг 4), затем отдай пользователю виджет и ссылку `htmlUrl`. Операции без JSX — метаданные, получатели, тестовая отправка — его не получают; кампания, которую отсюда не правят, может получить один как read-only.
- **Утверждение о вёрстке делается только после того, как открыты оба снимка.** Колонки строки на мобильном по умолчанию складываются в стопку, и то, что аккуратно стоит на десктопе, может развалиться. Открыть не удалось — скажи это вместо описания вёрстки: пользователь откроет ссылки.
- Каждый вызов открывает новый виджет; старые не обновляются. Если пользователь спрашивает, какому верить, — последнему; предыдущие показывают более ранние версии.
- **Предпросмотр — это полотно редактора, а не отправленное письмо**: примеры значений не являются данными клиентов, а где полотно расходится с отправленным письмом, написано на странице вики `email.tags.template`, «В предпросмотре».
- **Предпросмотр берёт настройки шаблона, который будет у письма после сохранения, когда такой есть.** Правка письма кампании — шаблон кампании редактируемой версии, как только у неё есть сохранённое письмо; сборка по сохранённому шаблону — сохранённый шаблон; кампания без сохранённого письма, которая не собрана по сохранённому шаблону, — ничего. Без них картинка показывает только документ и выглядит не менее убедительно. Бери версию, которую правишь, если пользователь не просил показать другую.
- **Ошибки предпросмотра.** Голый `Internal server error` без номера строки — не ошибка формы значения (те приходят с названием): передай её дальше, не повторяй слепо. Сквозной блок не найден при предпросмотре или сохранении: после текста редактора предложи убрать его `<SyncBlock>` или открыть письмо в редакторе.
- Никогда не собирай HTML письма или предпросмотр вручную. Предпросмотр и QA никогда не означают согласие на запись.

**Скачивание HTML, диагностика конкретной проблемы отрисовки, отсутствующие PNG-ссылки — ты ОБЯЗАН сначала прочитать `references/preview-qa.md`.**

## Правка визуального шаблона

Единственный подробный порядок работы для чтения, правки и записи JSX.

### 1. Подготовь цель

1. Прочитай кампанию через `campaign_get`. Запиши её имя, `internalId` и `rowVersion`, варианты, форматы и уже существующие ошибки валидации.
2. Прочитай строку редактируемости над вариантами. Если там сказано, что письмо отсюда не правится, ничего не сохраняй и скажи пользователю, что такая кампания правится в редакторе; предпросмотр всё равно разрешён.
3. Цель записи — **одна версия письма**: `variantInternalId` + `formatInternalId` из списков `campaign_get`. Работающая автоматическая кампания перечисляет две: правка идёт в черновик; если его ещё нет, пиши в активную — сохранение само создаст черновик и скажет об этом.
4. Запиши вид редактора целевого формата:
   - `Mindboxeditor` — визуальный маршрут разрешён;
   - `Rawhtml` с `html: yes` — существующий сырой HTML, никогда не визуальная цель: скажи, что письмо правится в редакторе; просьба конвертировать — «Смена типа шаблона»;
   - `Rawhtml` с `html: no` — кандидат на первичную инициализацию: переходи к `visual_template_get` (§2);
   - отсутствует или не распознан — не угадывай; остановись.
5. Один A/B-вариант — без вопроса, но покажи его в подтверждении. Несколько — попроси пользователя выбрать до правки. `variantInternalId` — это A/B-вариант, а не атрибут JSX `themeVariant`.

### 2. Прочитай исходное состояние

1. `visual_template_get` шаблона кампании целевой версии. `visualTemplateRowVersion` принадлежит ровно этой версии: никогда не передавай его в другую.
2. Вернулись JSX и `visualTemplateRowVersion` — визуальный шаблон существует; сохрани точный JSX как снимок. Если у формата `html: no`, сначала восстановление привязки: после подтверждения сохрани ровно этот JSX с текущим `rowVersion` кампании и `visualTemplateRowVersion` шаблона, затем проверь это как первое сохранение инициализации (§5, пункт 6). Никаких правок и новых версий, пока восстановление не удалось.
   - **2a.** Задача — собрать новое письмо (макет, описание, промпт, письмо по сохранённому шаблону) поверх существующего — спроси сначала: замена или правка существующего. Решает пользователь; передай ответ генератору вместе со снимком. Развилка привязана к намерению: «давай начнём заново», «переделай всё» посреди правки — это та же замена, сколько бы итераций ни прошло, — и снимок со стилями тогда перечитываются (`visual_template_get`, `visual_template_theme_get`).
   - **2b.** Выбрана замена, но не по сохранённому шаблону — `visual_template_theme_get` на шаблоне кампании с его JSX. Стили письма — его собственные, поэтому второй вопрос **обязателен**, с тремя ответами: собирать в **этих стилях** (заголовки и кнопки следуют им и меняются вместе со всем письмом), в **новых стилях** или **сбросить к умолчаниям платформы**. Уже умолчания платформы — не спрашивай. Вопрос обязателен, потому что полная перезапись не стирает стили: они принадлежат формату и переживают сохранение. Значения сброса приходят из того же инструмента **без шаблона**. Скажи прямо, что полного «как будто никто не настраивал» не бывает: стили остаются собственными стилями письма, просто равными умолчаниям платформы.
3. `No visual template was saved for` — проверь исходный `campaign_get`:
   - `html: no` с `Mindboxeditor` или `Rawhtml` — инициализация: снимка и `visualTemplateRowVersion` нет; первое сохранение идёт после подтверждения, без `visualTemplateRowVersion`;
   - `html: yes` или пустота не подтверждена — это не инициализация, не перезаписывай: там может быть сырой HTML. **Исключение** — черновик, который только что создало само сохранение (§5, пункт 5): у него есть тело как копия активной версии, но шаблона редактора ещё нет — повтор идёт по §5, пункту 5.
4. Шаблон нельзя выразить в JSX — не перезаписывай его.

### 3. Правка

1. Генератор вносит только запрошенные изменения; каждое изменение заканчивается предпросмотром.
2. Генератору нужны текущие общие стили — чтобы перенести вид в `<Theme>` или сверить значения после переноса: `visual_template_theme_get` на шаблоне кампании с текущим JSX; отдай фрагмент генератору как есть. Умолчания платформы (шаблона ещё нет) никогда не передаются пользователю как оформление его письма.
3. Просьба переоформить узлы, которые следуют общим стилям — сначала число. Посчитай, на сколько других элементов повлияет правка общих стилей, назови число и спроси: править общие стили или отвязать названные узлы. «Во всём письме», «все кнопки» — выбор сделан: правь общие стили и назови число без вопроса.

Состояние общих стилей нужно только когда документ называет вид, и отдельного вызова не требует: формата нет или `No visual template was saved for …` — умолчания платформы; письмо в формате — пункт 2, только когда генератору нужны значения. Ответ инструмента большой; не вызывай его ради одного этого вопроса.

### 4. Подтверждение

Существенное изменение письма — новое письмо или выполненная правка, которую просил пользователь, — заканчивается предложением сохранить его, в том же ответе, что и предпросмотр. Перед `visual_template_save` нужно одно явное подтверждение версии, которую пользователь видел в последнем предпросмотре:

```text
- кампания: <имя и internalId, если нужно>
- A/B-вариант: <описание человеческим языком, показывай только если у кампании несколько вариантов>
- куда идёт правка: для неработающей кампании не называй — письмо одно; для работающей скажи прямо, что правка идёт в черновик, а не в письмо, которое клиенты получают сейчас
- изменение: короткое описание
- таргетинг: по каждому таргетированному блоку, словами — «<блок>» только «<сегменту>» / всем, кроме «<сегмента>»; новое письмо (первое сохранение в пустой формат или заменяющее письмо формата) без таргетинга, а сегменты, которых в разговоре не касались, — спроси один раз, должен ли какой-то блок идти только сегменту; «нет» держится до конца разговора
- общие стили: эта строка обязательна в **каждом** подтверждении и читается прямо из документа, а не из памяти о заданных вопросах — три взаимоисключающих случая:
  - в документе есть `<Theme>` → «общие стили письма задаёт этот документ»;
  - `<Theme>` нет, и узлы называют свой вид → «письмо сохраняется со своими стилями на каждом элементе»;
  - `<Theme>` нет и узлы вид не называют → «общие стили письма остаются как есть, узлы следуют им».

  Нет строки — подтверждение неполное. Отдельно от строки: если документ отвечает условию шага 5 из `mindbox-email/SKILL.md`, а предложение в этом разговоре ещё не сделано — сделай его прямо здесь, вместе с остальными параметрами сохранения: «Сохранить стили этого письма как его общие стили? Тогда заголовки и кнопки можно будет менять во всём письме сразу». Один разговор — один такой вопрос: ответ держится до его конца, и ни второе сохранение, ни правки его не повторяют
- существующее письмо: только если у формата уже был визуальный шаблон и выбрана замена — «письмо в формате заменяется полностью»
- перенос стилей: только если правка переносит стили узлов в общие стили письма — «стили переезжают в общие стили письма, вид не меняется; дальше их можно править во всём письме сразу»
- строка применения: только для работающей кампании — «клиенты увидят правку после её применения в редакторе»
```

О неоднозначной цели спрашивают раньше и отдельно от подтверждения записи.

### 5. Сохранение

1. **Одна правка — одна запись** в выбранную версию; никакого второго вызова с тем же JSX в другую версию. Настройки сохранённого шаблона попадают только в то сохранение, которое его применяет (`references/saved-template.md`). Перенос стилей в общие — это **одно** сохранение: `<Theme>`, узлы, которые стили покинули, и `themeVariant` в одном документе — сохранённые по отдельности, они оставляют письмо без вида в промежутке.
2. Существующий шаблон: `rowVersion` кампании и `visualTemplateRowVersion` версии, в которую пишешь. Инициализация: только `rowVersion` кампании. Черновик, который создаёт само сохранение, версии шаблона тоже не требует.
3. Возьми из ответа новые версии, состояние и ошибки валидации; версию кампании — по «Цепочке версий кампании»: она меняется и при отказе.
4. Отказ «версия, которую ты назвал, не та, что видит пользователь» — то же событие конкурентности, что `ChangeConflict` (§7). Инструмент называет правильную версию — бери её из текста отказа, а не из памяти.
5. **Частичный сбой на работающей кампании:** сохранение создало черновик, но запись письма в него не удалась; инструмент называет версию черновика и новый `rowVersion` кампании. Повтор идёт в ту версию с тем `rowVersion` и **без** `visualTemplateRowVersion`. Успех здесь подтверждает только ответ самого сохранения: черновик — копия активной версии и до любой записи показывает `Mindboxeditor`/`html: yes`.
6. **После первого сохранения инициализации** перечитай `campaign_get` и найди тот же `formatInternalId`. Успех только если он стал `Mindboxeditor` с `html: yes`. Остался `Rawhtml`/`html: no`, исчез или неясен — не говори «сохранено», не повторяй автоматически: сообщи, что шаблон не привязался; продолжай только через восстановление привязки (пункт 7) после `visual_template_get` и нового подтверждения.
7. **Шаблон сохранён, а кампания нет** (`The template itself WAS stored — only the campaign was not`): сохрани возвращённый `visualTemplateRowVersion`, не создавай новый шаблон. После свежего `campaign_get` и повторного §1, пункты 2–3, восстановление привязки сохраняет ровно тот же JSX с этой версией.

### 6. Отчёт после операции

1. Кампания и результат. Работающая кампания — назови следствие: правка ушла в черновик, клиенты по-прежнему получают прежнее письмо и увидят новое, когда черновик применят в редакторе.
2. Отдели ошибки валидации, которые были в исходном `campaign_get`, от тех, что внесла правка.
3. Частичный исход — не «сохранено»: шаблон сохранён без кампании (§5, пункт 7); создан черновик с прежним письмом (§5, пункт 5) — скажи, что появился черновик и клиентов это не затрагивает.
4. Кампания не готова к отправке — «Чего кампании ещё не хватает для отправки».
5. Ответ сохранения — главный результат. Перечитывай `campaign_get`/`visual_template_get`, только если ответ неполон, версия потеряна или она нужна следующей операции, — и всегда после первого сохранения инициализации.

### 7. `ChangeConflict`

`ChangeConflict` — событие конкурентности, а не способ узнать текущую версию. При конфликте перечитай `campaign_get` (§1, пункты 2–3: всё ещё правится отсюда, та же цель), затем `visual_template_get` и сравни свежий JSX с исходным снимком из §2, а не с отредактированным JSX.

- **Совпадает со снимком** — конфликт в метаданных кампании. Автоматического повтора нет: скажи, что кампанию изменили параллельно, назови, что разошлось, и спроси, применять ли правку поверх. После явного «да» — одна попытка с тем же JSX и свежими версиями; нового предпросмотра не нужно, если JSX не изменился. Второй конфликт — остановись.
- **Не совпадает** — остановись: «Шаблон изменился после того, как его прочитали. Сохранение остановлено, чтобы не перезаписать чужую правку». Никогда не повторяй, не перезаписывай и не сливай. Если пользователь хочет продолжить: свежий JSX → заново применить изменение → предпросмотр → подтверждение → сохранение.
- **Инициализация, до первого успешного сохранения** — снимка нет. Перечитай только `campaign_get` и найди тот же `formatInternalId`: продолжай, только если у него по-прежнему `html: no` с `Mindboxeditor` или `Rawhtml`, иначе остановись, как выше. Затем `visual_template_get`: шаблон появился — восстановление привязки с ним и его `visualTemplateRowVersion`; всё ещё нет — покажи неизменившуюся цель, получи новое подтверждение, одна повторная попытка инициализации со свежим `rowVersion` кампании. Второй конфликт — остановись.

## Смена типа шаблона

«Пересобери в визуальном редакторе», «переведи в HTML» — тип шаблона принадлежит формату и через MCP не меняется: инструмента нет, `visual_template_save` в `Rawhtml` с `html: yes` запрещён, а `htmlBody` умеет только обратное. Форматы одной кампании одного типа, поэтому искать внутри неё формат под другой маршрут бессмысленно. Отказ известен заранее, поэтому перебор инструментов, сохранение «на пробу» и повтор после отказа запрещены.

Единственный путь — новая кампания, в которой то же письмо сразу собирается в нужном редакторе; исходная остаётся нетронутой. Предложи это и жди явного согласия; без него ничего не создаётся. После согласия: «Новая кампания с нуля» с тем же `mailingKind`, перенос темы, отправителя и прехедера через `campaign_edit_content`, названия и UTM — через `campaign_edit`, затем визуальный маршрут. Исходник письма бери из `campaign_get` с `includeBodyForVariants`; не восстанавливай его по памяти. Скажи заранее, что получатели, сегмент, подписка и расписание не копируются, а табличная вёрстка и нестандартный HTML не переносятся в блоки редактора один в один.

## `campaign_edit`, `campaign_edit_content`, `campaign_create`

Для правки метаданных предпросмотра нет. Явная просьба с конкретной кампанией и точными новыми значениями считается подтверждением. Показывай точный дифф и спрашивай отдельно, если цель или значение вывел агент, если план изменился или выполняется только часть просьбы. Изменения расписания, флагов транзакционности и ограничений и игнорирования ограничений подтверждай всегда отдельно.

**До любой записи метаданных читай строку редактируемости в `campaign_get`.** Ни один из инструментов не используется, когда:

- строка говорит, что письмо отсюда не правится — такая кампания управляется целиком в редакторе;
- кампания работает («This campaign is working, and …»): тема, отправитель, прехедер и расписание существуют в единственном экземпляре — у них нет черновика, и правка доходит до клиентов сразу.

Тогда остановись и скажи пользователю править такую кампанию в редакторе, где видно, что именно уйдёт. Ограничение живёт здесь, а не в инструменте: инструмент такую правку примет. `htmlBody` — это письмо, а не поле: у него есть черновик, и на работающей кампании правка идёт туда, не меняя того, что отправляется.

### Цепочка версий кампании

`rowVersion` кампании — один токен для инструментов кампании и `visual_template_save`, а не `visualTemplateRowVersion`; каждая запись возвращает следующий.

1. **Версию двигает не только успех.** Сохранение, создавшее черновик на работающей кампании, и тестовая отправка из черновика перезаписывают кампанию до того, как исход известен: если инструмент назвал новый `rowVersion` кампании, бери его, успех или нет. Поэтому `campaign_send_test` из черновика — тоже запись в этой цепочке.
2. Токен потерян, ответ неполон, есть сомнения — перечитай `campaign_get` перед следующей записью.
3. **Конфликт версий** на `campaign_edit` или `campaign_edit_content` — как `ChangeConflict` (§7, «совпадает со снимком»), сравнивая изменяемые поля с прочитанными ранее.

### Новая кампания с нуля

1. Спроси **папку и бренд словами, а не идентификаторами**, и часовой пояс. Значения для `campaign_create` найди сам: `entities_list(entityType: "Folder")` возвращает `internalId` папки и её бренды, `entities_list(entityType: "Brand")` — системное имя бренда. Ничего не найдено или несколько кандидатов — покажи найденное и дай пользователю выбрать, но не проси диктовать GUID. Настройки, которые пользователь называет сейчас (`name`, UTM, расписание, ограничения), вносятся после создания; остальное — «Чего кампании ещё не хватает для отправки».

   **`mailingKind` — это решение, а не необязательное поле: вид не меняется после создания** — исправить может только новая кампания:

   - **`Automatic`** — автоматическая кампания («Автоматические кампании» в интерфейсе): отправляется сценарием в ответ на событие — брошенная корзина, просмотренные товары, приветствие, статус заказа, реактивация, день рождения, любое «когда клиент …». У такого письма есть данные события — заказ, корзина, просмотры.
   - **`Manual`** — массовая кампания («Массовые кампании» в интерфейсе): разовая отправка сегменту, запускаемая из интерфейса — акция, анонс, дайджест.

   Вид нельзя однозначно прочитать из запроса — задай один вопрос до создания. У кампании `Manual` нет события для чтения, поэтому параметры с пометкой *(только для автоматических)* и товарные строки, а также коллекции шаблонов редактора на механиках, которые смотрят на действие клиента (корзина, просмотренные товары, позиции заказа), там не имеют смысла; рекомендации и списки товаров работают в обоих. Письмо, опирающееся на данные события, требует `Automatic` — скажи это до создания.
2. `campaign_create` → сразу `campaign_get`; собранные поля вносятся инструментами, которые называет его описание; дальше следуй цепочке версий.
3. Тело письма: пустой формат (`html: no`) идёт через `visual_template_get` и ветку инициализации из §2, пункта 3. Формат не найден — не придумывай ID и не сохраняй «на пробу»: скажи, что формат нужно инициализировать в интерфейсе. Ссылка на кампанию возвращается с первым сохранением; до этого сообщай `internalId` и имя, но никогда не адрес, собранный вручную.
4. После сохранения письма — «Чего кампании ещё не хватает для отправки».

### Чего кампании ещё не хватает для отправки

После первого сохранения письма в кампанию, не готовую к отправке (`readyForSending: no` в `campaign_get`), и всякий раз, когда пользователь просит подготовить её к отправке, читай `campaign_get` и называй словами то, чего не хватает, предлагая заполнить доступное через MCP:

- **тема** — `subject: not set`: предложи тему, написанную по содержимому письма, и прехедер к ней; поставь их после согласия пользователя или его собственного варианта;
- **отправитель** — у новой кампании обычно уже есть отправитель бренда: назови его и оставь, если пользователь не хочет другого; `not set` — спроси имя и адрес, списка отправителей на выбор нет;
- **получатели** массовой кампании — `Recipients: not selected`: предложи сегмент или фильтр (`references/recipients.md`); автоматическая кампания берёт аудиторию из сценария;
- **ошибки валидации** кампании — назови каждую словами; ошибка про письмо идёт Генератору;
- расписание, если пользователь хочет дату.

Поля вносятся через `campaign_edit_content` и `campaign_edit` по цепочке версий. Тема подписки и сам запуск делаются в интерфейсе — скажи это в конце и предложи тестовую отправку письма.

### `campaign_edit_content`

`htmlBody` — только по явной просьбе о сыром HTML, никогда как запасной путь для `visual_template_save` и никогда не предлагается для письма, собранного в визуальном редакторе. Через навык правится только кампания с одним вариантом: несколько A/B-вариантов — остановись и направь в интерфейс.

Пиши отчёт как следствие, а не как версию: инструмент называет её отдельной строкой — передай её и не выдумывай другой случай. Кампания, закрытая для правки, отклоняет `htmlBody`; не предлагай «тогда тему» — такая кампания не правится вовсе, по запрету выше. Не очищай тему и прехедер до пустого или null — контрактом это не описано: сообщи ограничение и направь в интерфейс; не используй `preHeaderPresentationMode`.

## Тестовая отправка

Тестовое письмо — настоящая отправка на тестовых получателей сотрудников, а не предпросмотр. Уходит сохранённое содержимое выбранной версии, а не то, что в твоём контексте.

1. Правка ещё не сохранена — сначала сохрани её либо скажи прямо, что тест уйдёт без неё.
2. `campaign_test_recipients` → получателей явно выбирает пользователь, даже если кандидат один.
3. `campaign_send_test`. Несколько A/B-вариантов — выбирает пользователь. Работающая кампания — спроси, что показать: то, что клиенты получают сейчас, или черновик, и отправляй из этой версии. Передай, из какой версии ушло письмо.
4. «Is not ready for test sending» или черновик не готов — не повторяй: верни ошибку дословно и найди в `campaign_get`, чего не хватает (тема, отправитель, содержимое, DKIM). Предлагай тест из активной версии только на работающей кампании, где это видно.
5. «Ready» — не доказательство, особенно при `transactional: yes`: тогда платформа не проверяет ни ссылку на отписку, ни синхронизацию. Не подавай это как «письмо в порядке»: настоящая проверка — предпросмотр и тестовое письмо глазами. Транзакционная кампания правится по общим правилам.
6. Кампанию не удалось прочитать — инструмент отказывает; не вызывай его снова без адреса «всё равно отправить»: тест уйдёт из активной версии, а не из черновика, который правил пользователь. Скажи это и вернись к вопросу позже.
