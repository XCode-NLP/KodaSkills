# Документация провайдера Terraform

## Следуй этому порядку работы

1. Определи охват и цели документации.
- Соотнеси изменения в коде с точными целями документации: индекс провайдера, ресурсы, источники данных, эфемерные ресурсы, списочные ресурсы, функции, действия или руководства.
- Реши, откуда должен браться текст: из описаний схемы, из шаблонов или из того и другого.

2. Сначала напиши описания в схеме.
- Добавь в поля схемы точные описания для пользователя, чтобы сгенерированная документация соответствовала поведению.
- Формулируй конкретно: назначение аргумента, ограничения, значения по умолчанию, вычисляемое поведение.

3. Добавь или обнови файлы шаблонов в `docs/`.
- Создавай только файлы, соответствующие реализованным объектам провайдера.
- Используй рекомендованные HashiCorp пути шаблонов:
  - `docs/index.md.tmpl`
  - `docs/data-sources/<name>.md.tmpl`
  - `docs/resources/<name>.md.tmpl`
  - `docs/ephemeral-resources/<name>.md.tmpl`
  - `docs/list-resources/<name>.md.tmpl`
  - `docs/functions/<name>.md.tmpl`
  - `docs/actions/<name>.md.tmpl` (tfplugindocs генерирует документацию действий начиная с Terraform v1.14.0)
  - `docs/guides/<name>.md.tmpl`
- Держи шаблоны сосредоточенными на обзоре и примерах; подробности по каждому полю оставляй сгенерированным разделам.
- Держи примеры HCL в директории `examples/` — один пример на файл, подключаемый в шаблон через `tffile` — а не встраивай их прямо в шаблоны (см. «Соглашения о файлах примеров» в `references/hashicorp-provider-docs.md`). Примеры не должны содержать блоки `terraform`, `provider` и `output`.
- Для страниц действий следуй структуре из `references/hashicorp-provider-docs.md` (раздел «Страницы действий»): примеры должны показывать и блок `action`, и привязку жизненного цикла `action_trigger`, а у действий нет раздела атрибутов и выходных значений.

4. Сгенерируй документацию через `tfplugindocs`.
- Предпочитай настроенные в репозитории значения по умолчанию:
```bash
go generate ./...
```
- Иначе запусти генератор напрямую:
```bash
go run github.com/hashicorp/terraform-plugin-docs/cmd/tfplugindocs generate --provider-name <provider_name>
```
- Повторяй генерацию после каждой правки схемы или шаблона.

5. Проверь сгенерированный markdown.
- Убедись, что файлы в `docs/` соответствуют текущей реализации провайдера.
- Убедись, что примеры — валидный HCL и отражают текущие имена аргументов и атрибутов.
- Убедись, что семантика обязательности, необязательности и вычисляемости в документации совпадает с поведением схемы.

6. Перед выпуском примени правила публикации в Registry.
- Используй теги семантических версий с префиксом `v` (например, `v1.2.3`).
- Создавай теги выпуска из ветки по умолчанию.
- Держи `terraform-registry-manifest.json` в корне репозитория.
- Учитывай, что документация в Registry версионируется и переключается выбором версии.

7. При необходимости посмотри предпросмотр или разбери проблемы публикации.
- Когда риск неточности высок, используй процесс предпросмотра HashiCorp, чтобы увидеть отрисованную документацию до выпуска.
- Если документации нет в Registry, проверь формат тега, ветку, из которой создан тег, наличие файла манифеста и статус публикации провайдера.

## Соблюдай планку качества

- Документация должна соответствовать поведению; никогда не описывай неподдерживаемые аргументы и атрибуты.
- Примеры должны быть минимальными, реалистичными и запускаемыми.
- Терминология и именование должны совпадать в провайдере, ресурсах и источниках данных.
- Не дублируй сгенерированные блоки аргументов и атрибутов в ручных шаблонах.
- По возможности вноси изменения в документацию в том же pull request, что и изменения схемы или API.

## Загружай справочники по необходимости

- Читай `references/hashicorp-provider-docs.md` ради правил со ссылками на источники и официальных ссылок.
- Загружай только те разделы, которые нужны для текущего изменения, чтобы не раздувать контекст.
