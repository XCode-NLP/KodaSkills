# Схема документа аудита

Каноническая схема документа аудита возможностей. Каждый аудит, созданный
`wp-abilities-audit`, должен соответствовать этой схеме, чтобы последующие инструменты (люди,
проводящие ревью, агенты-исполнители и валидаторы вроде `wp-abilities-verify`) могли его
использовать без неожиданностей при разборе.

Готовый к копированию минимальный пример с возможностью чтения и возможностью записи лежит
ниже в разделе «Минимальный корректный пример».

## Раскладка файла

```
<output-dir>/<YYYY-MM-DD>-abilities-audit-<plugin-slug>.md
```

`<output-dir>` задаётся явно — его берут у пользователя, а не выводят догадкой. Типичные
значения — директория `plans/` в хранилище пользователя или отдельный репозиторий аудитов.
Записывать в рабочее дерево плагина не рекомендуется (загрязняет историю Git).

Тело документа состоит из двух частей:

1. Блок в ограждении ` ```yaml ` со структурированными полями (метаданные верхнего уровня плюс
   `proposed_abilities`, `excluded_from_mvp`, `surfaced_gaps`).
2. Текстовые разделы ниже: таблица «Опись контроллеров» и раздел «Заметки и неожиданности».

Над всем находится заголовок `Last updated: YYYY-MM-DD HH:MM`.

## Поля верхнего уровня (все обязательны)

| Поле | Тип | Описание |
|---|---|---|
| `plugin` | string | Слаг плагина (например, `my-plugin`, `tasks-plugin`, `notifications`). |
| `repo` | string | `Owner/Repository`. |
| `branch_audited` | string | Ветка Git, против которой выполнялся аудит. |
| `audited_at` | string | Дата в формате ISO (YYYY-MM-DD). |
| `auditor` | string | Имя аудитора и команда или контекст (например, `Your Name (Your Team)`). |
| `baseline_abilities` | integer | Сколько возможностей плагин уже регистрировал на момент аудита. Обычно 0. |
| `capability_gate` | string ИЛИ object | Барьер прав, в который разрешается базовый контроллер. Принимается либо одна строка (плагины с одним правом), либо объект `{read, write}` (барьеры на основе типа записи и другие составные). Механизмы см. в `capability-gate-tracing.md`. |
| `plugin_family` | string (необязательно) | Свободная классификация, полезная последующим читателям (например, `core-post-type`, `forms-engine` или собственное имя семейства проекта). Необязательно и задаётся пользователем — канонического перечисления нет. Последующие потребители считают неизвестные значения непрозрачными и не падают. |

### Представления `capability_gate`

Две законные формы, обе используются последующими инструментами:

```yaml
# Плагин с одним правом (одно право во всех контроллерах)
capability_gate: manage_options  # подтверждено в includes/admin/class-my-plugin-rest-controller.php, строка 64
```

```yaml
# Составной барьер чтения и записи (обычно нужен плагинам на основе типа записи;
# чтение и запись разрешаются в разные права)
capability_gate:
  read: read_private_pages
  write: edit_others_pages
  confirmed: true
  verified_at: "custom_post_type capability_type='page' → core post-type cap map (wp-includes/post.php map_meta_cap)"
```

Права конкретного плагина (например, `manage_woocommerce`, `edit_shop_orders` в WooCommerce)
столь же допустимы — подставляй права своего плагина. Контракт — это форма; конкретные имена
прав зависят от проекта.

В реальной практике встречается устаревшая составная строковая форма
(`"<read_cap> / <write_cap>"`), она принимается для обратной совместимости, но структурная
форма выше предпочтительна для новых аудитов.

## `proposed_abilities` — массив

Каждая запись:

| Поле | Тип | Описание |
|---|---|---|
| `name` | string | Kebab-case `<plugin-slug>/<ability>`. |
| `intent` | string | Одно предложение в форме вопроса пользователя. |
| `backing` | object или `null` | См. ниже. `null` отмечает возможность без эндпоинта в источнике (известный пробел). |
| `permission` | object или `null` | См. ниже. `null`, когда `backing` равен null. |
| `return_type` | string | Краткое описание (например, `WP_REST_Response (wrapping array)`). Только подсказка; машинно не разбирается. |
| `effort` | enum | `S`, `M` или `L`. |
| `annotations` | object | `{ readonly: bool, destructive: bool, idempotent: bool }`. Все три обязательны. |
| `notes` | массив строк | Подробности для исполнителя (параметры фильтров, крайние случаи, альтернативные источники). |
| `risks` | массив строк | Всё, что исполнитель обязан учесть (нет ключа идемпотентности, двухфазное поведение, `permission_callback => '__return_true'` на уровне REST, который нельзя копировать в возможность, и т.п.). |
| `use_case_fit` | string | Одно предложение, называющее человеческий или агентский процесс, которому служит возможность. Проверка контрактом сценария использования (см. `wp-abilities-api/references/domain-vs-projection.md`): если ни один человек не стал бы делать это намеренно через поддерживаемый интерфейс или процесс, запись, скорее всего, принадлежит `excluded_from_mvp`. |
| `side_effects` | массив строк | Побочные эффекты, которые путь источника выдаёт при каждом вызове: хуки телеметрии, строки журнала аудита, уведомления, записи в кэш. По одной короткой строке на эффект. Пустой массив (`[]`), когда источник только читает данные: это *сам по себе* важный факт, именно он открывает условное сокращение через делегирование в `wp-abilities-api/references/shared-core-service.md`. Непустой массив сообщает исполнителю (и последующим инструментам режима проверки), что этой возможности нужна форма общего сервиса, а не сокращение через делегирование REST. |
| `seed_data_needs` | string ИЛИ `null` | Одна строка, описывающая, какие представительные данные должны быть в тестовом окружении, чтобы возможность выполнилась через публичную границу и вернула что-то осмысленное (например, `"хотя бы одна сущность в основной таблице плагина"`, `"засев не требуется"`). `null`, когда аудитор ещё не определил форму засева; последующие инструменты режима проверки считают `null` поводом спросить исполнителя, а не угадывать. |
| `reference_ability` | bool (необязательно) | Если `true`, помечает возможность как эталонную реализацию — первую, которую исполнитель должен реализовать (самое маленькое, безопасное и полезное чтение). В одном аудите так может быть помечено ровно ноль или одна возможность. |

### Семантика `backing: null`

Возможность с `backing: null` — известный пробел (аудитор нашёл ценную возможность, у которой
пока нет эндпоинта в источнике). Схема допускает это как предупреждение, а не ошибку:

- возможность ОБЯЗАНА также присутствовать в `surfaced_gaps` с обоснованием в одну строку;
- исполнители останавливаются, чтобы это разрешить, а не угадывают источник;
- аудит при этом остаётся корректным: `backing: null` — намеренный вывод, а не отсутствующие
  данные.

### Объект `backing`

| Поле | Тип | Описание |
|---|---|---|
| `kind` | enum (необязательно, по умолчанию `rest_controller`) | Путь реализации, который возможность должна использовать или исследовать. Одно из `rest_controller`, `service`, `helper`, `data_store`. Если опущено, по умолчанию `rest_controller` для обратной совместимости с аудитами, написанными до появления этого поля. Значение сообщает последующим инструментам, применим ли шаблон делегирования из `wp-abilities-api/references/shared-core-service.md` (кандидат только `rest_controller`; остальные с самого начала выбирают форму общего сервиса). |
| `class` | string | Полное имя класса PHP (класс контроллера для `rest_controller`; класс сервиса, вспомогательной функции или хранилища данных для остальных значений). Может быть опущено при `kind: data_store`, когда источник — просто ключ опции, ключ метаданных записи или таблица без собственного класса. |
| `file` | string | Путь относительно корня плагина. |
| `method` | enum (обязательно при `kind: rest_controller`) | HTTP-метод: `GET`, `POST`, `PUT`, `DELETE`, `PATCH`. Не применимо, когда `kind` равен `service`, `helper` или `data_store`. |
| `route` | string (обязательно при `kind: rest_controller`) | Полный путь маршрута REST. Не применимо к не-REST значениям. |
| `route_registration_line` | integer ИЛИ `null` | Для `kind: rest_controller`: номер строки вызова `register_rest_route(` или `null`, когда маршрут унаследован. Для остальных значений опускается. |
| `callback` | string | Для `kind: rest_controller`: имя метода контроллера, обрабатывающего маршрут. Для `kind: service` и `kind: helper`: имя метода класса сервиса или вспомогательной функции. Для `kind: data_store`: имя операции (`get_option`, `get_post_meta`) или шаблон чтения таблицы; может быть опущено. |
| `callback_line` | integer ИЛИ `null` | Номер строки определения колбэка или метода, либо `null`, когда он унаследован или не применим. |
| `inherited_from` | string (необязательно) | Полное имя родительского класса, когда маршрут и/или колбэк унаследованы от класса вне репозитория плагина (например, `WP_REST_Posts_Controller` из ядра WordPress или базовый класс REST другого плагина для расширений). Сочетается с `null` в номерах строк. Позволяет последующим инструментам чисто пропустить шаг повторного grep. В первую очередь относится к `kind: rest_controller`. |

### Объект `permission`

| Поле | Тип | Описание |
|---|---|---|
| `source` | enum (необязательно, по умолчанию `rest_controller`) | Где живут канонические права для этого поведения — не всегда в `permission_callback` контроллера REST. Одно из `rest_controller`, `admin_action`, `service`, `domain_policy`, `post_type_map`, `none`. Если опущено, по умолчанию `rest_controller` для обратной совместимости. `admin_action` — для поведений с барьером `check_admin_referer` и `current_user_can` в обработчике админки; `service` — когда право обеспечивает общий метод; `domain_policy` — для плагинов со слоем политик и авторизации; `post_type_map` — для прав, разрешаемых через `map_meta_cap()` на заимствованной карте прав типа записи; `none` — для действительно публичного поведения. Сообщает исполнителю, может ли `permission_callback` возможности повторять колбэк REST или должен обращаться к другому источнику истины. |
| `callback` | string | Имя метода или функции, обеспечивающей право в записанном `source`. Для `source: rest_controller` это значение `permission_callback`. Для `source: admin_action` — функция или метод обработчика админки. Для `source: service` — метод сервиса, выполняющий проверку права. |
| `resolves_to` | string | Вызов или вызовы `current_user_can()`, в которые это в итоге разрешается. Для составных барьеров укажи оба (например, `"current_user_can('read_private_pages')` для чтения; `current_user_can('edit_others_pages')` для записи"). |
| `confirmed` | bool | `true`, если проверено по исходнику; `false`, если выведено предположением. |

## `excluded_from_mvp` — массив

Возможности, намеренно отложенные по причинам риска. Каждая запись:

| Поле | Тип | Описание |
|---|---|---|
| `name` | string | Предлагаемое имя возможности (kebab-case). |
| `reason` | string | Одно предложение о причине отсрочки. |

## `surfaced_gaps` — массив

Кандидаты MVP без эндпоинта в источнике (парные к `backing: null` выше) плюс ценные эндпоинты,
найденные при перечислении, которых нет в MVP, но которые стали бы хорошей будущей работой.
Каждая запись:

| Поле | Тип | Описание |
|---|---|---|
| `name` | string | Предлагаемое имя возможности. |
| `one_line_rationale` | string | Почему это было бы выгодно. |

## Текстовые разделы (обязательны)

### Опись контроллеров

Таблица Markdown со столбцами `Class | File | REST Base | Routes`. Должна перечислять каждый
контроллер, найденный при перечислении, даже те, что не обосновывают ни одну возможность MVP.
Это даёт ревьюерам полную картину и снимает вопросы «почему X нет в MVP?».

### Заметки и неожиданности

Свободный текст для всего, что не поместилось в структурированную схему: расхождения барьеров
прав между контроллерами, зашитые в код пути маршрутов, парные контроллеры с разной формой
вывода, двухфазная семантика эндпоинтов и любые суждения аудитора.

## Минимальный корректный пример

Готовый к копированию отправной пункт для нового аудита:

````markdown
---
Last updated: 2026-04-20 14:30
---

# Example Plugin Abilities — Phase 1 Audit

```yaml
plugin: example-plugin
repo: Owner/example-plugin
branch_audited: feat/abilities-example-plugin
audited_at: 2026-04-20
auditor: Your Name (Your Team)
baseline_abilities: 0
capability_gate: manage_options  # подтверждено в includes/rest-api/class-example-rest-controller.php, строка 32

proposed_abilities:

  - name: example-plugin/get-items
    intent: "Перечислить элементы с фильтрами (статус, владелец, диапазон дат), чтобы агент одним вызовом ответил на вопрос «какие элементы требуют внимания?»."
    backing:
      kind: rest_controller
      class: Example_REST_Items_Controller
      file: includes/rest-api/class-example-rest-items-controller.php
      method: GET
      route: /example/v1/items
      route_registration_line: 26
      callback: get_items
      callback_line: 52
    permission:
      source: rest_controller
      callback: check_permission
      resolves_to: "current_user_can('manage_options')"
      confirmed: true
    return_type: "WP_REST_Response (wrapping array)"
    effort: S
    annotations: { readonly: true, destructive: false, idempotent: true }
    notes:
      - "get_items(WP_REST_Request $request) требует WP_REST_Request; создай его в execute_callback возможности."
    risks: []
    use_case_fit: "Агент одним вызовом отвечает на вопрос «какие элементы требуют внимания сейчас?», не листая интерфейс."
    side_effects: []
    seed_data_needs: "есть хотя бы один элемент в любом статусе, кроме корзины"
    reference_ability: true

  - name: example-plugin/close-item
    intent: "Закрыть один элемент — терминальный, необратимый переход состояния."
    backing:
      kind: service
      class: Example_Items_Service
      file: src/Service/class-items-service.php
      callback: close
      callback_line: 88
    permission:
      source: service
      callback: Example_Items_Service::assert_can_close
      resolves_to: "current_user_can('manage_options')"
      confirmed: true
    return_type: "WP_REST_Response (updated item object)"
    effort: M
    annotations: { readonly: false, destructive: true, idempotent: false }
    notes:
      - "Закрытие терминально — эндпоинта переоткрытия нет."
    risks:
      - "У эндпоинта в источнике нет ключа идемпотентности; повторные POST могут дать несогласованный журнал аудита."
    use_case_fit: "Пользователь или агент закрывает устаревший элемент из процесса, который такие элементы показывает (список в админке, агент с ежедневной сводкой)."
    side_effects:
      - "вызывает действие `example_plugin/item_closed` (слушатели ниже по стеку могут отправить письмо)"
      - "пишет строку журнала аудита в `example_plugin_audit_log`"
    seed_data_needs: "один открытый элемент для закрытия; тест должен сохранить id элемента до вызова"

excluded_from_mvp:
  - name: example-plugin/delete-item
    reason: "Жёсткое удаление необратимо и не имеет эндпоинта отмены; отложить до проектирования мягкого удаления."

surfaced_gaps:
  - name: example-plugin/get-overview
    one_line_rationale: "Эндпоинт-обзор без аргументов, отвечающий на вопрос «каково текущее состояние всех элементов?», был бы самой полезной возможностью, но эндпоинта в источнике пока нет."
```

Каждый контроллер наследует `Example_Base_REST_Controller` и использует `check_permission`

считать единственным барьером.
````

## Известные ограничения

Описаны, чтобы у последующих навыков был явный контракт:

- **Строковая форма `capability_gate` с комментарием в строке** теряет данные при разборе
  строгими парсерами YAML (комментарии отбрасываются). Предпочтительна структурная форма
  объекта; строковая принимается для обратной совместимости.
- **Устаревшая составная строка `capability_gate`** — форма `"<read_cap> / <write_cap>`
  появилась раньше структурного объекта `{read, write}` и всё ещё принимается для обратной
  совместимости. Валидаторы (например, `wp-abilities-verify`) выдают по ней WARN, подталкивая к
  переходу на структурную форму, но НЕ дают FAIL. Новые аудиты должны использовать форму
  объекта.
- **`return_type` — только подсказка.** Текст для человека-аудитора, машинно не разбирается.
  Последующие навыки в любом случае проверяют во время выполнения `is_wp_error(...)` и
  `instanceof WP_REST_Response` независимо от того, что говорит это поле.
- **Номера строк устаревают.** `route_registration_line` и `callback_line` фиксируются во время
  аудита и могут со временем разойтись. Последующие навыки находят маршруты заново по паре
  `(class, callback)` и не полагаются на точные номера строк.
- **`inherited_from` и `null` в номерах строк** — канонический способ представить маршруты и
  колбэки, определённые в родительском классе вне репозитория плагина.
- **Инвариант `backing: null`.** Возможности с `backing: null` — намеренные пробелы и ОБЯЗАНЫ
  также присутствовать в `surfaced_gaps` по `name`. Валидаторы дают FAIL аудитам, где этот
  инвариант нарушен (`null` в backing без парной записи в `surfaced_gaps` означает
  несогласованный вывод аудита).
- **Поля готовности к реализации добавлены 2026-05-21.** `use_case_fit`, `side_effects` и
  `seed_data_needs` обязательны в схеме возможности с этой даты. В аудитах, написанных по более
  ранней редакции схемы, эти три поля отсутствуют. Валидаторы (например,
  `wp-abilities-verify`) выдают WARN об отсутствующих полях готовности к реализации, подталкивая
  заполнить их при следующем касании аудита, но НЕ дают FAIL — так же, как с устаревшим
  `capability_gate` выше. Новые аудиты ОБЯЗАНЫ заполнять все три.
- **`backing.kind` и `permission.source` добавлены 2026-05-21.** Оба необязательны со значением
  по умолчанию `rest_controller`, чтобы старые аудиты проходили проверку как есть. Новые аудиты
  ДОЛЖНЫ заполнять оба явно: `backing.kind`, чтобы записать, что за возможностью стоит
  контроллер REST, общий сервис, вспомогательная функция или хранилище данных (ответ определяет
  решение «делегировать или выделять сервис» в
  `wp-abilities-api/references/shared-core-service.md`); `permission.source`, чтобы записать,
  где живут канонические права (колбэк REST — частый случай, но бывают и действия админки,
  методы сервисов, предметные политики и карты прав типов записей). Валидаторы считают
  отсутствующее поле значением по умолчанию, а не ошибкой.
