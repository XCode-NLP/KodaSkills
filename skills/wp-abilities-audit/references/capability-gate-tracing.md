# Прослеживание барьеров прав

Как определить фактическое право (или права), на которых стоят контроллеры REST плагина. Поле
`capability_gate` в аудите и поле `permission.resolves_to` каждой возможности должны отражать
реальность, а не то, что написано в docblock контроллера.

Два частых механизма покрывают большинство плагинов. Опиши оба явно, чтобы аудитор не зашивал
допущения одного семейства плагинов.

## Механизм A — прямой (`check_permission()` возвращает одно право)

Базовый контроллер REST объявляет метод `check_permission()` (или `permissions_check()`),
который один раз вызывает `current_user_can('<some_cap>')`. Каждый маршрут контроллера
использует этот метод как `permission_callback`.

### Признаки

- У базового контроллера есть метод вида:
  ```php
  public function check_permission() {
      return current_user_can( 'manage_options' );
  }
  ```
- Контроллеры наследуют собственный базовый класс плагина, а не класс ядра WordPress на основе
  типа записи.
- `grep -n 'current_user_can' <base-controller>.php` даёт одно совпадение.

### Как проследить

```bash
# Найди базовый контроллер (обычно родитель каждого контроллера REST).
grep -rn 'extends .*REST_Controller' includes/ | head

# Прочитай его реализацию permission_callback.
grep -n 'check_permission\|permissions_check' <base-controller>.php
```

Проследи один раз: единственный вызов `current_user_can()` и есть барьер плагина.

### Как представить в аудите

```yaml
capability_gate: manage_options  # confirmed at includes/admin/class-<plugin>-rest-controller.php line 64
```

Права конкретного плагина (например, `manage_woocommerce` в WooCommerce для контекстов магазина
или `edit_pages` в Jetpack Forms) подставляются вместо `manage_options` без изменений формы.

## Механизм B — на основе типа записи (механизм прав CPT ядра)

Контроллер наследует класс ядра WordPress на основе типа записи, который передаёт управление
карте прав типа записи. Локального `check_permission()` нет: колбэк прав разрешается динамически
во время запроса в зависимости от контекста (чтение или запись) и объекта `cap` типа записи.

### Признаки

- Базовый класс контроллера — один из:
  - `WP_REST_Posts_Controller` — базовый класс REST типа записи в ядре;
  - его подкласс, внутри репозитория плагина или вне его.
- Локального `check_permission()` нет: колбэки прав наследуются.
- Тип записи зарегистрирован с `capability_type => '<cpt_or_shadow>'`, а карту прав разрешает
  `map_meta_cap()` ядра.

### Как проследить

```bash
# Найди регистрацию типа записи.
grep -rn "register_post_type\s*(\s*['\"]<cpt_name>['\"]" .

# Прочитай блок регистрации. Значимые поля:
#   - capability_type: тип, чью карту прав использует этот тип записи.
#     Пользовательский тип записи может объявить свои права или заимствовать
#     права другого типа (например, capability_type => 'page', чтобы
#     переиспользовать права страниц).
#   - capabilities: необязательные явные переопределения строк прав.
#   - map_meta_cap: преобразуются ли метаправа (read_post, edit_post) в
#     примитивные права (read_private_<type>s, edit_others_<type>s).
```

Динамическое разрешение обычно сводится к:

- **Контекст чтения** (GET списка или GET элемента): `current_user_can('read_private_<type>s')`
  или `current_user_can('read_<type>', $id)`;
- **Контекст записи** (POST, PUT, DELETE): `current_user_can('edit_<type>s')`,
  `current_user_can('edit_others_<type>s')` или `current_user_can('delete_<type>s', $id)`.

Эти два часто различаются: у плагинов на основе типа записи регулярно бывают разные права на
чтение и запись.

### Как представить в аудите

Используй структурную форму `{read, write}` из `audit-schema.md`:

```yaml
capability_gate:
  read: read_private_pages
  write: edit_others_pages
  confirmed: true
  verified_at: "custom_post_type capability_type='page' → core map_meta_cap (wp-includes/post.php) → primitive page caps"
```

В блоке `permission` каждой возможности выпиши оба вызова:

```yaml
permission:
  callback: get_items_permissions_check
  resolves_to: "WP_REST_Posts_Controller::get_items_permissions_check (inherited) → current_user_can('read_private_pages')"
  confirmed: true
```

Пример A — обычный плагин, заимствующий права страниц ядра. Пользовательский тип записи,
зарегистрированный с `capability_type='page'`, наследует карту прав страниц, поэтому чтения
стоят на `read_private_pages`, а записи — на `edit_others_pages`.

Пример B — боковая панель в стиле WooCommerce. `shop_subscription` в WooCommerce регистрируется
с `capability_type='shop_order'`, поэтому чтения стоят на `read_private_shop_orders`, а записи —
на `edit_shop_orders`. Механически это то же, что пример A; имена прав зависят от проекта.
WooCommerce также публикует вспомогательную функцию `wc_rest_check_post_permissions()`, которая
оборачивает тот же механизм ядра: функция удобна, но в основе лежит `map_meta_cap()` ядра.

## Форма составной строки (допускается, но не предпочтительна)

Некоторые ранние аудиты кодировали составные барьеры одной строкой с разделителем `/`:

```yaml
capability_gate: read_private_pages / edit_others_pages
```

Это принимается для обратной совместимости, но:

- последующим потребителям приходится эвристически делить по `/`;
- комментарии YAML после строки молча отбрасываются строгими парсерами, поэтому сведения о
  происхождении теряются;
- форма объекта `{read, write}` машинно разбирается и несёт `confirmed` и `verified_at` внутри
  себя.

Для любого нового аудита предпочитай структурную форму.

## Порядок работы — проследи источник прав для каждого предлагаемого поведения

Права возможности должны соответствовать предполагаемому барьеру плагина для предлагаемого
*поведения*, а не обязательно для маршрута REST. Часто `permission_callback` контроллера REST —
верный источник истины, но в некоторых плагинах канонические права живут в другом месте:
обработчик действия админки со своим блоком `check_admin_referer` и `current_user_can`, метод
сервиса или вспомогательной функции, который выполняет проверку до работы, слой предметной
политики и авторизации либо заимствованная карта прав типа записи, разрешаемая через
`map_meta_cap()` ядра. Аудит должен сохранить, где права живут канонически, чтобы исполнитель не
съехал молча к тому источнику, который случайно публикует уровень REST.

Для каждой предлагаемой возможности пройди цепочку один раз:

1. Определи *поведение*, которое публикует возможность, затем найди, где плагин обеспечивает
   права для этого поведения. Сначала проверь `permission_callback` контроллера REST; если
   колбэк REST равен `'__return_true'`, полностью делегирует или не соответствует
   предполагаемому барьеру поведения, ищи канонический источник в обработчике админки, методе
   общего сервиса, классе предметной политики или карте прав типа записи.
2. Запиши, где живёт барьер, в поле `permission.source` возможности согласно
   `audit-schema.md`: одно из `rest_controller`, `admin_action`, `service`, `domain_policy`,
   `post_type_map`, `none`. По умолчанию `rest_controller`; выбирай другое значение, когда
   канонический источник в другом месте.
3. Определи, барьер это механизма A (локальный метод, одно право) или механизма B
   (наследуемый, на основе типа записи, динамический).
4. Разреши до фактических вызовов `current_user_can()`. Для механизма B разреши И чтение, И
   запись, если возможность пересекает контексты.
5. Запиши в поле `permission.resolves_to` возможности дословно: строка должна читаться как
   настоящая трассировка, а не как сводка-догадка.
6. Добавь замечание о риске, когда канонический источник прав расходится с колбэком контроллера
   REST: `permission_callback` возможности должен обращаться к каноническому источнику (или
   повторять его проверку), а не копировать колбэк REST по привычке.
7. Если каждое поведение в плагине разрешается в одно и то же право (или одну и ту же пару
   `{read, write}`) в одном и том же источнике, подними его в верхнеуровневый
   `capability_gate`. Если какое-то поведение расходится по праву ИЛИ по источнику, запиши
   расхождение в «Заметки и неожиданности».

## Частая ловушка — `permission_callback => '__return_true'`

Публичные эндпоинты без аргументов иногда объявляют `permission_callback => '__return_true'` на
уровне REST (например, проверки статуса, перечисления, которые безопасно публиковать). Аудиту
всё равно нужен барьер:

- запиши значение уровня REST как есть (`resolves_to: "__return_true (public)"`), чтобы аудитор
  не скрывал реальность;
- добавь замечание о риске: регистрация **возможности** НЕ должна копировать `'__return_true'` —
  собственный `permission_callback` возможности должен соответствовать предполагаемому барьеру
  пользователя в плагине (например, `manage_options`, `edit_pages` или что использует твой
  плагин). Уровень возможностей — поверхность для агентов, и ему нужен этот барьер, даже когда
  лежащий в основе маршрут REST публичный.
