# Разработка на C/C++

Базовый стандарт языка зависит от проекта: смотри `CLAUDE.md` проекта, систему сборки (флаги `-std=`) или конфигурацию компилятора. Все правила предполагают 32-битную ARM-цель, если не сказано иное.

## Генерация кода

- Соблюдай стандарт языка, настроенный в проекте. Не предполагай значение по умолчанию.
- Когда заголовочный файл общий для единиц трансляции C и C++, никогда не определяй переменные в заголовке — даже со `static`. Используй `extern` в заголовке и ровно одно определение в одном `.c`-файле.
- `goto` допустим, когда упрощает очистку ресурсов или снижает сложность, но это инструмент сопровождения, а не первый выбор.
- Комментарии Doxygen размещай в заголовочных файлах. Файлы реализации держи сосредоточенными на поведении.
- Избегай встраиваемых функций в заголовках. Держи определения функций в файлах исходников, чтобы интерфейс оставался маленьким.
- В C лёгкие макросы и вспомогательные обёртки допустимы, если они простые, локальные и явно названы.

## Раскладка памяти

- Следи за всплесками локальных переменных внутри функций. Большие автоматические массивы, структуры и множество временных значений — это расход бюджета стека.
- Проектируй структуры с учётом и семантики, и байтового выравнивания. Для разбора протоколов, байтовых потоков и сетевых форматов делай упаковку и порядок байтов явными.
- Используй `pragma` или атрибуты упаковки только когда они соответствуют требованию формата передачи и явно задокументированы.
- Осторожно используй двойную точность и 64-битные целые на 32-битных целях. Операции над 64-битными объектами создают проблемы производительности, совместимости и атомарности, если ширина явно не требуется.
- Когда 64-битное значение пересекает границу задачи, прерывания или модуля, сделай шаблон доступа явным: копирование, разделение, защита или предотвращение разрыва.

## Куча и владение указателями

- Считай объекты в куче и состояние, которым владеют указатели, ресурсами, чувствительными к времени жизни.
- Делай владение, точку освобождения и правила инвалидации явными.
- Не сохраняй заимствованные указатели дольше времени жизни, которое гарантирует их валидность.
- Для кода с кучей или множеством указателей документируй условия инвалидации, чтобы будущие изменения случайно не использовали устаревшие объекты.

## Специфика встраиваемого C

### Доступ к регистрам оборудования

Регистры периферии, отображённые в память, обязаны быть `volatile`, иначе компилятор выбросит повторные чтения и записи. Используй указатель на `volatile`-структуру (шаблон CMSIS/HAL), а не простые приведения типов.

```c
// ПРАВИЛЬНО: volatile-указатель на структуру периферии
typedef struct {
    volatile uint32_t SR;   // Состояние @ смещение 0x00
    volatile uint32_t DR;   // Данные    @ смещение 0x04
    volatile uint32_t BRR;  // Скорость  @ смещение 0x08
    volatile uint32_t CR1;  // Управление @ смещение 0x0C
} UART_Regs;
#define UART2 ((UART_Regs *)0x40004400)

// ПЛОХО: нет volatile — компилятор может выбросить повторные чтения
#define UART_SR (*(uint32_t *)0x40001000)
while (UART_SR & TX_BUSY);  // при оптимизации может стать бесконечным циклом
```

### Размещение секций линкером

Используй `__attribute__((section(...)))`, чтобы разместить данные и код в конкретных областях памяти.

```c
// .noinit: значение сохраняется через сброс сторожевым таймером и системный сброс (но не через сброс питания)
uint32_t reset_reason __attribute__((section(".noinit")));

// .ramfunc: функция остаётся в RAM, чтобы выполняться во время программирования флеша
__attribute__((section(".ramfunc")))
void flash_program_word(uint32_t addr, uint32_t data) { /* ... */ }

// Буфер, доступный DMA: не должен попадать в CCM (тесно связанную память)
uint8_t dma_buffer[1024] __attribute__((section(".dma_ram")));
```

### Разделение путей, безопасных и небезопасных для ISR

Держи путь обработчика прерывания минимальным, а работу в контексте задачи выноси в отдельные функции-обёртки. Никогда не вызывай блокирующие функции из ISR.

```c
// Путь ISR: минимальный, без блокировок, примитивы RTOS с суффиксом FromISR
static void uart_rx_isr(void) {
    BaseType_t xHigherPriorityWoken = pdFALSE;
    xSemaphoreGiveFromISR(xUartSem, &xHigherPriorityWoken);
    portYIELD_FROM_ISR(xHigherPriorityWoken);
}

// Путь задачи: можно блокироваться, логировать, выделять память, разбирать
void uart_rx_process_task(void) {
    if (xSemaphoreTake(xUartSem, portMAX_DELAY) == pdTRUE) {
        parse_and_dispatch(uart_rx_buf);
    }
}
```

### Обработчик отказа Cortex-M (naked)

Обработчик HardFault обязан быть `__attribute__((naked))`, чтобы пролог компилятора не испортил указатель стека до того, как будет захвачен кадр исключения.

```c
// naked: без пролога — SP точно указывает на кадр исключения. Обязательно для обработчиков отказов.
__attribute__((naked)) void HardFault_Handler(void) {
    __asm volatile(
        "tst lr, #4\n"          // Проверяем бит 2 EXC_RETURN: MSP или PSP
        "ite eq\n"
        "mrseq r0, msp\n"       // Поток использовал MSP → читаем из MSP
        "mrsne r0, psp\n"       // Поток использовал PSP (RTOS) → читаем из PSP
        "b HardFault_HandlerC\n"
    );
}
```

## Рефакторинг

- Сохраняй ясность исходного замысла, меняя структуру. Рефакторинг должен улучшать связность, читаемость или сопровождаемость, не меняя поведение незаметно.
- Пропускай изменения «ради запаха», которые не улучшают существенно корректность, риск, сопровождаемость или ясность.
- Предпочитай небольшие точечные выделения крупным переписываниям. Разделяй по одной ответственности за раз.
- Переноси помощник в общий код только когда переиспользование реально, а поверхность зависимостей остаётся простой.
- Если блок короткий, но семантически ясный и используется в нескольких местах, вынеси его в интерфейс, названный по смыслу, а не по деталям реализации.
- Если модуль на C стало трудно держать читаемым без борьбы с языком, рассмотри рефакторинг на C++ — но спроси пользователя перед сменой языка.
- Меняя API или поток управления, сохраняй целыми три пути: нормальный, отказный и восстановительный. После изменения перепроверь все три.
- Если рефакторинг затрагивает владение, время жизни или выделение памяти, сверься с разделом о раскладке памяти.
