# Запрос проверки кода

Запусти субагента-ревьюера, чтобы он нашёл проблемы до того, как они разойдутся по всей работе. Ревьюер получает точно подготовленный контекст для оценки — никогда не историю твоей сессии.

**Главный принцип:** проверяй рано, проверяй часто.

## Когда запрашивать проверку

**Обязательно:**

- после каждой задачи в разработке через субагентов
- после завершения крупной возможности
- перед слиянием в основную ветку

**Необязательно, но полезно:**

- когда ты застрял (свежий взгляд)
- перед рефакторингом (снять исходное состояние)
- после исправления сложной ошибки

## Как запросить проверку

**1. Получи хэши коммитов:**

```bash
BASE_SHA=$(git rev-parse HEAD~1)  # или: git merge-base origin/main HEAD
HEAD_SHA=$(git rev-parse HEAD)
```

**2. Запусти субагента-ревьюера:**

Запусти субагента `general-purpose`, заполнив шаблон из [code-reviewer.md](code-reviewer.md).

**Подстановки:**

- `{DESCRIPTION}` — краткое описание того, что ты сделал
- `{PLAN_OR_REQUIREMENTS}` — что должно получиться
- `{BASE_SHA}` — начальный коммит
- `{HEAD_SHA}` — конечный коммит

**3. Действуй по замечаниям:**

- критические проблемы исправляй сразу
- важные проблемы исправляй до продолжения работы
- незначительные проблемы записывай на потом
- возражай, если ревьюер ошибается (с обоснованием)

## Пример

```
[Только что завершена задача 2: добавлена функция проверки]

Ты: Запрошу проверку кода, прежде чем продолжать.

BASE_SHA=$(git log --oneline | grep "Task 1" | head -1 | cut -d' ' -f1)
HEAD_SHA=$(git rev-parse HEAD)

[Запуск субагента-ревьюера]
  DESCRIPTION: добавлены verifyIndex() и repairIndex() с четырьмя типами проблем
  PLAN_OR_REQUIREMENTS: задача 2 из docs/superpowers/plans/deployment-plan.md
  BASE_SHA: a7981ec
  HEAD_SHA: 3df7661

[Субагент отвечает]:
  Сильные стороны: чистая архитектура, настоящие тесты
  Проблемы:
    Важное: нет индикаторов прогресса
    Незначительное: магическое число (100) для интервала отчётов
  Оценка: можно продолжать

Ты: [Исправляешь индикаторы прогресса]
[Переходи к задаче 3]
```

## Частые оправдания

| Оправдание | Действительность |
|--------|---------|
| «Я сам посмотрю дифф вместо запуска ревьюера» | Ты координатор. Разбор диффа своими силами сжигает окно контекста, которое нужно для управления работой. Запусти субагента-ревьюера: дифф и оценка останутся в его контексте, а тебе вернутся только замечания. |
| «Ревьюеру нужна вся история моей сессии, чтобы понять изменения» | Передай ему точно подготовленный контекст, а не историю сессии. Так ревьюер смотрит на результат работы, а не на ход твоих мыслей. |

## Тревожные сигналы

**Никогда:**

- не пропускай проверку из-за «всё же просто»
- не игнорируй критические проблемы
- не продолжай работу с неисправленными важными проблемами
- не спорь с обоснованными техническими замечаниями

**Если ревьюер ошибается:**

- возрази с техническим обоснованием
- покажи код и тесты, доказывающие работоспособность
- попроси уточнить
