# Принципы тестирования подробно

## Поведение против реализации

**Поведение** — это всё, что пользователь кода может наблюдать через тот интерфейс, которым он
действительно пользуется:

| Поверхность | Наблюдаемое поведение |
| ---------------- | ------ |
| Команда CLI | код выхода; stdout; stderr; документ `--json`; `code` в JSON-ошибке; файлы, записанные в HOME или в проекте; запросы, отправленные в Cloud; процессы и браузеры, которые она запускает |
| Функция библиотеки | возвращаемое значение; тип или `code` выброшенной ошибки; состояние, читаемое через публичный API; эффекты во внешних системах |
| HTTP-сервер | статус; тело ответа; заголовки; эффекты в его хранилищах или нижестоящих сервисах |

**Реализация** — всё остальное: приватные помощники, порядок внутренних вызовов, промежуточные
данные, какой модуль выполнил работу, сколько раз запускалась внутренняя функция.

Решает контракт, а не форма утверждения:

- «Запрос с таким телом дошёл до Cloud» — это поведение, потому что Cloud его видит.
  «`api.request` был вызван с такими аргументами» — это реализация, поскольку `api.request` — наша
  собственная обёртка, и снаружи её никто не видит.
- Вызывающие ветвятся по `error.code` (`deployment_not_found`), поэтому проверяй код. `message` —
  проза для людей; фиксируй её, только когда точная формулировка и есть требование.
- Пустой список — верное утверждение, когда требование звучит как «ничего не совпадает». Это
  пустое утверждение, когда тесту нужно просто «что-то вернулось».
- Инвариант тоже может быть поведением: «у каждой команды в `--help` есть диспетчер», «имена
  записей в dist остаются стабильными».

## Литеральные ожидаемые значения

Ожидаемое значение берётся из требования и выписывается в тесте.

```ts
// Плохо: ожидаемое значение берётся из проверяемого кода, поэтому ошибка в
// formatDeploymentList копируется в ожидание.
expect(stdout).toBe(formatDeploymentList(fixture) + "\n");

// Хорошо: читатель может сверить это со спецификацией глазами.
expect(stdout).toBe(
  "DEPLOYMENT\tSERVER\tSTATUS\tTRIGGER\tBRANCH\tCREATED\tERROR\n" +
    "12345678\tserver_1\tfailed\tmanual\tmain\t2026-07-24T00:00:00Z\tBuild failed\n",
);
```

То же касается переписанных констант. Копирование текста `HELP` в тест и сравнение с константой
`HELP` никогда не выполняет код, который его печатает. Запусти `mcp-use deployments --help` и
проверь, что выходит.

## Не подменяй то, что можно запустить

Моки скрывают ошибки, живущие в тех частях, которые они заменяют. Старый `deployments.test.ts`
заменял `cloud-api.js` через `vi.mock` и следил за `process.stdout.write`. Он не мог увидеть:

- URL, строку запроса и заголовки, которые отправлял CLI;
- как ошибки `--json` попадают в stderr и в код выхода;
- разбор аргументов в `bin/`;
- подключена ли команда к маршрутизатору вообще.

Запускай настоящее там, где это дёшево: собранный CLI в дочернем процессе, настоящие временные
директории, настоящий `git`. Подменяй только то, что нельзя запустить локально или чего нельзя
касаться из теста:

- **Manufact Cloud:** используй стенд с поддельным Cloud (см. `cli-and-cloud.md`).
- **GitHub и другие HTTP-сервисы:** локальный сервер `node:http` или поддельный исполняемый файл в
  `PATH`, который записывает свои аргументы. Тесты `watch-pr` в pstack — хороший образец: они
  кладут поддельный `gh` в PATH и запускают настоящий подпроцесс.
- **Браузер:** направь открыватель на поддельный исполняемый файл, который записывает URL.

Считай то, что получает подделка, частью утверждения. Если требование звучит как «перезапуск
отправляет id сервера и ветку», проверяй тело, которое получил Cloud.

## «Ничего не произошло» нужен положительный двойник

`expect(cloud.requests).toEqual([])` проходит точно так же, когда стенд подключён неверно и никогда
не мог увидеть запрос. Сочетай его с тестом в том же файле, где запрос действительно происходит и
виден. Здесь помогает стенд поддельного Cloud: каждый запрос, не попавший на зарегистрированный
маршрут, валит тест, поэтому регистрация только ожидаемых маршрутов сама по себе является проверкой
«ничего другого не произошло», а зарегистрированные маршруты доказывают, что подделка видит трафик.

## Чего избегать

- **Снимков человеческой прозы.** Они падают от любой правки формулировки и проходят при реальных
  регрессиях, спрятанных в большом блоке. Проверяй части, которые и есть контракт: формат таблицы,
  который разбирают скрипты, документ JSON, код ошибки.
- **Задержек и гонок по времени.** Никогда не делай `await sleep(…)` в надежде, что что-то
  завершилось. Жди выхода процесса или получения запроса подделкой. Если проверяемый код опрашивает
  с настоящей задержкой, держи число опросов небольшим (два ответа, а не десять), вместо того чтобы
  подменять таймеры в дочернем процессе.
- **Утверждений о данных, которые построил тест.** Если тест пишет фикстуру, а затем утверждает,
  что у фикстуры есть поле, проверяемый код не запускался.
- **Свободных утверждений.** `toContain("failed")` проходит для неверной строки, а `toBeTruthy()`
  проходит для неверного объекта. Используй самое строгое утверждение, которое позволяет контракт:
  `toBe`, `toEqual` или `toMatchObject` по значимым полям.
- **Избыточной фиксации.** `toEqual` по всему ответу API фиксирует поля, которых контракт не
  обещает. Для них используй `toMatchObject`, а `toEqual` — для документов `--json`, где каждое
  поле входит в контракт для агента.

## Когда модульный тест всё ещё уместен

Запуск CLI стоит около 100 мс. Чистую функцию с настоящим контрактом и множеством входных случаев
(разбор аргументов, нормализация путей, функция маскирования) можно проверять напрямую через её
экспортируемый API, при условии что:

- входы и выходы функции — то, на что полагаются вызывающие;
- тест по-прежнему проходит после любого рефакторинга, сохраняющего эти входы и выходы.

Если тесту нужен `vi.mock` наших собственных модулей, чтобы добраться до функции, проверяй через
команду.
