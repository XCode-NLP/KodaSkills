# Написание тестов

Тест — это утверждение о том, что код делает для людей и программ, которые им
пользуются. Пиши его так, чтобы он падал при поломке этого поведения и
продолжал проходить, когда меняются только внутренности. Если такой тест
написать нельзя, не пиши тест вовсе:
**отсутствие нового теста лучше плохого теста.**

## Правила

1. **Проверяй то, что могут наблюдать вызывающие.** Для командной строки это
   код возврата, стандартный вывод и вывод ошибок, `code` ошибки, по которому
   ветвятся вызывающие, состояние, которое они могут прочитать (файлы,
   конфигурация), и эффекты вне процесса, например запросы, которые получает
   облако. Это не приватные вспомогательные функции, не внутренний порядок
   вызовов и не то, какой модуль выполнил работу.
2. **Ожидаемые значения — буквальные, из требования.** Пиши
   `"12345678\tserver_1\tfailed"`, а не `formatRow(item)`. Никогда не вычисляй
   ожидаемое значение тем кодом, который проверяешь.
3. **Не подделывай то, что можно запустить.** Запускай настоящую командную
   строку, пиши настоящие файлы, запускай настоящий git. Подделывай только
   настоящие внешние границы (Manufact Cloud, GitHub, браузер). Что получает
   подделка — это тоже поведение, поэтому проверяй и его.
4. **Каждую проверку «ничего не произошло» дополняй случаем, когда это
   происходит.** Тест, проверяющий «запрос не отправлен», нуждается ещё и в
   случае, доказывающем, что тест способен увидеть запрос.
5. **Избегай** снимков человеческого текста, точных _сообщений_ об ошибках
   (проверяй `code`), пауз и гонок по времени, а также проверок данных,
   которые тест сам и построил.

## Порядок работы

1. Назови наблюдаемое поведение, которое покрывает тест.
2. Проведи собранную командную строку через запуск в настоящем процессе и подделку облака.
3. Проверь вывод, код возврата, файлы и запросы, полученные подделкой.
4. Пересобери после правок исходников, затем запусти нужные тесты и проверку типов.
