# Аутентификация

## Выбор интеграции

Настраивай OAuth, когда сервер должен идентифицировать вызывающих или авторизовывать доступ по
пользователю, организации, роли, области действия или праву.

- Используй встроенный адаптер поставщика, когда поставщик идентичности поддерживает ожидаемый
  поток сервера ресурсов и динамической регистрации клиентов.
- Используй `oauthCustomProvider` из `mcp-use/oauth` для другого совместимого поставщика.
- Используй помощники прокси и верификатора OAuth, когда вышестоящий сервер авторизации работает
  с заранее зарегистрированными учётными данными, а не с динамической регистрацией клиентов.
- Смотри объявления установленных адаптеров и актуальную документацию поставщика, чтобы узнать
  обязательные параметры и переменные окружения.

Импортируй адаптеры по явным подпутям:

```ts
import { MCPServer } from "mcp-use";
import { oauthAuth0Provider } from "mcp-use/oauth/auth0";

const server = new MCPServer({
  name: "secure-server",
  version: "1.0.0",
  oauth: oauthAuth0Provider({ domain: process.env.AUTH0_DOMAIN! }),
});
```

В рабочем окружении проверяй конфигурацию при запуске, а не полагайся на утверждения о ненулевом
значении.

## Используй проверенную идентичность запроса

Когда OAuth настроен, колбэки получают:

- `ctx.auth.user`: нормализованная поставщиком проверенная идентичность. У встроенных
  пользователей есть `id`; необязательные поля различаются.
- `ctx.auth.scopes`: предоставленные области из проверенных данных аутентификации.
- `ctx.auth.permissions`: сопоставленные поставщиком права приложения.
- `ctx.auth.payload`: проверенные утверждения или данные самоанализа.
- `ctx.auth.accessToken`: bearer-токен, только для намеренного делегирования ниже по стеку.
- `ctx.auth.clientId`, `expiresAt` и `resource`, когда доступны.

Авторизовывай конкретное действие, а не просто проверяй, что пользователь существует:

```ts
async ({ documentId }, ctx) => {
  if (!ctx.auth.permissions.includes("documents:delete")) {
    return {
      isError: true,
      content: [{ type: "text", text: "Forbidden" }],
    };
  }

  await deleteOwnedDocument(documentId, ctx.auth.user.id);
  return { content: [{ type: "text", text: "Document deleted" }] };
};
```

Предпочитай нормализованные поля пользователя. Читай сырые утверждения из payload, только когда
поставщик не сопоставляет нужное проверенное значение.

## Границы безопасности

- Никогда не считай `ctx.client.user()`, локаль, местоположение, субъект, идентификатор беседы и
  другие метаданные запроса аутентифицированной идентичностью.
- Держи авторизацию рядом с чувствительными операциями или в узко ограниченном промежуточном ПО
  MCP.
- Передавай токен доступа только намеченному вышестоящему ресурсу и никогда не логируй и не
  возвращай его.
- Не включай секреты клиента, токены, полные утверждения и payload поставщика в примеры, журналы,
  содержимое инструментов, структурированный вывод, `_meta` и состояние представления.
- Храни состояние между запросами во внешнем доверенном хранилище. Используй проверенное состояние
  запроса для чувствительных сценариев уточнения; не выводи непрерывность из глобальных переменных
  модуля и деталей транспорта.
