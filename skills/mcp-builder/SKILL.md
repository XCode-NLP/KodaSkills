# Разработка на mcp-use

Источник истины — установленный пакет `mcp-use`, его экспортируемые типы, сгенерированные объявления и существующий код проекта. Прежде чем выбирать API или менять код, изучи установленную версию.

## Порядок работы

1. Изучи `package.json`, точку входа сервера, экспортируемые ссылки на инструменты, `mcp-env.d.ts`, `views/`, `skills/` и установленную версию `mcp-use`.
2. Создай заготовку нового стабильного проекта через `create-mcp-use-app@latest` с подходящим шаблоном. При работе с бета-версией, ночной сборкой или уже существующим проектом с закреплённой версией согласуй версию пакета или метку сборки.
3. Читай только те справочные материалы, которые нужны для задачи:
   - [Сервер](references/server.md) — инструменты, ресурсы, подсказки, промежуточный слой MCP, контекст запроса и оболочки результатов.
   - [Представления](references/views.md) — интерактивные приложения MCP, хуки React, контекст модели, возможности хоста, ресурсы, CSP и работа с доменами эндпоинтов и интерфейса.
   - [Аутентификация](references/auth.md) — провайдеры OAuth, подтверждённая личность, области доступа, разрешения и авторизация.
   - [Навыки поверх MCP](references/skills-over-mcp.md) — когда сервер должен поставлять повторяемые сценарии вместе со своими инструментами.
   - [Продвинутые возможности](references/advanced-features.md) — OpenAPI, проксирование, уведомления, подписки и запрос уточнений.
   - [Перенос](references/migration.md) — только если в коде есть устаревшие импорты, вспомогательные функции, формы регистрации, шаблоны интерфейса или допущения о сессиях, оставленные для совместимости.
   - [Проверка](references/verification.md) — перед тем как сообщить о завершении работы.
4. Реализуй, опираясь на установленные типы. Предпочитай текущие соглашения библиотеки скопированным примерам и старым спискам изменений.
5. Проверь наименьший настоящий жизненный цикл, доказывающий изменённое поведение, затем расширяй проверки соразмерно риску.

## Основные инварианты

- Импортируй API сервера из `mcp-use`, API React из `mcp-use/react`, а адаптеры провайдеров OAuth — из их подпутей `mcp-use/oauth/*`.
- Описывай аргументы инструментов через `inputSchema`. Добавляй `outputSchema` для структурированных результатов и для каждого инструмента, привязанного к представлению.
- Возвращай исходные оболочки результатов MCP. Успешный инструмент со схемой обязан содержать соответствующий `structuredContent`; ожидаемый сбой может вернуть `isError: true` с понятным модели `content`.
- Размещай каждое представление в `views/<name>/view.tsx` и привязывай его через `view: { name: "<name>" }`.
- Экспортируй каждую статически объявленную ссылку на инструмент, которую использует представление. Экспортируй по умолчанию точку входа сервера, которую используют `mcp-use dev`, `build` и `start`.
- Держишь личность и изменяемое состояние сценария в пределах запроса или во внешнем хранилище. Метаданные, сообщённые клиентом, считай непроверенными.
- Рассмотри навыки поверх MCP, если сервер предоставляет повторяемый многошаговый сценарий, который иначе раздул бы описания инструментов.

## Ограничения

- Не выдумывай экспорты, поля конфигурации и формы обратных вызовов. Неясные детали уточняй по установленным объявлениям или исходному коду.
- Не сохраняй API, которых нет в установленной версии, только потому, что они встречаются в существующем проекте.
- Не возвращай из обратного вызова инструмента обычный предметный объект.
- Не привязывай представление без соответствующего `outputSchema` и результата `structuredContent`.
- Не используй глобальные переменные модуля для личности между запросами, непрерывности уточнений или долговечного состояния бизнес-логики.
- Не заявляй об успехе на основании одной сборки из исходников, если менялись типы, экспорты пакета, аутентификация или интерактивное поведение.
- Не развёртывай и не меняй внешние системы без явной просьбы пользователя.
