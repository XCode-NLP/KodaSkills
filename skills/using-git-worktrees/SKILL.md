# Работа с git worktree

## Обзор

Добейся, чтобы работа шла в изолированной рабочей области. Сначала используй родные инструменты твоей платформы. К ручному созданию worktree через git переходи только тогда, когда родного инструмента нет.

**Главный принцип:** сначала проверь, есть ли изоляция. Затем используй родные инструменты. Затем git. Никогда не иди против своей среды.

**Объяви в начале:** «Использую навык using-git-worktrees, чтобы подготовить изолированную рабочую область».

## Шаг 0: проверь, есть ли изоляция

**Прежде чем что-то создавать, проверь, не работаешь ли ты уже в изолированной области.**

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)
```

**Защита от подмодулей:** условие `GIT_DIR != GIT_COMMON` выполняется и внутри подмодулей git. Прежде чем решить, что ты «уже в worktree», убедись, что это не подмодуль:

```bash
# Если вернулся путь, ты в подмодуле, а не в worktree — считай это обычным репозиторием
git rev-parse --show-superproject-working-tree 2>/dev/null
```

**Если `GIT_DIR != GIT_COMMON` (и это не подмодуль):** ты уже в связанном worktree. Переходи к шагу 2 (подготовка проекта). НЕ создавай ещё один worktree.

Сообщи о состоянии ветки:

- на ветке: «Уже в изолированной рабочей области `<путь>`, ветка `<имя>`.»
- отделённый HEAD: «Уже в изолированной рабочей области `<путь>` (отделённый HEAD, управляется извне). Ветку нужно будет создать при завершении.»

**Если `GIT_DIR == GIT_COMMON` (или это подмодуль):** ты в обычной рабочей копии.

Указал ли пользователь в инструкциях, какой worktree ему нужен? Если нет, спроси согласие, прежде чем создавать worktree:

> «Подготовить изолированный worktree? Он защитит твою текущую ветку от изменений.»

Если предпочтение уже объявлено, не спрашивай. Если пользователь отказался, работай на месте и переходи к шагу 2.

## Шаг 1: создай изолированную рабочую область

**У тебя есть два механизма. Пробуй их в этом порядке.**

### 1a. Родные инструменты worktree (предпочтительно)

Пользователь согласился на изолированную область (шаг 0). Есть ли у тебя способ создать worktree? Возможно, это инструмент с названием вроде `EnterWorktree`, `WorktreeCreate`, команда `/worktree` или флаг `--worktree`. Если он есть, используй его и переходи к шагу 2.

Родные инструменты сами размещают каталог, создают ветку и убирают за собой. Если ты вызываешь `git worktree add`, хотя родной инструмент доступен, возникает невидимое состояние, которым среда не может управлять.

Переходи к шагу 1b, только если родного инструмента нет.

### 1b. Запасной вариант через git worktree

**Используй это, только если шаг 1a не применим** — родного инструмента нет. Создай worktree вручную через git.

#### Выбор каталога

Соблюдай такой порядок. Явное пожелание пользователя важнее наблюдаемого состояния файловой системы.

1. **Проверь инструкции на указанный каталог worktree.** Если пользователь его назвал, используй без вопросов.

2. **Проверь, есть ли уже каталог worktree в проекте:**

   ```bash
   ls -d .worktrees 2>/dev/null     # предпочтительно (скрытый)
   ls -d worktrees 2>/dev/null      # альтернатива
   ```

   Если найден — используй его. Если есть оба, побеждает `.worktrees`.

3. **Если других указаний нет**, используй по умолчанию `.worktrees/` в корне проекта.

#### Проверка безопасности (только для каталогов внутри проекта)

**ОБЯЗАТЕЛЬНО убедись, что каталог игнорируется, прежде чем создавать worktree:**

```bash
git check-ignore -q .worktrees 2>/dev/null || git check-ignore -q worktrees 2>/dev/null
```

**Если каталог НЕ игнорируется:** добавь его в `.gitignore`, закоммить изменение и продолжай.

**Почему это важно:** так ты не закоммити содержимое worktree в репозиторий.

#### Создание worktree

```bash
# Определи путь по выбранному расположению
path="$LOCATION/$BRANCH_NAME"

git worktree add "$path" -b "$BRANCH_NAME"
cd "$path"
```

**Если песочница мешает:** если `git worktree add` падает с ошибкой доступа (запрет песочницы), сообщи пользователю, что песочница заблокировала создание worktree, и ты работаешь в текущем каталоге. Затем выполни подготовку и проверку исходного состояния на месте.

## Шаг 2: подготовка проекта

Определи подходящую подготовку и выполни её:

```bash
# Node.js
if [ -f package.json ]; then npm install; fi

# Rust
if [ -f Cargo.toml ]; then cargo build; fi

# Python
if [ -f requirements.txt ]; then pip install -r requirements.txt; fi
if [ -f pyproject.toml ]; then poetry install; fi

# Go
if [ -f go.mod ]; then go mod download; fi
```

## Шаг 3: проверь исходное состояние

Запусти тесты, чтобы убедиться, что рабочая область чистая:

```bash
# Используй команду, подходящую проекту
npm test / cargo test / pytest / go test ./...
```

**Если тесты падают:** сообщи о сбоях и спроси, продолжать или разбираться.

**Если тесты проходят:** сообщи о готовности.

### Отчёт

```
Worktree готов: <полный путь>
Тесты проходят (<N> тестов, 0 сбоев)
Можно реализовывать <название возможности>
```

## Краткая справка

| Ситуация | Действие |
|-----------|--------|
| Уже в связанном worktree | Не создавать (шаг 0) |
| В подмодуле | Считать обычным репозиторием (проверка на шаге 0) |
| Есть родной инструмент worktree | Использовать его (шаг 1a) |
| Родного инструмента нет | Запасной вариант через git worktree (шаг 1b) |
| Есть `.worktrees/` | Использовать (проверить игнорирование) |
| Есть `worktrees/` | Использовать (проверить игнорирование) |
| Есть оба | Использовать `.worktrees/` |
| Нет ни одного | Проверить файл инструкций, затем `.worktrees/` |
| Каталог не игнорируется | Добавить в `.gitignore` и закоммитить |
| Ошибка доступа при создании | Запрет песочницы: работать на месте |
| Тесты падают на исходном состоянии | Сообщить о сбоях и спросить |
| Нет `package.json` или `Cargo.toml` | Пропустить установку зависимостей |

## Частые оправдания

| Оправдание | Действительность |
|--------|---------|
| «Я явно не в worktree, проверять незачем» | Выполни шаг 0. Изоляция, созданная средой, и подмодули одинаково обманывают глаз; решают команды проверки. |
| «`git worktree add` быстрее, чем искать родной инструмент» | Родной инструмент (например, `EnterWorktree`) отвечает за размещение, ветку и уборку. Обход его — ошибка номер один: появляется невидимое состояние, которым среда не управляет. |
| «Каталог worktree наверняка уже игнорируется» | Запусти `git check-ignore`. Неигнорируемый каталог worktree закоммитит всё дерево в репозиторий. |
| «Подойдёт любое имя каталога» | Явные инструкции важнее существующего каталога в проекте, а он важнее значения по умолчанию `.worktrees/`. |
| «Рабочая область свежая, тесты можно потом» | Грязное исходное состояние делает любой последующий сбой неоднозначным. Запусти тесты сейчас; продолжать при сбоях решает твой собеседник. |
