# Справочник по доступам в API Kaiten

Этот навык помогает выбрать возможности CLI и передать уже выбранные цели, роли и параметры. Бизнес-правила, разбор спецификаций, сравнение с целевым состоянием, планирование и оркестрация выполнения остаются за внешними агентами и обвязкой. Не добавляй эти механизмы в CLI и не выводи сам, какой доступ должен быть у человека.

Передавай `--locale ru` для разговора на русском и `--locale en` в остальных случаях, перед именем команды, включая поиск инструментов. Предпочитай `--json`. Изучи семейство один раз через `search-tools`, `describe` и `examples`, прежде чем его использовать.

## Выбор маршрута

Предпочитай документированные API с https://developers.kaiten.ru/:

- `tree-entities list`: объекты, читаемые владельцем токена, а не инвентарь компании.
- `space-users list/add/update/remove`: назначения в пространствах.
- `company-groups.*`, `group-users.*`, `group-entities.*`: группы компании, состав и доступ групп к сущностям. Назначения групп используют `entity_uid` и `role_ids` (массив UUID).
- `group-entities list --limit 100 --offset 0` читает одну страницу назначений; для ограниченного полного списка используй `group-entities list-all --group-uid <uuid> --page-size 100 --max-pages 100`. Это агрегирует тот же документированный GET. Повторяющиеся UID, некорректные или слишком большие страницы и полная страница на пределе запроса явно приводят к ошибке. Серверы должны соблюдать limit и offset; запасной устаревший путь не используется. Параллельные изменения могут сдвигать страницы, так что это не атомарный снимок. `--fields` и `--compact` формируют локальный вывод после загрузки всех страниц и не уменьшают тело HTTP-ответа. Пагинация, временная выдача и отзыв доступа в группах и очистка были проверены на живом контуре обычным API-токеном 2026-11-04.
- `roles list`: доступные роли доступа по UUID.
- `company-users update`, `company-groups create/update`: административные `permissions` или `named_permissions`; один формат на запрос.
- `spaces.*`, `documents.*`, `document-groups.*`: операции с сущностями, включая размещение через `parent_entity_uid`, где это описано командой.

Где документированные маршруты не дают нужной операции, явно выбирай эти недокументированные расширения обычного API-токена:

- `admin-tree-entities list/list-all`: административные метаданные. `list` использует `parent_uid`, а не `parent_entity_uid`; для инвентаря компании пропускай `user_id`. `list-all` даёт ограниченную плоскую пагинацию, а не транзакционный снимок.
- `document-users`, `document-group-users`, `story-map-users`: `list/add/update/remove` прямых назначений.
- `space-access-groups`, `document-access-groups`, `document-group-access-groups`, `story-map-access-groups`: `list` доступа групп.
- `roles get/create/update/delete`: определения ролей доступа по UUID.
- `story-maps list/get/create/update/delete`: базовые операции со стори-мапами.

26 расширенных команд были проверены на живом контуре обычным API-токеном в авторизованной тестовой компании 2026-11-04, включая выдачу, отзыв и очистку. Создание стори-мапа подставляет недостающий sort_order как метку времени Unix, как и создание документа. Другие версии сервера всё равно требуют проверки совместимости. Смотри заметки о версиях и правах в `describe`. Сохраняй ошибки 401, 403, 404 и 405; не повторяй через сессии браузера, API супер-администратора, другой маршрут или самовыдачу. Заблокированный сервером `PATCH /admin-tree-entities` не предоставляется.

## Параметры и права

- Идентификаторы пользователей числовые. Прямые назначения используют `role_id` (UUID); группы — `role_ids` (массив). `roles` управляет доступом к сущностям; числовые `user-roles` относятся к табелю и не взаимозаменяемы.
- Команды пользователей пространства и карты принимают числовые `space_id` и `map_id`. Команды пользователей документов и папок принимают UUID `document_uid` и `group_uid` (второй — это папка). Любая `*-access-groups list` принимает UUID объекта `entity_uid`.
- Административному перечислению нужны `entitiesTree` или `members`. Управление пользователями документов, папок и карт требует `access_control` или `entitiesTree` у объекта. Назначения групп и запись своих ролей требуют `members` и соответствующих модулей. Создание, перемещение и удаление сущностей проверяет свои права на источник и цель.
- Токен не даёт дополнительных прав; `profile probe` только проверяет авторизацию. Доступность модулей и лицензий отдельна от прав. Требования к приглашениям смотри в заметках команд; ни одно имя роли не гарантирует все операции.
- `include_inherited_access=true` запрашивает унаследованный доступ. `own_role_ids` описывает прямые роли пользователя, `role_ids` может включать унаследованные роли пользователя. Роли групп отдельны: `own_groups_role_ids` — прямые, `groups_role_ids` — с наследованием. Эти массивы могут быть null. `role_permissions` описывает действующие права. CLI возвращает результаты сервера, а не вычисленный список доступа. Удаление одного назначения может оставить доступ через другую группу, родительский объект или режим «всем». Перемещение меняет наследование; правка общей роли влияет на все её назначения. Автор вложенного объекта может иметь только унаследованный доступ; перенос в корень или закрытие доступа может вернуть 400, если не останется ни одного управляющего доступом. Любая прямая выдача по решению вызывающего — отдельная команда, а не автоматический запасной вариант.
- Созданию роли нужен полный серверный JSON `permissions`. Обновление роли сливает переданные ключи; для удаления права используй явный `false`. Защита системных и заблокированных ролей и требования к замене остаются на стороне сервера.
- Именованные права компании — частичные карты: пропущенные имена сохраняются. `false` убирает прямой грант, но не грант другой группы. Сравнивай `own_named_permissions` и действующие `named_permissions`; неизвестные имена сервер может проигнорировать. Никогда не отправляй числовой и именованный форматы вместе. На тестовой компании запись именованных прав временному виртуальному пользователю вернула HTTP 500. Успех записи прав пользователя компании остаётся непроверенным; не повторяй неоднозначное изменение, не прочитав его состояние.

Примеры (замени заглушки на цели, уже выбранные вызывающей стороной):

```bash
kaiten --locale ru --json --read-only document-users list --document-uid <uuid> --include-inherited-access true
kaiten --locale ru --json document-users add --document-uid <uuid> --user-id 123 --role-id <role_uuid>
kaiten --locale ru --json document-users update --document-uid <uuid> --user-id 123 --role-id <role_uuid>
kaiten --locale ru --json group-users add --group-uid <user_group_uuid> --user-id 123
kaiten --locale ru --json group-entities add --group-uid <user_group_uuid> --entity-uid <uuid> --role-ids '["<role_uuid>"]'
kaiten --locale ru --json story-maps update --map-id 10 --parent-entity-uid <folder_uuid>
```

Для реальных записей следуй навыку [kaiten-cli-mutations](../kaiten-cli-mutations/SKILL.md) и соблюдай авторизацию, уже полученную под текущую задачу. Этот справочник не даёт права на записи.
