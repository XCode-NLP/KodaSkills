# Фаза 3 — Design (тип и схема интеграции)

При входе проверь свежесть данных навыка (SKILL.md, «Свежесть данных»).

Цель: принять проектные решения самостоятельно на основе брифа и
выбранных функций (STATE, раздел «Функции», фаза 2) и получить
одобрение пользователя на короткую спеку. Не устраивай пользователю опрос
по каждому пункту — реши сам, покажи результат.

## Решение 1. Тип интеграции

| Если… | Тип |
|---|---|
| Платформа со своим бэкендом/API, нужна связка «документ ↔ оплата ↔ статус» для многих клиентов | Standalone middleware |
| Код должен жить внутри CMS (WordPress, 1С-Битрикс, Opencart…) | Плагин CMS |
| Продукт-приложение с собственным UI (мини-приложение, WebApp) | Мини-приложение |
| Сайт/лендинг, нужно просто принимать оплату на странице | Платёжный виджет |
| Мерчант без разработки, готовой интеграции нет | No-code: виджет, ссылки, связки из каталога |

## Решение 2. Режим оплаты

- `do=link` — ссылку нужно сохранить и доставить (CRM, письмо, чат);
  генерация на сервере.
- `do=pay` — покупатель уходит на оплату из браузера (CMS, сайт);
  payload подписывается полем `signature`.
- Виджет — оплата прямо на странице сайта.
- Автоплатежи — если в брифе есть подписки/рекуррентные списания.

Детали протокола — `references/payform-protocol.md`.

## Решение 3. Схема данных и поток

Спроектируй по `references/architecture-patterns.md`:

- где хранится связка «документ ↔ ссылка ↔ статус» (mapping);
- как обеспечивается идемпотентность (повторный webhook, пересоздание ссылки);
- журнал обмена;
- если мультитенантность — сущность тенанта и ввод реквизитов
  (payform_url + secret_key через validateSecretKey);
- страница ожидания оплаты, если покупатель возвращается в браузере.

## Решение 4. 54-ФЗ

Определи номенклатуру чека: name/price/quantity + осознанное решение про
НДС и признаки расчёта (`tax`, `payment_object`, `payment_method`) — по
брифу или одним вопросом пользователю.

## Результат: короткая спека

Собери документ (0.5–1.5 страницы): тип, режим оплаты, поток данных
(текстовая диаграмма «событие → ссылка → оплата → webhook → отражение»),
схема хранения, идемпотентность, 54-ФЗ, ограничения (например, «webhook
принимать не можем — используем polling»).

Сохрани как `.prodamus/SPEC.md` (в чат-режиме — блоком), покажи пользователю
целиком и получи одобрение — ничего не реализовывать до него
(`references/dev-practices.md` §1). Правки — внеси и покажи снова.

Обнови STATE → переходи к `phases/04-sys.md`.

Исключение — короткий маршрут: если выбран тип «готовая интеграция из
каталога», «виджет» или «no-code», фазы 4–6 не нужны (отдельный sys не
требуется — работает payform клиента). Помоги пройти инструкцию/установить
виджет, затем сразу лёгкая проверка результата: тестовая оплата и
подтверждение, что статус дошёл куда нужно. Обнови STATE и завершай.
