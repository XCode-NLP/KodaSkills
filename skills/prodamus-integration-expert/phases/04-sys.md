# Фаза 4 — SYS (идентификатор интеграции)

Цель: получить от Prodamus подтверждённый `sys`-идентификатор и реквизиты
для тестирования.

`sys` — идентификатор интеграции в payload оплаты; согласуется с Prodamus.

При точечном входе (фазы 1–3 не пройдены) сначала собери у пользователя
минимум: платформа, тип интеграции, режим оплаты, нужен ли каталог. Это
и есть «спека» для заявки.

## Шаг 0. Проверка каталога (железное правило 3)

Если это первый контакт с платформой (фаза 1 не проходилась) — проверь
каталог существующих интеграций (`references/help-prodamus-map.md`, при
сети — живая страница). Платформа уже в каталоге → **сначала предложи
готовую интеграцию**, а не новое имя sys; собственную продолжай только по
осознанному решению пользователя (зафиксируй в STATE). Без сети — пометь
в STATE: «каталог проверен офлайн, перепроверить по живой странице».

## Шаг 1. Кандидат sys

Предложи кандидата по конвенции:

- латиница, snake_case (дефис допустим, если так читаемее);
- по имени платформы, коротко: `webasyst`, `wordpress-woo`, `moysklad`;
- без версий, дат и слова «prodamus».

Если для платформы уже есть интеграция, а пользователь осознанно делает
свою — возьми имя с уточнением (например, `<платформа>_<продукт>`).

## Шаг 2. Заявка в поддержку

Заполни `templates/sys-request.md` (кандидат sys, краткое описание
интеграции — из спеки, а при точечном входе из собранного минимума;
контакты автора) и отдай пользователю готовое
сообщение для отправки в поддержку Prodamus — бот в MAX
(**https://max.ru/id1215156909_2_bot**) или сообщество ВКонтакте (**https://vk.ru/prodamuspay**).

Отправляет пользователь сам. Попроси вернуться с ответом поддержки.

## Шаг 3. Фиксация ответа

Из ответа поддержки зафиксируй в STATE:

- подтверждённый `sys` (или новый кандидат, если занят — вернись к шагу 1);
- адрес тестового payform;
- **secret_key — НЕ в STATE и не в файлы репозитория**: попроси пользователя
  положить его в env/секрет-хранилище, в STATE запиши только «где лежит»
  (имя переменной);
- каким ключом будут подписаны webhook по этому sys — доменным secret_key
  или отдельным сервисным (вопрос есть в шаблоне заявки; ответ определяет
  env-переменную WEBHOOK_SECRET — см. payform-protocol.md, раздел Webhook).

## Не блокируйся (марафон)

Пока ждём ответа поддержки, продолжай фазы 5 (Plan) и 6 (Build) с
плейсхолдером `sys=TBD`. Фаза 7 (Verify) требует реальных реквизитов —
там ожидание блокирует.

Обнови STATE → в марафоне переходи к `phases/05-plan.md`; при точечном
входе — остановись: сообщи пользователю, что дальше (дождаться ответа
бота, вернуться с реквизитами).
