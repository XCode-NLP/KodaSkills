# Архитектурные паттерны интеграции

Рекомендации, проверенные на боевых интеграциях Prodamus. Стек пользователя —
приоритет: переноси паттерны, а не технологии. Пункты из
`security-checklist.md` — обязательны всегда, остальное адаптируй.

## Структура проекта

Эталонная раскладка отдельного сервиса-интеграции. Пример на Laravel, но
переносится сама раскладка, а не имена файлов: разделение «контроллеры →
use-case-сервисы → транспортные клиенты → фоновые задачи» работает на любом
стеке.

```
app/
  Enums/
    PaymentStatus.php               # pending / paid / error / refunded
    DocumentType.php                # типы сущностей платформы
  Http/
    Controllers/
      SettingsController.php        # подключение мерчанта и настройки
      WebhookController.php         # входящие события платформы
      ProdamusWebhookController.php # уведомления об оплате от Prodamus
      PaymentLinkController.php     # ручная выдача ссылки (опционально)
    Middleware/
      RemoveFrameOptions.php        # если настройки открываются в iframe
      VerifyPlatformAuth.php        # проверка подписи запросов платформы
  Jobs/
    GeneratePaymentLinkJob.php
    ProcessProdamusPaymentWebhookJob.php
  Models/                           # см. «Стандартные хранимые сущности»
    Merchant.php                    # тенант
    PayformCredential.php           # реквизиты Prodamus, свои у каждого тенанта
    PaymentLinkMapping.php          # документ ↔ ссылка ↔ статус оплаты
    WebhookLog.php                  # журнал обмена
  Services/
    <Platform>/Client.php           # транспорт: API платформы
    Prodamus/
      ProdamusClient.php            # создание ссылки, проверка реквизитов
      ProdamusHmac.php              # sign / verify — подключить обязательно
    Integration/                    # use-case'ы: единственное место бизнес-логики
      MerchantConnectionService.php
      PaymentLinkService.php
      PaymentRegistrationService.php
config/
  integration.php                   # вся параметризация интеграции — в одном месте
tests/                              # HMAC на тест-векторах, оба webhook'а, онбординг
```

Ориентиры:

- Вся специфика интеграции — в одном конфиг-файле двумя секциями
  (`<платформа>.*` и `prodamus.*`): базовые URL, ключи, лимиты попыток.
  Секреты — из переменных окружения, в коде и репозитории их нет.
- Тесты живут рядом с кодом и пишутся вместе с ним, а не после
  (`dev-practices.md`, §3).
- Плагин внутри CMS такой структуры не заводит: каркас, точки входа и
  хранилище настроек диктует движок (хуки и классы платёжного шлюза), своей
  БД, очередей и `.env` нет. Из этого справочника для него действуют разделы
  про подпись, идемпотентность и страницы ожидания.

## Слои

```
Контроллер webhook (тонкий, без бизнес-логики):
  найти тенанта → проверить подпись ЕГО ключом → записать в журнал →
  поставить обработку в очередь → сразу ответить
  (webhook Prodamus — строго HTTP 200, см. payform-protocol.md;
  webhook платформы — по её контракту)
Сервисы use-case (единственное место бизнес-логики):
  создать ссылку, зарегистрировать оплату, подключить мерчанта
Транспортные клиенты (Prodamus, платформа):
  только HTTP и маппинг ошибок; не знают про БД и очереди
Фоновые задачи:
  достать данные → вызвать сервис → обработать ретраи
```

Порядок «тенант → подпись» принципиален: секрет для verify — per-tenant,
поэтому тенанта нужно определить ДО проверки. Стандарт мультитенантных
интеграций — секретный токен в пути webhook-URL:
`/webhook/prodamus/{random48}`; неизвестный токен → 404 без лога.

Если у платформы нет очередей (плагин внутри CMS) — webhook обрабатывается
синхронно, идемпотентность обеспечивается средствами CMS (например,
«если заказ ещё не оплачен — отметить оплаченным» + собственная метка).

## Идентификатор заказа (order_id)

- Самоописывающий ключ `{тип}:{id}` (`invoiceout:{uuid}`, `record:{123}`):
  если mapping потерян, заказ восстанавливается парсингом `order_num` —
  stateless-fallback регистрации оплаты.
- Либо детерминированный: `sha256(uuid:number)[0:32]` — идемпотентная
  регенерация и однозначная корреляция.
- Плюс страховка: свой ID в query-string `urlNotification` — Prodamus
  вернёт его при POST.

## Стандартные хранимые сущности

Названия условные — адаптируй к своей схеме:

| Сущность | Ключевые поля | Назначение |
|---|---|---|
| merchant | ID аккаунта платформы (unique), токен доступа (шифрованно), is_active | Тенант — подключённый аккаунт |
| payform_credential | payform_url, secret_key (шифрованно), validated_at | Реквизиты Prodamus, вводит клиент |
| payment_link_mapping | document_type + document_id (unique вместе с merchant), payment_url, prodamus_order_id (индекс), payment_status, content_hash | Связка «документ ↔ ссылка ↔ статус» |
| webhook_log | source, event_type, status (received/rejected/processed/skipped/failed), payload, error_message | Журнал обмена — главный инструмент разбора инцидентов; rejected — не прошла подпись |

Деньги — DECIMAL/строки, не float. Уникальные ограничения — на уровне БД.

## Идемпотентность

- `content_hash` (например, sha256 от суммы и состава товаров): документ не
  изменился → ссылку не пересоздавать.
- Unique-ограничение (merchant, document_type, document_id) — вторая линия.
- Регистрация оплаты: статус уже «оплачен» → ранний выход (webhook Prodamus
  может прийти повторно — это норма).
- Побочные действия (уведомления, доступы) — только на первом переходе
  в конечный статус (`wasCompleted`/`shouldNotify`-паттерн; сбой
  уведомления не должен откатывать транзакцию — оборачивай в try/catch).
- Ключ идемпотентности: если планируешь обрабатывать смену статусов по
  одному платежу (отмена после оплаты) — включай `payment_status` в ключ,
  иначе unique по `payment_id` проглотит второе событие.
- Долгие многошаговые эффекты (выдача доступов, создание сущностей) —
  с инкрементальной фиксацией прогресса после каждого шага: ретрай
  продолжает, а не дублирует. Плюс лок «один платёж — один обработчик»
  (по ключу merchant+order_id). Ручное решение оператора (`manual`) —
  приоритетнее позднего автоуспеха.
- Подписка на webhook платформы — идемпотентная: ошибка «уже существует»
  считается успехом (у МойСклад это коды 30003/30007 — узнай аналог своей
  платформы).
- Частичный PUT в платформу может затирать смежные поля (эхо-массивы
  услуг/товаров считаются авторитетными) — возвращай в PUT всё, что
  получил, меняя только своё.

## Журнал обмена

Пиши запись на каждом шаге: received → processed / skipped / failed
(с текстом ошибки); запрос с неверной подписью — rejected. Секреты и персональные данные в журнал не попадают
(см. security-checklist.md). Это основной инструмент поддержки при разборе
«оплата прошла, а заказ не закрылся».

## Мультитенантность и онбординг мерчанта

- Одна инсталляция обслуживает много клиентов; тенант уникален по ID
  аккаунта внешней платформы.
- Установка через marketplace платформы: lifecycle-хуки install/uninstall →
  создать/деактивировать тенанта идемпотентно.
- Ввод реквизитов Prodamus: клиент вводит payform_url + secret_key →
  проверить через `validateSecretKey` → сохранить шифрованно с отметкой
  validated_at. Домен payform валидировать по белому списку
  (`payform-protocol.md`).
- Если UI встраивается в iframe платформы: снять X-Frame-Options / настроить
  CSP frame-ancestors, проверять подпись контекста iframe от платформы.

## Страницы ожидания (две разные!)

1. **Ожидание webhook об оплате**: покупатель возвращается с payform раньше
   webhook. Боевые числа: таймер 300 с (кламп 30–3600), опрос каждые 4 с,
   мгновенный redirect если уже оплачено, по таймауту — «проверить ещё
   раз / назад». Эндпоинт статуса скоупь секретом заказа (order_key).
   Не показывай «оплачено» до webhook.
2. **Ожидание генерации ссылки**: если ссылка создаётся в очереди, отдай
   мгновенный стабильный URL `/pay/{id}` — страница опрашивает готовность
   каждые 2 с (до ~30 попыток), затем redirect на оплату.

Краевой случай: остаток к оплате ≤ 0 (доплат нет) — проектируй явно
(«всё оплачено», ссылку не создавать), а не хаком в типе возврата.

## Ретраи фоновых задач

Экспоненциальный backoff, ограничение попыток, фиксация неудачи в журнале.
Боевые значения: обработка webhook — 5 попыток, 60/300/900/1800/3600 с;
генерация ссылки — 3 попытки, 30/120/300 с (ей незачем ждать час).
Prodamus сам ретраит webhook при не-200 — используй это при временных
сбоях. Тонкости очередей: timeout job'а меньше retry_after очереди;
срок лока ≥ срока жизни job.

## Онбординг marketplace — проверенные факты

- Ответы платформ бывают неожиданными: у YClients успешная регистрация
  callback — это HTTP 301 (нужен запрет follow-redirect и success<400);
  у МойСклад активация требует ответа `"status":"Activated"` на PUT.
- Подпись iframe-контекста платформы считается иногда от ДЕКОДИРОВАННОГО
  JSON, а не от base64-строки — проверяй оба варианта.
- JSON-тело POST не попадает в `$_REQUEST`; наличие cookie делает
  `$_REQUEST` непустым — читай php://input явно.
