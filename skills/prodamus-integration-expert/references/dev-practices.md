# Дисциплина разработки

Дистиллировано из открытого набора практик Superpowers (лицензия MIT,
Авторские права (C) 2025 Jesse Vincent) и адаптировано
под платёжные интеграции. Фазовые файлы ссылаются сюда; эти правила
обязательны при любом профиле пользователя. Нарушение буквы правила —
нарушение его духа: «в этот раз можно» — это рационализация, а не причина.

## §1. Бриф и дизайн до кода (фазы 1–3)

Ничего не реализовывать, пока дизайн не показан пользователю и не одобрен.
Это касается ЛЮБОЙ интеграции, даже «очевидной»: на простых проектах
непроверенные допущения стоят дороже всего.

- Вопросы — по одному за сообщение. Предпочитай варианты выбора открытым
  вопросам.
- Сначала собери контекст сам (документация, репозиторий, каталог
  интеграций) — спрашивай только то, чего не нашёл.
- Красные флаги, при которых остановись — ты рационализируешь:
  «это слишком просто для дизайна», «сначала быстренько посмотрю код»,
  «начну писать, а бриф потом», «пользователь и так всё сказал».
- Спека показывается целиком и получает явное «да». Правки → показать снова.

## §2. Письменный план (фаза 5)

План пишется так, будто исполнитель не знает ни проект, ни домен.

- Шаг = одно действие на 2–5 минут с проверяемым результатом: «написать
  падающий тест X», «запустить, убедиться что падает», «минимальный код»,
  «прогнать, зелёное», «закоммитить».
- В каждом шаге: точные пути файлов, точные команды, ожидаемый вывод.
- Запрещённые конструкции (это дыры плана, а не пункты): «TBD», «доделать
  потом», «добавить обработку ошибок» без кода, «написать тесты» без
  текста тестов, «аналогично шагу N».
- Самопроверка перед показом: каждый пункт спеки покрыт шагом? плейсхолдеров
  нет? имена/сигнатуры между шагами совпадают?

## §3. TDD (фаза 6)

Железный закон: **нет продакшен-кода без падающего теста, написанного
раньше него.** Написал код до теста — удали и начни с теста. Не «оставлю
как референс» — удали.

Цикл RED → GREEN → REFACTOR:

1. **RED**: один минимальный тест на одно поведение, с говорящим именем.
2. **Проверить RED — обязательно**: запусти и убедись, что тест падает
   по ожидаемой причине (нет функциональности), а не из-за опечатки.
   Тест сразу прошёл? Он ничего не проверяет — почини тест.
3. **GREEN**: минимальный код до зелёного. Ничего «на вырост» (YAGNI).
4. **Проверить GREEN — обязательно**: тест прошёл, остальные не сломались,
   вывод чистый (без варнингов).
5. **REFACTOR**: только на зелёном; поведение не менять.

Для интеграции Prodamus это означает конкретно:

- Первый тест проекта — HMAC на тест-векторах из `hmac.md` + негативный
  (чужой секрет → false). Пока не зелёный — дальше не идти.
- Внешние HTTP — только моки/фейки; но тесты проверяют СВОЙ код, а не мок
  («мок вызвался 3 раза» — плохой тест; «повторный webhook не создал второй
  грант» — хороший).
- Нашёл баг → сначала падающий тест, воспроизводящий его, потом фикс.
  Баг без теста не чинится.

Рационализации и ответы на них:

| Отговорка | Реальность |
|---|---|
| «Слишком просто, чтобы тестировать» | Простое тоже ломается. Тест — 30 секунд |
| «Напишу тесты после» | Тест, прошедший сразу, ничего не доказывает |
| «Я уже проверил руками» | Разово ≠ систематически: нет записи, нельзя перезапустить |
| «Удалять N часов работы жалко» | Sunk cost. Непроверенный код — долг, а не актив |
| «TDD догматичен, я прагматик» | Прагматично — не дебажить оплату в проде |

## §4. Верификация до «готово» (фаза 7)

Железный закон: **никаких заявлений об успехе без свежего доказательства.**
«Должно работать», «наверное, ок», «выглядит правильно» — запрещённые слова.

Порядок перед любым «готово/работает/исправлено»:

1. Определи команду, которая доказывает утверждение.
2. Выполни её полностью, сейчас (не «в прошлый раз проходило»).
3. Прочитай весь вывод, включая код возврата.
4. Вывод подтверждает? Заявляй ВМЕСТЕ с доказательством. Нет — честно
   назови фактическое состояние.

Чем доказываются типовые заявления интеграции:

| Заявление | Доказательство |
|---|---|
| «Подпись проверяется» | Запрос с битой подписью → 4xx + запись rejected (вывод) |
| «Идемпотентность есть» | Два одинаковых webhook → один эффект (тест/журнал) |
| «Оплата работает» | Сквозной прогон в demo_mode: журнал received→processed, статус изменился |
| «Тесты проходят» | Вывод прогона: 0 падений, только что |
| «Регрессия закрыта» | Red-green: фикс откатил → тест упал; вернул → прошёл |
| «Субагент сделал» | Свой diff/прогон, а не отчёт субагента |

## §5. Разбор инцидентов (после запуска)

Железный закон: **не чинить, пока не найдена причина.** Починка симптома —
это провал: маскирует проблему и добавляет новую.

Порядок для «оплата прошла, а заказ не закрылся» и любых сбоев:

1. **Прочитай ошибку и журнал обмена целиком** — там часто готовый ответ
   (webhook пришёл? подпись прошла? на каком шаге failed?).
2. **Воспроизведи**: тот же payload (captured-фикстура) на dev — стабильно
   ли ломается?
3. **Что менялось**: последние деплои, конфиги, смена ключей (сервисный vs
   доменный — частый случай!), изменения на стороне платформы.
4. **Инструментируй границы**: платформа → интеграция → Prodamus; на каждой
   границе залогируй вход/выход (без секретов) и найди слой, где данные
   ломаются. Чини источник, а не место падения.
5. Причина найдена → падающий тест на неё (§3) → фикс → зелёное →
  captured-фикстура в регрессию.

Под давлением («почини СРОЧНО») соблазн угадывать растёт — а систематический
разбор быстрее перебора догадок. Две неудачные попытки фикса подряд —
верный признак, что причина не найдена: вернись к шагу 1.
