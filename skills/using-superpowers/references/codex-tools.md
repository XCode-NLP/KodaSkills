## Запуск субагентов требует поддержки нескольких агентов

Добавь в конфигурацию Codex (`~/.codex/config.toml`):

```toml
[features]
multi_agent = true
```

Это включает инструменты для нескольких агентов, которые используют навыки
`dispatching-parallel-agents` и `subagent-driven-development`. Какие именно инструменты ты
получишь, зависит от версии поддержки нескольких агентов, которую выбирает твой пресет модели
(текущие пресеты работают на V2, более старые — на V1). Верь своему фактическому списку
инструментов, а не любой таблице — включая эту, — если они расходятся.

- **Запуск:** давай детям чистый контекст через `spawn_agent {fork_turns: "none"}`; значение по
  умолчанию `"all"` копирует в ребёнка всю твою переписку. В Codex 0.145+ файлы ролей в
  `~/.codex/agents/` привязываются к изолированным форкам через `agent_type`. Форки с полной
  историей принимают переопределения `model` и `reasoning_effort` (там отказывают только в
  `agent_type`) — изолированные форки являются умолчанием SDD ради чистоты контекста, а не потому,
  что переопределения их требуют.
- **Раунды исправлений:** возобновляй исполнителя через `followup_task` — он доставляет твоё
  сообщение, запускает ход и прозрачно перезагружает ребёнка, которого вытеснила обвязка. Никогда
  не запускай нового исполнителя из предположения, что запущенному агенту нельзя написать снова:
  на V2 можно всегда.
- **Жизненный цикл:** в V2 нет `close_agent`. Завершённые дети вытесняются автоматически, когда
  нужны слоты; оставлять их незакрытыми ничего не стоит. Только в сеансах V1 есть `close_agent` —
  там закрывай ревьюеров, когда их ревью вернулось, и каждого исполнителя после того, как ревью его
  задачи пройдено.
- **Имена моделей:** никогда не копируй имя модели из навыка, таблицы или старого сеанса в
  `spawn_agent`, не сверив его с текущим белым списком запуска: V2 принимает только пресеты,
  поддерживающие V2, и жёстко ошибается на остальных.

## Ожидание детей

`wait_agent` — это подписка на события, а не опрос: долгое ожидание просыпается в момент, когда
ребёнок проявляет активность в почтовом ящике, с той же задержкой, что и короткое. Опрос с коротким
таймаутом ничего не даёт и стоит вызова инструмента — и повторной оплаты контекста — на каждый
опрос. В измеренных сеансах примерно две трети всех вызовов ожидания были короткими опросами,
которые истекли.

- Пока у тебя есть локальная работа, не жди вовсе. Финальный ответ завершённого ребёнка
  отправляется в твой почтовый ящик и приходит со следующим твоим ходом.
- Когда ты действительно простаиваешь с незавершёнными детьми, жди ограниченными отрезками:
  `wait_agent` с `timeout_ms` 300000–600000 (5–10 минут). После каждого отрезка — по пробуждению
  или по таймауту — напиши одну строку статуса, выполни `list_agents` и проверь любого ребёнка,
  который завершился без отчёта. Никогда не ставь опросы короче пяти минут: подписка на события
  будит ограниченный отрезок так же быстро, как короткий.
- Письмо о завершении не может разбудить простаивающего контроллера (оно доставляется без запуска
  хода); покрыть это окно простоя — единственная задача `wait_agent`. Отрезок, истёкший без
  активности, — повод сверить состояние, а не сократить следующий отрезок.

## Маршрутизация моделей при запуске

Каждый `spawn_agent`, который ты выполняешь — включая случаи, когда ты сам запущенный ребёнок,
раздающий задачи, — задаёт `model` И `reasoning_effort` явно, согласно правилам выбора модели из
навыка, который ты исполняешь. Указать только `model` — ловушка: усилие ребёнка молча
сбрасывается к значению по умолчанию этой модели, а не к твоему.

Попроси собеседника добавить машинную страховку в `~/.codex/config.toml`, чтобы любой
пропущенный запуск всё равно попадал на осознанно выбранный уровень, а не наследовал молча самую
дорогую модель сеанса:

```toml
[agents]
default_subagent_model = "<a mid-tier model from your spawn allowlist>"
default_subagent_reasoning_effort = "medium"
```

## Определение окружения

Навыки, которые создают рабочие деревья или завершают ветки, должны определять своё окружение
командами git только для чтения, прежде чем продолжать:

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
BRANCH=$(git branch --show-current)
```

- `GIT_DIR != GIT_COMMON` → уже в связанном рабочем дереве (пропусти создание);
- `BRANCH` пуст → отсоединённый HEAD (нельзя создавать ветку, пушить и делать PR из песочницы).

Как каждый навык использует эти сигналы, см. в `using-git-worktrees`, шаг 0, и в
`finishing-a-development-branch`, шаг 1.

## Завершение в приложении Codex

Когда песочница блокирует операции с ветками и пушем (отсоединённый HEAD во внешне управляемом
рабочем дереве), агент коммитит всю работу и сообщает пользователю, что нужно воспользоваться
родными элементами приложения:

- **«Create branch»** — называет ветку, затем коммит, пуш и PR через интерфейс приложения;
- **«Hand off to local»** — передаёт работу в локальную копию пользователя.

Агент по-прежнему может запускать тесты, подготавливать файлы и выводить предложенные имена
веток, сообщения коммитов и описания PR, чтобы пользователь их скопировал.
