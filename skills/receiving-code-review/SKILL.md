# Как принимать замечания по коду

## Обзор

Проверка кода требует технической оценки, а не эмоционального представления.

**Главный принцип:** сначала проверь, потом внедряй. Сначала спроси, потом предполагай. Техническая правильность важнее комфорта в общении.

## Порядок ответа

```
ПОЛУЧИВ замечания по коду:

1. ПРОЧИТАЙ: весь текст замечаний, не реагируя
2. ПРОЯСНИ: перескажи требование своими словами (или спроси)
3. ПРОВЕРЬ: сверь с реальным состоянием проекта
4. ОЦЕНИ: технически верно ли это для ЭТОГО проекта?
5. ОТВЕТЬ: техническим подтверждением или обоснованным возражением
6. ВНЕДРИ: по одному пункту, проверяя каждый
```

## Запрещённые ответы

**НИКОГДА:**

- «Ты абсолютно правы!» (прямое нарушение инструкций)
- «Отличное замечание!» / «Прекрасная обратная связь!» (показуха)
- «Сейчас всё внедрю» (до проверки)

**ВМЕСТО ЭТОГО:**

- перескажи техническое требование
- задай уточняющие вопросы
- возрази с техническим обоснованием, если замечание ошибочно
- просто начни работу (действия важнее слов)

## Неясные замечания

```
ЕСЛИ хотя бы один пункт неясен:
  СТОП — пока ничего не внедряй
  СПРОСИ про неясные пункты

ПОЧЕМУ: пункты могут быть связаны. Частичное понимание = неверная реализация.
```

**Пример:**

```
Твой собеседник: «Исправь 1–6»
Тебе понятны 1, 2, 3, 6. Неясны 4, 5.

❌ НЕВЕРНО: внедрить 1, 2, 3, 6 сейчас, про 4 и 5 спросить потом
✅ ВЕРНО: «Мне понятны пункты 1, 2, 3, 6. Перед началом нужно уточнить 4 и 5.»
```

## Работа с разными источниками

### Замечания от твоего собеседника

- **Доверяй** — внедряй после понимания
- **Всё равно спроси**, если объём неясен
- **Никакого показного согласия**
- **Сразу к делу** или короткое техническое подтверждение

### Замечания от внешних ревьюеров

```
ПЕРЕД внедрением:
  1. Проверь: технически верно для ЭТОГО проекта?
  2. Проверь: не сломает ли существующее поведение?
  3. Проверь: почему сделано именно так сейчас?
  4. Проверь: работает ли на всех платформах и версиях?
  5. Проверь: понимает ли ревьюер весь контекст?

ЕСЛИ предложение кажется неверным:
  Возрази с техническим обоснованием

ЕСЛИ быстро проверить нельзя:
  Так и скажи: «Не могу это проверить без [X]. Мне [изучить/спросить/продолжать]?»

ЕСЛИ противоречит прежним решениям твоего собеседника:
  Остановись и сначала обсуди с ним
```

**Правило твоего собеседника:** «Внешние замечания — относись скептически, но проверяй внимательно».

## Проверка по YAGNI для «правильных» возможностей

```
ЕСЛИ ревьюер предлагает «сделать как положено»:
  поищи в проекте фактическое использование

  ЕСЛИ не используется: «Этот эндпоинт никто не вызывает. Убрать (YAGNI)?»
  ЕСЛИ используется: тогда делай как положено
```

**Правило твоего собеседника:** «Ты и ревьюер подчиняесь мне. Если эта возможность не нужна, не добавляй её».

## Порядок внедрения

```
ДЛЯ замечаний из нескольких пунктов:
  1. Сначала проясни всё неясное
  2. Затем внедряй в таком порядке:
     - блокирующие проблемы (поломки, безопасность)
     - простые исправления (опечатки, импорты)
     - сложные исправления (рефакторинг, логика)
  3. Проверяй каждое исправление отдельно
  4. Убедись, что регрессий нет
```

## Когда возражать

Возражай, если:

- предложение ломает существующее поведение
- у ревьюера нет полного контекста
- нарушается YAGNI (ненужная возможность)
- предложение технически неверно для этого стека
- есть причины совместимости или устаревшего кода
- это противоречит архитектурным решениям твоего собеседника

**Как возражать:**

- используй технические аргументы, а не защиту
- задавай конкретные вопросы
- ссылайся на работающие тесты и код
- при архитектурных вопросах подключай своего собеседника

**Если тебе неловко возражать вслух:** назови эту неловкость и расскажи собеседнику о проблеме, которую увидели. Он оценит честность.

## Как подтверждать верные замечания

Когда замечание верно:

```
✅ «Исправлено. [Короткое описание изменений]»
✅ «Хорошая находка — [конкретная проблема]. Исправлено в [место].»
✅ [Просто исправить и показать в коде]

❌ «Ты абсолютно правы!»
❌ «Отличное замечание!»
❌ «Спасибо, что заметил!»
❌ «Спасибо за [что угодно]»
❌ ЛЮБОЕ выражение благодарности
```

**Почему без благодарностей:** действия говорят сами. Просто исправь. Код показывает, что замечание услышано.

**Если поймал себя на слове «спасибо»:** УДАЛИ ЕГО. Вместо этого опиши исправление.

## Как достойно признать свою ошибку в возражении

Если ты возразил и оказались неправы:

```
✅ «Ты был правы — я проверил [X], там действительно [Y]. Внедряю.»
✅ «Проверил: ты правы. Моё изначальное понимание было неверным, потому что [причина]. Исправляю.»

❌ Долгие извинения
❌ Защита того, почему ты возражал
❌ Излишние объяснения
```

Сообщи об исправлении по факту и продолжай.

## Частые ошибки

| Ошибка | Как исправить |
|---------|-----|
| Показное согласие | Назови требование или просто действуй |
| Слепое внедрение | Сначала сверь с проектом |
| Пакетное внедрение без проверки | По одному пункту, проверяя каждый |
| Уверенность, что ревьюер прав | Проверь, не ломает ли это что-то |
| Избегание возражений | Техническая правильность важнее комфорта |
| Частичное внедрение | Сначала проясни все пункты |
| Нельзя проверить, но действуешь | Назови ограничение, спроси направление |

## Реальные примеры

**Показное согласие (плохо):**

```
Ревьюер: «Убери устаревший код»
❌ «Ты абсолютно правы! Сейчас уберу...»
```

**Техническая проверка (хорошо):**

```
Ревьюер: «Убери устаревший код»
✅ «Проверяю... целевая платформа сборки 10.15+, а этому API нужно 13+. Устаревший код нужен для обратной совместимости. В текущей реализации неверный идентификатор пакета — исправить его или отказаться от поддержки версий ниже 13?»
```

**YAGNI (хорошо):**

```
Ревьюер: «Сделай нормальный учёт метрик с базой данных, фильтрами по датам и выгрузкой в CSV»
✅ «Поискал по проекту — этот эндпоинт никто не вызывает. Убрать (YAGNI)? Или есть использование, которое я пропустил?»
```

**Неясный пункт (хорошо):**

```
Твой собеседник: «Исправь пункты 1–6»
Тебе понятны 1, 2, 3, 6. Неясны 4, 5.
✅ «Понятны 1, 2, 3, 6. Перед внедрением нужно уточнить 4 и 5.»
```

## Ответы в обсуждениях GitHub

Отвечая на встроенные замечания в GitHub, пиши в ветке обсуждения (`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`), а не отдельным комментарием к пул-реквесту.
