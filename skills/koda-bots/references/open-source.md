# Открытые и самоуправляемые платформы: Matrix, Rocket.Chat, Mattermost, Zulip

Общее свойство: сервер разворачивается у себя, данные не уходят третьей стороне, а API открыт и не требует согласования с владельцем платформы. Плата за это — администрирование и самостоятельная настройка федерации, обновлений и резервных копий.

## Matrix

Спецификация Client-Server API: <https://spec.matrix.org/latest/client-server-api/>.
Стандарты и расширения: <https://spec.matrix.org/latest/>.

### Модель

Matrix — открытый протокол федеративной передачи сообщений. Клиент общается с домашним сервером (homeserver), домашние серверы общаются между собой. Бот — обычный пользователь, поэтому работает всё, что доступно человеку: комнаты, вложения, шифрование.

- Транспорт — JSON поверх HTTP. HTTPS рекомендуется, открытый HTTP допустим только в тестовых окружениях.
- Авторизация — непрозрачный `access_token`.
- Все `POST` и `PUT` требуют тела с JSON-объектом, кроме загрузки медиа и выхода из системы.
- Версия API в путях — `v3` для большинства методов клиента, `v1` для части новых и медиа.

### Основные методы

| Метод                                                            | Назначение                                             |
|------------------------------------------------------------------|--------------------------------------------------------|
| `POST /_matrix/client/v3/login`                                  | Получить токен                                         |
| `GET /_matrix/client/v3/sync`                                    | Получить события, в том числе с `since` для инкремента |
| `PUT /_matrix/client/v3/rooms/{roomId}/send/{eventType}/{txnId}` | Отправить событие в комнату                            |
| `POST /_matrix/client/v3/createRoom`                             | Создать комнату                                        |
| `POST /_matrix/client/v3/join/{roomIdOrAlias}`                   | Войти в комнату                                        |
| `POST /_matrix/client/v3/rooms/{roomId}/invite`                  | Пригласить пользователя                                |
| `GET /_matrix/client/v3/rooms/{roomId}/messages`                 | История сообщений                                      |
| `POST /_matrix/media/v3/upload`                                  | Загрузить медиа                                        |
| `GET /_matrix/media/v3/download/{serverName}/{mediaId}`          | Скачать медиа                                          |

`txnId` в пути отправки — ключ идемпотентности. Повторный запрос с тем же `txnId` не создаёт второе сообщение. Это встроенный механизм, и его надо использовать.

### Синхронизация вместо вебхуков

В Matrix нет вебхуков. Клиент вызывает `GET /sync` с токеном `since` из предыдущего ответа и получает только новые события. Первый вызов без `since` возвращает начальное состояние и может быть большим, поэтому используй фильтры.

Опрос `sync` — долгий запрос: сервер держит соединение до появления событий или до таймаута. Не вызывай его в цикле без паузы.

### Ошибки и лимиты

Ответы об ошибках единообразны:

```json
{
  "errcode": "M_FORBIDDEN",
  "error": "Forbidden access"
}
```

Частые коды: `M_FORBIDDEN`, `M_NOT_FOUND`, `M_BAD_JSON`, `M_MISSING_TOKEN`, `M_LIMIT_EXCEEDED`, `M_RESOURCE_LIMIT_EXCEEDED`.

`M_LIMIT_EXCEEDED` означает превышение частоты: выдержи паузу и повтори. Ориентируйся на код ошибки, а не на HTTP-статус; при `M_UNKNOWN` смотри на статус.

### Шифрование

Matrix поддерживает сквозное шифрование (E2EE). Если включаешь его, бот должен уметь работать с ключами и устройствами, иначе не прочитает сообщения. Это заметно усложняет реализацию: используй библиотеку с поддержкой E2EE, а не сырой HTTP.

### SDK

| Язык                    | Библиотека                                           |
|-------------------------|------------------------------------------------------|
| Python                  | `matrix-nio`                                         |
| JavaScript / TypeScript | `matrix-bot-sdk`, `matrix-js-sdk`                    |
| Go                      | `maunium.net/go/mautrix`                             |
| Rust                    | `matrix-rust-sdk` (подключается как git-зависимость) |
| Kotlin                  | Trixnity                                             |

### Особенности

- Идентификаторы комнат и пользователей длинные и содержат префиксы; не обрезай их.
- Алиасы комнат (`#room:server`) удобнее для человека, но внутри API чаще нужен `roomId` (`!id:server`).
- Федерация означает, что собеседник может быть на другом сервере. Не рассчитывай на доступ к его профилю сверх того, что отдаёт API.
- Для домашнего сервера нужен домен и TLS-сертификат.

## Rocket.Chat

Документация: <https://developer.rocket.chat/apidocs/rocketchat-api>.
Спецификация OpenAPI: <https://github.com/RocketChat/Rocket.Chat-Open-API>.

### Модель

Rocket.Chat предоставляет два интерфейса:

- **REST API** — обычные HTTP-запросы, удобен для интеграций и ботов, которые отвечают на вебхуки.
- **Realtime API** — обмен по WebSocket, нужен для подписки на события в реальном времени.

Для бота, который только отправляет сообщения, хватит REST. Для бота, который слушает чат, нужен Realtime.

### Аутентификация

Основной способ — заголовки с идентификатором пользователя и токеном:

```
X-User-Id: <userId>
X-Auth-Token: <authToken>
```

Токен получают входом по логину и паролю либо создают персональный токен. Для бота заведи отдельного пользователя, а не используй учётную запись сотрудника.

### Основные группы методов

| Группа                     | Назначение                               |
|----------------------------|------------------------------------------|
| `channels`, `groups`, `im` | Каналы, приватные группы, личные чаты    |
| `chat`                     | Отправка, обновление, удаление сообщений |
| `users`                    | Пользователи и роли                      |
| `integrations`             | Входящие и исходящие вебхуки             |
| `webhooks`                 | Настройка вебхуков                       |

### Вебхуки

Rocket.Chat поддерживает входящие вебхуки (внешняя система отправляет сообщение в канал по URL) и исходящие (Rocket.Chat вызывает ваш URL на события). Для исходящих проверяй подлинность запроса: добавь собственный секрет в URL или заголовок и сверяй его.

### Особенности

- Версия сервера влияет на набор методов: часть появилась позже. Сверяйся со спецификацией своей версии.
- Права пользователя-бота ограничены ролями; лишние права — риск.
- Realtime API требует держать соединение и обрабатывать переподключение.
- При самоуправляемом развёртывании обновления ломают интеграции чаще, чем в облачных сервисах: фиксируй версию и проверяй после обновления.

## Mattermost

Документация: <https://developers.mattermost.com/api-documentation/>.
Спецификация OpenAPI лежит в основном репозитории: `mattermost/mattermost/api/v4/source/`.

### Модель

- Версия API — `v4`, стабильная и следующая семантическому версионированию.
- Порядка 550 методов в 38 группах ресурсов: пользователи, каналы, посты, команды, файлы, вебхуки и другое.
- Аутентификация — токен в заголовке `Authorization: Bearer <token>` либо сессионный токен после входа.

### Основные группы

| Группа     | Назначение                                                         |
|------------|--------------------------------------------------------------------|
| `users`    | Пользователи, роли, сессии, аватары                                |
| `channels` | Каналы: создание, участники, архив, заголовки                      |
| `posts`    | Сообщения: создание, правка, удаление, закрепление, реакции, поиск |
| `teams`    | Команды                                                            |
| `files`    | Загрузка и скачивание файлов                                       |
| `webhooks` | Входящие и исходящие вебхуки                                       |

### Вебхуки и боты

- **Входящий вебхук** — простой URL, по которому внешняя система публикует сообщение в канал. Подходит для уведомлений из CI и мониторинга.
- **Исходящий вебхук** — Mattermost вызывает ваш URL при событиях. Обязательно проверяй токен, который Mattermost передаёт в теле запроса.
- **Бот-аккаунт** — отдельный пользователь с типом `bot`, у него свой токен и ограниченные права.

### Особенности

- Для больших объёмов используй бот-аккаунт, а не личного пользователя.
- Спецификация генерируется из OpenAPI, поэтому клиент можно сгенерировать под свой язык.
- При самостоятельном развёртывании настрой уведомления и резервное копирование базы: без этого бот останется без истории.

## Zulip

Документация: <https://zulip.com/api/>.
Обзор REST API: <https://zulip.com/api/rest>.

### Модель

Zulip строит обсуждения вокруг тем внутри потоков (streams). Это влияет на дизайн бота: почти каждое сообщение должно попадать в тему, а не просто в поток.

- REST API покрывает всё, что делают веб- и мобильные клиенты Zulip.
- Официальные привязки есть для Python и JavaScript.
- В Python-привязках доступен `client.call_endpoint` для методов, которых нет в документации.
- Сервер открыт, поэтому в спорных случаях можно посмотреть исходники: <https://github.com/zulip/zulip/>.

### Аутентификация

Бот — отдельный пользователь с типом bot. Ему выдаётся API-ключ, а запросы подписываются этим ключом. Для ботов доступен механизм событий: бот регистрирует очередь и получает события длинным запросом.

### События

Вместо вебхуков Zulip использует очередь событий:

1. Бот регистрирует очередь и получает `queue_id` и `last_event_id`.
2. Бот запрашивает события с этими идентификаторами, сервер держит соединение до появления новых.
3. Очередь нужно периодически продлевать; при истечении её создают заново и разбирают пропущенное.

Это похоже на `sync` в Matrix и на long polling в Telegram.

### Вебхуки

Zulip поддерживает входящие вебхуки для внешних сервисов (GitHub, GitLab, CI и других) через отдельный механизм интеграций. Исходящих вебхуков в общем виде нет — для приёма событий используется очередь.

### Особенности

- Тема сообщения обязательна в большинстве сценариев; не отправляй всё в одну тему.
- Привязки Python удобнее сырого HTTP: они берут на себя подпись и повторные попытки.
- Для самоуправляемого сервера проверь версию: часть методов появилась в поздних релизах.

## Сравнение

| Критерий          | Matrix                         | Rocket.Chat                       | Mattermost                              | Zulip               |
|-------------------|--------------------------------|-----------------------------------|-----------------------------------------|---------------------|
| Приём событий     | `sync` (длинный запрос)        | Realtime API или исходящий вебхук | Исходящий вебхук                        | Очередь событий     |
| Отправка          | REST                           | REST                              | REST                                    | REST                |
| Федерация         | Да                             | Нет                               | Нет                                     | Нет                 |
| E2EE              | Да                             | Нет                               | Нет                                     | Нет                 |
| Модель обсуждений | Комнаты                        | Каналы                            | Каналы                                  | Потоки и темы       |
| Официальные SDK   | Нет, но есть зрелые сообщества | Нет                               | Нет, есть клиент в основном репозитории | Python и JavaScript |
| Публикация бота   | Не требуется                   | Не требуется                      | Не требуется                            | Не требуется        |

## Общие правила для самоуправляемых платформ

1. **Заведи отдельного пользователя для бота.** Не используй учётную запись сотрудника: она уйдёт вместе с ним.
2. **Ограничь права.** Бот должен уметь ровно то, что нужно сценарию.
3. **Фиксируй версию сервера.** Обновления меняют API и поведение интеграций.
4. **Настрой резервное копирование.** История бота и очереди событий хранятся на вашем сервере.
5. **Проверяй подлинность входящих запросов.** Секрет в URL, заголовок или подпись — в зависимости от платформы.
6. **Держи соединения под контролем.** `sync`, Realtime API и очереди событий требуют обработки переподключения и восстановления после разрыва.
7. **Планируй миграцию.** Открытые платформы позволяют вывезти данные, но формат экспорта у каждой свой.
