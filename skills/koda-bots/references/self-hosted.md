# Приватные и децентрализованные протоколы: Signal, XMPP, Delta Chat

Здесь нет платформы, которая выдаёт токен бота и принимает обновления. Всё строится на клиентских протоколах и собственных серверах, и это определяет ограничения.

## Signal

Официальный клиент и утилита: <https://github.com/AsamK/signal-cli>.
REST-обёртка (сообщество): <https://github.com/bbernhard/signal-cli-rest-api>.

### Главное ограничение

У Signal **нет официального API для ботов** и нет каталога ботов. Официальная позиция проекта: Signal — мессенджер для людей, а не платформа для автоматизации. Любая автоматизация — это работа от имени обычной учётной записи.

Практические следствия:

1. Бот регистрируется как отдельный номер или подключается как связанное устройство.
2. Учётная запись должна периодически выходить в сеть, иначе сообщения копятся и доставка ломается.
3. Номер нужно поддерживать: смена устройства, переустановка и потеря ключей требуют повторной привязки.
4. Массовые рассылки нежелательны: получатели легко блокируют незнакомый номер.

### signal-cli

`signal-cli` — консольная утилита на Java, которая работает с протоколом Signal от имени номера.

```bash
# Регистрация номера
signal-cli -a +79001234567 register

# Подтверждение кодом из SMS
signal-cli -a +79001234567 verify 123456

# Подключение как связанного устройства (показывает QR-код)
signal-cli link -n "bot"

# Отправка сообщения
signal-cli -a +79001234567 send +79007654321 -m "Сборка завершена"
```

### REST-обёртка

`signal-cli-rest-api` превращает `signal-cli` в HTTP-сервис: регистрация, отправка, приём, группы, профиль, вложения.

```bash
docker run -d --name signal-api --restart=always -p 8080:8080 \
  -v "$HOME/.local/share/signal-api:/home/.local/share/signal-cli" \
  -e MODE=native bbernhard/signal-cli-rest-api
```

Отправка:

```bash
curl -X POST -H "Content-Type: application/json" \
  'http://localhost:8080/v2/send' \
  -d '{"message": "Сборка завершена", "number": "+79001234567", "recipients": ["+79007654321"]}'
```

Режимы работы (`MODE`):

| Режим             | Особенности                                       |
|-------------------|---------------------------------------------------|
| `normal`          | Запуск JVM на каждый запрос, самый медленный      |
| `native`          | Скомпилированный бинарник, ниже задержка и память |
| `json-rpc`        | Один демон, самый быстрый, но больше памяти       |
| `json-rpc-native` | Демон на нативном бинарнике                       |

Приём сообщений — через WebSocket на `/v1/receive/{number}`. Это принципиально: REST-опрос не предусмотрен.

Важная тонкость режима `json-rpc`: по умолчанию (`JSON_RPC_RECEIVE_MODE=on-start`) `signal-cli` забирает сообщения с сервера Signal независимо от того, подключён ли подписчик. Сообщения, пришедшие во время перезапуска подписчика, теряются. Для продуктивной среды, где подписчик перезапускается или масштабируется, переключись на `manual`.

### Библиотеки

| Язык       | Библиотека           | Что это                                          |
|------------|----------------------|--------------------------------------------------|
| Python     | `signalbot`          | Фреймворк для ботов поверх `signal-cli-rest-api` |
| Python     | `pysignalclirestapi` | Тонкий клиент к тому же API                      |
| TypeScript | `signal-rest-ts`     | Модуль для ботов                                 |
| Go         | `secured-signal-api` | API-шлюз, не клиент                              |

Все они неофициальные. `signal-cli` тоже неофициальный проект, хотя и де-факто стандарт.

### Что важно проговорить с заказчиком

- Блокировка номера возможна, восстановление не гарантировано.
- Гарантий доставки нет: Signal не даёт статусов, сравнимых с бизнес-API.
- Юридические требования к уведомлениям (например, для банков) Signal не закрывает.
- Для продуктивных уведомлений обычно выбирают другой канал, а Signal оставляют для приватных сценариев.

## XMPP

Стандарты: <https://xmpp.org/standards/>.
Базовый протокол: RFC 6120 (ядро), RFC 6121 (обмен сообщениями и присутствие).

### Модель

XMPP — открытый протокол обмена сообщениями на основе XML. Клиент подключается к серверу по TCP с TLS, авторизуется по JID (`user@domain/resource`) и обменивается XML-станзами.

Бот — обычный клиент с собственным JID. Никакой регистрации приложения не нужно: нужен аккаунт на сервере.

### Что нужно знать

| Расширение | Назначение                                       |
|------------|--------------------------------------------------|
| RFC 6120   | Ядро: соединение, TLS, SASL-аутентификация       |
| RFC 6121   | Обмен сообщениями и присутствием, ростера        |
| XEP-0045   | Групповые чаты (MUC)                             |
| XEP-0199   | Пинг, чтобы замечать разрыв соединения           |
| XEP-0313   | Архив сообщений (MAM)                            |
| XEP-0198   | Возобновление потока после разрыва               |
| XEP-0352   | Отложенная доставка присутствия, экономит трафик |

Поддержка расширений зависит от сервера. Перед тем как обещать функциональность, проверь `<iq>`-запрос к `disco#info` у своего сервера.

### Библиотеки

| Язык       | Библиотека      | Комментарий               |
|------------|-----------------|---------------------------|
| Python     | `slixmpp`       | Асинхронная, MUC, плагины |
| JavaScript | `xmpp.js`       | Клиентская библиотека     |
| Go         | `gosrc.io/xmpp` | Базовый клиент, MUC есть  |

### Особенности

- Соединение долгоживущее, разрывы нормальны: нужны переподключение и восстановление потока (XEP-0198).
- В MUC у бота отдельный JID внутри комнаты, и сообщения приходят от имени участника комнаты.
- Шифрование OMEMO поддерживается не везде и требует отдельной работы с ключами.
- XML-разбор — источник уязвимостей: используй библиотеку с защитой от XXE и «billion laughs».

### Когда выбирать

XMPP уместен, когда в организации уже есть сервер (например, для внутренней связи) и нужен бот без внешних зависимостей. Для нового проекта вне такой инфраструктуры порог входа выше, чем у платформ с готовым API.

## Delta Chat

Документация: <https://delta.chat/en/help>.
Стандарты, на которых построен протокол: <https://github.com/chatmail/core/blob/main/standards.md>.
Фреймворк ботов: пакет `deltabot` на PyPI.

### Модель

Delta Chat — мессенджер, который использует электронную почту как транспорт. Сообщения пересылаются через обычные почтовые серверы или через chatmail-релеи, а содержимое защищено сквозным шифрованием на основе OpenPGP.

Ключевые свойства:

- нет центральной платформы и нет каталога ботов;
- идентификатор — адрес электронной почты;
- собеседника нельзя найти поиском: обмен контактами идёт через QR-код или ссылку-приглашение;
- входящие сообщения от незнакомцев приходят как «запрос» и требуют принятия;
- группы равноправные: любой участник может менять состав и название.

### Боты

Официальный фреймворк — `deltabot` (Python). Он построен на привязках `deltachat` к ядру `deltachat-core-rust`.

Бот — это отдельный адрес электронной почты, настроенный как профиль Delta Chat. Он подключается к серверу, получает сообщения и отвечает как обычный собеседник.

Практические шаги:

1. Заведи почтовый адрес для бота. Лучше использовать chatmail-релей или собственный сервер, а не публичный почтовый сервис с антиспам-фильтрами.
2. Настрой профиль: сервер, логин, пароль.
3. Подключи `deltabot`, обработай событие первого контакта: пользователь должен добавить бота и получить ответ.
4. Учти, что доставка зависит от почтовых задержек и фильтров: это не мгновенный мессенджер.

### Ограничения

- Задержки доставки: почтовые серверы не гарантируют мгновенность.
- Антиспам и лимиты отправки у почтовых провайдеров.
- Приватность: метаданные защищены, но сам факт переписки виден почтовому серверу.
- Шифрование OpenPGP: не все клиенты и серверы ведут себя одинаково, проверяй на своём окружении.
- Нет API для массовых рассылок: каждый получатель — отдельный контакт.

### Когда выбирать

Delta Chat уместен, когда нужен мессенджер без корпоративной платформы и с минимумом инфраструктуры: бот живёт на почте, которую легко развернуть. Для сценариев с гарантированной доставкой и статусами он не подходит.

## Сравнение

| Критерий                  | Signal                             | XMPP                    | Delta Chat               |
|---------------------------|------------------------------------|-------------------------|--------------------------|
| Официальный API для ботов | Нет                                | Нет, но протокол открыт | Нет, но есть `deltabot`  |
| Транспорт                 | Протокол Signal через `signal-cli` | XML по TCP/TLS          | Электронная почта        |
| Учётная запись            | Номер телефона                     | JID на сервере          | Почтовый адрес           |
| Приём событий             | WebSocket через обёртку            | Постоянное соединение   | Почтовый ящик            |
| Федерация                 | Нет, централизованный сервис       | Да                      | Да, через почту          |
| E2EE                      | Да, всегда                         | Зависит от OMEMO        | Да, OpenPGP              |
| Риск блокировки           | Высокий при автоматизации          | Низкий                  | Средний, из-за антиспама |
| Массовые рассылки         | Не рекомендуются                   | Ограничены сервером     | Не предусмотрены         |

## Общее правило

Во всех трёх случаях бот — это учётная запись обычного пользователя. Значит, действуют обычные правила приличия: не спамить, уважать блокировки, не выдавать себя за человека и предупреждать собеседника, что отвечает автоматика.
