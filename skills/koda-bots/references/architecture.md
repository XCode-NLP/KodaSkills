# Архитектура бота

Эти правила не зависят от платформы. Сначала спроектируй их, потом выбирай библиотеку.

## Вебхук или polling

| Критерий           | Вебхук                                   | Long polling                |
|--------------------|------------------------------------------|-----------------------------|
| Публичный HTTPS    | Обязателен                               | Не нужен                    |
| Задержка           | Минимальная                              | Зависит от интервала опроса |
| Нагрузка           | Только при событиях                      | Постоянные запросы          |
| Масштабирование    | Несколько экземпляров за балансировщиком | Обычно один экземпляр       |
| Отладка            | Сложнее: нужен туннель                   | Проще: запустил и смотришь  |
| Повторная доставка | Возможна                                 | Возможна                    |

Правило: локально — polling, в продуктивной среде — вебхук. Не включай оба режима одновременно.

## Идемпотентность

Платформа может доставить одно обновление несколько раз: при таймауте, перезапуске, сетевой ошибке.

1. Возьми уникальный ключ: `update_id`, `event_id`, `interaction.id` или собственный хеш.
2. Запиши ключ в хранилище с TTL до обработки.
3. Если ключ уже есть — заверши обработку без побочных эффектов.
4. Для платежей и заказов используй отдельный ключ идемпотентности, не связанный с сообщением.

```python
async def handle_once(key: str, ttl: int = 86400) -> bool:
    """Вернёт True, если ключ новый, и False, если уже обработан."""
    added = await redis.set(f"seen:{key}", "1", nx=True, ex=ttl)
    return bool(added)
```

## Очереди и фоновые задачи

В обработчике вебхука делай минимум: проверь подпись, запиши событие, поставь задачу, ответь `200`.
Тяжёлая работа — в фоновом исполнителе.

- Очередь: Redis, RabbitMQ, NATS, SQS или собственная таблица в БД.
- Фоновые исполнители должны быть идемпотентными.
- Ограничивай число одновременных задач на чат, чтобы не превышать лимиты.
- Настрой очередь недоставленных задач для тех, что падают постоянно.
- Логируй идентификатор корреляции, чтобы связать событие и задачу.

## Состояния диалога

Не храни состояние в памяти процесса.

| Хранилище  | Когда подходит                           |
|------------|------------------------------------------|
| Redis      | Быстрое FSM с TTL, несколько экземпляров |
| PostgreSQL | Нужна история, аудит, сложные переходы   |
| SQLite     | Локальный бот, один экземпляр            |

У состояния должен быть срок жизни и явный выход: команда отмены, кнопка, таймаут.
Не храни в состоянии весь объект сообщения и секреты.

## Лимиты и повторы

- Ограничивай частоту на уровне чата и на уровне бота.
- Используй экспоненциальную задержку со случайной составляющей.
- Уважай `retry_after` / `Retry-After`, если платформа его возвращает.
- Не повторяй неидемпотентные операции без проверки результата.
- Для массовых рассылок используй отдельную очередь с низкой скоростью.

```python
import asyncio
import random

async def with_retry(operation, attempts: int = 5):
    for attempt in range(attempts):
        try:
            return await operation()
        except Exception:
            if attempt == attempts - 1:
                raise
            delay = min(2 ** attempt, 30) + random.random()
            await asyncio.sleep(delay)
```

## Безопасность

1. Секреты — в переменных окружения или менеджере секретов.
2. Проверяй подлинность вебхука: подпись, секретный заголовок или IP.
3. Ограничивай админские команды по ID пользователей и ролям.
4. Валидируй и экранируй пользовательский ввод.
5. Не выполняй команды из сообщений.
6. Не делай запросы по пользовательским URL без проверки домена: это защита от SSRF.
7. Для LLM-бота отделяй системные инструкции от пользовательского текста и не давай модели доступ к секретам.
8. Ограничивай размер входящих файлов и проверяй MIME-тип.
9. Логируй события безопасности: неудачные проверки подписи, попытки админских команд.

## Наблюдаемость

Минимальный набор:

- проверка работоспособности процесса и зависимостей (БД, Redis, API платформы);
- счётчики: получено обновлений, обработано, ошибок, повторов;
- гистограмма задержки ответа;
- размер очереди и возраст старейшей задачи;
- алерты на рост ошибок и падение бота.

Логи должны быть структурированными. Не пиши в логи токены, `initData`, полные тексты приватных сообщений и персональные данные.

## Деплой

- Контейнер с непривилегированным пользователем.
- Переменные окружения через секреты оркестратора.
- Обратный прокси с TLS для вебхука.
- Корректное завершение: перестань принимать новые события, дождись текущих задач, закрой соединения.
- Один экземпляр на токен, если платформа не поддерживает несколько получателей.
- Для polling — supervisor или оркестратор с автоперезапуском.

```yaml
services:
  bot:
    build: .
    restart: unless-stopped
    env_file: .env
    depends_on:
      - redis
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8080/health')"]
      interval: 30s
      timeout: 5s
      retries: 3
```

## Тестирование

| Уровень            | Что проверять                                                  |
|--------------------|----------------------------------------------------------------|
| Юнит               | Парсеры, валидаторы, форматирование, чистая бизнес-логика      |
| Интеграция         | Обработка фейкового события, запись в БД, постановка в очередь |
| Контракт           | Соответствие ответов схеме платформы                           |
| Нагрузка           | Лимиты, очередь, поведение при `429`                           |
| Отказоустойчивость | Недоступность API, БД, Redis, повторная доставка               |

Обязательные сценарии:

- повторное событие не создаёт дубль;
- пустой или неожиданный ввод не роняет бота;
- долгая операция не блокирует вебхук;
- после перезапуска состояние и очередь восстанавливаются;
- ошибка одного чата не останавливает остальные.

## Антипаттерны

| Антипаттерн                               | Почему плохо                                   |
|-------------------------------------------|------------------------------------------------|
| Бизнес-логика прямо в обработчике вебхука | Таймауты и повторная доставка                  |
| Состояние в памяти                        | Ломается при перезапуске и масштабировании     |
| `sleep` вместо очереди                    | Блокирует обработку и не переживает перезапуск |
| Игнорирование `429`                       | Бан или длительная блокировка                  |
| Один общий токен на все окружения         | Утечка и невозможно отозвать точечно           |
| Логирование полного текста сообщений      | Персональные данные и секреты в логах          |
| Доверие данным из callback без проверки   | Подделка действий                              |
| Массовая рассылка без согласия            | Жалобы и блокировка бота                       |
