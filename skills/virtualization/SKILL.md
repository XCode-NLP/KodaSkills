# Виртуализация: гипервизоры, виртуальные машины и инфраструктура

Создание, настройка и управление виртуальными машинами на разных гипервизорах — от одного узла Proxmox до кластеров с высокой доступностью, живой миграцией и пробросом GPU. Цель — готовая к эксплуатации инфраструктура с корректными настройками хранилища, памяти и процессора, которые не подведут в три часа ночи.

## Когда использовать

- Создание и настройка виртуальных машин на Proxmox, libvirt/KVM, XCP-ng или VMware.
- Подготовка машин Proxmox через Terraform (провайдер bpg/proxmox).
- Сборка шаблонов машин через Packer и cloud-init.
- Настройка проброса PCI и GPU для вычислений или вывода изображения.
- Работа с хранилищами (LVM-thin, ZFS, Ceph, NFS).
- Настройка кластера Proxmox, высокой доступности и живой миграции.
- Диагностика производительности машины (дисковый ввод-вывод, память, процессор).
- Планирование резервного копирования (Proxmox Backup Server, снимки).
- Тонкая настройка дисковой производительности (virtio-scsi, iothread, discard и fstrim).
- Управление памятью (ballooning, топология NUMA, огромные страницы).

## Когда НЕ использовать

- Манифесты Kubernetes, Helm-чарты, оркестрация контейнеров.
- Общие шаблоны Terraform и OpenTofu, состояние, модули.
- Сетевая конфигурация, не связанная с гипервизором: DNS, VPN, обратные прокси.
- Плейбуки Ansible и управление конфигурацией.
- Оптимизация образов Docker и контейнеров.
- Управление межсетевыми экранами OPNsense и pfSense.
- Администрирование Synology DSM.
- Конфигурация и сборка образов NixOS.

## Самопроверка перед выдачей результата

Инструменты на основе ИИ стабильно допускают одни и те же ошибки в конфигурации машин. **Прежде чем отдать любую конфигурацию машины, HCL для Terraform или шаблон Packer, сверься с этим списком:**

- [ ] Нет жёстко заданных IP, паролей и SSH-ключей — только переменные или внедрение через cloud-init.
- [ ] Интерфейс диска — virtio (`scsi0` с контроллером `virtio-scsi`), а не IDE, если только это не устаревшая ОС.
- [ ] `iothread = true` на дисках SCSI только вместе с контроллером `virtio-scsi-single`.
- [ ] Эмуляция `ssd = true` включена, когда нижележащее хранилище — SSD (это включает TRIM в гостевой системе).
- [ ] `discard = on` в конфигурации диска QEMU для тонко выделяемых хранилищ (проброс fstrim).
- [ ] Раздувание памяти отключено, если гостевая система не загружает драйвер `virtio_balloon` (минимальные сборки Alpine, некоторые BSD). Увеличение `memory:` сверх текущего максимума — это горячее добавление модуля памяти, а не ballooning: нужны `hotplug: memory` и NUMA либо полная остановка и запуск.
- [ ] В Terraform bpg/proxmox раздувание отключается в блоке `memory` через `floating = 0`; синтаксис Proxmox `balloon: 0` держи отдельно.
- [ ] Тип процессора — `host` для эксплуатации (полный проброс возможностей), а не `kvm64` или `qemu64`.
- [ ] NUMA включена для многосокетных машин и машин с большим объёмом памяти.
- [ ] Агент QEMU включён (cloud-init его ставит, но проверь).
- [ ] Указан интерфейс cloud-init (bpg/proxmox по умолчанию берёт `ide2`, если значение пустое).
- [ ] Жизненный цикл Terraform: `prevent_destroy` для машин, `ignore_changes` для `node_name`; `disk` игнорируется только когда диски растут на хосте.
- [ ] У размера диска один владелец: рост через `disk.size` в bpg/proxmox (применяется на ходу, если `disk` есть в `hotplug`) либо через `qm resize` с игнорируемым `disk`, но никогда оба сразу.
- [ ] Проброс PCI: `pcie = false` для обычного проброса, `xvga = false`, если это не GPU для вывода изображения.
- [ ] Проброс PCI: тип машины `q35`, когда нужен `pcie = true`.
- [ ] Проброс GPU: видеокарты AMD склонны к ошибкам сброса (может понадобиться модуль ядра vendor-reset или `pcie_port_pm=off`); NVIDIA обычно сбрасывается чисто, но проверь на своей модели до эксплуатации.
- [ ] Тип BIOS соответствует задаче: по умолчанию `seabios`, `ovmf` для UEFI, Secure Boot и Windows 11.
- [ ] Настроен срок хранения резервных копий, а не бесконечные снимки, съедающие хранилище.
- [ ] Сетевое устройство использует модель `virtio`, а не `e1000` или `rtl8139`.
- [ ] В гостевой системе включён `fstrim.timer` для тонко выделяемых хранилищ (это замыкает цепочку discard).
- [ ] Контроллер SCSI задан явно (`virtio-scsi-single` при отдельных потоках ввода-вывода на диск; `virtio-scsi-pci` только когда они выключены).
- [ ] Тип машины соответствует требованиям прошивки (`q35` против `i440fx`).
- [ ] Тип видео соответствует задаче: `serial0` для безголовых облачных образов, `virtio` для машин с графическим интерфейсом, ничего для проброса GPU вывода (`x-vga=1` заменяет виртуальный дисплей).
- [ ] **Гипервизор и версия проверены**: советы по Proxmox, QEMU/KVM, libvirt, XCP-ng, vSphere и cloud-init соответствуют целевой платформе.
- [ ] **Риск для данных оценён**: команды работы с форматом диска, снимками, пробросом и миграцией сохраняют данные и допускают откат.

## Хорошие практики

- Делай снимок перед обновлением гостевого агента, диска, загрузчика, проброса или гипервизора, но не считай снимки резервными копиями.
- Резервные копии хоста, гостевой системы и хранилища должны восстанавливаться независимо.
- Документируй привязки PCI и GPU, чтобы обновление ядра не оставило хост неработоспособным.

## Учебные восстановления

Восстанови показательную гостевую систему в изолированную сеть без дублирования рабочих IP и идентификаторов. Проверь загрузку, данные приложения, зависимые сервисы и доступность ключей шифрования; измерь время восстановления и объём потери данных против RTO и RPO. Запиши, какую копию выбрал, что проверил и что убрал за собой. Успешное задание резервного копирования или снимок не доказывают восстанавливаемость.

## Порядок работы

Для изменений существующей машины или хоста скопируй этот список и отмечай шаги:

```markdown
- [ ] Шаг 1: задача определена, прочитан соответствующий раздел
- [ ] Шаг 2: зафиксированы гипервизор, гостевая ОС, хранилище и состояние резервных копий
- [ ] Шаг 3: изменение применено сначала на некритичной машине
- [ ] Шаг 4: проверка пройдена (при любом провале исправь и вернись к шагу 3)
```

### Шаг 1. Определи задачу

| Задача | С чего начать |
|------|------------|
| Создание машины в Proxmox | CLI (`qm`) или API (`pvesh`), cloud-init |
| Подготовка через Terraform | провайдер bpg/proxmox, правила жизненного цикла |
| Сборка образов | Packer плюс шаблоны cloud-init |
| Управление libvirt/KVM | `virsh`, XML-описания доменов |
| Проброс GPU и PCI | группы IOMMU, `vfio-pci` |
| Тонкая настройка производительности | конфигурация диска, памяти, процессора |
| Переезд на Proxmox | с VMware, XCP-ng или с физического сервера |

### Шаг 2. Собери требования

Прежде чем создавать или менять машины:

- **Гипервизор и версия** — Proxmox VE 9.x, libvirt, переезд с VMware?
- **Гостевая ОС** — дистрибутив Linux, Windows, BSD? От этого зависят драйверы virtio, ballooning и агент.
- **Процессор** — число ядер, тип (`host` или эмуляция), потребность в закреплении, топология NUMA.
- **Память** — выделенный объём, ballooning (обычно не нужен), огромные страницы для баз данных.
- **Хранилище** — бэкенд (LVM-thin, ZFS, Ceph, NFS), размер диска, формат (raw или qcow2).
- **Сеть** — мост, тег VLAN, virtio, межсетевой экран.
- **Проброс** — устройства GPU и PCI, USB, последовательные порты.
- **Способ подготовки** — вручную, Terraform, шаблон Packer плюс cloud-init.
- **Требования к доступности** — кластер, живая миграция, ограждение узлов.
- **Стратегия резервного копирования** — PBS, снимки, vzdump, частота.

### Шаг 3. Собери конфигурацию

Ключевые принципы:

- **Используй cloud-init для подготовки.** Не настраивай машину вручную после создания: внедряй SSH-ключи, сетевую конфигурацию, пакеты и учётные записи через cloud-init.
- **Используй virtio везде.** Диск (virtio-scsi), сеть (virtio-net), вывод (virtio-gpu для безголовых машин). IDE и e1000 существуют только для совместимости с устаревшими ОС.
- **Ставь тип процессора `host`.** Эмулируемые типы (kvm64, qemu64) скрывают нужные гостевой системе возможности (AES-NI, AVX, SSE4). Бери `host`, если не нужна живая миграция между разнородным железом.
- **Проверяй изменения конфигурации диска через остановку и запуск, а не перезагрузку.** Останови аккуратно через `qm shutdown`, убедись, что `qm status` показывает остановку, и запусти новый процесс QEMU.

### Шаг 4. Проверь

| Что проверять | Как |
|-----------------|-----|
| Машина загрузилась, агент отвечает | `qm agent <vmid> ping` (Proxmox) |
| cloud-init завершился | `cloud-init status --wait` в гостевой системе |
| Производительность диска | `fio --name=test --rw=randread --bs=4k --direct=1 --numjobs=4 --runtime=30` |
| TRIM и discard работают | `fstrim -v /` в гостевой системе, затем `data_percent` тонкого пула на хосте |
| Проброс PCI | `lspci` в гостевой системе показывает переданное устройство, драйвер загружен |
| Связность сети | `ping` до шлюза, `ip addr` совпадает с конфигурацией cloud-init |
| Память | `free -h` в гостевой системе совпадает с ожидаемым (не урезана раздуванием) |
| Живая миграция | сначала на некритичной машине: `qm migrate <vmid> <target> --online` |

`fio` в гостевых системах часто отсутствует: `command -v fio >/dev/null || echo "fio missing: sudo apt install fio (Debian/Ubuntu)"`. Если проверка не прошла, исправь конфигурацию и вернись к шагу 3; исправление на уровне железа требует нового запуска QEMU, а не перезагрузки гостевой системы.

## Быстрая задача: машина из облачного образа в Proxmox

Самый быстрый путь к готовой машине. Пропусти Packer и установку с ISO для стандартных случаев.

1. Скачай стабильный облачный образ на узел Proxmox (не из `daily/`, где возможны пробелы в cloud-init):
   `wget -P /var/lib/vz/template/iso/ https://cloud.debian.org/images/cloud/trixie/latest/debian-13-generic-amd64.qcow2`
2. Создай каркас машины:
   `qm create 100 --name myvm --memory 2048 --cores 2 --cpu host --net0 virtio,bridge=vmbr0 --agent enabled=1 --scsihw virtio-scsi-single`
3. Импортируй и подключи диск с оптимизациями для SSD:
   `qm importdisk 100 /var/lib/vz/template/iso/debian-13-generic-amd64.qcow2 local-lvm`
   `qm set 100 --scsi0 local-lvm:vm-100-disk-0,discard=on,iothread=1,ssd=1 --boot order=scsi0`
4. Добавь диск cloud-init и настрой:
   `qm set 100 --ide2 local-lvm:cloudinit`
   `qm set 100 --ciuser admin --sshkeys ~/.ssh/id_ed25519.pub --ipconfig0 ip=10.0.0.100/24,gw=10.0.0.1`
5. Запусти: `qm start 100`
6. Проверь: `qm agent 100 ping` (при первой загрузке может занять 1–2 минуты, пока работает cloud-init).

Чтобы сделать из этой машины переиспользуемый шаблон, сначала сбрось в гостевой системе состояние конкретного экземпляра: `sudo cloud-init clean --logs --machine-id && sudo rm -f /etc/ssh/ssh_host_* && sudo poweroff` (cloud-init создаст ключи хоста и machine-id заново при первой загрузке клона), затем `qm template 100`. Клонируй командой `qm clone 100 101 --name new-vm --full`.

## Краткий справочник по Proxmox VE

### Основные команды CLI

```bash
# Управление машинами
qm list                              # Список всех машин
qm create 100 --name test --memory 2048 --cores 2 --net0 virtio,bridge=vmbr0
qm start/stop/shutdown/reset 100     # Операции питания
qm config 100                        # Показать конфигурацию машины
qm set 100 --memory 4096             # Изменить конфигурацию (часть требует остановки и запуска)
qm resize 100 scsi0 +10G             # Расширить диск (уменьшить нельзя)
qm agent 100 ping                    # Проверить агент QEMU
qm migrate 100 pve2 --online --with-local-disks  # Живая миграция

# Управление контейнерами
pct list                              # Список контейнеров LXC
pct create 200 local:vztmpl/debian-12-standard_12.7-1_amd64.tar.zst

# Хранилища
pvesm status                          # Обзор пулов хранилищ
lvs -a -o+devices                     # Состояние тонкого пула LVM (на бэкенде LVM)

# Кластер
pvecm status                          # Состояние кластера
pvecm nodes                           # Список узлов
ha-manager status                     # Состояние высокой доступности
```

### Важнейшие подводные камни

Перед изменением рабочей машины или хоста проверь: снимки не заменяют резервные копии; тонкий пул при заполнении на 100% останавливает весь ввод-вывод; `qm migrate` в переднем плане обрывается при разрыве SSH — запускай через `nohup`; перезагрузка гостевой системы не перезапускает QEMU, поэтому изменения оборудования требуют остановки и запуска.

## Производительность хранилищ

| Бэкенд | Для чего лучше | Тонкое выделение | Снимки | Живая миграция |
|---------|----------|---------------|----------|----------------|
| LVM-thin | Локальные SSD, эксплуатация | Да | Да (копирование при записи) | С `--with-local-disks` |
| ZFS | Целостность данных, сжатие | Да | Да (нативные) | С репликацией |
| Ceph/RBD | Общее хранилище на несколько узлов | Да | Да | Нативная (общая) |
| NFS | ISO, шаблоны, резервные копии | Зависит от NAS | Зависит | Да (общая) |
| local (каталог) | Малое и тестовое | Нет (файловое) | Только qcow2 | Нет |

**Иерархия дисковых интерфейсов** (от быстрого к медленному):

1. **virtio-scsi-single** с iothread — контроллер на каждый диск, лучшие IOPS.
2. **virtio-scsi-pci** без отдельных потоков на диск — общий контроллер, хорошо для умеренного ввода-вывода.
3. **virtio-blk** — устаревший virtio, хорошая производительность, но меньше возможностей.
4. **IDE** — только для совместимости, нужен некоторым старым ОС.

**Список оптимизаций для SSD:**

- [ ] `ssd = 1` в конфигурации диска (сообщает гостевой системе, что она на SSD, включает TRIM).
- [ ] `discard = on` на диске QEMU (передаёт TRIM и UNMAP в хранилище).
- [ ] `fstrim.timer` включён в гостевой системе (по умолчанию раз в неделю в дистрибутивах с systemd).
- [ ] Проверка: `fstrim -v /` в гостевой системе, затем `lvs -o data_percent` на хосте.

**Изменение размера диска и ловушка Terraform:** расти можно с любой стороны, но владелец должен быть один. Провайдер bpg/proxmox увеличивает диск на месте при росте `disk.size` — на ходу, если `disk` есть в списке `hotplug` машины, иначе с перезагрузкой по инициативе провайдера. Уменьшение не поддерживается нигде. Выбери одного владельца:

- **Владелец Terraform:** увеличивай `size` в блоке `disk` и применяй. Не добавляй `disk` в `ignore_changes`, иначе рост не применится.
- **Владелец хост:** `qm resize <vmid> scsi0 +10G` на хосте Proxmox, `disk` остаётся в `ignore_changes`, а размер в Terraform обновляется после этого, чтобы план оставался чистым.

В обоих случаях заверши внутри гостевой системы: `growpart /dev/sda 1` (расширить раздел), затем `resize2fs /dev/sda1` или `xfs_growfs /` (расширить файловую систему). Смешение двух владельцев даёт планы, которые уменьшают или пересоздают диск.

## Управление памятью

**Раздувание памяти, коротко:** не используй, пока не проверил на конкретной гостевой ОС и нагрузке. Отключается через `balloon: 0` в конфигурации машины.

**NUMA:** включай для машин с 4 и более ядрами или от 8 ГБ памяти. В Proxmox: `numa: 1` в конфигурации. QEMU сам создаёт узлы NUMA по топологии хоста.

**Огромные страницы:** страницы 2 МБ или 1 ГБ уменьшают промахи TLB. Это заметно для баз данных и нагрузок, требовательных к памяти. Настрой на хосте:

```bash
# Зарезервировать 1024 страницы по 2 МБ (всего 2 ГБ)
echo 1024 > /proc/sys/vm/nr_hugepages
# Постоянно: добавить в /etc/sysctl.d/
vm.nr_hugepages = 1024
```

Затем включи в конфигурации машины. Учти: память огромных страниц нельзя разделять или отдавать через раздувание.

**Горячее добавление процессора и памяти:** процессор добавляется на ходу в большинстве современных гостевых Linux. Горячее добавление памяти (модули DIMM во время работы) требует `hotplug: memory` и NUMA у машины, а также гостевой системы, которая включает новые блоки, обычно через правило udev; без всех трёх условий изменение провалится молча. Это другой механизм, чем раздувание, которое лишь перемещает память между заданным минимумом и `memory:`. Задавай память правильно при создании.

## Выбор гипервизора

| Гипервизор | Тип | Для чего лучше | Когда избегать |
|------------|------|----------|------------|
| **Proxmox VE** | Тип 1 (KVM и LXC) | Домашняя лаборатория, малый и средний бизнес, автоматизация через API | Нужен инструментарий экосистемы VMware |
| **libvirt/KVM** | Тип 1 | Нестандартные схемы, OpenStack, прямой контроль | Нужен графический интерфейс или кластеризация из коробки |
| **XCP-ng** | Тип 1 (Xen) | Инфраструктура на Xen, интерфейс XenOrchestra | Нужны возможности KVM (virtio-fs) |
| **VMware ESXi** | Тип 1 | Крупные организации с уже вложенными средствами в VMware | После Broadcom: лицензионные расходы резко выросли |
| **VirtualBox** | Тип 2 | Рабочие станции разработчиков, тесты | Эксплуатация — никогда |

**VMware после Broadcom (2026):** Broadcom приобрела VMware (сделка закрыта в ноябре 2023). Бессрочные лицензии упразднены, осталась только подписка; бесплатный ESXi был прекращён, затем частично возвращён (ESXi 8.0 U3e, апрель 2025). Многие организации переезжают на Proxmox или XCP-ng. Путь миграции с VMware хорошо документирован, но для крупных хозяйств нетривиален.

## Правила

1. **Для изменений оборудования — остановка и запуск, а не перезагрузка.** Перезагрузка гостевой системы не перезапускает QEMU. Останови аккуратно, убедись в остановленном состоянии и запусти заново; принудительная остановка требует отдельного обоснования.
2. **У размера диска один владелец.** Либо рост через `disk.size` в bpg/proxmox без игнорирования `disk`, либо `qm resize` на хосте с игнорируемым `disk` — никогда оба сразу. Завершай `growpart` и затем `resize2fs` или `xfs_growfs` в гостевой системе.
3. **Отключай раздувание памяти по умолчанию.** Включай только после проверки на конкретной гостевой ОС.
4. **Следи за `data_percent` тонкого пула.** Предупреждение на 80%, критично на 90%. При 100% весь ввод-вывод отказывает.
5. **Для долгих миграций используй `nohup`.** Разрыв SSH убивает `qm migrate` в переднем плане.
6. **`prevent_destroy` и `ignore_changes` для машин в Terraform.** Защита от случайного удаления; игнорируй `node_name` и сгенерированный MAC, чтобы живая миграция не выглядела расхождением. Добавляй `disk` в `ignore_changes` только на пути, где размером владеет хост (правило 2).
7. **Проверяй до эксплуатации.** Новые конфигурации машин, схемы проброса, хранилища — сначала на некритичной машине.
