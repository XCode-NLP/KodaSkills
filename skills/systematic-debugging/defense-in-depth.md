# Проверки в глубину

## Обзор

Когда ты исправляешь ошибку из-за неверных данных, проверка в одном месте кажется
достаточной. Но эту единственную проверку можно обойти другим путём в коде,
рефакторингом или подделкой.

**Главный принцип:** проверяй на КАЖДОМ слое, через который проходят данные.
Сделай ошибку структурно невозможной.

## Зачем несколько слоёв

Одна проверка: «мы исправил ошибку».
Несколько слоёв: «мы сделал ошибку невозможной».

Разные слои ловят разные случаи:

- проверка на входе ловит большинство ошибок;
- бизнес-логика ловит крайние случаи;
- защита окружения предотвращает опасности конкретного контекста;
- отладочное журналирование помогает, когда другие слои не справились.

## Четыре слоя

### Слой 1: проверка на входе

**Назначение:** отклонять очевидно неверный ввод на границе API.

```typescript
function createProject(name: string, workingDirectory: string) {
  if (!workingDirectory || workingDirectory.trim() === '') {
    throw new Error('workingDirectory cannot be empty');
  }
  if (!existsSync(workingDirectory)) {
    throw new Error(`workingDirectory does not exist: ${workingDirectory}`);
  }
  if (!statSync(workingDirectory).isDirectory()) {
    throw new Error(`workingDirectory is not a directory: ${workingDirectory}`);
  }
  // ... продолжаем
}
```

### Слой 2: проверка в бизнес-логике

**Назначение:** убедиться, что данные имеют смысл для этой операции.

```typescript
function initializeWorkspace(projectDir: string, sessionId: string) {
  if (!projectDir) {
    throw new Error('projectDir required for workspace initialization');
  }
  // ... продолжаем
}
```

### Слой 3: защита окружения

**Назначение:** предотвращать опасные операции в конкретных контекстах.

```typescript
async function gitInit(directory: string) {
  // В тестах запрещаем git init вне временных каталогов
  if (process.env.NODE_ENV === 'test') {
    const normalized = normalize(resolve(directory));
    const tmpDir = normalize(resolve(tmpdir()));

    if (!normalized.startsWith(tmpDir)) {
      throw new Error(
        `Refusing git init outside temp dir during tests: ${directory}`
      );
    }
  }
  // ... продолжаем
}
```

### Слой 4: отладочное инструментирование

**Назначение:** сохранить контекст для разбора.

```typescript
async function gitInit(directory: string) {
  const stack = new Error().stack;
  logger.debug('About to git init', {
    directory,
    cwd: process.cwd(),
    stack,
  });
  // ... продолжаем
}
```

## Как применять образец

Когда ты нашёл ошибку:

1. **Проследи путь данных** — откуда пришло неверное значение? Где используется?
2. **Наметь все контрольные точки** — перечисли каждую точку, через которую
   проходят данные.
3. **Добавь проверку на каждом слое** — вход, бизнес-логика, окружение, отладка.
4. **Проверь каждый слой** — попробуй обойти слой 1 и убедись, что слой 2 это
   поймает.

## Пример из сессии

Ошибка: пустой `projectDir` вызвал `git init` в исходном коде.

**Путь данных:**

1. подготовка теста → пустая строка
2. `Project.create(name, '')`
3. `WorkspaceManager.createWorkspace('')`
4. `git init` выполняется в `process.cwd()`

**Добавлено четыре слоя:**

- слой 1: `Project.create()` проверяет, что значение не пустое, существует и
  доступно для записи;
- слой 2: `WorkspaceManager` проверяет, что projectDir не пустой;
- слой 3: `WorktreeManager` в тестах запрещает git init вне временного каталога;
- слой 4: журналирование трассировки стека перед git init.

**Результат:** все 1847 тестов прошёл, ошибка не воспроизводится.

## Ключевое наблюдение

Все четыре слоя был нужны. При тестировании каждый слой ловил ошибки, которые
пропускали остальные:

- разные пути в коде обходил проверку на входе;
- подделки обходил проверки бизнес-логики;
- крайние случаи на разных платформах требовали защиты окружения;
- отладочное журналирование выявило структурное неправильное использование.

**Не останавливайся на одной проверке.** Добавляй проверки на каждом слое.
