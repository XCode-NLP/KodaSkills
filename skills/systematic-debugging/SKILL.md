# Систематическая отладка

## Обзор

**Главный принцип:** ВСЕГДА сначала найди корневую причину, и только потом исправляй. Исправление симптома — это провал.

**Нарушение буквы этого процесса означает нарушение сути отладки.**

## Железный закон

```
НИКАКИХ ИСПРАВЛЕНИЙ БЕЗ ПРЕДВАРИТЕЛЬНОГО ПОИСКА КОРНЕВОЙ ПРИЧИНЫ
```

Если ты не завершил этап 1, предлагать исправления нельзя.

## Когда использовать

Используй при любой технической проблеме:

- сбои тестов
- ошибки в рабочей среде
- неожиданное поведение
- проблемы производительности
- сбои сборки
- проблемы интеграции

**Используй ОСОБЕННО тогда, когда:**

- давит время (в аварийной ситуации хочется угадывать)
- «одно быстрое исправление» кажется очевидным
- ты уже перепробовал несколько исправлений
- предыдущее исправление не помогло
- ты не до конца понимаешь проблему

**Не пропускай, если:**

- проблема кажется простой (у простых ошибок тоже есть корневые причины)
- ты спеши (спешка гарантирует переделку)
- руководитель требует исправить СЕЙЧАС (системный подход быстрее, чем метания)

## Четыре этапа

Каждый этап нужно завершить до перехода к следующему.

### Этап 1: поиск корневой причины

**ДО любых попыток исправления:**

1. **Внимательно читай сообщения об ошибках**
   - не пропускай ошибки и предупреждения
   - в них часто есть точное решение
   - читай трассировку стека целиком
   - запоминай номера строк, пути к файлам, коды ошибок

2. **Добейся воспроизведения**
   - удаётся ли вызвать проблему надёжно?
   - каковы точные шаги?
   - происходит ли это каждый раз?
   - если не воспроизводится → собирай данные, не угадывай

3. **Проверь недавние изменения**
   - что изменилось и могло это вызвать?
   - `git diff`, последние коммиты
   - новые зависимости, изменения конфигурации
   - различия окружения

4. **Собери доказательства в многосоставных системах**

   **КОГДА в системе несколько компонентов (сборка → подпись, API → сервис → база данных):**

   **ДО предложения исправлений добавь диагностику:**

   ```
   Для КАЖДОЙ границы компонентов:
     - логируй, какие данные входят в компонент
     - логируй, какие данные выходят из компонента
     - проверь передачу окружения и конфигурации
     - проверь состояние на каждом слое

   Запусти один раз, чтобы увидеть, ГДЕ ломается
   ЗАТЕМ проанализируй данные и определи сбойный компонент
   ЗАТЕМ разбирай именно этот компонент
   ```

   **Пример (многослойная система):**

   ```bash
   # Слой 1: рабочий процесс
   echo "=== Секреты, доступные в процессе: ==="
   echo "IDENTITY: $([ -n "${IDENTITY:-}" ] && echo SET || echo UNSET)"

   # Слой 2: скрипт сборки
   echo "=== Переменные окружения в скрипте сборки: ==="
   printenv IDENTITY >/dev/null 2>&1 && echo "IDENTITY в окружении" || echo "IDENTITY нет в окружении"

   # Слой 3: скрипт подписи
   echo "=== Состояние связки ключей: ==="
   security list-keychains
   security find-identity -v

   # Слой 4: фактическая подпись
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **Это показывает:** какой слой сбоит (секреты → процесс ✓, процесс → сборка ✗)

5. **Проследи путь данных**

   **КОГДА ошибка глубоко в стеке вызовов:**

   Полная техника обратной трассировки описана в файле `root-cause-tracing.md` рядом с этим файлом.

   **Краткая версия:**
   - откуда пришло неверное значение?
   - что вызвало этот код с неверным значением?
   - поднимайся по стеку, пока не найдешь источник
   - исправляй в источнике, а не в симптоме

### Этап 2: анализ закономерностей

**Найди закономерность до исправления:**

1. **Найди работающие примеры**
   - найди похожий работающий код в том же проекте
   - что работает так же, как сломанное?

2. **Сравни с эталоном**
   - если реализуешь известную схему, прочитай эталонную реализацию ЦЕЛИКОМ
   - не пробегай глазами — читай каждую строку
   - пойми схему полностью, прежде чем применять

3. **Найди различия**
   - чем работающий вариант отличается от сломанного?
   - перечисли все различия, даже мелкие
   - не считай, что «это не может влиять»

4. **Пойми зависимости**
   - какие ещё компоненты нужны?
   - какие настройки, конфигурация, окружение?
   - какие допущения делаются?

### Этап 3: гипотеза и проверка

**Научный метод:**

1. **Сформулируй одну гипотезу**
   - скажи прямо: «Думаю, корневая причина в X, потому что Y»
   - запиши это
   - будь конкретны, не размыты

2. **Проверяй минимально**
   - внеси МАКСИМАЛЬНО малое изменение, чтобы проверить гипотезу
   - одна переменная за раз
   - не исправляй несколько вещей сразу

3. **Убедись в результате до продолжения**
   - сработало? Да → этап 4
   - не сработало? Сформулируй НОВУЮ гипотезу
   - НЕ добавляй новые исправления поверх

4. **Когда ты не знаешь**
   - скажи «Я не понимаю X»
   - не делай вид, что знаешь
   - попроси помощи
   - изучи вопрос

### Этап 4: реализация

**Исправляй корневую причину, а не симптом:**

1. **Создай падающий тест**
   - максимально простое воспроизведение
   - автоматический тест, если возможно
   - отдельный скрипт, если нет тестовой среды
   - он ДОЛЖЕН появиться до исправления
   - для правильного падающего теста используй навык `superpowers:test-driven-development`

2. **Внеси одно исправление**
   - устрани найденную корневую причину
   - ОДНО изменение за раз
   - никаких улучшений «раз уж я здесь»
   - никакого попутного рефакторинга

3. **Проверь исправление**
   - тест теперь проходит?
   - другие тесты не сломались?
   - проблема действительно решена?
   - перед заявлением об успехе используй навык `superpowers:verification-before-completion`

4. **Если исправление не помогло**
   - СТОП
   - посчитай: сколько исправлений ты уже попробовал?
   - если меньше трёх: вернись к этапу 1 и пересмотри анализ с новыми данными
   - **если три и больше: СТОП и поставь под сомнение архитектуру (шаг 5)**
   - НЕ пытайся сделать исправление №4 без обсуждения архитектуры

5. **Если три и больше исправлений не помог: сомневайся в архитектуре**

   **Признаки архитектурной проблемы:**
   - каждое исправление вскрывает новое общее состояние, связанность или проблему в другом месте
   - для исправлений требуется «масштабный рефакторинг»
   - каждое исправление порождает новые симптомы в других местах

   **СТОП и поставь под сомнение основы:**
   - эта схема вообще правильна?
   - не «держимся ли мы за неё по инерции»?
   - не пора ли переделать архитектуру вместо исправления симптомов?

   **Обсуди это со своим собеседником, прежде чем делать новые исправления**

   Это не провалившаяся гипотеза — это неверная архитектура.

## Тревожные сигналы — СТОП и следуй процессу

Если поймал себя на мыслях:

- «Быстро исправлю, потом разберусь»
- «Просто попробую изменить X и посмотрю, что будет»
- «Добавлю несколько изменений и запущу тесты»
- «Пропущу тест, проверю вручную»
- «Наверное, дело в X, давай это исправим»
- «Я не до конца понимаю, но, может, сработает»
- «В описании схемы сказано X, но я сделаю иначе»
- «Вот основные проблемы: [список исправлений без исследования]»
- предложение решений до трассировки данных
- **«Ещё одна попытка исправления» (когда уже две и больше)**
- **каждое исправление вскрывает новую проблему в другом месте**

**ВСЁ это значит: СТОП. Вернись к этапу 1.**

**Если три и больше исправлений не помог:** сомневайся в архитектуре (см. этап 4, шаг 5).

## Сигналы от собеседника, что ты делаешь не так

**Следи за такими поправками:**

- «Разве это происходит?» — ты допустил, не проверив
- «Оно нам это покажет?» — надо было добавить сбор доказательств
- «Хватит угадывать» — ты предлагаешь исправления, не понимая причину
- «Подумай как следует» — сомневайся в основах, а не только в симптомах
- «Мы застрял?» (с раздражением) — твой подход не работает

**Заметив такое:** СТОП. Вернись к этапу 1.

## Частые оправдания

| Оправдание | Действительность |
|--------|---------|
| «Проблема простая, процесс не нужен» | У простых проблем тоже есть корневые причины. Для простых ошибок процесс быстрый. |
| «Авария, на процесс нет времени» | Систематическая отладка БЫСТРЕЕ, чем метания по принципу «угадай и проверь». |
| «Сначала попробую это, потом разберусь» | Первое исправление задаёт образец. Делай правильно с самого начала. |
| «Напишу тест после того, как убедюсь, что исправление работает» | Непроверенные исправления не держатся. Тест до исправления это доказывает. |
| «Несколько исправлений сразу экономят время» | Нельзя понять, что помогло. Появляются новые ошибки. |
| «Эталон слишком длинный, я адаптирую схему» | Частичное понимание гарантирует ошибки. Читай целиком. |
| «Я вижу проблему, давай исправлю» | Видеть симптом ≠ понимать корневую причину. |
| «Ещё одна попытка исправления» (после двух и более сбоев) | Три и больше сбоев = архитектурная проблема. Сомневайся в схеме, а не исправляй снова. |

## Краткая справка

| Этап | Ключевые действия | Критерий успеха |
|-------|---------------|------------------|
| **1. Корневая причина** | Читать ошибки, воспроизводить, проверять изменения, собирать доказательства | Понимание ЧТО и ПОЧЕМУ |
| **2. Закономерность** | Найти работающие примеры, сравнить | Выявленные различия |
| **3. Гипотеза** | Сформулировать теорию, проверить минимально | Подтверждённая или новая гипотеза |
| **4. Реализация** | Создать тест, исправить, проверить | Ошибка устранена, тесты проходят |

## Когда процесс показывает, что «корневой причины нет»

Если систематическое исследование показало, что проблема действительно связана с окружением, временем или внешними системами:

1. ты прошёл процесс до конца
2. опиши, что именно исследовали
3. реализуй подходящую обработку (повтор, таймаут, сообщение об ошибке)
4. добавь мониторинг и логирование для будущего разбора

**Но:** в 95% случаев «корневой причины нет» означает неполное исследование.
