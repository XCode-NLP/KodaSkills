# Разбор снимков трафика через tshark

Навык описывает работу утилитами Wireshark из командной строки: как найти нужный канал в снятом обмене, вытащить из него кадры и поля, посчитать статистику, снять новый снимок и подготовить его к разбору.

Если разбор должен работать без установленного tshark, повторяемо и в автоматических проверках, лучше проигнорировать этот анвык и написать собственный парсер.

`tshark` удобен для исследования, а не как зависимость готового инструмента.

## Когда применять

- Нужно быстро посмотреть, что лежит в снимке, и не писать ради этого код.
- Нужно вытащить кадры одного канала или одной команды в текстовом виде.
- Нужно снять трафик с живого устройства или интерфейса и сразу ограничить его по времени или длине.
- Нужно обрезать, склеить, распаковать или пересжать готовые снимки перед разбором.
- Нужно сверить гипотезу о формате кадра с тем, как его разбирает сам Wireshark.

## Проверка окружения

```sh
tshark -v                            # версия и поддерживаемые форматы
tshark -G protocols | grep -i usb    # какие диссекторы включены
tshark -G fields | grep -i usb       # какие поля есть в этой версии
dumpcap -D                           # интерфейсы для живого захвата
```

Набор полей и вид вывода меняются между версиями, поэтому команды ниже стоит сверять с `-G fields`, а не считать вечными.

## Утилиты

| Утилита    | Назначение                                                |
|------------|-----------------------------------------------------------|
| `tshark`   | чтение, фильтрация, статистика, короткая съёмка           |
| `dumpcap`  | долгая запись, кольцевой буфер, ограничение длины кадра   |
| `editcap`  | обрезка по времени, слияние дублей, смена формата, сжатие |
| `mergecap` | склейка файлов в хронологическом порядке                  |
| `capinfos` | паспорт файла: число кадров, длительность, интерфейсы     |

## Порядок работы

1. **Сними паспорт файла.**
   `capinfos` покажет число кадров, длительность, формат и список интерфейсов, и по нему сразу видно, стоит ли читать файл целиком.
2. **Посмотри иерархию протоколов.**
   `-z io,phs` отвечает на вопрос, что вообще в файле: один транспорт, несколько или служебные записи вперемешку с данными.
3. **Найди участников обмена.**
   `-z endpoints` даёт адреса и объём по каждому, `-z conv` — разбивку по направлениям и парам.
   Рабочий канал прикладного обмена обычно тот, где много кадров одинаковой длины.
4. **Отдели полезную нагрузку от метаданных.**
   Служебные записи и пустые завершения отсекаются фильтром по непустым данным.
5. **Вытащи кадры в текстовом виде.**
   Сначала `-T fields` с полями адреса, длины и данных, затем сузьте выборку фильтром по каналу и коду команды.
6. **Посчитай статистику.**
   `-z io,stat` по интервалу показывает частоту кадров, а `-z expert` — битые и обрезанные пакеты.
7. **Сверь вывод с разбором Wireshark.**
   `-V` или `-O <протокол>` на одном кадре показывает, как инструмент трактует поля; расхождение с гипотезой — повод перепроверить смещения.

## Поля, которые нужны чаще всего

Общие поля кадра:

| Поле                                         | Тип            | Что содержит                                |
|----------------------------------------------|----------------|---------------------------------------------|
| `frame.number`                               | uint32         | номер кадра в файле                         |
| `frame.len`, `frame.cap_len`                 | uint32         | длина кадра и длина сохранённой части       |
| `frame.time_relative`                        | time           | время от первого кадра, удобно для периодов |
| `frame.interface_id`, `frame.interface_name` | uint32, string | интерфейс, с которого снят пакет            |
| `frame.protocols`                            | string         | цепочка протоколов кадра                    |
| `_ws.col.Protocol`, `_ws.col.Info`           | string         | колонки списка пакетов                      |

Поля USB.
Имена одинаковы для usbmon, USBPcap и захвата на macOS, но заполняются они по-разному:

| Поле                                | Тип      | Что содержит                                       |
|-------------------------------------|----------|----------------------------------------------------|
| `usb.src`, `usb.dst`                | string   | адрес источника и получателя                       |
| `usb.bus_id`                        | uint16   | шина, на которой снят пакет                        |
| `usb.device_address`                | uint8    | адрес устройства на шине                           |
| `usb.idVendor`, `usb.idProduct`     | uint16   | VID и PID из `GET DESCRIPTOR`                      |
| `usb.transfer_type`                 | uint8    | `0` iso, `1` interrupt, `2` control, `3` bulk      |
| `usb.endpoint_address`              | uint8    | адрес конечной точки вместе с битом `0x80`         |
| `usb.endpoint_address.number`       | uint8    | номер конечной точки без бита направления          |
| `usb.endpoint_address.direction`    | uint8    | `0` — в устройство, `1` — из устройства            |
| `usb.capdata`                       | bytes    | payload interrupt, bulk и iso                      |
| `usb.data_fragment`                 | bytes    | данные фазы control-трансфера                      |
| `usbhid.data`                       | bytes    | payload HID, если отчёт разобрал HID-диссектор     |
| `usb.data_len`                      | uint32   | длина данных, которую ожидало устройство           |
| `usb.urb_len`, `usb.totlen`         | uint32   | ожидаемая длина трансфера                          |
| `usb.urb_status`                    | int32    | код ошибки трансфера, ненулевой у сбоев            |
| `usb.irp_id`, `usb.urb_id`          | uint64   | идентификатор запроса, не ключ склейки             |
| `usb.setup.bmRequestType`           | uint8    | тип и получатель setup-запроса                     |
| `usb.setup.bRequest`                | uint8    | код запроса, например `0x09` — `SET_REPORT`        |
| `usb.setup.wValue`                  | uint16   | у HID: тип отчёта в старшем бай, номер в младшем |
| `usb.setup.wIndex`                  | uint16   | обычно номер интерфейса                            |
| `usb.setup.wLength`                 | uint16   | длина фазы данных                                  |
| `usb.request_in`, `usb.response_in` | framenum | номер парного кадра, нужен `-2`                    |
| `usb.bad_length`, `usb.undecoded`   | label    | признаки битого или неразобранного кадра           |

В сетевом снимке полезны `ip.addr`, `ipv6.addr`, `tcp.stream`, `tcp.port`, `udp.stream`, `udp.port`, `tls.handshake.type`, `http.request.method` и `data.data`.
Payload в сети лежит в `tcp.payload`, `udp.payload` или `data.data`, а не в `usb.*`.

## Готовые команды

| Задача                      | Команда                                                                |
|-----------------------------|------------------------------------------------------------------------|
| Паспорт файла               | `capinfos -c -u -S capture.pcapng`                                     |
| Иерархия протоколов         | `tshark -r c.pcapng -q -z io,phs`                                      |
| Устройства и конечные точки | `tshark -r c.pcapng -q -z endpoints,usb`                               |
| Объём обмена по парам       | `tshark -r c.pcapng -q -z conv,usb`                                    |
| Сетевые сессии              | `tshark -r c.pcapng -q -z conv,tcp`                                    |
| Кадры одного канала         | `tshark -r c.pcapng -Y 'usb.endpoint_address == 0x81'`                 |
| Только payload в hex        | `tshark -r c.pcapng -T fields -e @usb.capdata`                         |
| Поля в TSV с шапкой         | `tshark -r c.pcapng -T fields -E header=y -e frame.number`             |
| Команда и её ответ          | `tshark -2 -r c.pcapng -T fields -e usb.request_in -e usb.response_in` |
| Частота кадров по времени   | `tshark -r c.pcapng -q -z io,stat,0`                                   |
| Битые кадры                 | `tshark -r c.pcapng -q -z expert`                                      |
| Экспорт в JSON              | `tshark -r c.pcapng -T json -x > capture.json`                         |
| Оставить только канал       | `tshark -r c.pcapng -Y 'usb.endpoint_address == 0x81' -w ch.pcapng`    |
| Обрезка по времени          | `editcap -A '2026-01-01 12:00:00' -B '2026-01-01 12:00:10' in out`     |
| Слияние дублей              | `editcap -d in out`                                                    |
| Склейка двух файлов         | `mergecap -w all.pcapng a.pcapng b.pcapng`                             |
| Сжатие на выходе            | `editcap --compress gzip in out.pcapng.gz`                             |

## Фильтры

```sh
# только кадры с полезной нагрузкой, без служебных записей и пустых завершений
-Y 'usb.data_len != 0 && (usb.capdata || usb.data_fragment)'

# один канал в одном направлении
-Y 'usb.endpoint_address == 0x81 && usb.endpoint_address.direction == 1'

# control-запись отчёта: SET_REPORT с непустыми данными
-Y 'usb.transfer_type == 0x02 && usb.setup.bRequest == 0x09 && usb.data_fragment'

# один интерфейс в файле с несколькими источниками
-Y 'frame.interface_id == 1'

# ошибки обмена
-Y 'usb.urb_status != 0 || usb.bad_length'

# сетевой пример: одна TCP-сессия
-Y 'tcp.stream == 3'
```

Поля печатаются в том порядке, в каком указаны `-e`.
`-E header=y` добавляет шапку, `-E separator=/t` задаёт разделитель, `-E occurrence=f` оставляет первое вхождение поля в кадре.
Префикс `@` в имени поля печатает байтовую последовательность в hex.

## Живой захват

Запись снимается `dumpcap`: `tshark` для долгой записи теряет кадры, потому что разбирает поток на лету.

```sh
dumpcap -D                                           # список интерфейсов
dumpcap -i <iface> -w capture.pcapng                 # запись до Ctrl+C
dumpcap -i <iface> -a duration:30 -w capture.pcapng  # запись на 30 секунд
dumpcap -i <iface> -s 128 -w capture.pcapng          # ограничить длину кадра
dumpcap -i <iface> -b filesize:10240 -b files:10 -w ring.pcapng
```

USB-интерфейсы зависят от системы: на Linux это `usbmonN` после загрузки модуля `usbmon`, на Windows — `USBPcapN` из комплекта Wireshark, на macOS — интерфейсы вида `XHC…`.
Номер шины на Linux берётся из `lsusb`, а нужный интерфейс на Windows и macOS выбирается по списку `-D`.
Имена интерфейсов и номера шин меняются между машинами и перезагрузками, поэтому их нельзя зашивать в скрипты.

Права на захват требуются отдельно: повышенные права или возможности на `dumpcap`.
Менять правила `udev`, выдавать capability или править системные настройки самостоятельно нельзя — это решение владельца машины.

Ограничивай длину кадра: прикладной обмен устройства редко превышает сотню байт, а полный кадр тянет заголовки в каждый пакет.
Фильтровать живой захват по полям протоколов нельзя: у `-f` другой язык, и полей вроде `usb.*` или `tcp.flags` в нём нет.
Снимай всё и сужай выборку потом через `-Y`.

## Пример разбора

Пусть есть снимок обмена с устройством: в файле два интерфейса, а прикладной обмен идёт по interrupt-каналу кадрами фиксированной длины.

1. Паспорт и состав: `capinfos -c -u capture.pcapng` и `tshark -r capture.pcapng -q -z io,phs`.
2. Участники и каналы: `tshark -r capture.pcapng -q -z endpoints,usb`; рабочий канал — тот, где много кадров одной длины.
3. Кадры канала: `tshark -r capture.pcapng -Y 'usb.endpoint_address == 0x81' -T fields -E header=y -e frame.number -e usb.data_len -e @usb.capdata`.
4. Код команды ищется по позиционной статистике: выгрузи payload и посчитай, какие байты постоянны на каждом смещении.
   `tshark` такой статистики не даёт, её считают по выгрузке.
5. Сверка: `tshark -r capture.pcapng -Y 'frame.number == 17' -V` показывает, как Wireshark разбирает один кадр, и помогает проверить смещения.

Второй снимок, отличающийся одной настройкой, подтверждает трактовку полей быстрее, чем разбор первого.

## Ловушки

Порядок — это частота, с которой они портят разбор.

### Payload лежит в разных полях

`usb.capdata` — данные interrupt, bulk и iso, `usb.data_fragment` — данные control-фазы, `usbhid.data` — HID-отчёт после разбора диссектором.
В сети это `tcp.payload`, `udp.payload` или `data.data`.
Если искать только в одном поле, легко получить пустоту и решить, что кадров нет.

### `-T fields` портит длинные байтовые поля

Длинные последовательности в табличном выводе обрезаются, а при нескольких вхождениях поля склеиваются разделителем.
Если payload длиннее десятков байт, бери `-T json` или `-T pdml` и разбирай структуру, а не строку.
Для коротких кадров `-T fields` удобнее и дешевле.

### Парные кадры видны только при `-2`

`usb.request_in`, `usb.response_in` и подобные ссылки заполняются вторым проходом.
В однопроходном режиме они пусты, и пары «команда — ответ» приходится искать глазами.
`-2` требует файла на диске и заметно замедляет разбор большого снимка.

### `-z` без `-q` тонет в списке пакетов

Статистика печатается вместе с обычным выводом кадров.
Всегда добавляй `-q`, если нужны только цифры.

### `-Y` и `-f` — разные языки

`-Y` — display filter Wireshark, `-f` — фильтр захвата в синтаксисе pcap.
Ошибка в `-Y` даёт сообщение о неизвестном поле, ошибка в `-f` — «syntax error» и пустой файл.

### В фильтре захвата нет полей протоколов

`usb.*`, `tcp.flags`, `http.*` и подобные поля доступны только в `-Y`.
Сужай выборку при чтении файла, а не при записи.

### Сжатие определяется по содержимому

`tshark`, `editcap` и `capinfos` сами распознают gzip, zstd и lz4, а расширение файла игнорируют.
Файл `capture.pcapng` может быть сжат, а `capture.pcapng.gz` — лежать несжатым.
Не полагайсь на имя при выборе команды и не распаковывай файл заранее без нужды.

### Несколько интерфейсов в одном файле

pcapng хранит linktype в блоке IDB, а пакеты ссылаются на интерфейс по номеру.
Один файл может содержать разные транспорты и служебные интерфейсы сразу.
Смотри `-z io,phs` и `frame.interface_id`, иначе статистика смешает несвязанные каналы.

### Идентификатор запроса — не ключ склейки

У многих драйверов `irp_id` и `urb_id` переиспользуются подряд для всех запросов.
Склейка по ним даёт один «вечный» трансфер и теряет остальные.
Ориентируйсь на форму пакета и порядок следования.

### `-z follow` есть только у потоковых транспортов

Поток можно смотреть у tcp, udp, tls, http и подобных протоколов.
Для USB и других не-потоковых транспортов собирай кадры фильтром и склеивай сами.

### Обрезанный снимок выглядит как поломка протокола

Если запись шла с `-s`, payload короче ожидаемого, а кадр помечен `usb.bad_length`.
Проверяй `capinfos -l` и не считай короткий хвост ошибкой разбора.

### Версии различаются набором полей

`usbhid.data`, `usb.data_fragment` и `usb.bad_length` появились в разных версиях, а структура `-T json` местами менялась.
Скрипт, который разбирает вывод `tshark`, должен проверять версию или падать явно, а не молча выдавать пустые поля.

### Много вхождений одного поля

По умолчанию `-T fields` печатает все вхождения поля, склеивая их разделителем.
`-E occurrence=f` оставляет первое, `-E occurrence=l` — последнее, а `-E aggregator` задаёт свой разделитель.
Без этого разбор строки по позициям ломается на первом же кадре с несколькими значениями.

### Имена и адреса не переносимы

Имена интерфейсов, номера шин и адреса устройств зависят от машины, порта и перезагрузки.
Скрипт не должен опираться на них: подставляй значения из `-D`, `lsusb` или `-z endpoints`.

### Большой файл читается долго

`-2`, `-V` и `-T pdml` на гигабайтном снимке идут минутами.
Сначала отрежьте нужный участок `editcap -A/-B` или `-c`, потом разбирай.

## Как оформлять результат

Отделяй проверенное от предполагаемого.
В отчёте полезно указать:

- версию `tshark` и чем снят снимок;
- какие интерфейсы, участники и каналы есть в файле;
- какой канал выбран рабочим и по какому признаку;
- команды, которыми получены цифры, чтобы их можно было повторить;
- что подтверждено вторым снимком, а что выведено из одного.
