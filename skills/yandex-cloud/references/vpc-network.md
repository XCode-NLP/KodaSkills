# VPC — Virtual Private Cloud

Каноническая документация: https://github.com/yandex-cloud/docs/tree/master/ru/vpc · Публичная: https://yandex.cloud/ru/docs/vpc/

## Иерархия

```
Облако (корень биллинга)
└── Каталог              (область IAM и квот)
    ├── Сети            (частное наложение; несколько подсетей по зонам)
    │   └── Подсети     (CIDR на зону)
    ├── Группы безопасности (stateful-файрвол)
    ├── Таблицы маршрутов    (свои маршруты — NAT-шлюз, пиринг)
    └── Ресурсы Compute, управляемых БД, Kubernetes
```

**Сеть** охватывает зоны; **подсети** зональны. Ресурс выбирает подсеть при создании → это фиксирует его зону.

## Сеть по умолчанию

Создаётся автоматически при инициализации облака: одна сеть `default`, по одной подсети на зону (`default-ru-central1-a` и т. д.) с CIDR `10.128.0.0/24`, `10.129.0.0/24` и так далее. Подходит для разработки — для продакшена замени.

## Планируй CIDR

Выбирай **непересекающиеся** с локальной сетью (для VPN) и с пирингом AWS и GCP. Пример:

| Сеть | Зона | CIDR подсети |
|---|---|---|
| `prod-net` | `ru-central1-a` | `10.10.0.0/20` |
| `prod-net` | `ru-central1-b` | `10.10.16.0/20` |
| `prod-net` | `ru-central1-d` | `10.10.32.0/20` |

Не делай подсети слишком большими: после создания CIDR расширить нельзя.

## Группы безопасности (stateful-файрвол)

Входящий трафик по умолчанию запрещён, исходящий разрешён. Привязываются к машинам Compute, хостам управляемых БД, ALB, целям NLB, узлам Kubernetes.

```bash
yc vpc security-group create \
  --name app-sg --network-name prod-net \
  --rule "direction=ingress,port=443,protocol=tcp,v4-cidrs=[0.0.0.0/0]" \
  --rule "direction=ingress,port=22,protocol=tcp,v4-cidrs=[YOUR_OFFICE_IP/32]" \
  --rule "direction=egress,from-port=0,to-port=65535,protocol=any,v4-cidrs=[0.0.0.0/0]"
```

**Правило продакшена**: никакого порта 22 из `0.0.0.0/0`. Только IP офиса или бастион.

Для трафика между сервисами разрешай по ссылке на группу безопасности, а не по CIDR:

```bash
yc vpc security-group update-rules app-sg \
  --add-rule "direction=ingress,port=5432,protocol=tcp,security-group-id=$(yc vpc security-group get db-sg --format value)"
```

Это означает «всё из `db-sg` может обращаться ко мне по 5432» — правило переживает смену IP.

## NAT-шлюз

Для частных подсетей, которым нужен выход в интернет (например, `apt update`) без публичных IP на каждой машине:

```bash
yc vpc gateway create --name natgw --shared-egress-gateway-config ""
yc vpc route-table create --name prod-rt --network-name prod-net \
  --route "destination=0.0.0.0/0,gateway-id=$(yc vpc gateway get natgw --format value)"
yc vpc subnet update default-ru-central1-a --route-table-name prod-rt
```

После этого машины в этой подсети без публичных IP всё равно могут обращаться наружу. Исходящий трафик тарифицируется.

## Пиринг и связность

| Что нужно | Инструмент |
|---|---|
| Две сети YC в одном или разных облаках | **Yandex Cloud Interconnect** (платно, BGP) или мост через NAT-машину |
| YC ↔ локальная сеть | **Cloud Interconnect** (выделенный) или **VPN-шлюз** (IPsec) |
| YC ↔ AWS и GCP | VPN-шлюз (IPsec) через партнёра |

Для большинства проектов это не нужно; проектируй в пределах одной сети.

## Частный DNS

`yc dns` даёт частные зоны — внутренние сервисы разрешают `db.prod.internal` в частные IP внутри VPC и никогда публично. Используй это вместо зашитых FQDN управляемых БД.

## Подводные камни

| Симптом | Причина | Что делать |
|---|---|---|
| У машины нет интернета | Нет NAT-шлюза и нет публичного IP | Либо NAT-шлюз и свой маршрут, либо `assign-public-ip=true` |
| Managed PG недоступен с машины | Разные сети или группы безопасности не разрешают | Одна сеть; входящее правило от группы безопасности машины |
| Конфликт CIDR при пиринге | Пересечение с другой сетью | Перепланируй; создай новые подсети в непересекающемся диапазоне |
| `getaddrinfo ENOTFOUND <fqdn>` с машины | DNS не настроен на частную зону | `resolv.conf` должен смотреть на `169.254.169.254` (cloud-init по умолчанию это делает) |
| Правка правила группы безопасности вызвала простой | Забыл исходящее правило при смене умолчаний | Сначала проверяй группу через `nc -zv host port` с другой машины |

## Смежные темы

- Машины живут в подсетях → `compute.md`
- Хосты управляемых БД выбирают подсеть при создании → `managed-databases.md`
- ALB и NLB используют группы безопасности и подсети → `load-balancer.md`
- Кластеры Kubernetes охватывают подсети по зонам → `kubernetes.md`
