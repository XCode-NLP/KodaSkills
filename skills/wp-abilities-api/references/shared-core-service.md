# Общий сервис ядра — держим возможности синхронными с REST и интерфейсом

Когда возможность повторяет то, что человек уже может сделать через поддерживаемый
интерфейс или процесс, возможность ДОЛЖНА использовать тот же путь кода, что этот
интерфейс или процесс: те же права, те же проверки, те же бизнес-правила. Три места вызова
одной операции (интерфейс, REST, возможность, возможно ещё и CLI) со временем расходятся,
если все они не делегируют общему сервису.

Форма по умолчанию, которую рекомендует этот файл, — общий сервис, который используют и
возможность, и контроллер REST, и интерфейс. Направление возможности через существующий
контроллер REST (шаблон делегирования ниже) — условное сокращение: оно годится, когда
контроллер только читает данные и возможность выполняется преимущественно в контекстах
REST, но это неверное умолчание для любой возможности с реальным потенциалом роста. Здесь
описано, когда сокращение безопасно, когда нет и какие побочные эффекты существующего
пути REST чаще всего его дисквалифицируют.

Сначала прочитай `domain-vs-projection.md`: возможности — контракты сценариев
использования на предметном уровне, а интерфейс, REST, CLI и MCP — проекции. Этот файл
описывает механизм реализации, который держит эти проекции честными.

## Почему это важно

Зарегистрированная возможность, которая заново реализует логику вместо вызова
существующих путей кода, — источник расхождений. Расхождения проявляются предсказуемо:

- новый фильтр, добавленный в список интерфейса, не доходит до возможности;
- ужесточённая проверка прав на контроллере REST оставляет возможность недостаточно
  защищённой;
- правило проверки, добавленное в форму админки, отсутствует в возможности;
- переход состояния получает побочный эффект (журнал аудита, вебхук), который
  срабатывает при записи из интерфейса, но не при записи через возможность.

Ничто из этого не ломает возможность сразу. Это становится заметно только когда агент
вызывает возможность и результат тихо расходится с тем, что дала бы та же операция в
интерфейсе. К этому моменту возможность уже в работе, и расхождение трудно обнаружить без
контрактного теста, которого почти наверняка нет.

Решение — держать один источник бизнес-логики и считать возможность, REST, интерфейс и CLI
адаптерами над ним.

## Три формы колбэка выполнения

| Форма | Пример | Вывод |
|---|---|---|
| **Заново реализовать** логику в колбэке выполнения. | Колбэк выполняет свой SQL, применяет свои проверки прав, собирает свой ответ. | **Избегай.** Гарантированное расхождение при первом же изменении исходного пути кода. |
| **Делегировать существующему контроллеру REST** через `WP_REST_Request`. | Возможность собирает `WP_REST_Request` из своего ввода, отправляет через `rest_do_request()` и возвращает данные ответа. Отправленный запрос проходит проверку прав, валидацию и обработчик зарегистрированного контроллера. | **Условное сокращение.** Допустимо только когда выполняются *все три* условия: обработчик только читает данные (без побочных эффектов), сама операция — чтение и возможность выполняется преимущественно в контекстах REST. Прочитай раздел «Побочные эффекты существующего пути REST», прежде чем считать условия выполненными. |
| **Выделить класс сервиса**, который используют возможность, контроллер REST и обработчик интерфейса. | `My_Plugin::get_things_service()->list( $args )` вызывается из возможности, контроллера REST и обработчика админки. | **Умолчание.** Выбирай это, если не выполняются все условия делегирования выше. Это единственная форма, полностью устраняющая расхождения, и единственная, которая масштабируется, когда у эндпоинта позже появляется побочный эффект, парная операция записи или вызывающий код вне REST. |

Третья строка — умолчание, потому что только она отделяет возможность (предметную
возможность) от транспорта REST. Средняя строка — реальное сокращение: нет смысла
выделять сервис для `get_option('something')`, но область её применимости достаточно узка,
чтобы к ней приходили осознанно, а не по умолчанию. Выделение сервиса поначалу более
инвазивно (обычно это значит переписать существующий контроллер REST так, чтобы он вызывал
сервис, а не содержал логику), но именно оно выдерживает изменения.

## Как выглядит шаблон делегирования

Средняя строка таблицы — «делегировать существующему контроллеру REST» — это шаблон, а не
единственная каноническая вспомогательная функция. Минимальная форма достаточно мала,
чтобы написать её прямо в `execute_callback` возможности:

```php
public static function execute_get_things( $input = null ) {
    $request = new WP_REST_Request( 'GET', '/my-plugin/v1/things' );
    $request->set_query_params( (array) $input );

    $response = rest_do_request( $request );
    if ( $response->is_error() ) {
        return $response->as_error();
    }

    return $response->get_data();
}
```

Пять шагов: создать `WP_REST_Request` с нужным HTTP-методом и маршрутом; перенести `$input`
возможности в параметры запроса (или в тело для записей); отправить через
`rest_do_request()`, который проходит через зарегистрированный контроллер, включая его
`permission_callback` и побочные эффекты; превратить ошибочный ответ обратно в `WP_Error`,
чтобы вызывающий видел обычную ошибку; иначе вернуть данные.

В реальном коде такую обвязку обычно выносят в небольшую приватную вспомогательную
функцию, чтобы её использовали несколько колбэков. Форма этой функции вне рамок данного
файла; важно, что шаблон делегирования механически прост и не зависит от наличия
конкретного помощника фреймворка.

## Побочные эффекты существующего пути REST

Делегирующая возможность переиспользует весь путь кода контроллера REST, включая любые
побочные эффекты, которые контроллер даёт при каждом вызове:

- **Телеметрия использования и события аналитики** — возможность завышает показатели
  панелей трафиком агентов, и сигнал о происхождении «человек или агент» теряется. Двойной
  учёт метрик — тихий режим отказа: система «работает», а панели уезжают.
- **Журналы аудита** — записи приписываются актору «REST», которым на самом деле является
  агент. Расследование становится шумнее.
- **Хуки пользовательских событий** (`do_action(...)`) — слушатели этих хуков теперь
  срабатывают при каждом вызове возможности, с неожиданными побочными эффектами в
  несвязанных подсистемах.
- **Отправка писем и уведомлений** — вызовы агента порождают видимые пользователю
  уведомления, которых быть не должно.
- **Инвалидация кэша, перепланирование задач, захват блокировок** — безвредно, когда так
  задумано; вредно, когда срабатывает от трафика, которого обработчик не ожидал.
- **Стоимость первой инициализации REST** (производительность, не семантика).
  `rest_do_request()` вызывает `rest_get_server()`, который лениво создаёт `WP_REST_Server`
  и запускает `rest_api_init` при первом вызове в жизненном цикле запроса. В обычном
  HTTP-запросе REST эта стоимость оплачивается до того, как уровень возможностей вообще
  начнёт работу; в CLI, cron, агенте и транспортах MCP вне REST её оплачивает *первая*
  делегирующая возможность — в этот момент подключаются колбэки `register_rest_route()`
  всех плагинов. Стоимость одноразовая на жизненный цикл запроса (`rest_get_server()`
  защищён проверкой `if ( empty( $wp_rest_server ) )`), но на холодном пути первый вызов
  заметно медленный. Если возможность в основном работает вне контекстов REST, предпочитай
  прямой вызов лежащего в основе сервиса или класса запроса вместо `rest_do_request()`.

Решение — третья строка таблицы выше:

- выдели бизнес-логику в класс сервиса;
- пусть контроллер REST вызывает сервис И выдаёт свои побочные эффекты как тонкий
  адаптер;
- пусть возможность вызывает сервис напрямую, а НЕ контроллер REST. Возможность выдаёт
  свои побочные эффекты с пометкой возможности или никаких.

Так побочные эффекты остаются привязанными к поверхности, которая их вызывает, а
возможность по-прежнему использует ту же бизнес-логику, что интерфейс.

Если существующий эндпоинт REST только читает данные и не имеет побочных эффектов, шаблон
делегирования — нормальное сокращение.

## Правило публикации через MCP

Не публикуй REST И возможность для одной операции одному и тому же клиенту MCP. Выбери
одно.

Возможность — контракт для агента: типизирована схемой, защищена проверкой прав, названа
по смысловому намерению. Эндпоинт REST остаётся для интеграций без агентов (интерфейс,
существующие сторонние клиенты, внутренние сервисы, использующие контракт JSON). Уровень
MCP показывает возможность и скрывает эндпоинт REST.

Публикация обоих порождает у любой модели, видящей и то и другое, вопрос «какую
поверхность использовать?» — а ответ влияет на метрики, журналирование и обработку ошибок.
Выбирай возможность.

## Правило для `AGENTS.md`

Добавь в `AGENTS.md` плагина строку (в раздел, который описывает изменения кода в этой
области):

> Когда меняешь путь кода за зарегистрированной возможностью, проверь, не нужно ли
> обновить и возможность. Новый фильтр в лежащем в основе списке обычно означает, что
> возможность должна предоставлять тот же фильтр. Изменение прав означает, что проверку
> возможности, скорее всего, нужно подтянуть. Новый побочный эффект при записи может
> изменить то, что мы обещаем от возможности.

Это переносит нагрузку с «не забудь обновить возможность» на «модель, работающая с
изменением, напомнит». Во время написания это ничего не стоит и предотвращает самый
частый источник расхождений.

## Разобранный пример — выделение сервиса

Обычный плагин с ресурсом `Things`. До выделения контроллер REST содержит логику списка, а
возможность заново выполняет тот же код фильтрации, сортировки и пагинации:

```php
// includes/admin/class-rest-things-controller.php
class My_Plugin_REST_Things_Controller {
    public function get_things( WP_REST_Request $request ) {
        $args = self::sanitize_query_args( $request->get_params() );
        $rows = $this->repo->find( $args );

        // Побочные эффекты (аудит, хуки, уведомления) живут в адаптере REST.
        do_action( 'my_plugin/things_listed', $rows );

        return rest_ensure_response( array_map( [ $this, 'format' ], $rows ) );
    }
}

// src/Internal/Abilities/Abilities_Registrar.php
public static function execute_get_things( $input = null ) {
    // ПРОБЛЕМА: заново реализует санитизацию, вызов репозитория, форматирование.
    // Расходится при первом же изменении get_things() в контроллере.
    $args = MyPlugin\Sanitize::query_args( (array) $input );
    $rows = ( new MyPlugin\Things_Repo() )->find( $args );
    return array_map( [ MyPlugin\Things_Formatter::class, 'format' ], $rows );
}
```

После выделения оба пути используют `Things_Service::list()`:

```php
// src/Service/class-things-service.php
class Things_Service {
    public function list_things( array $args ) {
        $clean = Sanitize::query_args( $args );
        $rows  = $this->repo->find( $clean );
        return array_map( array( Things_Formatter::class, 'format' ), $rows );
    }
}

// includes/admin/class-rest-things-controller.php
class My_Plugin_REST_Things_Controller {
    public function get_things( WP_REST_Request $request ) {
        $rows = $this->service->list_things( $request->get_params() );

        // Побочные эффекты (аудит, хуки, уведомления) остаются в адаптере REST — чисто.
        do_action( 'my_plugin/things_listed', $rows );

        return rest_ensure_response( $rows );
    }
}

// src/Internal/Abilities/Abilities_Registrar.php
public static function execute_get_things( $input = null ) {
    if ( ! class_exists( '\MyPlugin\Things_Service' ) ) {
        return new WP_Error( 'myplugin_not_initialized', __( 'My Plugin is not initialized.', 'my-plugin' ) );
    }
    return MyPlugin::get_things_service()->list_things( (array) $input );
}
```

Теперь возможность и эндпоинт REST используют общую бизнес-логику. Побочные эффекты
(аудит, хуки, уведомления, любая телеметрия) остаются в адаптере REST и не срабатывают при
вызовах агента. Следующий человек, добавляющий параметр фильтра, меняет одно место —
сервис — и оба места вызова это подхватывают.

## Практическое правило

Исходи из того, что возможность выделяет (или использует уже выделенный) сервис. Отступай к
делегированию, только когда выполняются все условия для него.

- **Любая запись** → выделяй сервис. Расхождения наиболее опасны при записи (потерянная
  валидация, отсутствующие хуки аудита). Без вариантов.
- **Существующего эндпоинта REST нет** → начинай с сервиса. Первая выпущенная возможность —
  подходящий момент добавить структуру, которую будет использовать будущий эндпоинт REST.
- **Чтение, где обработчик REST делает больше, чем читает данные** (аудит, хуки,
  уведомления, телеметрия) → выделяй сервис. Не выдавай побочные эффекты интерфейса при
  вызовах агента.
- **Чтение, которое в основном вызывают вне REST** (CLI, cron, агент, транспорт MCP вне
  REST) → предпочитай прямой вызов сервиса или класса запроса. Делегирование оплачивает
  стоимость первой инициализации REST на каждом холодном пути.
- **Чтение без побочных эффектов на пути REST, простая логика, в основном через REST** →
  шаблон делегирования допустим как сокращение. Риск расхождений ограничен, потому что
  контроллер REST в одном коротком переходе, — но только пока выполняются все три условия.

Смещение намеренное. Выделение сервиса — единственная форма, которая выдерживает, когда у
обработчика REST позже появляется побочный эффект, когда возникает парная запись или когда
появляется вызывающий код вне REST (новая команда CLI, задача cron, вызов агента через
транспорт MCP вне REST). Делегирование снова связывает предметный уровень с транспортом
REST; такая связь нормальна, когда условия выполняются *и* меняться не собираются, но цена
её последующего развязывания выше, чем старт с сервиса.

## Запасной путь — когда повторная реализация допустима

Два узких случая:

1. **Возможность только читает, и у источника нет выделяемой формы.** Иногда «логика» —
   одна строка: `get_option( 'something' )`, и класс сервиса избыточен. Пиши на месте.
2. **Плагин одноцелевой и не будет расти.** Плагин на 200 строк с одной возможностью и без
   поверхности REST, с которой можно разойтись, может держать логику в колбэке выполнения.
   Риск расхождений проявляется только при двух и более адаптерах.

В обоих случаях оставь комментарий
`// TODO: extract to service if a REST/UI surface gets added`, чтобы следующий человек
видел условие-триггер.

## Переопределение для семейства плагинов

Этот файл описывает общую базовую линию. Конкретные семейства плагинов могут — и регулярно
делают это — ужесточать правила. Плагин семейства платежей может вообще запретить шаблон
делегирования на том основании, что ни один платёжный эндпоинт нельзя считать свободным от
побочных эффектов. Плагин подписок может требовать выделения сервиса даже для чтения
опции одной строкой, если опцию читают более чем в одном транспорте. Плагин со своим
транспортом MCP может исключить делегирование для любой возможности, публикуемой через
него.

Когда ты работаешь в таком плагине, побеждают локальные правила. Проверь `AGENTS.md`
плагина, руководство для контрибьюторов или плейбук по регистрации возможностей, прежде чем
прибегать к сокращению делегирования, описанному здесь.
