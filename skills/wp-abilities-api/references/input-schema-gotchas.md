# Ловушки входной схемы

Три неожиданности, которые `input_schema` в Abilities API преподнесёт, если полагаться
только на объявления схемы. Все три встречались в реальной работе над плагинами уже после
того, как схема выглядела правильно и тесты проходили; для каждой есть защитный шаблон,
делающий колбэк выполнения устойчивым.

## 1. Значения `default` из схемы НЕ подставляются во ввод колбэка выполнения

### Проблема

`wp_register_ability()` позволяет объявлять значения по умолчанию для каждого свойства в
`input_schema`:

```php
'input_schema' => [
    'type'       => 'object',
    'properties' => [
        'submit' => [
            'type'        => 'boolean',
            'default'     => false,
            'description' => __( 'Whether to submit evidence for review.', '<text-domain>' ),
        ],
    ],
],
```

Путь проверки в Abilities API обеспечивает `type` и `required`, но НЕ заполняет
отсутствующие свойства объявленными `default`. Если агент вызывает возможность с
`{ dispute_id: "dp_..." }` и опускает `submit`, колбэк выполнения получает `$input`
**без** ключа `submit`: `$input['submit'] = false` не появится.

### Симптомы

- Логические значения по умолчанию молча становятся «неопределёнными» в колбэке, и любая
  проверка `if ( $input['submit'] )` сравнивает с `null`: это случайно работает, но ломает
  проверки `isset` и ветки со строгой типизацией.
- Целочисленные значения по умолчанию для пагинации вроде `'page' => [ 'default' => 1 ]`
  никогда не доходят до контроллера в основе, поэтому пагинация откатывается к внутреннему
  значению контроллера, а не к объявленному в схеме.
- Значения по умолчанию для объектов (`'metadata' => [ 'default' => [] ]`) становятся
  `null`, а не `[]`, и любой `foreach ( $input['metadata'] as ... )` даёт ошибку типа.

### Решение — нормализуй значения по умолчанию явно в колбэке выполнения

```php
public static function execute_submit_evidence( $input = null ) {
    if ( ! is_array( $input ) ) {
        $input = [];
    }

    // Применяем значения по умолчанию из схемы, которые Abilities API не подставляет.
    if ( ! array_key_exists( 'submit', $input ) || null === $input['submit'] ) {
        $input['submit'] = false;
    }
    $input['submit'] = (bool) $input['submit'];

    if ( ! array_key_exists( 'metadata', $input ) || null === $input['metadata'] ) {
        $input['metadata'] = [];
    }

    // ... остальное тело колбэка
}
```

Шаблон `array_key_exists` вместе с проверкой на null ловит и «ключа нет», и «явный null»
(некоторые сериализаторы дают null для необязательных полей).

Объявленный `default` в `input_schema` всё равно оставь: он документирует ожидаемое
поведение для всех, кто читает регистрацию, и виден агентам в эндпоинтах самоописания схемы.
Просто не полагайся на него для заполнения во время выполнения.

## 2. Расхождение имён параметров пагинации

### Проблема

Соглашение `input_schema` в большинстве эндпоинтов REST WordPress — `per_page` (как в
эндпоинтах списков ядра WP и `get_collection_params()` у `WP_REST_Controller`). Однако
некоторые контроллеры REST в плагинах делегируют внутреннему классу-построителю запроса,
который читает другой ключ (например, `pagesize` или `page_size`), обычно по историческим
причинам.

Если `input_schema` возможности показывает `per_page`, а контроллер в основе читает
`pagesize`, то `per_page: 50` от агента молча никогда не доходит до пагинации: значение
принимается, передаётся в источник как есть и игнорируется. Агенты продолжают получать
размер страницы по умолчанию и подозревают, что сломан их фильтр.

### Симптомы

- Возможности со списками возвращают размер страницы по умолчанию из контроллера
  независимо от `per_page` в вводе агента.
- Интеграционные тесты, проверяющие только «список вернулся», проходят; ловит только тест,
  проверяющий `count( $response['data'] )`.
- В прогонах стенда число элементов в сыром ответе совпадает со значением по умолчанию
  (25, 10 и т.п.) при каждом вызове.

### Как обнаружить

Перед выпуском возможности с пагинацией проверь цепочку вызовов контроллера в основе:

```bash
# Проверь контроллер в основе и всё, чему он делегирует.
grep -rn "pagesize\|page_size" <path/to/backing-controller.php> <path/to/request-helpers/>
```

Если `pagesize` (или любой ключ, отличный от `per_page`) встречается в цепочке, а схема
возможности показывает `per_page`, колбэк выполнения ОБЯЗАН выполнить перевод.

### Решение — переведи до делегирования

```php
/**
 * Translate pagination keys for abilities whose backing reads a non-standard key.
 *
 * Abilities expose `per_page` uniformly for agent-facing consistency; this
 * helper rewrites it to whatever key the backing actually reads.
 *
 * @param array|null $input Ability input (or null).
 * @return array|null       Input with `per_page` rewritten to `<backing_key>` when present.
 */
private static function translate_pagination_keys( $input ) {
    if ( ! is_array( $input ) ) {
        return $input;
    }
    if ( isset( $input['per_page'] ) ) {
        $input['<backing_key>'] = $input['per_page'];
        unset( $input['per_page'] );
    }
    return $input;
}

public static function execute_get_things( $input = null ) {
    $input = self::translate_pagination_keys( is_array( $input ) ? $input : null );

    return self::delegate_to_rest_controller(
        '<Backing_Controller_Class>',
        'get_things',
        '/my-plugin/v1/things',
        $input
    );
}
```

Ставь перевод ДО вызова делегирования, чтобы `per_page` никогда не дошёл до источника.

### Когда это НЕ применять

Не применяй слепо. Если источник читает `per_page` напрямую (так делают большинство
современных контроллеров REST в WP), такой перевод молча сломает пагинацию, переименовав
ключ в тот, который источник не понимает.

**Всегда сначала проверяй источник через grep.** Перевод верен только для конкретной цепочки
в основе; это не универсальная страховка.

## 3. Проверка идентификатора не должна использовать `empty()`

### Проблема

`empty()` в PHP снисходителен так, что это бьёт по проверке идентификаторов:

```php
empty( '0' )   // true  — но "0" это допустимый строковый ID (ID заказа, строки, записи в некоторых путях кода)
empty( 0 )     // true  — то же для целочисленного нуля
empty( [] )    // true  — ожидаемо, но то же ключевое слово используют для разных случаев
```

Колбэк выполнения, который защищает обязательные идентификаторы через
`empty( $input['order_id'] )`, ложно отклонит законный `"0"` и вернёт ошибку «отсутствует»
для ввода, который на самом деле есть. Агент повторит с тем же вводом, получит ту же ошибку,
и вызов застрянет.

### Симптомы

- Возможности отклоняют конкретные идентификаторы, оканчивающиеся на ноль или состоящие из
  нуля.
- Модульные тесты с ненулевыми идентификаторами проходят; регрессия появляется в тот день,
  когда агент пробует реальный нулевой ID.
- `WP_Error( '<plugin>_missing_<field>' )` срабатывает для ввода, который валидатор схемы
  принял бы.

### Решение — три явные проверки

```php
if ( ! isset( $input['order_id'] )
    || ! is_string( $input['order_id'] )
    || '' === $input['order_id']
) {
    return new \WP_Error(
        '<plugin>_missing_order_id',
        __( 'An order_id is required to fetch order detail.', '<text-domain>' )
    );
}
```

Три отдельные проверки, каждая нелишняя:

1. `! isset( ... )` — ключ присутствует в массиве.
2. `! is_string( ... )` — тип верный. (Для целочисленных ID используй `is_int` и проверку
   на неотрицательность.) Без этого вызывающий, передавший `123` (целое) там, где схема
   документирует строку, дойдёт до шага с `rawurlencode( $input['order_id'] )` и получит
   невнятную ошибку приведения вместо чистого ответа об отсутствующем поле.
3. `'' === $input[ ... ]` — непустое в строгом смысле. Отклоняет только пустую строку;
   принимает `"0"` как допустимое значение.

Для этого случая используй стандартизованный код ошибки `<plugin>_missing_<field>` (см.
`error-code-vocabulary.md`).

### Добавь модульный тест-страж от регрессии

Проверка настолько важна, что заслуживает явного теста: иначе кто-нибудь в будущем
рефакторинге упростит её обратно до `empty()`:

```php
public function test_execute_returns_wp_error_when_id_not_a_string() {
    $result = My_Plugin_Abilities::execute_get_thing( [ 'order_id' => 123 ] );
    $this->assertInstanceOf( \WP_Error::class, $result );
    $this->assertSame( '<plugin>_missing_order_id', $result->get_error_code() );
}
```

Целое `123` — хороший маячок: оно непустое, проходит `isset`, но не является строкой.
Колбэк, использующий только `isset` и `empty`, ложно пропустил бы этот ввод и дошёл до
построения URL с целочисленным аргументом.

## 4. Прямой и косвенный вызов различаются строгостью

### Проблема

Вызвать `execute_callback` возможности можно двумя способами:

- **Прямой.** Вызывающий импортирует регистратор и вызывает статический метод
  (`Abilities_Registrar::execute_get_things( $input )`). Работают значения по умолчанию из
  сигнатуры PHP; проверка схемы не выполняется.
- **Косвенный.** Вызывающий получает возможность через
  `wp_get_ability( '<id>' )->execute( $input )`. WordPress выполняет
  `WP_Ability::normalize_input()`, затем `validate_input()` (затем `check_permissions()`)
  перед вызовом колбэка.

Пути различаются в трёх местах, на которых спотыкаются агенты:

1. **Проверка по `input_schema` выполняется только на косвенном пути.** Если возможность
   объявляет схему типа «объект» со свойствами, а косвенный вызывающий передаёт `null` (или
   вообще опускает аргумент, как делает `$ability->execute()`), `validate_input()` отклоняет
   вызов ошибкой `ability_invalid_input` до запуска колбэка. Значение по умолчанию
   `$input = null` в сигнатуре колбэка на этом пути — мёртвый код.

2. **Верхнеуровневый `default` схемы ПРИМЕНЯЕТСЯ, но только на косвенном пути.**
   `normalize_input()` подставляет верхнеуровневый `default` схемы, когда вызывающий передаёт
   `null`. Прямые вызывающие через этот метод не проходят и получают то значение по
   умолчанию, которое объявлено в сигнатуре колбэка. Объявление
   `default => (object) array()` в корне схемы позволяет `$ability->execute()` работать без
   аргументов, но тот же колбэк, вызванный напрямую, всё равно получит `null` из PHP.

3. **Первый аргумент колбэка приходит только если `input_schema` не пуста.** WordPress
   передаёт `$input` в колбэк только когда схема объявлена. Без входной схемы колбэк
   вызывается без аргументов: значения по умолчанию из сигнатуры PHP это компенсируют, если
   ты их написал; без них косвенный путь даёт `ArgumentCountError`.

### Симптомы

- Возможность выглядит нормально в модульном тесте с прямым вызовом статического метода, а
  потом падает, как только её вызывают через `wp_get_ability(...)->execute()` из MCP, палитры
  команд или стенда агента.
- «Работает в тесте, ломается в MCP» — типичная картина, когда тест вызывает
  `Abilities_Registrar::execute_get_things( [] )` (передавая пустой массив), а вызов агента
  идёт через косвенный конвейер.
- Схема, где все свойства необязательны, всё равно отклоняет косвенные вызовы без
  аргументов, потому что `null` не является объектом.

### Решение — объяви верхнеуровневый `default` в схеме для любой возможности, допускающей вызов без аргументов

```php
'input_schema' => [
    'type'       => 'object',
    'default'    => (object) array(),  // применяется normalize_input() при null на входе
    'properties' => [
        'per_page' => [ 'type' => 'integer', 'default' => 10 ],
        // ...
    ],
],
```

`(object) array()` предпочтительнее `[]`, потому что в JSON он кодируется как `{}`, а не как
литерал массива `[]`, что снимает неоднозначность массивов и объектов на границе валидатора.

### Чем это отличается от ловушки 1

Верхнеуровневый `default` схемы учитывается `normalize_input()` и доходит до колбэка.
Значения по умолчанию на уровне свойств (ловушка 1) — НЕТ: валидатор их отбрасывает, и
колбэк должен защитно применять их сам. Разные слои — разная судьба.

Если ты объявил верхнеуровневый `default` в схеме, значение по умолчанию в сигнатуре PHP
существует только для прямых вызывающих. Не добавляй третий слой запасных значений внутри
колбэка с проверкой `if ( $input === null )`: три компенсирующих значения друг поверх друга
размывают смысл «ввода нет».

## Собираем ловушки 1–3 вместе

Укреплённый колбэк выполнения для возможности со списком, с обязательным идентификатором,
значениями по умолчанию из схемы и расхождением пагинации в источнике:

```php
public static function execute_get_thing_details( $input = null ) {
    if ( ! is_array( $input ) ) {
        $input = [];
    }

    // Ловушка 3: проверка обязательного ID (не empty()).
    if ( ! isset( $input['thing_id'] )
        || ! is_string( $input['thing_id'] )
        || '' === $input['thing_id']
    ) {
        return new \WP_Error(
            '<plugin>_missing_thing_id',
            __( 'A thing_id is required.', '<text-domain>' )
        );
    }

    // Ловушка 1: применяем значения по умолчанию, которые Abilities API не подставляет.
    if ( ! array_key_exists( 'include_history', $input ) || null === $input['include_history'] ) {
        $input['include_history'] = false;
    }
    $input['include_history'] = (bool) $input['include_history'];

    // Ловушка 2: переводим пагинацию до делегирования (только если источник читает нестандартный ключ).
    $input = self::translate_pagination_keys( $input );

    return self::delegate_to_rest_controller(
        '<Backing_Controller_Class>',
        'get_thing',
        '/my-plugin/v1/things/' . rawurlencode( $input['thing_id'] ),
        $input
    );
}
```

За каждой из трёх строк, которые колбэк добавляет к шаблону «просто делегируй», стоит
дорого обошедшаяся ошибка. Оставь их.
