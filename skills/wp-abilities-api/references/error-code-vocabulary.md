# Словарь кодов ошибок

Каждый `WP_Error`, который возвращает колбэк выполнения возможности, должен использовать
код из этого небольшого словаря. Согласованный словарь позволяет агенту (или вызывающему
коду в твоей автоматизации) строить логику повторов и восстановления, опираясь на коды, а
не разбирая сообщения об ошибках.

## Почему стандартные коды важны

Агентам, которые оркестрируют несколько возможностей, нужно понимать: «это сломалось
из-за моего ввода или потому что что-то ниже по стеку недоступно?» Ответ определяет
стратегию повтора:

- сбои начальной инициализации → сообщить человеку, не повторять;
- ошибки формы ввода → исправить ввод и повторить тот же вызов;
- временные ошибки бэкенда → повторить с задержкой; может пройти само;
- ошибки внешнего поставщика → может понадобиться совсем другая стратегия.

Без соглашения каждый плагин изобретает свои коды, и агенты не могут рассуждать о них
единообразно. Категории ниже покрывают 95% реальных ошибок возможностей; если держаться
их, агент, выучивший логику повторов для одного плагина, сможет применить её к
следующему.

## Словарь

Подставляй вместо `<plugin>` слаг плагина строчными буквами, только с подчёркиваниями.
Это соответствует соглашениям WordPress о кодах ошибок. Если в плагине уже есть свой
стиль — например, однословный слаг, где подчёркивания между опущенными словами намеренно
не ставятся, — следуй ему. Согласованность внутри плагина важнее согласованности по всему
словарю.

| Код | Когда использовать | Поведение агента |
|---|---|---|
| `<plugin>_not_initialized` | Класс плагина отсутствует, аксессор общего сервиса возвращает null, обязательная зависимость не разрешается. | Со стороны агента повтор невозможен. Обычно это проблема конфигурации или порядка инициализации. Эскалируй. |
| `<plugin>_missing_<field>` | Обязательное поле ввода отсутствует или пусто (проверка самого колбэка выполнения, а не валидатора схемы). | Агент должен добавить поле и повторить. |
| `<plugin>_invalid_<field>` | Поле есть, но семантически неверно (недопустимое значение перечисления, искажённая дата, неверный тип). | Агент должен исправить значение и повторить. |
| `<plugin>_<resource>_data_unavailable` | Сервис-источник вернул временную ошибку (промах кэша вместе с ошибкой удалённого запроса, 5xx у поставщика, неудачное обновление устаревших данных). | Агент может повторить, вероятно с задержкой. |
| `ability_invalid_input` | Собственный валидатор схемы Abilities API отклонил ввод до запуска колбэка выполнения. | Эквивалентно `<plugin>_missing_<field>` или `<plugin>_invalid_<field>`, только возникает раньше в конвейере. Агент должен исправить ввод. |

### `ability_invalid_input` — более ранний путь

Когда возможность вызывают через мост REST Abilities API, сначала работает
зарегистрированная `input_schema`. Отсутствующие обязательные поля и несовпадения типов
дают `WP_Error( 'ability_invalid_input' )` ДО запуска колбэка выполнения. Прямой вызов
(модульные тесты, обёртки вне REST) обходит проверку схемы и попадает на собственные
проверки колбэка, давая `<plugin>_missing_<field>` или `<plugin>_invalid_<field>`.

Оба пути допустимы: поведение для конечного агента эквивалентно (детерминированная ошибка
проверки без побочных эффектов). Опиши это наблюдение в описании PR возможности или в
разделе «заметки для ревьюеров», чтобы ревьюеры знали, что в разных прогонах ожидаются
оба кода.

## Разобранные примеры

```php
// Инициализация не завершена — класс плагина отсутствует или аксессор вернул null.
return new \WP_Error(
    '<plugin>_not_initialized',
    __( '<Plugin> is not initialized.', '<text-domain>' )
);

// Отсутствует обязательное поле (проверка колбэка, схема была обойдена).
return new \WP_Error(
    '<plugin>_missing_<field>',
    __( 'A <field> is required to <do the thing>.', '<text-domain>' )
);

// Поле есть, но имеет неверную форму.
return new \WP_Error(
    '<plugin>_invalid_<field>',
    sprintf(
        /* translators: %s: input parameter name. */
        __( 'The "%s" parameter must be an ISO 8601 date-time string.', '<text-domain>' ),
        $key
    )
);

// Временная ошибка бэкенда.
return new \WP_Error(
    '<plugin>_<resource>_data_unavailable',
    __( 'Unable to retrieve <resource> data. The cache may be stale or the remote service returned an error.', '<text-domain>' )
);
```

## Коды поставщика могут проходить насквозь — и обычно должны

Если лежащий в основе контроллер обращается к API третьей стороны (Stripe, WPCOM, другой
SaaS), его собственные коды ошибок могут попадать в `WP_Error::get_error_code()`
возвращаемой возможности без изменений. Типичные примеры:

- `resource_missing` — код Stripe «объект с таким ID не найден». Говорит агенту, что
  конкретный ID был неверным.
- `rate_limited` — ограничение частоты на стороне поставщика. Говорит агенту сбавить темп.

**Пропускай их, а не переоборачивай.** Переобёрнутый
`<plugin>_<resource>_not_found` теряет информацию, которая помогла бы агенту действовать.
Опиши замеченные коды поставщика в `description` возможности или в заметках к PR, чтобы
ревьюеры знали, что они ожидаемы.

## Правила именования кодов

1. **Строчные буквы, только подчёркивания.** `<plugin>_missing_order_id`, а не
   `<plugin>-missingOrderId` или `<Plugin>-MissingOrderId`.
2. **Сначала префикс плагина.** Многословные слаги нормализуй к однословному префиксу там,
   где плагин уже так делает (например, `woopayments`, а не `woo_payments`).
3. **Затем действие.** Используй одно из `missing`, `invalid`, `not_initialized`,
   `<resource>_data_unavailable`.
4. **В конце имя поля или ресурса.** `<plugin>_missing_dispute_id`, а не
   `<plugin>_dispute_id_missing`. Это соответствует английской формулировке («a dispute_id
   is required») и быстрее читается в журналах ошибок.

## Интернационализация

СООБЩЕНИЯ об ошибках переводятся через `__()` или `sprintf(__())`. КОДЫ ошибок — нет: это
стабильные машинные идентификаторы.

```php
// НЕВЕРНО — не переводи код.
return new \WP_Error( __( '<plugin>_missing_order_id', '<text-domain>' ), ... );

// ВЕРНО — код литерал, сообщение переводится.
return new \WP_Error(
    '<plugin>_missing_order_id',
    __( 'An order_id is required.', '<text-domain>' )
);
```

Когда сообщение подставляет имя или значение параметра, добавляй комментарий для
переводчиков:

```php
return new \WP_Error(
    '<plugin>_invalid_date',
    sprintf(
        /* translators: %s: input parameter name. */
        __( 'The "%s" parameter must be an ISO 8601 date-time string.', '<text-domain>' ),
        $key
    )
);
```

## Не переусердствуй с детализацией

Цель — согласованные коды во всех возможностях плагина, а не предельно мелкая
гранулярность. `<plugin>_missing_dispute_id` — правильный уровень.
`<plugin>_missing_dispute_id_in_submit_evidence_context` — нет: имя возможности место в
`WP_Error::get_error_data()` или в контексте вызова у агента, а не в коде.

## Итог — четыре вопроса

Пиша колбэк выполнения, спрашивай по порядку:

1. Может ли плагин вообще обслужить этот вызов? → `<plugin>_not_initialized`.
2. Есть ли обязательный ввод? → `<plugin>_missing_<field>`.
3. Правильной ли формы обязательный ввод? → `<plugin>_invalid_<field>`.
4. Не сломался ли сервис-источник? → `<plugin>_<resource>_data_unavailable` или пропусти
   код поставщика насквозь.

Четыре категории, один согласованный словарь кодов на плагин. Этого достаточно, чтобы
агенты строили надёжную логику повторов.
