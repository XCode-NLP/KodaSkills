# Предметная возможность и проекция — на каком уровне регистрировать

> В этой модели три уровня: **предметный** (domain), **проекция** и необязательный
> **рабочий процесс**, который объединяет возможности в многошаговые задачи. В заголовке
> названы два основных решения; рабочий процесс вводится там, где он оправдан.

Abilities API можно применять на двух высотах. Можно регистрировать возможности как
поверхность, которую напрямую использует клиент MCP, REST или палитры команд. А можно
регистрировать их на предметном уровне — «что умеет этот плагин, независимо от
транспорта?» — и давать каждому потребителю видеть проекцию этой поверхности,
подходящую его ограничениям. Этот файл объясняет, почему вторая схема выгоднее, какая
трёхуровневая модель её реализует и как ею пользоваться при выборе того, что
регистрировать.

## Почему это важно

Когда публикацию через MCP считают целью регистрации, смешиваются два решения:

1. какие возможности предлагает этот плагин?
2. как каждый потребитель должен их видеть?

Первое решение стабильно. Второе изменчиво: бюджеты токенов меняются, клиенты MCP
совершенствуются, палитра команд приобретает новые соглашения, большие плагины
перерастают плоские списки инструментов и переходят к вложенному обнаружению. Связывая
оба решения, ты перерегистрируешь возможности каждый раз, когда вопрос проекции
открывается заново.

Разделяя их, ты оставляешь регистрации на месте, пока проекции развиваются на уровень
ниже.

## Три уровня

| Уровень | Назначение | Примеры |
|---|---|---|
| **Предметная возможность** | Стабильная, независимая от транспорта, с проверкой прав. Контракт плагина «что он умеет». | `myplugin/list-things`, `myplugin/update-thing`, `myplugin/get-overview` |
| **Рабочий процесс** *(необязательно)* | Композиции одной или нескольких возможностей в задачу, удобную человеку или агенту. | «Подключить нового продавца» = `verify-account` → `enable-feature` → `send-welcome` |
| **Проекция** | Представление предметного уровня для конкретного потребителя. Экономное сжатие для MCP, подобранные рабочие процессы для палитры команд, обнаруживаемая поверхность выполнения для REST, формы для админки, цепочки команд для CLI. | Встроенный адаптер WordPress MCP проецирует каждую опубликованную возможность через три мета-возможности (`mcp-adapter/discover-abilities`, `mcp-adapter/execute-ability`, `mcp-adapter/get-ability-info`) — агенты проходят по этим трём, а не видят весь реестр плоско. Палитра команд, напротив, может показывать те же предметные возможности плоско, потому что бюджет токенов там не ограничение. |

Предметный уровень — это то, что хранит реестр. Уровень проекции — то, что видит каждый
потребитель. Уровень рабочего процесса необязателен и существует, когда осмысленная для
пользователя или агента задача требует больше одной возможности.

## Проверка контрактом сценария использования

Зарегистрированная возможность — это контракт сценария использования: короткий путь на
естественном языке к действию, которое человек уже может выполнить в интерфейсе.
Эндпоинты REST и команды CLI — контракты транспорта, они показывают внутреннюю
механику. Возможности показывают действия.

Из этой формулировки следуют два вывода.

### 1. Проверка на включение — «сделал бы человек это намеренно через поддерживаемый интерфейс или процесс?»

Если да, операция — кандидат в возможности. Взгляд шире, чем только wp-admin:
«поддерживаемый интерфейс или процесс» включает экраны админки, публичные интерфейсы
(витрина, личный кабинет, просмотр курса, запись на приём), сценарии самообслуживания
пользователей на лицевой части сайта и поддерживаемые процессы, в которых другой плагин
или агент вызывает операцию как часть цепочки действий. Возможности вроде
`store/get-my-orders`, `events/list-available-tickets` или
`profile/update-public-profile` подходят ровно так же, как возможности админки вроде
`myplugin/list-pending-orders` или `myplugin/approve-submission`.

Если нет, операция остаётся эндпоинтом REST, командой CLI или внутренним хуком.
Внутренняя механика — инвалидация кэша, тики планировщика, отладочные снимки, учёт
жизненного цикла — не должна быть возможностью, даже если у неё чистая схема. Нет
осмысленной точки вызова человеком, значит нет и контракта сценария использования.

Проверка асимметрична: не всё, что показывает интерфейс, должно быть возможностью
(правило 1 в `grouping-heuristic.md` покрывает группировку). Но всё, у чего нет
осмысленной для человека поверхности вызова, почти наверняка не имеет смысла и как
возможность.

### 2. Тот же путь кода, что у интерфейса

Если возможность повторяет действие интерфейса, она должна использовать те же права,
проверки и бизнес-правила. Механизм, обеспечивающий это, описан в
`shared-core-service.md`. Формулировка здесь такая: возможность — это сценарий
использования; интерфейс, REST, CLI и MCP — тонкие адаптеры над ней.

## Что из этого следует

### Ты можешь регистрировать возможности, которые НЕ публикуешь через MCP

Abilities API — примитив ядра WordPress. Он задаёт формальный контракт «выполни этот код
с такими входными данными при такой проверке прав». MCP, REST и палитра команд —
уровни публикации поверх него. Ты подключаешь их сам.

Значит, плагин может регистрировать возможности, которые использует палитра команд, но
не видит MCP, или наоборот. Регистрация не зависит от транспорта, публикация настраивается
для каждого потребителя.

### Одна и та же предметная возможность может появляться в разных проекциях с разной формой

Небольшой плагин может показать свои три возможности плоско и в MCP, и в палитре команд.
Больший плагин может сохранить те же три предметные возможности, но проецировать их через
фасад вложенного обнаружения для MCP (три мета-инструмента, ведущие к лежащим в основе
регистрациям), показывая их плоско в палитре команд, где бюджет токенов не ограничение.

Предметный уровень не меняется. Работу под конкретного потребителя делает уровень
проекции.

### Компромиссы по экономии токенов живут на уровне проекции

Выбор между плоским видом с полными схемами, смысловой группировкой, фасадом из одного
инструмента и вложенным обнаружением — это решение *проекции*. Разные формы служат
разным ограничениям потребителей. Ни одна из них не требует менять то, что
зарегистрировано на предметном уровне; они меняют то, как потребитель видит
зарегистрированный набор.

Вот что значит «независимость от шаблона» на практике: регистрация — одно решение,
проекция — другое, и переработка второго не отменяет первого.

## Порядок решений

Проектируя поверхность возможностей плагина, работай в таком порядке:

1. **Сначала предметный уровень.** Что умеет этот плагин, независимо от транспорта?
   Используй проверку на включение. Примени `grouping-heuristic.md`, чтобы выбрать
   подходящую гранулярность (смысловое намерение вместо разбиения по REST).
2. **Потом проекция.** На каких поверхностях появляется каждая возможность и в какой
   форме? Для большинства плагинов с менее чем ~10 возможностями плоский вид во всех
   проекциях работает. Для больших плагинов рассмотри вложенное обнаружение для MCP,
   сохраняя плоский вид для палитры команд и REST.
3. **В третью очередь рабочий процесс (только если нужно).** Есть ли многошаговые
   задачи, которые стоит объединить в одну точку входа для пользователя или агента? Если
   да, рабочий процесс живёт над предметным уровнем и ссылается на несколько
   возможностей.

Большинству плагинов третий шаг не нужен.

## Разобранный пример — обычный плагин уведомлений

Плагин «Уведомления» управляет лентой уведомлений для каждого пользователя. Он
поддерживает просмотр списка, отметку о прочтении и отклонение всех.

### Предметный уровень

Три возможности, зарегистрированные один раз:

- `notifications/list` — чтение; фильтры по `unread_only`, `since`, `category`;
- `notifications/mark-read` — запись; принимает `notification_id`;
- `notifications/dismiss-all` — запись; без аргументов.

Это контракты сценариев использования. Они не зависят от транспорта и не предполагают
ни MCP, ни палитру команд, ни REST.

### Проекция — MCP

Поверхность маленькая, плоский вид работает. Проекция MCP показывает три возможности
как есть. Вложенное обнаружение не нужно.

### Проекция — палитра команд

Проекция палитры команд добавляет небольшой рабочий процесс, который оборачивает
`notifications/list` с фильтрами по умолчанию (`unread_only=true`) и открывает страницу
уведомлений в админке при выборе. Две другие возможности остаются плоскими командами.
Предметная регистрация не изменилась; уровень палитры команд добавил рабочий процесс
сверху.

### Проекция — REST

Проекция REST показывает только возможность чтения. Записи идут через админку по
соображениям проверки безопасности. Предметная регистрация не изменилась: уровень REST
просто не публикует две из трёх.

Те же три регистрации, три разные проекции, никакой перерегистрации при развитии решений
о проекции.

## Запасной путь — крошечные плагины

Для плагинов с одной-тремя возможностями только для админки и без других поверхностей
уровень проекции тривиально совпадает с тождественной функцией. Тебе не нужно
*реализовывать* уровни, нужно *думать* уровнями, чтобы не загнать себя в угол, когда
плагин вырастет или бюджеты токенов MCP станут ограничением.

Конкретно: называй возможности на предметном уровне (`myplugin/get-thing`, а не
`myplugin-mcp/get-thing`), держи регистрацию с проверкой прав и без привязки к
транспорту и пропускай уровень проекции, пока он кому-то не понадобится.

## Связанные справочники

- `grouping-heuristic.md` — решения внутри предметного уровня: сколько возможностей и
  куда ставить фильтры.
- `shared-core-service.md` — механизм реализации «того же пути кода, что у интерфейса».
