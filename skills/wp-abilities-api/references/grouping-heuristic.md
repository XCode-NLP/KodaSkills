# Эвристика группировки — гранулярность предметного уровня

Как решить, ЧТО регистрировать, когда у плагина уже есть поверхность REST или внутренний
сервис. Сложная часть внедрения Abilities API — не синтаксис регистрации, а выбор верной
*гранулярности предметного уровня*, чтобы возможности соответствовали осмысленным для
пользователя действиям, а не механике HTTP.

> **Замечание об области действия.** Этот файл управляет решениями *предметного
> уровня*: сколько возможностей регистрировать, где ставить фильтры и где вводить новое
> имя возможности. Он НЕ управляет выбором на уровне проекции (плоский вид с полными
> схемами, фасад из одного инструмента, вложенное обнаружение или смысловая группировка
> в представлении потребителя). Это отдельные решения, принимаемые *после* того как
> предметный уровень определён, — об уровнях см. `domain-vs-projection.md`. Хорошо
> выбранный предметный уровень переиспользуется в нескольких проекциях; смешение двух
> уровней заставляет перерегистрировать всё каждый раз, когда меняются ограничения
> потребителя.

## Три наблюдаемых подхода

| Подход | Форма | Пример | Вывод (предметный уровень) |
|---|---|---|---|
| **Пакет действий** | Одна возможность объединяет много подопераций за строкой действия. | `my_plugin_account` с `action: "get" \| "update" \| "delete"`. | **Избегай.** Скрывает поверхность возможностей от списка инструментов агента и обесценивает модель самоописания Abilities API: агенты не видят, что умеет пакет, пока его не вызовут. |
| **Разбиение по REST** | Одна возможность на каждый HTTP-метод каждого ресурса (обычно 5 на ресурс: list, get, create, update, delete). | `orders-list`, `orders-get`, `orders-create`, `orders-update`, `orders-delete`. | **Избегай как формы регистрации.** Привязывает имена возможностей к механике HTTP, а не к намерению пользователя, и вынуждает перерегистрировать всё, если уровню проекции когда-нибудь понадобится сжать поверхность. |
| **Смысловое намерение** | Одна возможность на каждый реальный вопрос или переход состояния. Параметры фильтров в `input_schema` сводят N вариантов к одному. | Одна возможность `feedback/get-responses` с фильтрами `status`, `is_unread`, `search` и диапазоном дат в `input_schema` заменяет то, что иначе было бы 8+ разбитых вариантов. | **Рекомендуется для предметного уровня.** |

## Почему смысловое намерение выигрывает на предметном уровне

1. **Пользователи думают вопросами, а не HTTP-глаголами.** «Какие ответы формы не
   прочитаны?» чисто ложится на одну возможность с фильтром `is_unread`. Это НЕ ложится
   на 8 возможностей (`get-unread-responses`, `get-spam-responses`,
   `get-trashed-responses`, ...). Имена возможностей — *контракты сценариев
   использования*, см. `domain-vs-projection.md`.
2. **`input_schema` в Abilities API рассчитана на богатый ввод.** Ограничения
   перечисления, форматы даты и времени и проверка обязательных полей делают ту работу по
   разделению вариантов, которую при разбиении переложили бы на имя возможности.
3. **Записи в любом случае остаются узкими.** Возможность записи уже должна быть одним
   переходом состояния; для записей разбиение и смысловое намерение сходятся.
4. **Стоимость токенов в списке инструментов — следствие, а не причина.** Регистрации со
   смысловым намерением также дешевле сериализуются в плоских проекциях MCP, но стоимость
   токенов — забота *уровня проекции*. Если регистрации дешевы случайно, потому что
   формулировка сценариев использования их сжала, это приятный побочный эффект; если они
   дороги, исправлять нужно на уровне проекции (фасад из одного инструмента, вложенное
   обнаружение), а не перегруппировывая предметный уровень.

## Правила, которые делают это работоспособным

### 1. Группируй чтения по вопросу, который ввёл бы пользователь

Сформулируй вопрос простым языком. Этот вопрос и есть возможность. Параметры фильтров
идут в `input_schema`.

- НЕВЕРНО: одна возможность на каждое значение статуса.
- ВЕРНО: одна возможность `get-<resource>` с
  `status: { type: "string", enum: [...] }`.

### 2. Держи записи узкими — один переход состояния на возможность

Возможность записи должна делать ровно одно, о чём агент может рассуждать изолированно и
объяснить пользователю. Разные переходы состояния — разные возможности (разные
последствия, разные аннотации, разные следствия для прав).

- НЕВЕРНО: `update-resource`, который внутри ветвится по перечислению действий.
- ВЕРНО: `submit-evidence` и `close-resource` как отдельные возможности.

### 3. Предпочитай 1 возможность с параметрами фильтра вместо N возможностей без параметров

Спроси: «если в источнике данных появится новое значение фильтра, возникнет ли новая
возможность?» Если нет, фильтр принадлежит `input_schema`, а не имени возможности.

### 4. Возможности-обзоры без аргументов очень эффективны

Перечисляя поверхность источника данных, специально ищи агрегатные эндпоинты и
эндпоинты-обзоры без аргументов: «какой у меня баланс?», «какая следующая выплата?»,
«сколько у меня ответов формы?». Они отвечают на самые частые вопросы пользователей без
ввода и без места для ошибки агента. Отмечай их, даже если их не было в исходном плане.

### 5. Не выпускай возможности, которые не можешь объяснить одним предложением

`label` и `description` каждой возможности должны помещаться в подсказку выбора
инструмента у агента. Если не получается описать возможность одним предложением без
«и», это обычно признак двух возможностей.

## Разобранный пример A — feedback/responses: 3 возможности на всю поверхность ответов

Рассмотрим обычный плагин обратной связи или ответов форм. Его экраны админки
показывают: список с 8+ фильтрами, просмотр подробностей, массовую смену статуса
(спам, корзина, публикация), переключение прочитано и непрочитано и сводку количества по
статусам на панели управления.

Разбиение по REST выпустило бы ~6 возможностей (list, get, delete, update, bulk-update,
count). Смысловое намерение регистрирует **три**:

- `feedback/get-responses` — список и поиск, с `status`, `is_unread`, `search`, `before`,
  `after`, `parent` в `input_schema`;
- `feedback/update-response` — одна запись, покрывающая и смену статуса, и переключение
  прочтения одного ответа (по смыслу «изменить ответ»);
- `feedback/get-status-counts` — возможность-сводка для панели управления. Дружелюбна к
  вызову без аргументов (только необязательные фильтры).

Почему три работают: пользователь, спрашивающий «покажи спам-ответы за прошлую неделю»,
использует одну возможность. Агент, переводящий один ответ в `spam`, использует одну
возможность. Сводный вопрос «сколько непрочитанных?» использует одну возможность. Вся
поверхность продукта помещается в три записи списка инструментов.

## Разобранный пример B — обычный плагин тикетов: одна возможность с фильтром статуса, а не восемь

Гипотетический плагин `myplugin-tickets` управляет очередью обращений в поддержку. Его
эндпоинт REST `GET /myplugin/v1/tickets` принимает `status`, `priority`, `assigned_to`,
`tag`, `date_before`, `date_after`, `search`. Значения статуса включают `new`, `triaged`,
`in_progress`, `waiting_customer`, `waiting_internal`, `resolved`, `closed`, `reopened` —
всего восемь.

- Разбиение выпустило бы ~8 возможностей (`get-tickets-new`, `get-tickets-resolved`,
  `get-tickets-closed`, ...).
- Смысловое намерение выпускает **одну** — `myplugin-tickets/get-tickets` с
  `status: { type: "string", enum: ["new", "triaged", "in_progress", "waiting_customer", "waiting_internal", "resolved", "closed", "reopened"] }`.

Вопрос пользователя «какие тикеты ждут ответа клиента?» превращается в один вызов
возможности с `status: "waiting_customer"`. Агент не просматривает список из 8 почти
одинаковых имён инструментов: он смотрит один, а перечисление документирует допустимые
значения.

Тот же плагин также регистрирует возможность `myplugin-tickets/get-queue-summary` без
аргументов (число открытых, среднее время ответа, самый старый нерешённый), потому что
«как дела с очередью сегодня?» — самый частый вопрос команды поддержки, а эндпоинт
источника не принимает аргументов. Одна возможность даёт огромную ценность за одну
строку кода регистрации — правило 4 в действии.

## Запасной путь — когда гранулярность по операциям уместна (для чтений)

Два случая, когда одна возможность на операцию ДЕЙСТВИТЕЛЬНО уместна на стороне чтения,
несмотря на рекомендацию не разбивать чтения по REST:

1. **Действительно разные модели прав.** Если `list-<resource>` и `search-<resource>`
   требуют разных прав или разных сценариев подтверждения, разделение честно.
2. **Разные аннотации разрушительности и идемпотентности.** Возможность, которая и
   читает, и пишет, не может честно объявить `readonly: true`; выдели часть только для
   чтения в отдельную возможность.

Для записей этот запасной путь не нужен: правило 2 («один переход состояния на
возможность») уже задаёт гранулярность по операциям как умолчание. Разделение
`submit-evidence` и `close-resource` на отдельные возможности — не исключение, а действие
правила 2.
