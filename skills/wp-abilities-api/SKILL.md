# WordPress Abilities API

## Когда использовать

Используй этот навык, когда задача связана с:

- регистрацией возможностей или категорий возможностей в PHP;
- публикацией возможностей для клиентов через REST (`wp-abilities/v1`);
- использованием возможностей в JavaScript (прежде всего `@wordpress/abilities`);
- разбором ситуаций «возможность не появляется», «клиент не видит возможность»,
  «REST возвращает пусто».

## Что нужно на входе

- Корень репозитория (сначала запусти `wp-project-triage`, если ещё не запускал).
- Целевые версии WordPress и понимание, это ядро WP или плагин с темой.
- Где должно жить изменение (плагин, тема, mu-плагин).

## Порядок работы

Прежде чем решать, что регистрировать, прочитай `references/domain-vs-projection.md`:
возможности живут на уровне предметных возможностей, а публикация через MCP, палитру
команд и REST — это проекция. Форма регистрации и форма публикации — разные решения, и
их смешение заставляет регистрировать заново каждый раз, когда меняются требования
потребителя.

### 1) Подтверди доступность и ограничения по версиям

- Если это работа по ядру WP, проверь `signals.isWpCoreCheckout` и
  `versions.wordpress.core`.
- Если проект рассчитан на WP ниже 6.9, может понадобиться плагин или пакет Abilities
  API, а не ядро.

### 2) Найди существующее использование Abilities

Поищи в репозитории:

- `wp_register_ability(`
- `wp_register_ability_category(`
- `wp_abilities_api_init`
- `wp_abilities_api_categories_init`
- `wp-abilities/v1`
- `@wordpress/abilities`

Если ничего нет, реши, вводишь ли ты Abilities API с нуля (новые регистрации и
использование на клиенте) или только используешь его.

### 3) Зарегистрируй категории (необязательно)

Если нужна логическая группировка, зарегистрируй категорию возможностей заранее (см.
`references/php-registration.md`).

### 4) Зарегистрируй возможности (PHP)

Решения о группировке (сколько возможностей регистрировать и где ставить фильтры, а где
вводить новые имена) описаны в `references/grouping-heuristic.md`: это убережёт тебя от
одной атомарной возможности на каждую операцию REST.

Чтобы возможность не расходилась с существующим интерфейсом и кодом REST, см.
`references/shared-core-service.md`: возможности, обработчики REST, команды CLI и
контроллеры интерфейса должны быть тонкими адаптерами над общим сервисом. Там же
описана ловушка метрик (обработчики REST, отправляющие телеметрию использования) и
правило для `AGENTS.md` о синхронизации регистраций при изменении лежащих в основе
путей кода.

Общие шаблоны вспомогательных функций, когда несколько колбэков выполнения делегируют
существующим контроллерам REST, см. в `references/plugin-family-patterns.md` (как
отличить общий клиент API от контроллеров без аргументов) и
`references/delegate-helper-pattern.md` (одна рабочая форма помощника и когда её не
использовать).

Стандартизованные коды `WP_Error`, по которым агенты различают повтор и эскалацию, см.
в `references/error-code-vocabulary.md`.

Реализуй возможность при регистрации на PHP с такими данными:

- стабильный `id` с пространством имён;
- `label` и `description`;
- `category`;
- `meta`:
  - добавляй `readonly: true`, когда возможность только читает данные;
  - ставь `show_in_rest: true` для возможностей, которые должны быть видны клиентам.

Используй документированные хуки инициализации Abilities API, чтобы регистрация
происходила в нужный момент (см. `references/php-registration.md`).

### 5) Подтверди публикацию через REST

- Проверь, что эндпоинты REST существуют и возвращают ожидаемые результаты (см.
  `references/rest-api.md`).
- Если клиент всё равно не видит возможность, проверь, что включён `meta.show_in_rest`
  и что ты обращаешься к нужному эндпоинту.

### 6) Используй из JavaScript (если нужно)

- Для доступа и проверок на клиенте предпочитай API `@wordpress/abilities`.
- Убедись, что сборка включает зависимость и конвейер сборки проекта её упаковывает.

## Проверка

- `wp-project-triage` показывает `signals.usesAbilitiesApi: true` после твоих изменений
  (если применимо).
- Проверка REST (в окружении WP): эндпоинты в `wp-abilities/v1` возвращают твою
  возможность и категорию, когда это ожидается.
- Если в репозитории есть тесты, добавь или обнови покрытие рядом с:
  - PHP: регистрация возможности и публикация метаданных;
  - JS: использование возможности и ограничение интерфейса.

## Сбои и отладка

- Возможность не появляется:
  - код регистрации не выполняется (неверный хук или файл не загружен);
  - не задан `meta.show_in_rest`;
  - несовпадение категории или идентификатора.
- REST показывает возможность, а JavaScript нет:
  - неверная база или пространство имён REST;
  - зависимость JS не попала в сборку;
  - кэширование (объектное и страничное) скрывает изменения.
- Колбэк выполнения возвращает неожиданные ошибки или молча игнорирует ввод:
  - значения по умолчанию `input_schema` не применяются, ключ пагинации расходится
    между возможностью и источником данных либо идентификатор проверяется через
    `empty()` — см. `references/input-schema-gotchas.md`.

## Когда эскалировать

- Если неясна поддержка версий, уточни целевые версии ядра WP и ожидается ли Abilities
  API из ядра или как плагин.
- За каноническими подробностями обратись к файлам:
  - `references/rest-api.md`
  - `references/php-registration.md`
