# Лучшие практики Rust

Собрано из пяти руководств по стилю и проектированию Rust, краткое изложение
каждого лежит в `references/`. Где они расходятся, этот файл говорит, чему
следовать и почему.

## 1. Образ мыслей

- **Пиши код, который выглядит как Rust.** Не переносишь конструкции C++, Java,
  C# или Python один к одному. Моделируй ошибки через `Result`, ресурсы — через
  владение и `Drop`, полиморфизм — через трейты и перечисления, отсутствие
  значения — через `Option`. Приёмы из мира наследования (`Deref` на «базовую»
  структуру, типы `Manager` и `Factory`, помощники вида `throw_if_null`) — это
  дурной запах.
- **Делай недопустимые состояния непредставимыми.** Втаскивай инварианты в
  типы: перечисления вместо логических флагов и комментариев «если Y, то должно
  быть X», обёртки-новые типы для единиц измерения и идентификаторов, конструкторы,
  которые проверяют один раз и могут отказать. Тогда компилятор проверяет то, о чём
  комментарий только просил.
- **Код приложения — это не код библиотеки.** Код библиотеки (всё, у чего есть
  внешние пользователи) строго следует правилам проектирования API ниже. Код
  приложения должен предпочитать простоту и прямоту: конкретные типы, `String` или
  `&str` вместо параметра `impl Into<String>`, ошибки в духе `anyhow`, возврат
  `Vec`, никакой умозрительной общности.
- **Пусть инструменты делают работу.** За форматирование отвечает rustfmt, за
  идиоматичность — clippy, за безопасность памяти — компилятор. Своё внимание
  трать на проектирование.

## 2. Прежде чем отдать код

Запусти эти команды и исправь всё, о чём они сообщат:

```bash
cargo fmt
cargo clippy --all-targets --all-features -- -D warnings
cargo test
cargo doc --no-deps   # для библиотек: ловит битые ссылки в документации и пропуски
```

- Исправляй предупреждение анализатора, а не заглушай его. Когда
  предупреждение действительно неверно для одного элемента, используй
  `#[expect(clippy::name, reason = "...")]` на самом узком элементе. `expect`
  предупредит, когда предупреждение перестанет срабатывать, поэтому устаревшие
  заглушки будут вычищены. `#[allow]` применяй только в сгенерированном коде или
  выводе макросов.
- Никогда не пиши `#![deny(warnings)]` в исходниках: новые версии инструментов
  добавляют предупреждения и ломают сборку. Навязывай «предупреждения как
  ошибки» в CI через `cargo clippy -- -D warnings`.
- Настраивай анализаторы один раз в `Cargo.toml` (раздел `[lints]` или
  `[workspace.lints]`), а не разбросанными атрибутами пакета. Если в проекте такой
  настройки нет, предложи `lints/lints.toml` и `lints/clippy.toml` из
  https://github.com/morganlinton/BeautifulRust; анализаторам заглушек из него нужен
  `rust-version` 1.81 или новее.

## 3. Владение и заимствование

**Предпочитай единоличное владение.** Берись за `Rc` и `Arc`, только когда
общее владение — часть замысла, а за `RefCell` и `Mutex` — только когда нужна
внутренняя изменяемость. Это не провал, но проверка переезжает со времени
компиляции на время выполнения, поэтому применяй их осознанно.

**Не клонируй, чтобы заставить проверку заимствований замолчать.** Клон,
существующий только чтобы закончить заимствование, порождает молчаливую копию,
чьи дальнейшие изменения теряются. Сначала попробуй это, примерно в таком
порядке:

1. Продлить время жизни временного значения именованным `let` или сократить
   заимствование блоком.
2. Разбить длинное выражение на типизированные промежуточные значения, чтобы
   сбойный шаг стал виден.
3. Вынести поле из `&mut self` через `std::mem::take` (нужен `Default`),
   `std::mem::replace` или `Option::take` вместо клонирования.
4. Разделить большую структуру на меньшие, чтобы непересекающиеся поля можно было
   заимствовать по отдельности. Компилятор отслеживает раздельные заимствования
   полей внутри одной функции, но не между вызовами методов.
5. Осознанно клонировать небольшие неизменяемые данные и сказать об этом в
   комментарии, если это неочевидно.
6. Как крайняя мера — индексы в владеющем `Vec` или `Rc<RefCell<_>>` с обратными
   указателями `Weak`. Избегай самоссылающихся структур.

```rust
// Выносим значение из &mut-перечисления без клонирования.
fn a_to_b(e: &mut MyEnum) {
    if let MyEnum::A { name, x: 0 } = e {
        *e = MyEnum::B { name: std::mem::take(name) };
    }
}
```

**Принимай самый общий заимствованный тип.** `&str`, а не `&String`; `&[T]`, а не
`&Vec<T>`; `&T`, а не `&Box<T>`; `Option<&T>`, а не `&Option<T>`. Тогда разыменование
позволит вызывающим передавать и владеющие значения, и заимствования, и литералы.
Там, где ты только читаешь путь, строку или буфер байтов, на параметрах годится
`impl AsRef<Path>`, `impl AsRef<str>` или `impl AsRef<[u8]>` (никогда в полях
структуры; там храни `PathBuf` и `String`). Код библиотеки, который только
перебирает элементы, должен принимать `impl IntoIterator<Item = T>`; код
приложения может просто принимать `&[T]`.

**Забирай владение, только когда оно нужно, и тогда бери по значению.** Если
функция хранит аргумент или потребляет его, бери `T`, а не `&T` с внутренним
`.clone()`. Если только читает — `&T`; если меняет на месте — `&mut T`.
Возвращай несколько значений кортежем или структурой, а не через выходные
параметры `&mut` (исключение — переиспользование буфера, принадлежащего
вызывающему, как в `Read::read`).

**Предпочитай владеющие данные в структурах.** Структура с полем `&'a T`
навязывает время жизни каждому контейнеру. Владение `String` или `Vec<u8>` обычно
проще и редко бывает узким местом. Когда тип действительно несёт время жизни,
дай ему описательное имя (`'src`, `'conn`); `'_` и `'a` годятся в простых
функциях.

**Замораживай после настройки.** Собирай через `let mut`, затем переприсвой
`let data = data;`, чтобы дальнейший код не мог случайно это изменить.

**Держишь `Rc`, `Arc`, `Box` и `RefCell` вне публичных сигнатур.** Принимай `&T`,
`&mut T` или `T`, а способ владения пусть выбирает вызывающий. Служба, которую
нужно делить, реализует дешёвый `Clone`, обернув своё состояние в `Arc<Inner>`
внутри.

## 4. Типы и проектирование API

### Именование

| Что | Регистр | Заметки |
|---|---|---|
| Типы, трейты, варианты перечислений | `UpperCamelCase` | Аббревиатуры пишутся одним словом: `Uuid`, `HttpClient` |
| Функции, методы, модули, локальные значения | `snake_case` | |
| Константы, статические значения | `SCREAMING_SNAKE_CASE` | |
| Параметры типов | короткие, из основного ограничения | `T`, `R: Read`, `W: Write` |
| Времена жизни | короткие строчные | описательные, когда на типе |

- Никакой приставки `get_` у геттеров: `fn len(&self)`, `fn name(&self) -> &str`,
  `fn name_mut(&mut self)`. Голое `get` применяй, только когда есть одна очевидная
  вещь для получения (`Cell::get`). Смежное: `set_foo(T)`, `take_foo()`,
  `with_foo(|f| ..)` для доступа через замыкание и небезопасные двойники
  `_unchecked` у проверенных аксессоров.
- Приставки преобразования сообщают о цене и владении: `as_` (бесплатно,
  заимствование в заимствование), `to_` (дорого, заимствование во владение или
  заимствование в заимствование), `into_` (потребляет `self`). `mut` ставь в
  порядке типа: `as_mut_slice`, а не `as_slice_mut`.
- Конструкторы: `new` (основной), `with_capacity` или `new_with_foo` (варианты),
  `try_new` (может отказать), `from_foo` (преобразование; важные пары
  сопровождай реализацией `From`). Ресурсы ввода-вывода используют предметные
  глаголы: `File::open`, `TcpStream::connect`.
- `iter`, `iter_mut`, `into_iter` возвращают типы с именами `Iter`, `IterMut`,
  `IntoIter`; `keys()` возвращает `Keys`.
- Типы ошибок читаются как «объект-действие-ошибка»: `ParseBoolError`, а не
  `BoolParseError`.
- Избегай размытых окончаний `Service`, `Manager`, `Factory`, `Helper`, `Util`.
  Называй вещь тем, что она есть (`Bookings`, `Dispatcher`, `FooBuilder`). Не
  повторяй имя модуля в типе (`foo::Id`, а не `foo::FooId`). Избегай
  сокращений, которых не поймёт посторонний.
- Если реализуешь `len()`, реализуй и `is_empty()`.
- Имена возможностей — голые: `std`, `serde`, `alloc`, никогда `use-std` или
  `no-std`.

### Моделируй предметную область типами

- **Новые типы** для смысловых различий: `struct Miles(f64)` и
  `struct Kilometers(f64)` нельзя перепутать, а псевдоним типа позволяет. Добавляй
  `#[repr(transparent)]`, когда важна раскладка, и наследуй или пересылай нужные
  трейты (`derive_more` снимает обвязку). Новый тип, который кодирует инвариант
  (`Month`), проверяет его в конструкторе, способном отказать (`TryFrom`, `FromStr`,
  `try_new`), и никогда не даёт безотказного `From` из сырого типа.
- **Никаких параметров `bool` в публичных и общих сигнатурах.** `report(true)`
  нечитаем в месте вызова и не может отрасти третьим режимом. Используй
  перечисление из двух вариантов (`Verbosity::Summary`, `Verbosity::Full`) или два
  метода (`report()`, `report_verbose()`): `Widget::new(Size::Small, Shape::Round)`,
  а не `Widget::new(true, false)`. Единственное исключение — приватный помощник,
  места вызова которого лежат в нескольких строках. При рефакторинге существующий
  параметр `bool` — один из запахов, которые нужно убрать, а не деталь, которую надо
  сохранить.
- **Именованные поля вместо кортежей**, кроме новых типов с одним полем и совсем
  локального кода.
- **`Option` для отсутствия, никогда не сигнальные значения** вроде `-1` или `""`.
  **Перечисления, несущие данные**, вместо правила «поле X имеет смысл, только
  когда задано Y».
- **Используй сильнейший тип из стандартной библиотеки:** `PathBuf` и `&Path` для
  путей, `Duration` для промежутков, `NonZeroU32` только внутри (на границах API
  оставляй простые целые).
- **Независимые флаги** моделируй пакетом `bitflags`; перечисление моделирует ровно
  один выбор.

### Наследуй и реализуй стандартные трейты сразу

Пакеты ниже по зависимостям не могут добавить твоим типам стандартные трейты
(правило сироты), поэтому это должны сделать ты. Наследуй везде, где это
поддерживает каждое поле: `Debug` (на каждом публичном типе; пиши вручную, чтобы
скрыть секреты), `Clone` (кроме уникальных ресурсов и ключевого материала), `Copy`
(только небольшие типы, которые копируются побитово, потому что компилятор копирует
молча), `PartialEq` и `Eq`, `PartialOrd` и `Ord` (никогда не выпускай `PartialOrd`
без `Ord`, когда полный порядок существует), `Hash` (согласованный с `Eq`),
`Default`. Реализуй `Display` для всего, что предназначено для чтения: типы
ошибок, строкоподобные обёртки. Добавляй `#[must_use]` чистым функциям и типам,
отбрасывание которых — ошибка, например ошибкам и ленивым значениям.

Реализуй `From` и `TryFrom`, никогда напрямую `Into` и `TryInto` (общие
реализации дают их тебе). Предпочитай `from` и `into` приведению `as`, которое
молча допускает потери. Реализуй `FromStr`, а не самодельный метод `from_str`,
`FromIterator` и `Extend` для коллекций, `IntoIterator` и для владеющей, и для
заимствованной формы. Реализуй `Deref` только на умных указателях и владеющих
коллекциях (`Vec<T>` в `[T]`), никогда для имитации наследования. Перегружай
операторы только для их математического смысла.

Не ставь наследуемые ограничения трейтов на определение структуры:
`#[derive(Clone)] struct Good<T>`, а не `struct Bad<T: Clone + Debug>`. Ограничения
место в тех блоках `impl`, которым они нужны.

Если пишешь `Ord` вручную, напиши вручную `PartialEq`, `PartialOrd` и `Hash`,
согласованные с ним (сравнивай те же поля, игнорируй те же поля). Наследованный
`PartialEq` рядом с собственным `Ord` нарушает контракт стандартной библиотеки и
ведёт себя неверно в `BTreeMap`, `sort` и `dedup`. Укажи в документации, какие
поля равенство игнорирует.

### Конструкторы, сборщики, значения по умолчанию

- Предоставляй `new()`, даже когда есть `Default`, и сделай так, чтобы они
  совпадали (один вызывает другой). Наследуй или реализуй `Default`, чтобы
  вызывающие мог писать `..Default::default()`; структуры-наборы параметров с
  публичными полями должны иметь его всегда.
- До двух необязательных параметров — собственные конструкторы (`new`, `with_a`,
  `with_b`). Больше, а также когда конструирование проверяет данные или имеет
  побочные эффекты, — добавляй сборщик: `Foo::builder()` возвращает `FooBuilder`,
  установщики называются по полям (`timeout(d)`, а не `set_timeout`) и не могут
  отказать, а `build() -> Result<Foo, Error>` выполняет всю проверку, включая
  взаимные проверки полей. Предпочитай установщики, не потребляющие значение
  (`&mut self -> &mut Self`), если только `build` не должен вынести значение.
- Конструктор с четырьмя и более разрозненными аргументами должен сгруппировать их в
  смысловые типы: `Deposit::new(account, amount)` вместо четырёх параметров `&str`
  и `u64`.

### Видимость и развитие

- По умолчанию приватно. Поля остаются приватными, если только структура не
  пассивные данные в стиле C. Прежде чем делать `pub`, расширь до `pub(crate)` или
  `pub(super)`. Сделать элемент более публичным позже — не ломающее изменение;
  обратное — ломающее, и каждый элемент `pub` это обещание.
- Помечай публичные перечисления и структуры с публичными полями, которые
  пересекают границы пакетов, атрибутом `#[non_exhaustive]`, если набор не является
  устойчивой онтологией. Сопоставляя такой тип, перечисли варианты, которые
  обрабатываешь, и добавь ветвь с джокером.
- Запечатывай трейты, которые не хочешь давать реализовывать снаружи, и скажи об
  этом в документации:

  ```rust
  pub trait TheTrait: private::Sealed { /* ... */ }
  mod private {
      pub trait Sealed {}
      impl Sealed for usize {}
  }
  ```

- Код библиотеки возвращает итераторы, а не `Vec`, собранный только для возврата, за
  `impl Iterator<Item = T>` (внутренние API) или новым типом (публичные API, которые
  нужно держать стабильными).
- Выставляй каждый публичный элемент ровно по одному пути. Не делай `pub use`
  элементов чужого пакета, если ты не пакет-зонтик. Избегай протекания типов
  третьих сторон в твой публичный API; реализации `serde` прячь за возможностью с
  именем `serde`. Если тип зависимости обязан появиться, переэкспортируй его,
  чтобы вызывающие мог назвать совпадающую версию.
- Помечай функцию `const`, только если она останется `const`. Не выставляй
  перечисления `ErrorKind` и прочие внутренности, которые закрепляют режимы отказа,
  считающиеся приватными.

### Трейты и обобщения

- Определяй трейт только для обобщённого программирования (`T: Trait`,
  `impl Trait`, `dyn Trait`) или как трейт-расширение (`FooExt`). Не используй
  трейты просто для организации кода. Основную функциональность держишь в
  собственных методах, а реализации трейтов пересылай к ним, чтобы вызывающим не
  нужен был импорт.
- Предпочитай в таком порядке: конкретные типы; обобщения (`T: Trait`,
  `impl Trait`); `dyn Trait`, желательно обёрнутый в твою структуру
  (`struct DynStore(Arc<dyn Store>)`). Обобщения дают статическую диспетчеризацию и
  встраивание; трейт-объекты — разнородные коллекции и меньшие бинарники. Не
  вкладывай обобщения в типы уровня службы (`Service<Backend>` нормально,
  `Service<Backend<Store>>` — нет).
- Реши заранее, должен ли трейт быть объектно-безопасным. Обобщённые методы и
  `Self` вне получателя ломают это; исключай такие методы через
  `where Self: Sized`.
- Держишь обязательные методы трейта минимальными и давай значения по умолчанию
  для всего, что выводится из них, как `Iterator` делает из `next`.
- Если у функции есть ясный получатель, сделай её методом. Вычисление без
  получателя — свободная функция, а не `Database::check(params)`. Связанные функции
  нужны для конструирования.
- Замыкания: бери самое общее ограничение, которое работает (`FnOnce`, если
  вызывается один раз, `FnMut`, если меняет состояние, иначе `Fn`), и предпочитай
  ограничения `Fn*` голым указателям на функции. Параметры-замыкания идут
  последними; не бери больше одного.
- Держишь порядок параметров единым по пакету: сначала специфичные для вызова,
  последними — повсеместный контекст (журналы, распределители памяти).
- Берись за макрос, только когда функции, обобщения и трейты не справляются.
  Предпочитай `macro_rules!` процедурным макросам, делай вход макроса похожим на
  то, что он порождает, и никогда не позволяй макросу менять вид типа или
  сигнатуру функции.

### Рефакторинг чужого кода

- Исправляй каждый запах, о котором просил, а не только дешёвые: клоны, которые
  только ублажают проверку заимствований, параметры `&String` и `&Vec<T>`, `unwrap`
  на путях, способных отказать, `Rc<RefCell<_>>` в сигнатурах, геттеры с `get_`,
  параметры `bool`, склейку строк через `+`, `#![deny(warnings)]`, типы ошибок без
  `Error`, недетерминированный обход `HashMap` в выводе.
- Сохраняй публичное поведение неизменным, если изменение не является целью: те же
  операции, та же семантика успеха и отказа, те же байты вывода. Превратить панику в
  `Err` — это то изменение, которого ждут вызывающие. Убрать вариант ошибки, убрать
  наследование трейта или изменить то, что принимает конструктор, — нет; если
  сигнатура обязана измениться, покажи до и после в списке изменений и объясни
  почему.
- Сохраняй особенности, которых не понимаешь, и отметь их, а не «исправляй»
  молча.
- Когда в модуле нет тестов, закрепи текущее поведение несколькими тестами, прежде
  чем трогать код.

## 5. Ошибки и паники

Выбирай механизм по контракту:

| Ситуация | Что использовать |
|---|---|
| Отсутствие нормально (`first()`, `checked_add`) | `Option<T>` |
| Вызывающему может понадобиться знать, что пошло не так | `Result<T, E>` |
| Ошибка или нарушенный инвариант в твоём коде | `panic!`, `assert!`, `expect("почему")` |

**Паники — не исключения.** Паника означает «остановиться сейчас». Никогда не
используй её для сообщения о плохом вводе, никогда не полагайся на
`catch_unwind` для управления ходом выполнения (при `panic = "abort"` он ничего не
делает и может оставить состояние несогласованным) и никогда не перехватывай
панику, чтобы продолжить, внутри библиотеки. Где паникующий удобный вариант
оправдан, сопровождай его API, способным отказать (`v[i]` и `v.get(i)`, `new` и
`try_new`), и опиши его в разделе `# Panics`.

**Каждая намеренная паника несёт сообщение с относящимися значениями:**
`assert!(buf.len() >= HEADER, "buffer too small: {} bytes", buf.len())`,
`expect("config is loaded before workers start")`. Предпочитай
`expect("причина")` вызову `unwrap()`. Не пересказывай в сообщении само условие.

**Сопоставляй с образцом вместо проверки с последующим `unwrap`:**
`if let Some(v) = opt { .. }` или `let Some(v) = opt else { return .. };`, никогда
`if opt.is_some() { opt.unwrap() }`.

**Отравление блокировки фатально:** `.lock().expect("lock poisoned")`. Не
восстанавливайся через `into_inner`.

**Типы ошибок библиотеки** (любой `E` в публичном `Result`):

- реализуй `std::error::Error` (что требует `Debug` и `Display`), будь
  `Send + Sync + 'static` и реализуй `source()` для обёрнутых причин. Никогда не
  используй `()`, `String` или `Box<dyn Error>` как публичный тип ошибки
  библиотеки;
- сообщения `Display` строчные, краткие, без завершающей пунктуации:
  `"invalid header length"`;
- реализуй `From<Upstream>`, чтобы `?` преобразовывал. `map_err` применяй только
  для чужих ошибок или чтобы добавить контекст;
- две разумные формы: перечисление с одним вариантом на причину (`thiserror`
  порождает это хорошо) или структура на каждую ситуацию с приватным `kind` плюс
  методы `is_xxx()` и аксессоры. В любом случае не делай одно перечисление на весь
  пакет, перечисляющее все режимы отказа, и не выставляй детали, с которыми
  вызывающий не может ничего сделать;
- если функция, способная отказать, потребляет аргумент, верни его внутри ошибки,
  чтобы вызывающий мог повторить без клонирования (`FromUtf8Error::into_bytes`);
- никогда не выставляй `anyhow::Error` в публичном API библиотеки.

**Обработка ошибок в приложении:** `anyhow` или `eyre` с
`.context("opening config")` — правильный инструмент. Используй один тип ошибки
уровня приложения, а не несколько. `main` может возвращать
`Result<(), anyhow::Error>`.

**Деструкторы никогда не отказывают, не паникуют и не блокируются.** Предоставь
`close(self) -> Result<()>` для завершения, способного отказать, а `Drop` пусть
делает чистку по мере сил.

**Описывай режимы отказа:** `# Errors` для любого `Result`, `# Panics` для любой
достижимой паники, `# Safety` для каждой небезопасной функции.

## 6. Повседневные идиомы

- **Итераторы вместо ручных циклов**, когда цепочка короткая и читается сверху вниз:
  `values.iter().filter(..).map(..).collect()`, `.any()`, `.sum()`, `.fold()`.
  Собирай шаги, способные отказать, в `Result<Vec<_>, E>` и применяй `?`.
  Оставляй явный цикл `for`, когда тело большое, делает несколько дел или требует
  неудобных ранних выходов. Присваивай длинную цепочку именованной переменной, а не
  помещай её в заголовок `for`, и предпочитай `for x in it` вызову
  `.for_each(|x| ..)`.
- **Комбинаторы `Option` и `Result`** (`map`, `and_then`, `ok_or_else`,
  `unwrap_or_else`, `as_ref`, `as_deref`), когда они яснее `match`, и `match`, когда
  нет.
- **`format!` и `write!`** со встроенными аргументами (`format!("{name}: {count}")`)
  для склейки и подстановки, а не цепочки `+` или `str::replace`. В горячих участках
  пиши через `write!` в существующий буфер.
- **Явные типы там, где вывод скрывает замысел:** у `.into()`, `.parse()`,
  `.collect()` и сложных результатов итераторов. Предпочитай
  `let x: Vec<u32> = ..` турбо-рыбе.
- **Стражи на выходе из области видимости** для чистки, которая должна выполниться при
  раннем возврате или раскрутке стека. Привязывай их к имени (`let _guard = ..`),
  потому что `let _ = ..` отбрасывает значение немедленно.
- **Замыкания, захватывающие смешанное владение:** переприсвой в блоке, затем
  `move`:

  ```rust
  let job = {
      let cfg = cfg.clone();
      move || run(cfg, data)
  };
  ```

- **Стиль импорта:** один `use` на путь модуля (`use foo::bar::{Bar, Baz};`); типы и
  трейты импортируются и используются без квалификации (`Regex`); свободные функции
  квалифицируются модулем (`mem::take`, `fs::read`). Импортируй трейт внутри
  функции, которой он нужен, если его не использует весь файл. Никаких звёздочек,
  кроме `use super::*` в тестах, `use Enum::*` в функции, которая по нему
  сопоставляет, и прелюдии библиотеки вроде `use bevy::prelude::*`.
- **Магические числа** становятся именованными `const` с комментарием, откуда
  значение взялось и на что влияет его изменение.
- **Журналирование:** структурированные события через `tracing` или `log`, а не
  `println!` или `dbg!`, кроме собственного вывода командной строки в стандартный
  поток.

## 7. Конкурентность и асинхронность

- Публичные типы и возвращаемые ими фьючерсы должны быть `Send` (и обычно `Sync`).
  Закрепи это проверкой во время компиляции, чтобы рефакторинг не откатил это
  молча:

  ```rust
  const _: () = {
      const fn assert_send<T: Send>() {}
      assert_send::<MyClient>();
  };
  ```

  Удержание `Rc` или заимствования `RefCell` через `.await` делает фьючерс
  не-`Send`.

- Предпочитай передачу сообщений (каналы) общему состоянию. Когда общее состояние
  необходимо: держишь данные со связанными инвариантами под одной блокировкой,
  ограничивай области блокировки несколькими строками, никогда не вызывай
  пользовательские замыкания под блокировкой и никогда не возвращай `MutexGuard` из
  публичного метода.
- Пиши `async fn`, а не `fn -> impl Future`, кроме трейтов и случаев, когда
  подготовка должна выполниться вне асинхронного блока ради горячего пути.
- Долгая работа, нагружающая процессор, внутри асинхронного кода должна уступать
  управление (`tokio::task::yield_now().await` каждые десятки микросекунд) или
  переезжать в `spawn_blocking`.
- Код библиотеки не порождает потоки напрямую и не предполагает наличие среды
  выполнения; он принимает исполнитель, функцию порождения или `impl AsyncRead` и
  `impl Read` от вызывающего.

## 8. Небезопасный код и FFI

- Пиши `unsafe` только по одной из трёх причин: новая абстракция, которую
  безопасный код выразить не может; измеренная потребность в производительности;
  вызовы FFI и платформы. Сначала берись за стандартную библиотеку и хорошо
  проверенные пакеты: проверенный `unsafe` там уже есть.
- Каждый блок или реализация `unsafe` получает комментарий `// SAFETY:` о том,
  почему инварианты соблюдены. Каждая небезопасная функция получает раздел
  документации `# Safety` с перечнем того, что обязан обеспечить вызывающий.
  Включай `unsafe_op_in_unsafe_fn`.
- Держишь `unsafe` в наименьшем модуле, который может обеспечить его инвариант, и
  оборачивай в безопасный API; граница модуля и есть граница корректности.
  Безопасная функция, которая через любую последовательность безопасных вызовов
  может вызвать неопределённое поведение, некорректна, а некорректный код
  недопустим.
- Помечай функцию `unsafe`, только когда неправильное использование может вызвать
  неопределённое поведение, а не потому что она опасна (`delete_database()` —
  безопасная функция).
- Никакого `transmute` для приведения перечислений или обхода времён жизни и
  никакого `unsafe impl Send` для успокоения компилятора.
- Проверяй небезопасный код под Miri и на враждебных входных данных.
- FFI: `#[repr(C)]` на общих структурах, целые типы фиксированного размера,
  `CString` и `CStr` для строк, выделяй и освобождай на одной стороне, оборачивай
  указатели, принадлежащие C, в тип с автоматическим управлением ресурсами, чей `Drop`
  освобождает их, проверяй на null и возвращай `Result`, а паники останавливай на
  границе через `catch_unwind`. Порождения привязок делай `bindgen` в пакешь
  `foo-sys`, а бизнес-логику держишь в безопасном основном пакешь.

## 9. Пакеты, модули, зависимости

- **Предпочитай небольшие пакеты с одной целью** в плоской рабочей области
  `crates/`; никогда не вкладывай пакет в `src/` другого пакета. Дели, когда у
  пакета появляется вторая цель или подкаталог. Дели версии и настройки анализаторов
  через `[workspace.dependencies]` и `[workspace.lints]`.
- **Модули:** конечный модуль называй по основному элементу (`Foo` живёт в
  `foo.rs`). Неконечные модули содержат только объявления `mod` и переэкспорты.
  Основные элементы клади в корень пакета, остальные группируй по сценарию
  использования (`account`, `network`), а не по виду (`traits`, `errors`). Не
  определяй свою прелюдию.
- **Переэкспортируй поимённо** (`pub use foo::{A, B};`), никогда звёздочкой.
- **Зависимости:** каждая стоит времени компиляции, размера бинарника и риска в
  цепочке поставок, включая `build.rs` и процедурные макросы. Используй диапазоны
  (`"1"`, `"1.4"`), никогда `"*"` и ненужное `"="`. Для бинарников коммить
  `Cargo.lock`. Проверяй через `cargo tree --duplicates`, `cargo deny`,
  `cargo udeps` и `cargo audit`.
- **Возможности аддитивны и называются голо:** `std`, `serde`, `alloc`, `test-util`.
  Никогда `no-std`, `use-serde` или возможность, которая убирает либо меняет
  публичный элемент. Не прячь за возможностями поля структур и методы трейтов.
  Подделки и заглушки держишь за `test-util`.
- **Семантическое версионирование:** ломающие изменения включают удаление или
  переименование публичных элементов, добавление варианта в перечисление без
  `#[non_exhaustive]`, добавление поля в публично конструируемую структуру,
  добавление ограничения трейта и потерю объектной безопасности трейта. Устаревай
  в минорном выпуске до удаления в мажорном. Для новых пакетов бери последнюю
  стабильную редакцию и осознанно задавай минимальную поддерживаемую версию Rust.
- Не выполняй код до `main()` (никаких пакетов в духе `ctor`). Не используй
  нестабильные возможности на стабильном инструментарии.

## 10. Документация и комментарии

- `///` на каждом публичном элементе; `//!` в начале каждого публичного модуля и
  корня пакета. Первое предложение — одна строка примерно из пятнадцати слов, потому
  что оно становится сводкой в списках.
- Разделы в таком порядке, по применимости: `# Examples`, `# Errors`, `# Panics`,
  `# Safety`. В примерах используй `?` со скрытыми за строками `# ` строками
  `fn main`, никогда `unwrap()`, потому что пользователи копируют их дословно.
  Параметры описывай прозой, а не таблицей.
- Описывай то, чего не может сказать сигнатура: предусловия, побочные эффекты,
  передачу владения, сложность и причины. Не пересказывай тип или имя;
  `/// Removes an element.` у `remove_element` — это шум.
- Связывай элементы через `` [`Type`] ``. Скрывай реализации, которые
  пользователи никогда не вызывают (`From<PrivateError> for PublicError`), атрибутом
  `#[doc(hidden)]`.
- Комментарии `//` объясняют почему, а не что: `// SAFETY:`, `// TODO(issue-123):`,
  неочевидные магические значения, обходы со ссылкой. Никаких дневников
  проектирования, эссе «почему мы выбрал X» и таблиц соответствия правилам в
  документации кода. Описывай конечное состояние.

## 11. Тесты

- Модульные тесты в `#[cfg(test)] mod tests { use super::*; .. }` для приватных
  внутренностей. Интеграционные тесты в `tests/` для всего, что достижимо через
  публичный API, и предпочитай это место, когда подходит и то и другое. Примеры в
  документации тоже тесты.
- Проверяй наблюдаемое поведение и свойства (монотонность, обратимость,
  идемпотентность), а не пересказанные константы и зеркальные ветви.
- Пиши падающий тест до исправления ошибки. Покрывай каждое сочетание
  возможностей и каждый платформенный путь.
- Всё, что работает с вводом-выводом, временем, случайностью или сетью, должно
  поддаваться подделке: `new_mocked() -> (Self, MockCtrl)` за `test-util`, а не
  `Default`, который выполняет ввод-вывод.
- Разбирай парсеры недоверенного ввода через `cargo fuzz`. Замеряй
  `criterion` или `divan` с `std::hint::black_box`. Прогоняй Miri по `unsafe`.
- Проверки получают контекст, чтобы сбои читались хорошо:
  `assert_eq!(got, want, "input {input:?}")`.

## 12. Производительность, по порядку

Сначала проектируй для удобства использования и оптимизируй после измерений.
Когда оптимизируешь: `Vec::with_capacity` или `collect()` вместо циклов с `push`;
переиспользуй буферы, принадлежащие вызывающему, в горячих API
(`fn read_into(&mut self, buf: &mut Vec<u8>)`); `Box<[T]>`, `Box<str>`, `Arc<str>` для
долгоживущих неизменяемых последовательностей; `shrink_to_fit` на долгоживущих
коллекциях, собранных без резервирования; более быстрый хешер (`foldhash`, `FxHash`)
только для доверенных ключей; пакетная работа вместо блокировки на каждый элемент;
приложения могут задать `#[global_allocator]` вроде `mimalloc`. Наследуй `Copy`
небольшим простым типам и никогда большим.

## 13. Итоговый контрольный список

Прежде чем отдать код на Rust, убедись:

- `cargo fmt`, `cargo clippy -- -D warnings` и `cargo test` проходят чисто.
- Никаких `unwrap()` вне тестов и `main`; у каждого `expect`, `assert` и `panic`
  есть сообщение с относящимися значениями.
- Публичные функции принимают `&str`, `&[T]`, `impl AsRef<_>` или
  `impl IntoIterator`, а не `&String` и `&Vec<T>`.
- Каждый публичный тип наследует `Debug` и применимые общие трейты; типы ошибок
  реализуют `Error + Display + Send + Sync + 'static`.
- Никаких параметров `bool` в публичных сигнатурах; никакого ручного `Ord` без
  согласованных `PartialEq` и `Hash`.
- Никакого `.clone()`, единственная задача которого — ублажить проверку
  заимствований.
- Никаких звёздочек (кроме прелюдии библиотеки), никаких своих прелюдий, никаких
  протёкших типов третьих сторон.
- У каждого блока `unsafe` есть комментарий `// SAFETY:`; у каждой небезопасной
  функции есть документация `# Safety`.
- У публичных элементов есть документация с однострочной сводкой и разделами
  `# Errors` и `# Panics`, где они уместны.
- Код приложения остался простым; код библиотеки следовал правилам проектирования
  API.

## Справочные материалы

Читай их, когда нужны основания правила или полный контрольный список для задачи.
Каждый — сжатое изложение одного источника.

- `references/rust-api-guidelines.md` (https://rust-lang.github.io/api-guidelines/):
  проектирование публичного API или пакета; все 54 пункта контрольного списка с
  соглашениями.
- `references/effective-rust.md` (https://www.lurklurk.org/effective-rust/): выбор
  между альтернативами — обобщения против `dyn`, `Result` против паники, итераторы
  против циклов, приёмы обхода проверки заимствований, зависимости, CI.
- `references/rust-design-patterns.md` (https://rust-unofficial.github.io/patterns/):
  идиомы, образцы и антиобразцы с кодом.
- `references/microsoft-rust-guidelines.md`
  (https://microsoft.github.io/rust-guidelines/): проектирование структур ошибок,
  политика паник, политика небезопасного кода, асинхронность, раскладка рабочей
  области, производительность.
- `references/google-rust-style-guide.md`
  (https://google.github.io/styleguide/rustguide.html): форматирование, импорты,
  раскладка модулей, именование аксессоров, приложение против библиотеки.
- `references/bevy.md` (https://docs.rs/bevy/0.20.0): читай первым, если пакет
  использует Bevy.
