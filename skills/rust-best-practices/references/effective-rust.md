# Effective Rust (дайджест)

Источник: *Effective Rust* Дэвида Драйсдейла (O'Reilly, 2024), бесплатно онлайн:
https://www.lurklurk.org/effective-rust/ . Тридцать пять пунктов о том, как писать Rust хорошо.
Читай это, когда взвешиваешь альтернативы: обобщения против трейт-объектов, `Result` против
паники, итераторы против циклов, как пройти проверку заимствований, политика зависимостей и CI.
Книга рассчитана на Rust с 1.70 по 1.76; всё, что она называет «предстоящим», давно появилось.

## Типы (пункты 1–9)

1. **Используй систему типов, чтобы выражать структуры данных.** Заменяй комментарии вида
   «должно быть (0,0,0), если монохромный» перечислением, которое несёт данные. `Option` для
   отсутствия, никогда не сигнальные значения. Результаты, которые могут отказать, всегда
   `Result<T, E>`. Перечисление вместо параметра `bool`, если когда-нибудь может появиться третий
   вариант; новый тип, если он всегда будет логическим.
2. **Используй систему типов, чтобы выражать общее поведение.** Принимай трейт-типы, а не
   конкретные, когда важна гибкость. Для замыканий используй самое общее ограничение `Fn*`, которое
   работает: `FnOnce`, если вызывается один раз, `FnMut`, если изменяет, иначе `Fn`. Предпочитай
   ограничения `Fn*` голым указателям `fn`, которые не могут захватывать состояние. Трейты-маркеры
   (безметодный `StableSort: Sort`) выражают гарантии, которых подпись выразить не может.
3. **Предпочитай преобразования `Option` и `Result` явному `match`.** `map`, `and_then`, `ok_or`,
   `map_err`, `unwrap_or_else`, `as_ref()` и `?`. `Result` лучше `Option`, когда отказ может нести
   полезную информацию. `unwrap` и `expect` — решения упасть (пункт 18).
4. **Предпочитай идиоматичные типы ошибок.** Реализуй `std::error::Error` (требует `Debug` и
   `Display`; `source()` раскрывает причины). Сохраняй вложенные ошибки перечислением плюс
   реализацией `From` для каждой внутренней ошибки (`thiserror` это генерирует). Когда их не нужно
   сохранять, приложения используют `anyhow`; держи `anyhow` вне публичных API библиотек. Голая
   `String` не может реализовать `Error` (правило сиротства), поэтому оборачивай её.
5. **Понимай преобразования типов.** Реализуй `From` (даёт `Into` бесплатно); `TryFrom` — только
   когда преобразование может отказать. В ограничениях используй `Into<T>`, чтобы принимались оба
   вида реализаций. Предпочитай `from` и `into` вместо `as`, который молча допускает потери, кроме
   случаев, где точная семантика приведения и есть цель (взаимодействие с C).
6. **Применяй шаблон нового типа.** `PoundForceSeconds(f64)` и `NewtonSeconds(f64)` нельзя
   перепутать; псевдоним типа этого не предотвращает. Новые типы также позволяют реализовать
   чужой трейт для чужого типа. Цена: реализации внутренних трейтов теряются, и их нужно
   восстановить или переслать. `#[repr(transparent)]` сохраняет идентичную раскладку.
7. **Используй конструкторы для сложных типов.** `Default` с `..Default::default()`, когда у
   большинства полей разумные значения по умолчанию; конструктор, когда есть необязательные или
   проверяемые поля. Поглощающие конструкторы (`fn x(self) -> Self`) наиболее эргономичны, но их
   нельзя выстраивать по условию или переиспользовать. Конструкторы с `&mut self` позволяют
   выстраивать цепочку, но требуют именованной привязки `let`, а повторяемый `build(&self)` должен
   создавать свежие значения.
8. **Освой ссылочные и указательные типы.** `&T` — указатель, который компилятор гарантирует
   валидным, выровненным и проверенным по заимствованиям. `Box<T>` для данных в куче с единственным
   владельцем; `Rc` и `Arc` для разделяемого владения (с `Weak`, чтобы избежать циклов); `Cell` и
   `RefCell` или `Mutex` и `RwLock` для внутренней изменяемости. `RefCell` переносит проверки
   заимствований в время выполнения, поэтому используй `try_borrow` там, где паника недопустима.
   Выбирай нужную гранулярность изменяемости: `Rc<RefCell<Vec<T>>>` против `Rc<Vec<RefCell<T>>>`.
9. **Рассматривай преобразования итераторов вместо явных циклов.** Источник, адаптеры (`filter`,
   `take`, `map`, `zip`), потребитель (`sum`, `fold`, `find`, `any`, `collect`). Передавай первую
   ошибку, собирая в `Result<Vec<_>, _>` и применяя `?`. Оставляй цикл, когда тело большое или
   делает несколько работ, когда ранние возвраты неудобны внутри замыканий или когда преобразование
   вынуждено. Измеряй, когда это важно.

## Трейты (пункты 10–13)

10. **Освой стандартные трейты.** Выводи `Clone`, `Copy`, `Debug`, `PartialEq`, `Eq`,
    `PartialOrd`, `Ord`, `Hash`, `Default`, когда их поддерживает каждое поле; реализуй вручную,
    только когда выведенное поведение неверно. Пропускай `Clone` для ресурсов с уникальным доступом
    и материала секретных ключей; `Copy` — только когда побитовая копия валидна и быстра. Сочетай
    `Eq` с `PartialEq` (не для чисел с плавающей точкой), держи `Hash` согласованным с `Eq`,
    никогда не выпускай `PartialOrd` без соответствующего `Ord`.
11. **Реализуй `Drop` для шаблонов RAII.** Любой тип, владеющий ресурсом, который нужно освободить
    (дескриптор файла, блокировка, сырая память), реализует `Drop`. Ограничивай область охранников
    блоками, чтобы блокировки не держались дольше нужного. `drop` не может вернуть ошибку, поэтому
    давай отдельный метод `release()`, который может отказать. Вызывай `drop(x)`, никогда
    `x.drop()`.
12. **Понимай компромиссы между обобщениями и трейт-объектами.** Предпочитай обобщения.
    Мономорфизация даёт статическую диспетчеризацию и скорость, но по копии кода на тип (больше
    двоичные файлы, медленнее сборка). Трейт-объекты (`&dyn`, `Box<dyn>`) используют одну копию
    плюс таблицу виртуальных методов и подходят для неоднородных коллекций, ограничений размера или
    времени компиляции либо кода, загружаемого во время работы. Объектная безопасность: никаких
    обобщённых методов, никакого `Self` в аргументах или возвратах кроме получателя, если не
    помечено `where Self: Sized`.
13. **Используй реализации по умолчанию, чтобы сократить обязательные методы трейта.** Мало
    обязательных методов; значения по умолчанию для всего выводимого (как `Iterator` строит 50+
    методов на `next()`). Значения по умолчанию могут нести ограничения (`cloned()` только для
    элементов `Clone`). Добавление метода со значением по умолчанию обычно обратно совместимо.

## Понятия (пункты 14–20)

14. **Понимай времена жизни.** Ссылка не может жить дольше своего референта. Элизия покрывает
    единственную входную ссылку, отдающую в вывод, и методы, отдающие время жизни `&self`. В
    остальных случаях называй их. Структура, держащая ссылку, требует времени жизни, которое
    распространяется на каждый контейнер, поэтому предпочитай владеющие данные. `'static` — для
    глобальных значений или намеренно утёкших данных (`Box::leak`).
15. **Понимай проверку заимствований.** Любое число `&T` или ровно одна `&mut T`, никогда оба, и
    нелексические времена жизни заканчивают ссылку при последнем использовании. Тактики
    преодоления: продли временное значение именованным `let` или сократи блоком; разбей сложное
    выражение на типизированные промежуточные значения; перепроектируй владение, клонируя небольшие
    неизменяемые данные, используя владеющий `Vec` с индексами (хрупко) либо `Rc` и `RefCell` с
    обратными указателями `Weak`. Избегай самоссылающихся структур (`ouroboros`, если без них
    нельзя).
16. **Избегай написания небезопасного кода.** Сначала используй std и crates.io, где уже живёт
    проверенный в бою `unsafe` (`Rc`, `Mutex`, `Pin`, `cxx`). Когда без него нельзя: ограничь его
    небольшой обёрткой с безопасным API, опиши предусловия каждого блока в комментарии о
    безопасности, минимизируй каждый блок, включи `unsafe_op_in_unsafe_fn`, напиши дополнительные
    тесты, запусти Miri.
17. **Остерегайся параллелизма с разделяемым состоянием.** `Send` и `Sync` вместе с проверкой
    заимствований устраняют гонки данных в безопасном коде; взаимные блокировки и логические гонки
    остаются. Предпочитай передачу сообщений. Когда делишь: держи данные со связанными инвариантами
    под одной блокировкой, держи области блокировок небольшими, никогда не вызывай замыкания под
    блокировкой, никогда не возвращай `MutexGuard` вызывающему, добавь обнаружение взаимных
    блокировок в CI. Документированная иерархия блокировок — крайняя мера.
18. **Не паникуй.** Предпочитай `Result`; паника — для неисправимых ошибок или испорченного
    состояния. Практическое правило: `panic!`, `unwrap()` и `expect()` допустимы, когда ты
    контролируешь `main`, потому что дальнейшего вызывающего нет. Где паника оправдана, сочетай
    безотказную функцию (с документацией в разделе `# Panics`) с функцией, которая может отказать.
    `catch_unwind` не заменяет исключения: он ничего не делает при `panic = "abort"` и может
    оставить состояние несогласованным. Используй его только на границах FFI.
19. **Избегай рефлексии.** Общей рефлексии времени выполнения нет. `type_name` только для
    диагностики; `TypeId` и `Any::downcast_ref` работают только со значениями, уже обёрнутыми как
    `dyn Any`. Кодируй требуемое поведение трейтами, свойства — трейтами-маркерами, генерацию во
    время компиляции — производными макросами.
20. **Избегай соблазна чрезмерной оптимизации.** Сначала проектируй ради удобства использования:
    тип, владеющий `Vec<u8>`, избавляет от распространения времён жизни, а копирование небольших
    данных обычно нормально. Добавляй выделения памяти и клоны, только когда замеры показывают, что
    это важно; `Rc` и `Arc` с `RefCell` и `Mutex` — законные инструменты. Исключение — `Copy`.
    Выводи его для небольших побитово копируемых типов и никогда для больших или нетривиальных.

## Зависимости (пункты 21–26)

21. **Понимай, что обещает семантическое версионирование.** `"1.2.3"` означает `^1.2.3`; `"~"`
    допускает только патчи; `"="` фиксирует; `"*"` принимает что угодно. Ломающие изменения:
    удаление публичных элементов, добавление варианта в перечисление, по которому можно
    сопоставлять (если оно не `#[non_exhaustive]`), добавление публичного поля в публично
    создаваемую структуру, лишение трейта объектной безопасности, добавление сквозной реализации.
    Лицензия и набор возможностей по умолчанию — часть API. Помечай устаревшим в минорном релизе,
    прежде чем удалить в мажорном.
22. **Минимизируй видимость.** По умолчанию приватное; `pub(crate)`, `pub(super)`, `pub(in path)`
    раньше `pub`. Расширять позже — минорное изменение; сужать — ломающее. Держи поля приватными;
    `pub` на перечислении или трейте раскрывает все варианты или методы.
23. **Избегай импортов с подстановочными знаками.** Не импортируй целиком пакеты, которые не
    контролируешь: минорный релиз может добавить конфликтующее имя (ошибка E0034). Это нормально
    для `use super::*` в тестах, в собственных модулях и в намеренно подобранном прелюде. Если всё
    же импортируешь зависимость целиком, зафиксируй её версию.
24. **Реэкспортируй зависимости, чьи типы появляются в твоём API.** Вызывающий на другой,
    семантически несовместимой версии `rand` получит непонятное «trait bound not satisfied».
    Реэкспортируй (`pub use rand;`), чтобы вызывающие могли назвать подходящую версию, и хорошо
    подумай, прежде чем вообще раскрывать чужие типы.
25. **Управляй графом зависимостей.** Cargo позволяет сосуществовать семантически несовместимым
    версиям пакета и никогда — двум совместимым. Коммить `Cargo.lock` для бинарников. Предпочитай
    `"1"` или `"1.4.23"` вместо `"=1.2.3"` и `"*"`. Используй `cargo tree` (`--invert`,
    `--duplicates`, `--edges features`), `cargo-deny`, `cargo-udeps`. Каждая зависимость стоит
    времени сборки, размера бинарника и риска цепочки поставок, включая `build.rs` и
    процедурные макросы.
26. **Остерегайся разрастания возможностей.** Возможности должны быть аддитивными, потому что
    Cargo объединяет их по всему графу. Не привязывай к возможностям публичные поля структур или
    методы трейтов. Имена возможностей делят пространство имён с именами пакетов. Каждая
    независимая возможность удваивает число конфигураций; CI должен покрывать важные комбинации.
    Образец: возможность `std` или `alloc` на базе `no_std`.

## Инструменты (пункты 27–32)

27. **Документируй публичные интерфейсы.** `///` и `//!`, перекрёстные ссылки через
    `` [`Name`] ``, разделы `# Examples`, `# Panics`, `# Safety`. Описывай то, что подпись выразить
    не может (предусловия, ошибки, паники, причины), а не типы. `cargo doc --open`; рассмотри
    запрет `broken_intra_doc_links`; избегай наспех написанной документации только чтобы заглушить
    `missing_docs`.
28. **Используй макросы рассудительно.** Только когда функция или обобщение не справляются либо
    чтобы держать параллельный код синхронным (одна таблица, порождающая перечисление плюс
    `group()`, `text()`, `TryFrom`). Макросы могут вставлять `return`, `?` или изменения в месте
    вызова, поэтому держи поток управления видимым, а аргументы-выражения привязывай через `let`,
    чтобы избежать повторного вычисления. Предпочитай производный макрос процедурному, который
    порождает новый тип. Сначала проверь `strum`, `enumn`, `num_enum`.
29. **Слушай Clippy.** Держи код без предупреждений. Исправляй, а не подавляй; там, где lint
    действительно неверен, узкий `#[allow(clippy::..)]`. `cargo clippy -- -Dwarnings` в CI. Читай
    полный список lint'ов, включая выключенные по умолчанию, например `as_conversions`, чтобы
    учиться идиомам.
30. **Пиши больше, чем модульные тесты.** Модульные тесты в `#[cfg(test)] mod tests` (видят
    приватные элементы); интеграционные в `tests/` (только публичный API); доктесты; примеры
    (`cargo test --examples`). Замеры с `std::hint::black_box`. `cargo-fuzz` для недоверенного
    ввода. Пиши падающий тест до исправления ошибки. Тестируй каждую комбинацию возможностей и
    платформы с отличающимся кодом.
31. **Пользуйся экосистемой инструментов.** `cargo fmt`, `check`, `clippy`, `doc`, `bench`,
    `update`, `tree`, `metadata`; `rust-analyzer`; `cargo-expand`, `cargo-tarpaulin`,
    `cargo-udeps`, `cargo-deny`, `cargo-semver-checks`, Miri. Подключай полезные инструменты к CI,
    а быстрые и без ложных срабатываний — к редактору.
32. **Настрой CI.** Сборка, запуск всех видов тестов, `cargo clippy -- -Dwarnings`,
    `cargo fmt --check`, `cargo doc`, `cargo-deny`. Закрепи инструментарий через
    `rust-toolchain.toml`, собирай каждую комбинацию возможностей, проверяй MSRV, собирай цель
    `no_std`, отслеживай расхождения сгенерированного кода. Удаляй нестабильные тесты; делай каждую
    проверку запускаемой локально; добавляй проверку CI на проблему процесса до того, как её
    исправлять.

## За пределами стандартного Rust (пункты 33–35)

33. **Рассмотри совместимость кода библиотеки с `no_std`.** В `core` есть `Option`, `Result`,
    итераторы; `alloc` добавляет `Box`, `Rc`, `Arc`, `Vec`, `String`, `BTreeMap`. `HashMap` и
    `Mutex` требуют ОС. Часто дело только в путях `std::` и `BTreeMap`. Проверяй
    кросс-компиляцией в CI (`thumbv6m-none-eabi`); раскрывай аддитивные возможности `std` и
    `alloc`, никогда — `no_std`. Предпочитай `try_reserve` там, где память ограничена.
34. **Контролируй, что пересекает границы FFI.** Вызовы в C небезопасны. Блоки `extern "C"`,
    `#[link]` или `build.rs`, типы известного размера, `#[repr(C)]`, `CString` и `CStr`. Выделяй и
    освобождай на одной стороне; оборачивай указатели, принадлежащие C, в RAII-тип; проверяй на null
    и возвращай `Result`; держи `unsafe` внутри обёртки. Экспортируемым функциям нужны `extern "C"`,
    `#[no_mangle]`, уникальный префикс; `Box::into_raw` и `from_raw` для передачи владения; никогда
    не возвращай указатели на стек; останавливай паники через `catch_unwind`.
35. **Предпочитай `bindgen` ручным FFI-отображениям.** Генерируй объявления из заголовков C
    (`--allowlist-function`), подключай вывод через `include!` и падай в CI, если перегенерированный
    файл отличается. Большие C-API: сырой пакет `xyzzy-sys` под безопасным пакетом `xyzzy`. C++:
    `cxx`.
