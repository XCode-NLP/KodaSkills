# Google Rust Style Guide (краткий пересказ)

Источник: https://google.github.io/styleguide/rustguide.html. Внутреннее руководство Google,
его также приняли Android, Chromium и Fuchsia. Оно опирается на официальный Rust Style
Guide и API Guidelines и добавляет правила сверху. Правила проектирования API обязательны для
библиотечного кода и настоятельно рекомендуются для прикладного, который «должен в целом
предпочитать простоту и прямоту широкой переиспользуемости». Читай это про форматирование,
импорты, структуру модулей, именование аксессоров и различие между приложением и библиотекой.
Правила, специфичные для сборок Chromium или Fuchsia, ниже опущены.

## Предпосылки и цели

Читаемость важнее удобства написания; автоматизация (массовые изменения должны быть
механическими); согласованность с экосистемой Rust; правила должны себя оправдывать. Следуй
официальным Rust Style Guide и API Guidelines, если это руководство не противоречит им.
rustfmt применяет большую часть форматирования автоматически.

## Организация кода

- Предпочитай небольшие крейты, в идеале — но не обязательно — в одном файле. Крейты
  побольше допустимы ради согласованности по orphan rule или для фундаментальных
  библиотек. Определяй границы крейтов раньше подмодулей; корень может реэкспортировать
  из листовых подмодулей.
- Называй листовой модуль по его главному элементу: `Foo` даёт `mod foo` / `foo.rs`.
- Нелистовые модули содержат только объявления `mod` и реэкспорты. Небольшой код,
  «связывающий всё вместе», допустим. Листовые модули могут содержать `mod tests`.
- Никаких glob-импортов, кроме случаев на усмотрение ревьюера: `use super::*` во вложенных
  модулях, `use Enum::*` в телах методов перечисления, `pub use submodule::*` в нелистовых
  модулях. Избегай создания prelude.
- Один модуль на инструкцию `use` (rustfmt `imports_granularity = Module`): никаких `::`
  внутри фигурных скобок.

  ```rust
  use foo::bar::{Bar, Baz};  // OK
  use foo::{Foo, bar::Bar};  // avoid
  ```

- Импортируй трейты внутри тел функций, если трейт не используется по всему файлу.
- Квалифицируй вызовы свободных функций модулем (`mem::transmute(y)`, а не `transmute(y)`), но
  используй типы и трейты неквалифицированными (`Regex`, а не `regex::Regex`). Исключения:
  неоднозначные имена вроде `io::Error` (или `use std::io::Error as IoError`), большие группы
  типов, макросы и сгенерированный код.

## Форматирование

- Всегда запускай форматтер. Рекомендуемые настройки rustfmt: `max_width = 100`,
  `hex_literal_case = Lower`, `format_macro_matchers = true`.
- `#[rustfmt::skip]` только для осознанного ручного выравнивания или сгенерированного кода,
  никогда — ради личного стиля.

## Владение и заимствование

- Избегай `Rc` / `Arc`; предпочитай единоличное владение. Исключение: когда альтернатива
  неразумно сложна, — это решение на усмотрение ревьюера.
- Заимствуй вместо `.clone()`. Клонируй, когда нужна настоящая глубокая копия или заимствование
  становится чрезмерно сложным, и взвешивай производительность. Клонирование `Rc` / `Arc`
  ожидаемо.

## Входы и выходы функций

- Принимай максимально гибкий заимствованный тип: `&[T]`, а не `&Vec<T>`; `&str`, а не
  `&String`; `&T`, а не `&Box<T>`; `Option<&T>`, а не `&Option<T>` (clippy `borrowed_box`,
  `ptr_arg`).
- Библиотечный код возвращает итераторы (конкретные или `impl Iterator`) вместо `Vec<T>` и
  принимает `impl IntoIterator`, если нужна только итерация. Прикладной код может возвращать
  или принимать `Vec` / `&[T]`, когда так проще. Исключения: вызывающему нужен собственный
  вектор, произвольный доступ по индексу или назначение функции — построение коллекции.
- Параметры `impl Into<T>` только там, где эргономика места вызова важнее всего, с поправкой
  на раздувание кода. В прикладном коде их почти никогда не стоит использовать.
- Используй `enum` вместо параметра `bool`, если назначение неочевидно. Если оставляешь
  `bool`, добавь строчный комментарий в месте вызова.
- Ошибки выбираются по контракту API: `Option` для очевидных отказов (`checked_add`);
  `Result`, когда вызывающему нужны подробности (`fn open_file(path: &Path) -> Result<File,
  io::Error>`); `panic!` для багов и нарушенных инвариантов, которые нужно исправлять в
  коде, а не обрабатывать в рантайме. Бинарники для разработчиков могут паниковать на
  некритичных ошибках; тесты могут паниковать для утверждений.

## Типы

- Используй newtype вместо алиаса при заметных смысловых различиях, для типа, которому нужен
  собственный API, при возможной смене нижележащего типа в будущем или ради типобезопасности
  (`Day` / `Month` / `Year`).
- Предпочитай именованные поля кортежам, потому что `.0` и `.1` путают. Исключения:
  newtype с одним полем и очень локальный контекст.

## Трейты

- Добавляй реализации трейтов по необходимости. Низкоуровневый библиотечный код предугадывает
  потребности; прикладной добавляет их по запросу.
- Реализуй стандартный трейт вместо собственного метода: `impl FromStr for Foo`, а не
  `fn from_str` (clippy `should_implement_trait`). Оставлять оба варианта допустимо.
- Используй `#[derive]` везде, где он может выразить реализацию.
- Библиотечный код принимает дженерики (`T: Trait`, `impl Trait`) вместо `dyn Trait`, кроме
  случаев, когда важен размер кода. Причины: косвенность через vtable, отсутствие инлайнинга,
  а некоторые трейты не dyn-совместимы (дженерик-функции, ассоциированные функции без `self`,
  функции, возвращающие `Self`).
- Определяй трейт только для обобщённого программирования, для приёма или возврата
  `impl` / `dyn Trait` либо как трейт-расширение. Иначе используй собственный impl.
  Не используй трейты просто для организации кода.
- Трейты-расширения: суффикс `Ext`, единственное назначение — добавлять методы (не для
  дженериков и не для `dyn`), владелец — команда, владеющая расширяемым типом.
- Рекомендации по трейтам: типы с публичными полями реализуют трейты, которые реализуют все
  подполя. Типы ошибок: `Copy`, когда возможно. `Copy` всегда, когда он явно останется `Copy`;
  `Clone` для большинства типов, кроме внешних ресурсов; `Default`, когда есть `new()` или
  состояние по умолчанию (clippy `new_without_default`); `PartialEq` вместо `Eq`, если не нужна
  рефлексивность; `PartialOrd` вместо `Ord`, если не нужен полный порядок; ключи словаря
  получают `Hash` и `Eq`, плюс `Ord` при явном полном порядке.
- Сопровождай важную реализацию `From` собственным `::new()`, `::new_from_foo()` или
  `::from_foo()`.
- Структуры-наборы опций, все поля которых публичны, реализуют `Default`, что позволяет
  `..Default::default()`.

## Конкурентность

- Никогда не залезай внутрь отравленного мьютекса, «как бы ни тянуло».
- Библиотечный код не должен сам запускать потоки.

## Макросы

Порядок предпочтений: обычные функции, типы, трейты и модули; затем `macro_rules!`;
затем другой кодогенератор; затем `proc_macro`. Взвешивай издержки для IDE и поиска по коду,
создание диалекта и сложность массовых изменений.

## Именование

- Методы следуют стилю std: `as_`, `to_`, `into_` с соответствующей конвенцией `self`
  (clippy `wrong_self_convention`).
- Времена жизни должны быть описательными, особенно у типов. Исключения: обобщённые
  абстракции вроде `Cow`, `'_` и односимвольные имена для простых связей входа и выхода.
- Параметры-дженерики: короткие, связанные с тем, что они представляют, в идеале — буква из
  самого важного ограничения. `T` / `U` для API, рассчитанных почти на любой тип.
- Конструкторы: `new()` или `new_with_foo()`; `try_new()`, если возможна ошибка. Преобразования
  значение-в-значение: `from_foo()` с реализацией `From`.
- Избегай сокращений, которые не поймут сторонние, включая аббревиатуры и выбрасывание букв.
  Исключения: общеизвестные термины и ясные случаи вроде `IpAddr`.

## Документация

- Документируй публичные API; рассмотри линт `missing_docs`.
- Включай примеры где-нибудь в крейте, не обязательно к каждой функции.
- Документируй паники из-за некорректного ввода и инварианты небезопасных функций и
  трейтов.
- Используй заглавные буквы и знаки препинания. Не объясняй основы языка. Комментарии должны
  добавлять информацию: `/// Removes an element.` над `remove_element()` — плохо; опусти его или
  разреши линт. Документацию вариантов перечисления часто можно опустить.
- `///` для элементов; `//!` в начале файла для модулей и крейтов; Markdown; `//` для заметок
  о реализации, TODO и закомментированного кода. Смешивать `///` и `//` на одном элементе
  нормально:

  ```rust
  /// Finds the first `FooItem` with the given `name`, or `None` if not present.
  // TODO(issue-12345): `name` should be &str, not String.
  ```

- Предпочитай обычные doc-комментарии документации, сгенерированной макросами.

## Прочие возможности Rust

- **Unsafe**: не пиши его, если безопасный код может то же самое. Оборачивай в безопасную
  абстракцию, изолируй (в идеале в отдельный крейт с малым числом зависимостей), добавь
  комментарий `SAFETY:` и обоснуй, а если причина — производительность, то бенчмарками.
- **Нестабильные возможности**: не используй их.
- **Аксессоры**: `foo()` возвращает значение или ссылку, `foo_mut()`, `take_foo()`,
  `set_foo(T)`, `replace_foo(T) -> T`, а `with_foo(|f| ..)` / `with_mut_foo(|f| ..)` — для
  доступа через замыкание. Аксессоры с замыканием подходят обёрткам с внутренней изменяемостью
  (`Mutex`, `RefCell`) или для последующей валидации, где нельзя применить `set_foo`.
- Если реализуешь `len()`, реализуй и `is_empty()` (clippy `len_without_is_empty`).
- Не обращайся к элементам с `#[doc(hidden)]`, которыми ты не владеешь.
- Помечай публичную функцию `const`, только если она останется `const`; снятие `const` —
  ломающее изменение.
- Перегружай операторы только для их математического или логического смысла, не как
  синтаксический сахар.
- `#[non_exhaustive]` на публичных перечислениях и структурах с публичными полями, используемых
  между командами. Исключения: стабильные онтологии (`Color`), двухсостоянийные перечисления или
  обязательство исправлять поломки массовым изменением (clippy `exhaustive_enums`).
- `#[must_use]` на функциях, когда игнорирование результата — ошибка использования (чистые
  функции вроде `HashMap::get()`) или результат несёт ошибки либо критичную информацию; не нужен,
  если у возвращаемого типа он уже есть (`Result`). На типах, возвращаемых такими функциями:
  типы ошибок и ленивые вычисления.
- Не выполняй код до `main()` (никакого крейта `ctor`).

## Вопросы реализации

- Не злоупотребляй выводом типов. Добавляй явные типы для `.into()`, `.parse()` и сложных
  результатов итераторов. Предпочитай объявления переменных с типом вместо turbofish; используй
  `_`, где компилятор вынуждает turbofish.
- Сопоставляй с образцом вместо «проверить и развернуть»: `if let Some(value) = option { .. }`,
  а не `is_some()` с последующим `unwrap()`.
- Используй `expect("reason")` вместо `unwrap()`, когда паники не избежать.
- На перечислениях `#[non_exhaustive]` перечисляй все варианты, которые обрабатываешь, с
  wildcard для остальных. Используй `if let` или `let .. else`, когда важен один вариант
  (линт `non_exhaustive_omitted_patterns`).
- Добавляй строки контекста в `assert!`, особенно когда сбой увидит человек или нужно отличить
  ошибку использования API от бага:

  ```rust
  assert!(self.stream.is_some(), "Call connect() before executing queries");
  ```

  Не повторяй условие в качестве сообщения.
- Избегай длинных или сложных цепочек итераторов. Не помещай цепочку в заголовок `for`;
  сначала привяжи её к переменной. Избегай `for_each`. Короткие цепочки нормальны:
  `values.iter().any(|&v| v > threshold)`.
- Не вызывай `panic::catch_unwind` в собственном коде, кроме как для дополнительной защиты, на
  которую никогда не полагаются, и только там, где действует `panic = "unwind"`.
- Используй `format!` / `write!` для конкатенации более двух строк (`format!("{a}{b}{c}")`)
  и для подстановок вместо `str::replace`.

## Тесты

Используй тестовый фреймворк кодовой базы. Тесты могут применять паники для утверждений. Тесты
живут в `mod tests` внутри листовых модулей.
