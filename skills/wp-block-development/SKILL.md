# Разработка блоков WordPress

## Когда использовать

Используй этот навык при работе с блоками, например:

- при создании нового блока или обновлении существующего;
- при изменении `block.json` (скрипты, стили, supports, атрибуты, отрисовка,
  viewScriptModule);
- при исправлении ситуаций «блок невалиден», «не сохраняется», «атрибуты не
  сохраняются»;
- при добавлении динамической отрисовки (`render.php` или `render_callback`);
- при работе с устаревшими версиями блока и миграциями;
- при настройке сборки блоков (`@wordpress/scripts`, `@wordpress/create-block`,
  `wp-env`).

## Что нужно на входе

- корень репозитория и цель (плагин, тема или весь сайт);
- имя и пространство имён блока и где он живёт (путь к `block.json`, если известен);
- целевой диапазон версий WordPress (особенно при использовании модулей и
  `viewScriptModule`).

## Порядок работы

### 0. Разберись и найди блоки

1. Запусти разбор:

   ```bash
   node skills/wp-project-triage/scripts/detect_wp_project.mjs
   ```

2. Получи список блоков (детерминированный поиск):

   ```bash
   node skills/wp-block-development/scripts/list_blocks.mjs
   ```

3. Определи корень блока (каталог с `block.json`), который меняешь.

Если репозиторий содержит весь сайт (есть `wp-content/`), явно скажи, в каком
именно плагине или теме лежит блок.

### 1. Создай новый блок (если нужно)

Если создаёшь новый блок, предпочитай заготовку ручному написанию структуры:

- используй `@wordpress/create-block`, чтобы получить современную заготовку блока
  и плагина;
- если Interactivity API нужен сразу, бери интерактивный шаблон.

Прочитай:

- `references/creating-new-blocks.md`

После создания заготовки:

1. Запусти скрипт списка блоков заново и подтверди корень нового блока.
2. Продолжай с остальными шагами: выбор модели, метаданные, регистрация,
   сериализация.

### 2. Обеспечь apiVersion 3 (WordPress 6.9+)

WordPress 6.9 требует `apiVersion: 3` в схеме block.json. Блоки с apiVersion 2 и
ниже вызывают предупреждения в консоли, когда включён `SCRIPT_DEBUG`.

**Почему это важно:**

- WordPress 7.0 запускает редактор записей во фрейме независимо от apiVersion
  блока;
- apiVersion 3 обеспечивает правильную работу блока внутри редактора во фрейме
  (изоляция стилей, единицы области просмотра, медиазапросы).

**Переход:** обычно достаточно изменить поле `apiVersion` в `block.json`. Однако:

- проверь в локальном окружении с включённым редактором во фрейме;
- убедись, что все дескрипторы стилей указаны в `block.json` (стили, отсутствующие
  во фрейме, не применятся);
- сторонние скрипты, привязанные к конкретному `window`, могут получить проблемы с
  областью видимости.

Прочитай:

- `references/block-json.md` (apiVersion и подробности схемы)

### 3. Выбери правильную модель блока

- **Статический блок** (разметка сохраняется в содержимом записи): реализуй
  `save()`; держи сериализацию атрибутов стабильной.
- **Динамический блок** (отрисовывается на сервере): используй `render` в
  `block.json` (или `render_callback` в PHP), а `save()` держи минимальным или
  `null`.
- **Интерактивное поведение на лицевой части**:
  - предпочитай `viewScriptModule` для современных скриптов на модулях, где это
    поддерживается;
  - если работаешь в основном с директивами `data-wp-*` и хранилищами, используй
    также навык `wp-interactivity-api`.

### 4. Меняй `block.json` безопасно

Делай изменения в `block.json` блока, затем убедись, что регистрация соответствует
метаданным.

По отдельным полям читай:

- `references/block-json.md`

Частые ловушки:

- изменение `name` ломает совместимость (считай его стабильным API);
- изменение сохранённой разметки без добавления `deprecated` даёт «невалидный
  блок»;
- добавление атрибутов без правильного указания источника и сериализации даёт
  «атрибут не сохраняется».

### 5. Зарегистрируй блок (предпочтительно на сервере)

Предпочитай регистрацию на PHP через метаданные, особенно когда:

- нужна динамическая отрисовка;
- нужны переводы (`wp_set_script_translations`);
- нужна условная загрузка ресурсов.

Прочитай и примени:

- `references/registration.md`

### 6. Реализуй образцы редактирования, сохранения и отрисовки

Соблюдай практику с атрибутами обёртки:

- редактор: `useBlockProps()`;
- статическое сохранение: `useBlockProps.save()`;
- динамическая отрисовка (PHP): `get_block_wrapper_attributes()`.

Прочитай:

- `references/supports-and-wrappers.md`;
- `references/dynamic-rendering.md` (если блок динамический).

### 7. Внутренние блоки (композиция)

Если твой блок — «контейнер», вкладывающий другие блоки, относись к внутренним
блокам как к полноценной возможности:

- используй `useInnerBlocksProps()`, чтобы связать внутренние блоки с атрибутами
  обёртки;
- помни о миграциях, если меняешь внутреннюю разметку.

Прочитай:

- `references/inner-blocks.md`

### 8. Атрибуты и сериализация

Прежде чем менять атрибуты:

- подтверди, где живёт значение атрибута (разделитель комментария, HTML или
  контекст);
- избегай устаревшего источника атрибута `meta`.

Прочитай:

- `references/attributes-and-serialization.md`

### 9. Миграции и устаревшие версии (чтобы не было «невалидного блока»)

Если меняешь сохранённую разметку или атрибуты:

1. Добавь запись `deprecated` (от новых к старым).
2. Опиши `save` для старых версий и при необходимости `migrate` для приведения
   атрибутов.

Прочитай:

- `references/deprecations.md`

### 10. Инструменты и команды проверки

Используй то, что уже принято в репозитории:

- `@wordpress/scripts` (часто) → запускай существующие скрипты npm;
- `wp-env` (часто) → используй для локального WordPress и сквозных тестов.

Прочитай:

- `references/tooling-and-testing.md`

## Проверка

- блок появляется в списке вставки и вставляется успешно;
- сохранение и перезагрузка не дают «невалидного блока»;
- вывод на лицевой части соответствует ожиданиям (статический блок — сохранённая
  разметка, динамический — вывод сервера);
- ресурсы загружаются там, где нужно (редактор или лицевая часть);
- запусти линтер, сборку и тесты, которые рекомендовал разбор.

## Режимы отказа и отладка

Если что-то не работает, начни с этого:

- `references/debugging.md` (частые сбои и быстрые проверки);
- `references/attributes-and-serialization.md` (атрибуты не сохраняются);
- `references/deprecations.md` (невалидный блок после изменения).

## Когда эскалировать

Если не уверен в поведении вышестоящего кода или поддержке версии, сначала сверься
с канонической документацией:

- ресурсы для разработчиков WordPress (справочник по редактору блоков, справочник
  по темам, справочник по плагинам);
- документация репозитория Gutenberg для самых новых возможностей.
