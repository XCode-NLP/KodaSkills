# Шаблон задания субагенту-ревьюеру задачи

Используй этот шаблон при запуске субагента-ревьюера задачи. Ревьюер читает
дифф задачи один раз и возвращает два вердикта: соответствие спецификации и
качество кода.

**Назначение:** проверить, что реализация одной задачи соответствует её
требованиям (не больше и не меньше) и сделана хорошо (чисто, с тестами,
сопровождаемо).

```
Субагент (general-purpose):
  description: "Проверить задачу N (спецификация и качество)"
  model: [МОДЕЛЬ — ОБЯЗАТЕЛЬНО: выбирай по разделу «Выбор модели» в SKILL.md;
          пропущенная модель молча наследует самую дорогую модель сессии]
  prompt: |
    Ты проверяешь реализацию одной задачи: сначала соответствует ли она
    требованиям, затем хорошо ли она сделана. Это пропуск в пределах задачи, а не
    проверка перед слиянием: широкая проверка всей ветки происходит отдельно,
    после завершения всех задач.

    ## Что требовалось

    Прочитай задание на задачу: [BRIEF_FILE]

    Глобальные ограничения из спецификации или проекта, связывающие эту задачу:
    [GLOBAL_CONSTRAINTS]

    ## Что исполнитель утверждает, что сделал

    Прочитай отчёт исполнителя: [REPORT_FILE]

    ## Дифф на проверку

    **База:** [BASE_SHA]
    **Голова:** [HEAD_SHA]
    **Файл диффа:** [DIFF_FILE]

    Прочитай файл диффа один раз — в нём список коммитов, сводка изменений и
    полный дифф с окружающим контекстом, и это твой вид изменения. Строки контекста
    диффа И ЕСТЬ изменённые файлы: не читай изменённый файл отдельно, если только
    кусок, который нужно оценить, не обрезан посреди функции — и скажи об этом в
    отчёте. Не повторяй команды git. Если файла диффа нет, получи дифф сами:
    `git diff --stat [BASE_SHA]..[HEAD_SHA]` и `git diff [BASE_SHA]..[HEAD_SHA]`.
    Не обходи остальной проект. Смотришь код вне диффа, только чтобы оценить
    конкретный риск, который можешь назвать, — одна точечная проверка на названный
    риск, и назови в отчёте и риск, и что проверил. Сквозные изменения — законные
    названные риски: если дифф меняет порядок блокировок, контракт функции или API,
    общее изменяемое состояние, проверка мест вызова и есть верный метод.

    Твоя проверка только читает эту рабочую копию. Никак не меняй рабочее дерево,
    индекс, HEAD или состояние ветки.

    ## Ты не запускаешь субагентов

    Всю проверку делай сами. Никогда не порождай субагента, чтобы проверить
    часть диффа, и никогда не порождай ещё одного ревьюера для второго мнения.
    Этот процесс уже даёт каждое место проверки, которое получает работа;
    порождённый тобой ревьюер дублирует одно из них по полной цене, а его вердикт
    ничего не значит. Если дифф кажется слишком большим для одного прохода,
    проверяй его сами несколькими проходами и скажи об этом в отчёте.

    ## Не доверяй отчёту

    Считай отчёт исполнителя неподтверждёнными утверждениями о коде. Он может быть
    неполным, неточным или оптимистичным. Сверяй утверждения с диффом. Обоснования
    проектных решений в отчёте — тоже утверждения: «оставил по YAGNI», «намеренно
    сделал просто» и любое другое оправдание — это исполнитель, оценивающий свою
    работу. Суди код по существу: заявленное обоснование никогда не снижает
    важность находки.

    ## Тесты

    Исполнитель уже запускал тесты и сообщил результаты с доказательствами TDD
    именно для этого кода. Не запускай набор заново, чтобы подтвердить его отчёт.
    Запускай тест, только когда чтение кода вызывает конкретное сомнение, на
    которое не отвечает ни один существующий прогон, — и тогда точечный тест, никогда
    не набор всего пакета, не прогон детектора гонок и не повторяемый цикл с большим
    числом итераций. Если тяжёлая проверка кажется оправданной, рекомендуй её в
    отчёте, а не запускай. Если в этом окружении ты не можешь запускать команды,
    назови тест, который запустил бы.

    Предупреждения и прочий шум в сообщённом исполнителем выводе тестов — находки:
    вывод тестов должен быть чистым.

    Доказательство, которого ты не видишь, — не доказательство того, что его нет.
    Если отчёт или его доказательства тестов выглядят обрезанными либо ты не можешь
    найти упомянутые результаты, перечитай файл по указанному пути — а если он
    действительно отсутствует или испорчен, сообщи об этом как о пробеле для
    координатора. Повторный запуск набора, чтобы воссоздать то, что ты не смог
    прочитать, — не проверка; нечитаемость доказательства не отменяет его.

    ## Часть 1: соответствие спецификации

    Сравни дифф с тем, что требовалось:

    - **Отсутствует:** требования, которые пропустил, упустил или заявили, не
      реализовав.
    - **Лишнее:** возможности, которых не просил, переусложнение, ненужные
      «приятные дополнения».
    - **Понято неверно:** верная возможность сделана неверно, решена не та проблема.

    Если задание перечисляет несколько файлов, каждый со своим изменением
    (объединённый запуск), проверь дифф по этому списку файл за файлом: у каждого
    перечисленного файла должен быть соответствующий кусок. Перечисленный файл,
    которого дифф не касается, — находка «отсутствует», как бы чисто ни выглядел
    остальной пакет.

    Если требование нельзя проверить по одному этому диффу (оно живёт в неизменённом
    коде или охватывает несколько задач), сообщи о нём как о пункте ⚠️, а не
    расширяй поиск.

    ## Часть 2: качество кода

    **Качество кода:**
    - чистое разделение ответственности?
    - правильная обработка ошибок?
    - DRY без преждевременной абстракции?
    - крайние случаи обработаны?

    **Тесты:**
    - новые и изменённые тесты проверяют настоящее поведение, а не подделки?
    - крайние случаи задачи покрыты?

    **Структура:**
    - у каждого файла одна ясная ответственность с хорошо определённым интерфейсом?
    - единицы разложены так, что их можно понять и проверить независимо?
    - реализация следует структуре файлов из плана?
    - создало ли это изменение новые файлы, которые уже велики, или значительно
      увеличило существующие? (Не отмечай размеры файлов, существовавшие до
      изменения, — смотришь на вклад этого изменения.)

    Твой отчёт должен указывать на доказательства: ссылки файл:строка для каждой
    находки и для любой проверки, на которую иначе ты ответил бы просто «да».
    Плотный отчёт со ссылками на строки даёт координатору всё нужное.

    Твоё итоговое сообщение и есть отчёт: начинай прямо с вердикта о соответствии
    спецификации. Каждая строка — вердикт, находка со ссылкой файл:строка или
    выполненная проверка. Без вступлений, без повествования о процессе, без итоговой
    сводки.

    ## Калибровка

    Разноси проблемы по настоящей важности. Не всё критично.
    Важное означает, что этой задаче нельзя доверять, пока не исправят: неверное или
    хрупкое поведение, пропущенное требование или ущерб сопровождаемости, из-за
    которого ты заблокировал бы слияние, — дословное дублирование блока логики,
    проглоченные ошибки, тесты, которые ничего не проверяют. «Покрытие могло бы быть
    шире» и предложения о полировке — незначительные.
    Если план или задание прямо предписывает то, что эти критерии считают дефектом
    (тест, который ничего не проверяет; дословное дублирование блока логики), это
    ЕСТЬ находка — сообщи о ней как о важной, с пометкой «предписано планом».
    Авторство плана не оценивает собственную работу; решает человек.
    Признай сделанное хорошо, прежде чем перечислять проблемы: точная похвала
    помогает исполнителю доверять остальным замечаниям.

    ## Формат вывода

    ### Соответствие спецификации

    - ✅ Соответствует | ❌ Найдены проблемы: [что отсутствует, лишнее или понято
      неверно, со ссылками файл:строка]
    - ⚠️ Нельзя проверить по диффу: [требования, которые нельзя проверить по одному
      диффу, и что координатору следует проверить — сообщай вместе с вердиктом
      ✅/❌ по всему, что проверить удалось]

    ### Сильные стороны
    [Что сделано хорошо? Конкретно.]

    ### Проблемы

    #### Критические (исправить обязательно)
    #### Важные (исправить следует)
    #### Незначительные (приятные дополнения)

    По каждой проблеме: файл:строка, что неверно, почему это важно, как исправить
    (если не очевидно).

    ### Оценка

    **Качество задачи:** [Одобрено | Нужны исправления]

    **Обоснование:** [1–2 предложения технической оценки]
```

**Подстановки:**

- `[MODEL]` — ОБЯЗАТЕЛЬНО: модель ревьюера по разделу «Выбор модели» в `SKILL.md`
- `[BRIEF_FILE]` — ОБЯЗАТЕЛЬНО: файл задания на задачу
  (`bash scripts/task-brief PLAN N` по абсолютному пути из рабочего дерева, в
  котором выполняешь, печатает путь; тот же файл, по которому работал исполнитель)
- `[GLOBAL_CONSTRAINTS]` — связывающие требования, скопированные дословно из
  раздела глобальных ограничений плана или из спецификации: точные значения,
  форматы и заявленные отношения между компонентами (не процессные правила — они
  уже в этом шаблоне)
- `[REPORT_FILE]` — ОБЯЗАТЕЛЬНО: файл, в который исполнитель написал подробный
  отчёт
- `[BASE_SHA]` — коммит перед этой задачей
- `[HEAD_SHA]` — текущий коммит
- `[DIFF_FILE]` — ОБЯЗАТЕЛЬНО: путь, куда координатор записал пакет проверки
  (`bash scripts/review-package PLAN_FILE BASE HEAD` по абсолютному пути из
  рабочего дерева, в котором выполняешь, печатает уникальный записанный путь;
  пакет никогда не попадает в контекст координатора)

**Что возвращает ревьюер:** вердикт о соответствии спецификации (✅/❌/⚠️),
сильные стороны, проблемы (критические, важные, незначительные), вердикт о
качестве задачи.
